# 4.44 Первый замер качества за всё время. Он же вскрыл дефект, который я сам внёс

`PLAN.md` и §4.36 держали строку «качество не мерялось никогда» с самого начала. Она
закрыта — и по дороге выяснилось, почему её нельзя было закрыть раньше: стенд был сломан, и
сломал его я.

## Замер, который пришлось выбросить

Первые числа перплексии я снял сборкой **ON** на карте:

```
16 из 16 → 16.14      12 из 16 → 4891.6      8 из 16 → 5619.5      4 из 16 → 1584108
```

Вывод напрашивался сам: «выбрасывание четверти каналов ломает модель в триста раз». Прежде
чем его записывать, я поставил контроль — усечение на **одну** полосу из шестнадцати. Если
модель ломается и от этого, виноват мой код, а не отсечение.

Контроль опроверг не гипотезу, а **сам замер**: неусечённая модель дала `PPL = 156.82` там,
где двадцатью минутами раньше та же модель на том же корпусе той же командой дала `16.14`.

Три прогона подряд на неизменном файле:

```
ON, CUDA:   28.46      36.45      210.70
```

Разброс в семь раз. Мерилось не отсечение, а шум. Числа выше **не записаны никуда** и не
используются.

## Где именно недетерминизм

| сборка | устройство | PPL | воспроизводимость |
|---|---|---|---|
| OFF | CUDA | `8.1441 ± 0.335` | **точно**, три прогона до знака |
| ON | CPU | `8.7051 ± 0.499` | **точно**, три прогона до знака |
| ON | CUDA | 28.46 / 36.45 / 210.70 | **нет** |

Чистый `llama.cpp` на карте детерминирован. Организм на процессоре детерминирован.
Разъезжается только **пересечение** — субстрат плюс GPU.

## Дефект: запись по освобождённой памяти, партия C

`llama_context::myc_readback_issue`, введён в §4.40:

```cpp
if (P.armed) P.n_dropped++;   // только СЧИТАЕТ

P.selected.clear();           // <- освобождает буферы, в которые ещё идёт DMA
P.demand  .clear();
```

`ggml_backend_tensor_get_async` пишет в `st.raw` **асинхронно**. Если предыдущий набор не
был вычитан (`armed`), `clear()` освобождает эти буферы при живой передаче.

**Почему не проявлялось.** Зонд декодирует по одному токену: один убатч на декод, `armed`
не взводится никогда. Перплексия гоняет батч 2048 при убатче 512 — **четыре убатча на
декод, четыре выдачи, одна вычитка**, то есть три записи по освобождённой памяти на каждый
декод.

**Почему дожило.** Единственный режим, который его вскрывает, — многоубатчевый префилл с
проверкой результата. Скорость его не видит: она не смотрит на числа. Зонд не видит: у него
один токен на декод. Качество увидело сразу — и качество не мерялось ни разу.

Это семнадцатый дефект того же класса и **второй, который внёс я сам**, оптимизируя. Первый
(§4.32) был чужой гонкой; этот — моей.

**Исправление** — не счётчиком, а по существу: при взведённом `armed` дождаться передач и
**вычитать** их. Данные предыдущего убатча полноценны, терять их незачем — организм получает
наблюдение с каждого убатча вместо последнего. Цена платится только там, где раньше была
ошибка: на генерации `armed` не взводится, и быстрый путь партии C сохраняется целиком.
Счётчик `n_dropped` убран: терять больше нечего.

## Что субстрат делает с качеством

Согласованное сравнение на процессоре, где обе сборки детерминированы:

```
OFF, CPU, 8 кусков:  PPL = 8.7351 ± 0.50146
ON,  CPU, 8 кусков:  PPL = 8.7051 ± 0.49896
```

**Разницы нет** — 0.3 % при погрешности ±0.5. Смещение роутера, которое организм
накладывает на выбор экспертов, качества не меняет: ни портит, ни улучшает.

Это первый ответ на вопрос, стоявший с начала работы. Он скромный, но он ответ: субстрат в
нынешнем виде **безвреден для качества** и стоит 9.9 % скорости (§4.40).

## Качество при отсечении полос

Чистая сборка, три прогона на точку не нужны — воспроизводимость проверена.

| оставлено | доля FFN | PPL | ×базы |
|---|---|---|---|
| 16 из 16 | 100 % | **8.1441** | 1.00 |
| 15 | 94 % | 8.9487 | 1.10 |
| 14 | 88 % | 10.2854 | 1.26 |
| 12 | 75 % | 14.6076 | 1.79 |
| 8 | 50 % | **182.30** | 22.4 |
| 4 | 25 % | 1 563 871 | 192 000 |

Монотонно, и обрыв виден точно: между **25 % и 50 % удаления**. Убрать четверть каналов —
модель хуже вдвое, но работает. Убрать половину — сломана.

> **Правка (§4.47).** Эта кривая снята критерием отбора **по норме весов**, и он оказался
> решающим: на той же доле 50 % отбор по вкладу (`‖W‖·E|h|`) даёт перплексию в девяносто
> три тысячи раз ниже. «Обрыв» — артефакт выбора, а не предел отсечения. Числа ниже верны
> для этого критерия и неверны как утверждение о том, сколько каналов можно выбросить.

## Что это значит и чего не значит

**Значит.** Статическое отсечение каналов FFN **без компенсации** терпит примерно четверть.
§13.1 целится в резидентность 5 % — там, где у меня 25 %, перплексия уже 1.5 миллиона.
Разрыв, который обязана закрыть каверна, теперь измерен, и он огромен.

> **Правка (§4.47).** «Огромен» относилось к плохому критерию отбора. С отбором по вкладу и
> с применённой каверной 25 % сохранённых дают ×4.0, а не ×192 000.

**Не значит, что схема мертва**, и здесь важное различение, которое легко потерять:

```
мой замер          каналы удалены НАВСЕГДА, для всех токенов
схема §9.4         неризидентные веса не удалены — они на диске и подкачиваются
схема §6.4         промах НЕ догружается, а компенсируется
```

Мой замер моделирует **только второй вариант** — пропуск без компенсации, — и говорит:
пропускать больше четверти нельзя. Про подкачку он не говорит ничего: там качество не
страдает вовсе, платится полоса шины.

То есть выбор, который схема обязана сделать явно: **либо компенсация закрывает разрыв в
192 000 раз, либо ярус подкачки должен покрывать не меньше трёх четвертей спроса.**
Третьего вывода из этой таблицы не следует.

**Оговорка о модели.** У OLMoE эксперт маленький — `n_ff = 1024` при 64 экспертах, и активны
8. Внутри такого эксперта избыточности меньше, чем в широком плотном FFN, поэтому кривая
может быть пессимистичной для GPT-OSS. Проверяется тем же инструментом на любой MoE-модели.

**Оговорка о корпусе.** Смесь русской прозы, английской, C++ и Python — текст неестественный
для языковой модели. Абсолютная перплексия `8.14` качеством не является; сравниваются
**отношения** на одном и том же тексте, и для этого корпус годится.

# 4.49 Пункт 3: генерация быстрее на 41 %, и −46 % оказались не тем, чем считались

Третий пункт списка §4.46 — «прореживание наблюдений». Прежде чем прореживать, я разложил
цену. Разложение отменило половину постановки задачи и нашло однострочный дефект.

## Разложение по врезкам без пересборки

Врезка энтропии внимания живёт только в не-FA ветке `build_attn_mha`, поэтому разность
разностей по `-fa` выделяет её, не требуя нового бинарника. `OLMoE` MXFP4, `ngl=99`,
`tg32`, `r=3`, одна и та же сборка.

| | наблюдения ON | OFF | разность |
|---|---|---|---|
| `-fa 1` | 11.17 мс/ток | 6.30 | **4.87** ← четыре врезки FFN/MoE |
| `-fa 0` | 12.41 | 6.70 | 5.71 ← все пять |

**Врезка энтропии внимания стоит 0.84 мс — 15 %.** Остальные 85 % в тракте FFN/MoE. Это уже
полезно: энтропия была самой подозрительной врезкой (`log`, `mul`, два `sum_rows` на слой), а
оказалась наименьшей из значимых.

## Переиспользование графа было выключено, и не по замыслу

Дальше проверялась гипотеза, что цена — это потеря переиспользования графа: в CUDA-бэкенде
быстрый путь захвата графа завязан на неё напрямую (`if (cgraph->uid == graph->uid) return
false` в `ggml_cuda_graph_update_required`).

| | мс/ток |
|---|---|
| OFF, переиспользование работает | 6.37 |
| OFF, `LLAMA_GRAPH_REUSE_DISABLE=1` | 7.27 |
| ON, `LLAMA_GRAPH_REUSE_DISABLE=1` | 11.16 |
| ON, переиспользование «включено» | **11.17** ← то же самое |

Последние две строки совпадают. **В ON-сборке переиспользование не работало никогда** —
выключать было нечего.

Причина — одна отсутствующая строка. `llm_graph_input_mycelium_expert_bias` не переопределял
`can_reuse`, а база возвращает `false` с комментарием ровно об этом случае:

> returning false here by default will prevent from reusing the graph if the check for the
> input type has not been implemented yet

Форма входа определяется `n_expert` и номером слоя, оба у модели постоянны; значения меняются
каждый шаг, но `set_inputs()` вызывается и на пути переиспользования. То есть `can_reuse` мог
возвращать `true` с самого начала.

## Главное: `MYC_NO_OBSERVE` гасил не только наблюдение

Смещение роутера — `selection_probs = ggml_add(ctx0, selection_probs, inp->bias)` — стояло
**внутри того же условия**, что и наблюдательные врезки. Значит все прежние замеры «цены
наблюдений», включая −46 % из §4.43, меряли сумму двух разных вещей:

```
наблюдение   кормит статистику, усредняется          ПРОРЕЖИВАЕМО
смещение     и есть управление (§5)                  НЕ прореживаемо
```

Ещё: `llama_mycelium_get_routing_bias` в шапке API описан как «`il` … reserved for future
per-layer differentiation; **the current implementation shares one graph across all
layers**». Шестнадцать пер-слойных тензоров смещения содержали одни и те же 64 числа, а
`ggml_backend_tensor_set` на буфере CUDA — это `cudaMemcpyAsync` **плюс**
`cudaStreamSynchronize`: шестнадцать полных синхронизаций потока на шаг ради одного вектора.

## Партия E

Одна пересборка, пять правок.

| # | правка | обоснование |
|---|---|---|
| E1 | `can_reuse` → `true` у входа смещения | переиспользование не работало ни разу |
| E2 | `MYC_NO_OBSERVE` и `MYC_NO_STEER` разделены | иначе 46 % остаются одним числом |
| E3 | пер-врезочные `MYC_NO_OBS_{BANDS,DEMAND,SELECTED,ATTN}` | разложить остаток без новой сборки |
| E4 | `MYC_OBS_STRIDE` + поле `myc_observe` в `llm_graph_params::allow_reuse` | собственно прореживание |
| E5 | одно смещение `[n_expert, n_layer]` вместо входа на слой | 1 синхронизация вместо 16 |

**E4 снимает блокер, из-за которого D2 откладывалась.** Опасение было: шаг прореживания
меняет структуру графа, а ключ переиспользования о ней не знает — переиспользованный граф либо
свёл бы эффект к нулю, либо молча потерял наблюдения. Решение: шаг с наблюдениями и шаг без
них объявлены двумя разными графами явно.

## Результат

`OLMoE` MXFP4, `ngl=99`, `-fa 1`, `tg32`, `r=3`.

| режим | т/с | мс/ток | сверх базы |
|---|---|---|---|
| база (ни наблюдения, ни руля) | 157.85 | 6.335 | — |
| **только руль** | 135.09 | 7.402 | **1.07** |
| **только наблюдение** | 103.51 | 9.661 | **3.33** |
| всё, шаг 1 | 99.42 | 10.058 | 3.72 |
| шаг 2 | 100.96 | 9.905 | 3.57 |
| шаг 4 | 118.00 | 8.475 | 2.14 |
| **шаг 8** | **126.19** | **7.925** | **1.59** |

```
было (до партии E)   11.17 мс/ток,  89.5 т/с
стало (шаг 8)         7.93 мс/ток, 126.2 т/с      +41 % к генерации
накладные расходы     4.87 -> 1.59 мс/ток          -67 %
```

E1 и E5 сами по себе дали 11.17 → 10.06, то есть **1.11 мс/ток** вернулись без всякого
прореживания — это была плата за неработавшее переиспользование и пятнадцать лишних
синхронизаций.

## Качество не тронуто

Это проверялось первым делом: в §4.44 «выигрыш» уже один раз оказался порчей выхода.

| режим | PPL |
|---|---|
| база | 6.2271 ± 0.177 |
| всё, шаг 1 | 6.2209 ± 0.176 |
| шаг 8 | 6.2219 ± 0.176 |

Расхождения — тысячные доли при погрешности 0.18. Прореживание наблюдений на выход не влияет.

## Модель цены и промах предсказания

Числа складываются в проверяемую формулу:

```
t = 6.335 (база) + 1.067 (руль, каждый шаг) + 3.33/N (наблюдения) + ~0.5·(2/N) (пересборки)
```

При N=8: `6.335 + 1.067 + 0.416 + 0.125 = 7.94` против измеренных `7.925`. Последнее
слагаемое — честная пересборка графа на границе прореживания, две на N шагов; при N=2 она
приходится на каждый шаг, поэтому шаг 2 почти ничего не даёт (9.905 против 10.058).

**Предсказание, записанное до замера, было 7.10 — промах на 0.83.** Причина ровно та, которую
этот же раздел и описывает: я вычел из прореживаемой части стоимость руля, хотя руль работает
каждый шаг по замыслу. То есть, документируя смешение наблюдения и управления, я тут же
сделал прогноз, всё ещё их смешивающий.

## Что это меняет дальше

**Главная оставшаяся статья — руль, а не наблюдение.** Из 1.59 мс сверх базы 1.07 приходится
на смещение роутера, и прорежены они быть не могут: шаг без смещения — это шаг, на котором
организм не управляет. Уменьшать эту статью придётся не частотой, а устройством: одна заливка
4 КБ и шестнадцать `ggml_add` по 64 числа не должны стоить миллисекунды, значит цена где-то
ещё — вероятный кандидат — шестнадцать вызовов `llama_mycelium_get_routing_bias` в
`set_input` на каждом шаге плюс несостоявшийся сплав `softmax → add → argsort_top_k`.

## Верхняя граница шага не произвольна

Резидентность меняется на границе эпохи, 15–32 токена (§12.8). Чтобы статистика эпохи не
превращалась в выборку из одной точки, наблюдений на эпоху нужно не меньше двух, откуда
**шаг ≤ 8**. Шаг 16 даёт одно наблюдение на короткую эпоху, шаг 32 — ни одного гарантированно.
По умолчанию шаг равен 1, то есть без переменной среды поведение форка не меняется.

## Чего этот раздел не показывает

**Разложение внутри 3.33 мс не сделано.** Выключатели E3 собраны, но не прогнаны: сколько там
узлов полос, сколько спроса, сколько флага `ggml_set_output` на `selected_experts` — открыто.

**Префилл не мерян после партии.** Все числа — генерация.

**Что организм теряет, наблюдая вчетверо реже, не измерено.** PPL показывает, что модель не
портится, но это про выход модели, а не про качество решений организма: он к фазе 5 ещё ничего
не решает.

**Одна модель, 16 слоёв.** На 36 слоях GPT-OSS доля постоянных накладных расходов на шаг
упадёт сама, и приоритеты могут сместиться.

# 4.55 Пункт 11: кривая отсечения снята целиком. Цель §13.1 статикой не берётся

Весь конвейер был проверен в **одной** точке — 25 % сохранённых каналов. Цель §13.1 — 5 %,
впятеро меньше, и до сих пор ничто не говорило, что там происходит. Кривая снята от 75 % до
6.25 %, с каверной и без, на `test` — тексте, не участвовавшем ни в статистике, ни в подборе
λ.

## Кривая

База `6.4999`. λ = 0.03, выбранная на `dev` при 25 % (см. оговорку ниже).

| оставлено | доля | без каверны | ×базы | с каверной | ×базы | снято избытка |
|---|---|---|---|---|---|---|
| 16/16 | 100 % | 6.4999 | 1.00 | — | — | — |
| 12/16 | 75 % | 8.8452 | 1.36 | — | — | — |
| 8/16 | 50 % | 16.8994 | 2.60 | **15.0182** | 2.31 | **18 %** |
| 4/16 | 25 % | 54.9009 | 8.45 | **35.3857** | 5.44 | **40 %** |
| 2/16 | 12.5 % | 266.372 | 41.0 | **85.0262** | 13.1 | **70 %** |
| 1/16 | 6.25 % | 3310.17 | 509 | **266.514** | 41.0 | **92 %** |

**Контроль сошёлся до последнего знака.** Точка 25 % без каверны получена здесь отсечением
уже квантованной модели (`54.9009`), а в §4.54 — отсечением f16 с последующим квантованием
(`54.9009`). Два независимых маршрута дают одно число.

**Предсказание, записанное до замера, попало во всех четырёх точках:** 75 % ждал 9–11 (вышло
8.85), 50 % — 15–20 (16.90), 12.5 % — 250–350 (266.37), 6.25 % — 2500–4000 (3310).

## Каверна тем сильнее, чем сильнее ломаешь

Доля снятого избытка растёт монотонно: 18 % → 40 % → 70 % → 92 %. Это ровно то, что §4.47
увидел на плотной модели (91 % там, где база была ×3988), теперь измерено систематически, на
одной модели и одной шкале.

И отсюда точное соотношение:

```
6.25 % С каверной   ->  266.51
12.5 % БЕЗ каверны  ->  266.37
```

Совпадение до третьего знака. **На этом участке каверна стоит ровно одного халвинга
резидентности:** она покупает вдвое меньше памяти при том же качестве. Выше по кривой это уже
не так — 12.5 % с каверной (85.0) хуже, чем 25 % без (54.9), то есть там каверна стоит около
семи десятых халвинга, а при 25 % — около половины.

## Цель §13.1 статикой не берётся

Правило было записано заранее: «если при 12.5 % с каверной выйдет ниже полусотни, 5 %
мыслимы». Вышло 85.0.

Формулировка в абсолютной перплексии некорректна — она зависит от корпуса, — поэтому
переформулирую в отношении и держусь его: **×13.1 при 12.5 %, ×41 при 6.25 %.**

Арифметика цели, ради которой строится весь форк:

```
GPT-OSS-120B в MXFP4      ~63 ГБ
доступно под веса         ~4.5 ГБ из 6
требуемая резидентность   ~7 %
измерено при 6.25 %       x41 к базе
```

> **Правка (§4.56).** Колено на 25 % — свойство **этой модели**, а не архитектуры. На Granite MoE та же доля даёт ×209 вместо ×8.45: у неё восемьро меньше параметров FFN на слой, и резать нечего. Режущая величина — **избыточность FFN**, а не доля отсечения сама по себе.

**Колено кривой — около 25 %**, где качество ×5.4. Ниже 12.5 % обмен памяти на качество
становится невыгодным при любой компенсации: цена халвинга растёт (×1.9, ×3.3, ×4.9, ×12.4)
быстрее, чем экономия от него, а компенсация, даже снимая 92 % избытка, отыгрывает всего один
халвинг.

## Что из этого следует для фазы 5

**Проектировать под резидентность около четверти, а не под пять процентов.** Это не отказ от
цели, а признание того, что статическая её половина исчерпана: дальше должна работать
динамика, и именно её надо мерить, а не достраивать статику.

Запас, который у динамики есть, измерен в §4.52: оракул при 25 % удерживает 0.63–0.69 массы
против 0.37–0.44 у статической перестановки, то есть **×1.6**. Если этот запас реализуется
целиком, 25 % статики соответствуют примерно 15 % динамики — до 7 % всё равно не хватает, но
разрыв сокращается втрое.

## Оговорки

**λ подобрана при 25 % и применена ко всем долям.** При других долях оптимум может быть
другим: при 6.25 % неизвестных 64 на 3000 строк (система переопределена вдесятеро), при 50 % —
512 на те же 3000. Переподбор λ по долям не делался; для крайних точек это может стоить
процентов, но не порядка, а выводы здесь про порядки.

**Одна модель.** OLMoE: 64 эксперта, top-8, `n_ff_exp` 1024. У GPT-OSS другая форма, и
перенос кривой не проверен.

**Считаются только каналы FFN.** Внимание, эмбеддинги и нормировки в отсечение не входят и
резидентны целиком; в арифметике цели выше это не учтено, то есть реальная требуемая доля от
FFN ещё меньше 7 %.

**Перплексия на перемешанных кусках** выше, чем на связном тексте. Сравнимы отношения внутри
таблицы, абсолютные значения качеством не являются.

# 4.66 Срез gate/up и методическая находка: серии врут на своей же величине

Пункт 8в: регулятор глубины пропускал полосы `down`, но каналы этих полос всё равно
считались в `gate` и `up` — они не нарезаны на тензоры. §4.65 назвал это прямо: **качество
резалось на полную долю, а работа на треть.**

## Правка

У весов `{n_embd, n_ff, n_expert}` обрезается `ne[1]`, у смещений `{n_ff, n_expert}` —
`ne[0]`. Вид со сдвигом законен и для квантованного тензора: полоса кратна 64 каналам, то
есть целому числу блоков MXFP4 по 32. Ограничений на непрерывность нет ни в
`ggml_mul_mat_id`, ни в бэкенде CUDA — ядра используют шаг эксперта явно.

Но это чтение кода, а не замер, поэтому проверка ставилась двойная, и критерий записан
заранее: **если перплексия разойдётся — вид со сдвигом считается неверно, и это ошибка, а не
находка.**

## Корректность: перплексия совпала до знака

| глубина | до среза | после среза |
|---|---|---|
| 16/16 | 5.8588 | **5.8588** |
| 8/16 | 14.8254 | **14.8254** |
| 4/16 | 48.6243 | **48.6243** |
| 2/16 | 246.8264 | **246.8264** |

Совпадение полное. Срезаемые каналы и так не влияли на выход — их полосы `down`
пропускались; теперь они ещё и не вычисляются. Вид со сдвигом под `mul_mat_id` верен.

## Скорость: +18 %, и это видно только парным замером

Первое сравнение (серия против серии, разнесённые часами) дало +10 % при глубине 4. Но в тех
же данных глубина 16/16 «изменилась» на −4.8 %, **хотя при полной глубине срез не
срабатывает вовсе и код тождествен**. Машина дрейфовала.

Парный замер — три круга, в каждом монолит, полная глубина и глубина 4 подряд:

| круг | монолит | полосы 16/16 | полосы 4/16 |
|---|---|---|---|
| 1 | 94.01 ± 3.5 | 43.30 | 89.00 |
| 2 | 94.52 ± 3.0 | 48.21 | 91.61 |
| 3 | 79.42 ± 9.8 (выброс) | 49.02 | 93.00 |

Отношение глубины 4 к монолиту в одном круге:

```
до среза   (§4.65, серией)   0.813
после среза (парно)          0.958
```

**Плюс 18 %** — вдвое больше, чем показывало сравнение серий. Полосатая модель при четверти
глубины практически догнала неразрезанную.

## Почему выигрыш ограничен именно здесь

Полная арифметика FFN на токен у OLMoE:

```
8 экспертов x 16 слоёв x 3 матрицы x 1024 x 2048 = 1.6 ГФЛОП
при 5 ТФЛОПС                                     = 0.32 мс из двадцати
```

**Резать арифметику бессмысленно — её почти нет.** Экономится чтение весов: 417 МБ на токен
при 336 ГБ/с это 1.24 мс. Срез при глубине 4/16 убирает `12/16 × 2/3 × 417 = 208` МБ, то есть
0.62 мс. Намеренный выигрыш того же порядка.

**Это ограничение модели, а не правки.** Те же байты у `gpt-oss-20b` пойдут не по внутренней
шине видеопамяти (336 ГБ/с), а через PCIe (6.6 ГБ/с) — **в пятьдесят раз медленнее**. Доля
экономии та же, цена секунды другая. Замер на OLMoE проверяет корректность среза и не может
проверить его выгоду.

## Методическая находка: серии врут на своей же величине

Монолит дал 99.65 ± 0.51 час назад и 94.0 ± 3.5 сейчас — **шесть процентов дрейфа между
прогонами**, разделёнными пересборкой и десятками гигабайт дисковых записей. При этом
внутренняя погрешность каждого замера меньше процента.

**Правило, которое должно было действовать с самого начала: сравниваемые конфигурации мерить
чередованием в одном прогоне, а не последовательными сериями.** Всё, где разница меньше
десяти процентов, при серийном замере недостоверно.

Это задним числом снижает точность части прежних сравнений — прежде всего §4.49, где партия E
оценивалась разностью между сериями, разделёнными пересборкой. Там эффект крупный (11.17
против 7.93 мс, 41 %), поэтому вывод устоит, но заявленные проценты точнее, чем позволял
метод. То же относится к §4.65: «полосатая при глубине 4 медленнее монолита» — на парном
замере оказалось 96 %, а не 81 %.

## Что осталось несделанным

**Слитый путь `gate_up`** (когда модель хранит одну матрицу вместо двух) не тронут. У OLMoE
его нет; есть ли у `gpt-oss` — проверю на модели.

**Смещения экспертов** режутся тем же приёмом, но у OLMoE их нет, поэтому эта ветка **не
исполнялась ни разу**. Первый прогон `gpt-oss` её и проверит — там `ffn_up_exps_b` есть.

**Полосы за порогом по-прежнему лежат в видеопамяти.** Не считаются, но и не выгружаются:
экономии памяти нет, есть только экономия счёта и чтения. Выгрузка — это пункт 8б.

# 4.90 Раскладка глубины выигрывает 4.8 %. Моё предсказание опровергнуто

## Предсказание и его опровержение

В `PREDICTION-4.90.md`, записанном ДО прогона, стояло: **«равномерность не будет побита ни при
одной из перебираемых сил (0.15, 0.3, 0.5), разница будет монотонно расти: примерно +0.1 %,
+0.4 %, +1.2 %»**. Рассуждение опиралось на выпуклость кривой «глубина -> качество»: забирая
канал у обеднённого слоя, теряешь больше, чем выигрываешь, отдавая его слою, уже насыщенному.

Замер:

| сила наклона | границы глубин | PPL | к контролю |
|---|---|---|---|
| равномерно (контроль) | 8..8 | 19.0514 | — |
| 0.00 | 8..8 | 19.0514 | +0.00 % |
| 0.15 | 7..9 | 18.4399 | **−3.21 %** |
| 0.30 | 6..10 | 18.2261 | **−4.33 %** |
| 0.50 | 5..11 | **18.1325** | **−4.82 %** |
| 0.65 | 5..11 | **18.0493** | **-5.26 %** |
| 0.80 | 4..12 | 18.5678 | -2.54 % |
| 1.00 | 3..13 | 19.5607 | +2.67 % |

Оптимум взят в вилку: он около **0.65** и даёт **-5.26 %**. Кривая по силе наклона
одногорбая — растёт до 0.65, затем падает и к полной силе уходит в минус, что и
соответствует борьбе двух причин: различия слоёв против выпуклости.

**Наклон выигрывает, и предсказание неверно и по знаку, и по величине.** Ошибка была в оценке
весов: различие слоёв между собой (девятнадцатикратное по §4.89) перевешивает выпуклость на
всём диапазоне до половинной силы, и лишь дальше выпуклость берёт своё — при полной силе
наклон снова проигрывает. Оптимум лежит между 0.5 и 1.0.

Самопроверка оснастки прошла: сила 0 дала ровно контрольное значение до четвёртого знака,
то есть раскладка не делает ничего помимо наклона.

## Что именно измерено

**Первый выигрыш на весах при равном объёме счёта.** Сумма глубин во всех плечах одна и та же
по построению (раскладка нормирована к среднему), значит 4.8 % получены не тем, что посчитали
больше, а тем, что посчитали в правильных местах.

Перевод в практическую величину: та же перплексия, что даёт равномерная глубина 8, достигается
наклоном при меньшем среднем. По кривой из §4.89 (8 -> 21.22, 16 -> 4.73) выигрыш в 4.8 %
перплексии соответствует примерно половине шага глубины, то есть около 6 % экономии счёта и
резидентных каналов при том же качестве. Оценка грубая — кривая снята в четырёх точках.

## Чего этот результат НЕ даёт

**Сигнала.** Наклон задан руками по номеру слоя: «ранним больше, поздним меньше». Организм
такого правила не вычислял и вычислить пока не может — теплота, единственная величина, которую
он о слоях знает, плоская (§4.88) и раскладку не порождает.

То есть построен исполнитель и доказано, что рычаг работает и стоит 4.8 %. Не хватает
измеряемой величины, которая воспроизвела бы найденную форму сама.

**Кандидат, вытекающий из §4.89:** чувствительность слоя к урезанию, измеряемая прямо —
вклад отбрасываемых каналов в норму выхода слоя. Она по определению есть то, что наклон
приближает номером слоя, и в отличие от теплоты не обязана быть плоской.

## Оговорка о переносимости

Всё измерено на olmoe: 16 слоёв, 16 полос на слой, переставленная модель. На целевом gpt-oss
24 слоя и 45 полос, и форма оптимума там будет другой. Переносится утверждение «раскладка по
слоям — рычаг, стоящий процентов», а не конкретная сила 0.5.

теперь сравнима с этим числом, а не оценивается на глаз.

**«Критерий отбора полос верен только для исходного порядка; перестановка его создаёт»** —
подтверждено сильнее прежнего: именно перестановка отвечает за четыре порядка разницы.

**«Эпоха как гранулярность верна для ОЗУ»** — подтверждено и уточнено. Глубина полос задаёт
ТОПОЛОГИЮ графа, поэтому менять её можно только на границе эпохи; цена пересборки графа
измерена ранее в 0.90 мс на токен, а происходит она 13 раз на 201 шаг — то есть гранулярность
эпохи здесь не терпимое ограничение, а дешёвое.

## ОСТАЁТСЯ В СИЛЕ: ярусность против отсечения

§4.79 дал на gpt-oss: отсечение при одной резидентности `PPL 524.36`, ярусность `10.0973` —
разрыв в 52 раза. Раскладка даёт по показателю −2.18 множитель `1.108^2.18 = 1.25`, то есть
524 → примерно 420. **Разрыв в 52 раза этим не закрывается**, и вывод «ярусность нужна»
остаётся.

Это важно назвать прямо: не всякое сегодняшнее число что-то опровергает.

## СУЖАЕТСЯ: блокер уровня 5

Уровень 5 (сборка на границе эпохи) откладывался из-за нужды в ядре сборки на GPU. §4.88
установил: для ПЕРЕСТАВЛЕННОЙ модели резидентность префиксная, а префикс даётся видом без
копирования — ядро не нужно. Ядро требуется только для НЕПРЕФИКСНОЙ резидентности.

И теперь у непрефиксной появился порог, который ей надо перешагнуть: префиксная раскладка по
слоям уже даёт 13.19 %. Непрефиксную придётся обосновывать превышением этого, а не самой
возможностью.

## Считается, а не проверяется опытом: цель 5 % статикой

По закону `PPL ~ d^-2.18` резидентность 5 % (одна полоса из шестнадцати) даёт

```
PPL = 4.73 · 16^2.18 = 4.73 · 422 ≈ 2000
```

при монолите 4.72. Раскладка не спасает: она стоит множителя порядка 1.25, а нужен множитель
порядка ста. **Вывод «цель 5 % статикой недостижима» подтверждается расчётом**, а не только
прежним замером, и теперь у него есть величина недостачи.

Оговорка: при малой глубине разброс профиля растёт (10.8 раза при глубине 4 против 4.2 при
восьми), поэтому выигрыш раскладки там может быть больше расчётного. Это проверяется одним
прогоном и будет проверено.

# 4.95 Очная ставка со встроенным решением. Отсечение полос проигрывает по обеим осям

`llama.cpp` в том же дереве поставляет:

| схема | т/с | PPL |
|---|---|---|
| `-ncmoe 6` | 3.02 | **60.98** |
| `-ncmoe 12` | 7.86 | **60.98** |
| **`-ncmoe 18`** | **7.89** | **60.98** |

| полосы, глубина 22 из 45 | 4.22 | 365.32 |

**Встроенное средство выигрывает по обеим осям сразу:** на 48 % быстрее лучшего полосного
плеча и вдвое-вшестеро лучше по качеству. Одинаковая перплексия при всех `N` — внутренняя
проверка: размещение действительно не трогает качество.

## Оговорка о режиме, без которой вывод был бы шире, чем позволяют числа

**gpt-oss-20b (11.3 ГиБ) ПОМЕЩАЕТСЯ в VRAM + ОЗУ (29.9 ГиБ).** Это не целевой режим. В
целевом (120b, около 60 ГиБ) `-ncmoe` не поможет: он статически размещает веса, а размещать
их некуда — не хватает и оперативной памяти. Там нужна потоковая подкачка с вытеснением,
которой нет ни у `-ncmoe`, ни у полос в нынешнем виде.

Поэтому замер говорит следующее и только следующее:

1. **В режиме, где памяти хватает, встроенное средство доминирует.** Строить своё незачем.
2. **Цена отсечения на целевой модели много выше, чем на olmoe:** половина глубины стоит
   множителя 36 против 4.5. Это свойство модели, а не режима, и оно переносится.

Пункт 2 существенно бьёт по линии отсечения: она проверялась на модели, где обходится
дешевле всего.

## Что отсюда следует для направления работ

> ### ⚠ ПОПРАВКА СНЯТА ЗАМЕРОМ §4.98 — оставлена как след ошибки
>
> Я написал «линия отсечения полос доминируется». **Это переоценка, и она снимается.**
>
> Замер шёл на модели, которая ПОМЕЩАЕТСЯ в VRAM + ОЗУ, а `-ncmoe` есть средство
> РАЗМЕЩЕНИЯ: он перекладывает веса в оперативную память. В целевом режиме — модель больше
> VRAM + ОЗУ — размещать некуда, и весь его выигрыш там исчезает по построению.
>
> Отсечение же уменьшает **объём, который вообще надо где-то держать**, и это ровно тот
> рычаг, который в целевом режиме работает. Сравнивать их на модели, что помещается, значит
> мерить одно средство там, где важное свойство второго не проявляется вовсе.
>
> **Что замер говорит на самом деле:** там, где памяти хватает, своё строить незачем. О
> целевом режиме он не говорит ничего, и очную ставку надо ставить заново — под баллоном,
> как в §4.96.

Линия **ярусности** (полоса на диске, подкачивается по нужде) этим замером не затронута: у неё
нет потери качества, она платит временем, и встроенного конкурента у неё нет.

Линия **отсечения** тоже не затронута в целевом режиме, и у неё есть свойство, которого нет ни
у квантования, ни у размещения: **доля меняется во время работы**. Регулятор, подстраивающийся
под наличную память, без этого невозможен.

И главное направление подсказано другим замером того же дня — моделированием кэша по настоящей
трассе:

```
ёмкость 43 %:   LRU 82.5 %   LFU 84.3 %   Белади 92.6 %
```

Разрыв между простым счётчиком частот и оптимумом — **8.3 пункта, а в дисковом режиме это
2.1 раза по скорости**. Вот измеренный приз предсказания, и он на порядок весомее всего, что
дало отсечение.

# 4.101 Ярус против урезания у KV. Вердикт §4.97 не переносится

> **ПОПРАВКА, ЗАДАННАЯ ВОПРОСОМ.** «Почему мы ориентируемся на перплексию? Ведь мы не собираемся
> выбрасывать нерезидентный KV, а лишь перегружать его на более медленную память. Не делаешь ли
> ты ту же ошибку, что и с весами?»
>
> Ошибка была сделана. Весь день мерилась ветка «резать» — окно, сток, отбор тяжёлых,
> квантование, — то есть ровно та, которую §4.97 для весов уже отверг. Ветка «течь» не мерилась
> вовсе. Ниже она измерена, и вывод оказался ОБРАТНЫМ выводу §4.97.

## Цена спуска KV на ярус ниже

`llama.cpp` несёт готовый флаг `-nkvo`: KV остаётся в ОЗУ, веса — на видеокарте, внимание
считается там, где лежат данные. Это тот же приём, что и `-ncmoe` у весов, и качество он не
трогает ВОВСЕ. olmoe-mxfp4, веса целиком на видеокарте, `llama-bench -n 64`:

| глубина | KV в VRAM, т/с | KV в ОЗУ, т/с | замедление |
|---|---|---|---|
| 0 | 86.56 | 41.76 | 2.07 x |
| 1024 | 81.07 | 27.63 | 2.93 x |
| 2048 | 76.90 | 19.47 | 3.95 x |
| 3968 | 70.03 | 14.40 | **4.86 x** |

Замедление растёт с глубиной, потому что растёт то, что переносится: на глубине 3968 KV этой
модели читается **496 МиБ на каждый порождённый токен** (128 КиБ на токен контекста, без GQA).
По PCIe 3.0 x16 это около 41 мс, то есть потолок ~24 т/с и без всякого счёта на процессоре;
измеренные 14.40 ложатся в тот же порядок. Иначе говоря, цифра не артефакт `-nkvo`: любая
схема, где KV живёт этажом ниже, упрётся в ту же полосу.

## Почему вывод §4.97 сюда не переносится

Сопоставление двух обменов, каждый по своим замерам:

| | урезание | поток |
|---|---|---|
| **веса** (§4.96, §4.97) | x3.7 качества за x2 скорости | x3.5 скорости за ноль качества |
| **KV** (здесь) | **x1.18 качества за вчетверо меньше трафика** | **x4.9 скорости за ноль качества** |

Урезание KV дёшево по качеству там, где урезание весов было разорительно, а поток KV дорог по
скорости там, где поток весов был терпим. **Обе стороны обмена поменялись местами.**
Для весов правило «дешевле течь медленно, чем резать»; для KV — обратное.

Причина в том, что веса читаются выборочно (8 экспертов из 64, то есть активна пятая часть), а
KV читается ЦЕЛИКОМ каждый токен. Поэтому у весов поток экономит на выборе, а у KV экономить не
на чем — и единственный способ уменьшить перенос есть уменьшение самого KV.

## Отсюда: кривая качества нужна не как крайняя мера, а как условие достижимости нижних ярусов

Трафик на порождённый токен при глубине 3968 и то, что он означает для яруса:

```
f16, весь KV          496 МиБ/токен   NVMe 3.5 ГБ/с -> 7 т/с    SATA 0.5 ГБ/с -> 1 т/с
q4_0                  124 МиБ/токен   NVMe -> 28 т/с            SATA -> 4 т/с
q4_0 + окно 2048      66 МиБ/токен    NVMe -> 53 т/с            SATA -> 7.5 т/с
```

То есть на диск KV в исходном виде не выносится вовсе, а с квантованием и окном — выносится.
**Сжатие KV здесь не альтернатива ярусности, а её предпосылка.**

## Линия отбора тяжёлых закрыта замером

Для проверки в граф добавлен актуатор (`myc_kv_oracle_mask` в `llama-graph.cpp`): после softmax
обнуляется всё, кроме удержанного, и сумма возвращается к единице — это тождественно вниманию,
посчитанному только по удержанным позициям. Проверка пропускания: бюджет во весь контекст даёт
контрольные 4.4702.

Первая постановка — «оставить m наибольших» — дала невозможное на первый взгляд:

```
топ-4096 (всё)    4.4702        топ-1024   12.9527
топ-3072          4.5417        топ-512    76.1806   <- окно 512 даёт 6.32
топ-2048          5.1514
```

**Отбор по величине внимания катастрофически хуже простого окна того же размера — при БОЛЬШЕЙ
удержанной массе.** Объяснение видно из устройства внимания: сток забирает основную долю массы,
а извлечение размазано по хвосту малых весов; обнуляя хвост и перенормируя, голова обращается
почти в сток и перестаёт работать.

Отсюда правильная постановка, совпадающая с устройством опубликованных методов (H2O, Quest):
окно ПЛЮС тяжёлые сверх него, при равном общем бюджете.

| бюджет | только окно | пополам с тяжёлыми | тяжёлые вперёд |
|---|---|---|---|
| 1024 позиций | **4.6555** | 6.9494 | 9.7223 |
| 512 позиций | **5.3186** | 13.3959 | 41.2582 |

**Добавка тяжёлых за счёт окна ухудшает монотонно и сильно.** Лучшая политика при данном
бюджете есть сток плюс самое свежее окно, то есть StreamingLLM без добавок.

Оговорка, которая держится открытой: оракул выбирает СВОЙ набор на каждый запрос, а H2O и Quest
выбирают устойчивый по накопленной статистике. Возможно, вредна именно неустойчивость набора, и
тогда довод «раз оракул хуже, то и оценка хуже» не строг. Но платить за проверку этого стоит
только если ярусность упрётся, а она пока не упёрлась.

## Удержанная масса внимания как заместитель качества — опровергнута

Замер §4.100 опирался на долю удержанной массы. Он был бы обманчив:

```
бюджет 128 из 1024, по головам:  только окно 0.386, окно+сток 0.735, оракул 0.831
```

Оракул удерживает БОЛЬШЕ всех и работает ХУЖЕ всех. Масса ранжирует политики в обратном порядке
относительно перплексии. Всё, что в §4.100 выведено из удержанной массы (в том числе «слои 9–15
держат 91 % массы в четырёх позициях, значит старый KV там почти весь лишний»), этой опоры

Тем же опровергается и раскладка бюджета по слоям, выведенная из профиля массы: профиль обещал

Самая дешёвая раскладка оказалась и самой качественной.

## Масштабирование на gpt-oss (разобрано из вчерашней оборванной трассы)

Пересъёмка не понадобилась: файл был дописан на 82 %. Чёткое расслоение по чётности слоя —

```
чётные слои   наклон d log n95 / d log t = 0.00..0.07,  n95 = 15..40 при любом контексте
нечётные      наклон 0.52..0.77
```

Чётные — это слои со скользящим окном 128, они O(1) по устройству модели. Средний наклон 0.35
против 0.76 у olmoe ровно поэтому: половина слоёв у gpt-oss уже не растёт.

Оговорка: у gpt-oss GQA 8:1, а числа посчитаны по Q-головам. Единица хранения — KV-голова, и
реализуемая доля требует объединения по восьми Q-головам группы. По квантильной трассе оно не
считается, нужны индексы. Пункт открыт — но после отмены массы как заместителя он потерял
срочность.

## Дефект сборки, тише всех прежних

Правка `src/llama-hparams.h` в 10:35 НЕ вызвала пересборки `llama-kv-cache.cpp` — объектник
остался от 20:05 предыдущего дня, и в бинарник попала старая подставляемая `is_masked_swa`.
Ручка стока была мертва, и первая развёртка измерила окно БЕЗ стока, дав вывод «окно проигрывает
квантованию вдесятеро», который после починки не подтвердился.

Причина: ccache перехватывает вывод `/showIncludes`, из которого CMake добывает зависимости от
заголовков, и ninja остаётся без их списка. Сборка рапортует успех.

**Признак в замере:** ручка даёт ПОБИТОВО одинаковый результат при разных значениях. Не
«близко», а точное совпадение — значит вход маскирования не изменился вовсе.

Заплата в `scratchpad/build-fast.ps1`: отметка времени, и если заголовок свежее её — трогаются
все исходники библиотеки, ninja пересобирает, ccache возвращает неизменившиеся почти даром.

## Что теперь стоит перед форком

Ярусность KV упирается в полосу, и это измерено. Значит работа не в отборе (закрыт) и не в
предсказании (его у KV нет), а в двух вещах:

1. **Ярус SSD для KV, которого в llama.cpp нет вовсе.** Достижим только вместе со сжатием:
   f16 даёт 1–7 т/с, `q4_0` с окном — 7.5–53 в зависимости от диска.
2. **Единый планировщик полосы на веса и KV.** Они делят один PCIe и один диск, у весов
   расписание вероятностное, у KV точное. KV ставится в очередь первым, веса подкачиваются в
   оставшуюся полосу.
