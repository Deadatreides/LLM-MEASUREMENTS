# Почему сборка занимала 25–30 минут

Разбор 5 сентября 2026. Причина оказалась ОДНА, но проявлялась двумя независимыми путями, и
каждый из них по отдельности выглядел как самостоятельная беда.

## Корень: кириллица в пути проекта

Путь дерева — `<PROJECT_ROOT>\fork-tree`.

Видно на уровне байтов. Файл зависимостей, который пишет nvcc:

```
ggml\src\...\arange.cu.obj : H:/M-pM-`M-aM-nM-rM-`/M-qM-`M-iM-rM-{/...
                                F0 E0 E1 EE F2 E0  =  «работа» в cp1251
                                             M-^W  =  0x97, длинное тире в cp1251
```

nvcc записывает пути в **cp1251** — системной кодовой странице. А `build.ninja`, который
породил CMake, держит те же пути в **UTF-8**. Сопоставить их невозможно.

## Проявление первое: сборка никогда не была инкрементной

`ninja -d explain` СРАЗУ после успешной сборки:

```
ninja explain: .../ggml.h is dirty
ninja explain: .../ggml-impl.h is dirty
ninja explain: .../vendors/cuda.h is dirty
...
[1/139] Building CUDA object ...
```

Грязными объявлены ВСЕ заголовки, включая никем не тронутые `arange.cu` и `cuda.h`. Ninja не
может сопоставить пути из файла зависимостей — и на всякий случай пересобирает. Отсюда:
каждая сборка была полной пересборкой CUDA-ядра, сколько бы строк ни изменилось.

## Проявление второе: кэш компиляции был мёртв дважды

**Раз.** ggml подключает ccache так:

```cmake
set_property(GLOBAL PROPERTY RULE_LAUNCH_COMPILE "${GGML_CCACHE_VARIANT}")
```

`RULE_LAUNCH_COMPILE` работает **только для генератора Makefile**; Ninja его игнорирует.
В `build.ninja` слова «ccache» не было ни разу, хотя `GGML_CCACHE_FOUND` в кэше CMake стоял.
Ninja-совместимый способ — `CMAKE_<LANG>_COMPILER_LAUNCHER`.

**Два.** Подключив launcher правильно (434 упоминания в `build.ninja`), получил:

```
Cacheable calls:                 1 / 138 ( 0.72%)
Uncacheable calls:             137 / 138 (99.28%)
  Unsupported source encoding: 137 / 137 (100.0%)
```

ccache отказывается кэшировать по той же причине — кодировка пути. В пробе на одном файле он
кэшировал прекрасно (6.6 с против 0.1 с, в 66 раз), но там я взял ASCII-стык.

## Решение: собирать через ASCII-стык

`mklink /J H:\ftree "<WORKDIR>\...\fork-tree"` даёт тем же файлам путь без кириллицы. Дерево
`build-fast` конфигурируется через него, и обе беды снимаются разом: ninja сопоставляет
зависимости, ccache кэширует.

Стык не требует прав администратора и ничего не копирует. Исходное дерево не трогается.

## Почему первая попытка этого обхода провалилась

Бинарник из `build-fast` падал на старте:

```
GGML_ASSERT(prev != ggml_uncaught_exception) failed   ggml/src/ggml.cpp:22
```

Утверждение срабатывает, если обработчик terminate уже установлен, то есть статический
инициализатор ggml отработал дважды. Тогда я проверил, что `ggml.cpp` компилируется по одному
разу, флаги компоновки совпадают, определения тоже — и объяснения не нашёл, обход бросил.

**Объяснение было в порядке действий, а не в коде.** Первая конфигурация прошла с
`BUILD_SHARED_LIBS=ON` (я не задал его явно, а умолчание оказалось иным, чем в рабочем
дереве). Обнаружив это по неразрешённому `llama_mycelium_runtime_of`, я переконфигурировал
каталог, удалив только `CMakeCache.txt` — но артефакты сборки с ОБЩИМИ библиотеками остались
на месте. Смесь остатков и дала двойной статический инициализатор.

Правильное действие — стереть каталог целиком, а не только кэш CMake.

## Что сделано

| # | изменение | эффект |
|---|---|---|
| 1 | `CMAKE_{C,CXX,CUDA}_COMPILER_LAUNCHER=ccache` вместо игнорируемого `RULE_LAUNCH_COMPILE` | кэш подключён на самом деле |
| 2 | `CCACHE_DIR=H:\ccache`, размер 30 ГБ | на C: было свободно 8.4 ГиБ, кэш по умолчанию лёг бы туда |
| 3 | Переменные кэша задаются при СБОРКЕ | ggml ставит `CCACHE_SLOPPINESS` при конфигурации, до сборки это не доживает |
| 4 | Дерево `build-fast` через ASCII-стык, сконфигурированное НАЧИСТО | снимает корень: и зависимости, и кодировку |

## Замер до и после

| состояние | время |
|---|---|
| как было (полная пересборка CUDA каждый раз) | 25–30 мин |
| ccache подключён, но путь кириллический | 11.5 мин |
| ASCII-стык, кэш холодный, полная сборка | 13.4 мин |
| **ASCII-стык, правка одного файла субстрата** | **6.0 с** |

Итог: **25–30 минут → 6 секунд** на обычной правке. Пересобираются четыре цели — сам файл,
библиотека субстрата и два бинарника.

## Эквивалентность деревьев ДОКАЗАНА, а не предположена

Прежде я отказался мерить на быстром дереве именно потому, что не мог объяснить его
поведение. Теперь объяснение есть, но одного его мало:

```
скорость   build-cuda 73.10 ± 1.39 т/с   build-fast 75.45 ± 4.60 т/с   совпадает
состояние  70 полей организма, расхождений 0                           бит в бит
```

Оснастка переведена на быстрое дерево; `build-cuda` оставлен нетронутым как запасной.
