# Задание: зонд компактности пространства вычислительных траекторий

Автономный измерительный скрипт. **Не требует форка llama.cpp, не требует незавершённой
архитектуры.** Стоковые модели + HuggingFace transformers + forward-хуки.

Железо: **GTX 1660 Super 6 ГБ, 24 ГБ RAM.** Все модели ниже подобраны под него.

---

## 0. Гипотеза, которая проверяется

Строится рантайм, который держит в VRAM малую долю весов и догружает остальное по PCIe.
Промах не портит качество (недостающее догружается), но стоит времени.

Схема жизнеспособна тогда и только тогда, когда

> **пространство реально используемых вычислительных маршрутов существенно меньше
> пространства запросов, и внутри него есть условная структура.**

Это гипотеза. Она не проверялась. Замер её проверяет — и, что важно, может её убить дёшево.

### Главная величина

```
q(M, policy) = доля активаций, обслуженных из кэша размера M
```

и кривая по `M` и по политике.

### Как из q читается вердикт

Целевая конфигурация (GPT-OSS-120B на 6 ГБ): 144 экспертных активации на токен, одна
активация 13.19 МБ, чтение резидентного 6.3 мс, один промах по PCIe 1.10 мс.

```
t_токен = 6.3 + 144·(1−q)·1.10   мс
```

| `q` при `M` ≈ 5 % массы FFN/MoE | tok/s | Вердикт |
|---|---|---|
| ≥ 0.93 | 60+ | схема работает как задумано |
| 0.83 – 0.93 | 30–60 | цель достижима |
| 0.72 – 0.83 | 20–30 | приемлемо, нужен кэш крупнее |
| 0.60 – 0.72 | 12–20 | пограничный |
| **< 0.60** | **< 12** | **гипотеза не подтверждена** |

**Накопления по слоям нет.** Наивно кажется, что надо угадать все слои и вероятность будет
`q^L`. Неверно: каждый промах догружается независимо, поэтому значима **средняя доля
обслуженных активаций**, а не произведение.

## 1. Что чем решается — какая модель на какой вопрос отвечает

Ни одна доступная модель не даёт прямого ответа за GPT-OSS-120B. Разные модели отвечают на
разные части, и это надо держать раздельно.

| Модель | Отвечает на | Не отвечает на |
|---|---|---|
| **OLMoE-1B-7B** (MoE) | есть ли условная структура при балансировке нагрузки; бьёт ли адаптивный кэш статический | абсолютный `q` для 120B (у неё 64 эксперта, top-8, 16 слоёв) |
| **Qwen3-1.7B fp16** (dense) | компактно ли пространство маршрутов **в принципе**, без артефакта балансировки | MoE-специфику |
| **тот же 4-bit** | размер искажения от квантования | — |
| **Qwen3-30B-A3B** (stretch, CPU) | ближе к цели: 128 экспертов, top-8, 48 слоёв | — |

**Что переносится с малой модели на большую:**

- концентрируется ли множество активных единиц (да/нет — структурный факт);
- бьёт ли адаптивный кэш статический (да/нет — есть ли условная структура);
- перекрытие между соседними токенами `o`;
- длина жизни режима;
- выходит ли число уникальных единиц на плато.

**Что не переносится:** абсолютное значение `q` при заданной доле бюджета. У MoE
разрежённость архитектурная (4 из 128), у dense — по величине активации. Числа разные.

Поэтому вердикт по §0 читается по **OLMoE**, а dense-прогон даёт структурный фон и
отдельно закрывает вопрос по плотному пути (DeepSeek-70B на P40).

## 3. Единица учёта — полоса, а не канал. Обоснование

Это центральное решение замера, от него зависит устойчивость к квантованию.

**Проблема.** Ошибка квантования `W' = W + ε` меняет `a_c = ⟨W_gate[c], x⟩`. Для сильно
активных каналов сигнал ≈ 3σ, вклад шума Q4 ≈ 0.03σ — ранг устойчив. Но у **границы
отсечения** соседние ранги разделены зазором порядка шума и тасуются свободно. Канальный
замер поэтому завышает число уникальных маршрутов и занижает hit rate.

**Решение — две меры сразу.**

**3.1 Агрегировать в полосы.** Полоса из `s` соседних каналов промежуточной размерности.
Масса полосы — сумма по `s` каналам, поэтому перестановки внутри полосы её не меняют:

```
дрожание канала ±1 %  →  дрожание массы полосы ±1%/√s
при s = 50           →  ±0.14 %          практически нечувствительно
```

Размер полосы выбирать так, чтобы **на слое было ≥ 100 полос**:

```
s = d_ffn / 128            dense
s = d_expert / 45          внутри эксперта у MoE (уровень 2)
```

**3.2 Порог по массе, а не по рангу.**

```
активные полосы слоя = минимальное множество, покрывающее 90 % суммы |a| по слою
```

Порог по массе определяется формой распределения, а не порядком у среза. Почти-равные
полосы могут меняться местами без изменения покрытой массы.

**Проверка, что мера сработала:** метрики на B (fp16) и B′ (4-bit) должны совпасть в
пределах нескольких процентов. Если разошлись сильно — полосы слишком мелкие, увеличить `s`
и повторить. **Это обязательная часть отчёта, не опция.**

## 4. Сбор трассы

### 4.1 MoE (модель A) — уровень 1, обязательный

Для каждого слоя `l` и токена `t` снять **полный вектор логитов роутера**, не top-k:

```python
# forward hook на роутер каждого MoE-слоя
# у OLMoE это обычно model.layers[l].mlp.gate — НАЙТИ ИНТРОСПЕКЦИЕЙ, не угадывать
router_logits[l] -> softmax -> p[l] ∈ R^{64}
```

Записывать:

```
request_id, token_idx, layer, top_k_ids, top_k_probs, gap_last_next
```

`gap_last_next` = `logit[ранг k] − logit[ранг k+1]`, у OLMoE k = 8. Нужен отдельно, см. §7.

### 4.2 MoE — уровень 2, желательный

Внутри каждого **активного** эксперта: полосы по `|silu(gate)·up|`, критерий из §3.2.
Даёт единицу `(layer, expert, band)`. Если снять тяжело — уровень 1 отвечает на главный
вопрос сам, просто грубее.

### 4.3 Dense (модели B, B′, C)

Роутера нет. Единица — `(layer, band)`:

```python
act = silu(gate_out) * up_out          # [n_tokens, d_ffn], один hook на слой
band_mass = act.abs().reshape(n_tokens, n_bands, s).sum(-1)
active_bands = минимальное множество, покрывающее 90 % от band_mass.sum()
```

Записывать `request_id, token_idx, layer, active_band_ids, покрытая доля массы`.

### 4.4 Объём

```
dense, 28 слоёв × ~30 активных полос × 2 Б  ≈ 1.7 КБ / токен
MoE,   16 слоёв × (8 id + 8 prob + gap)     ≈ 0.7 КБ / токен
```

60 тыс. токенов — 40–100 МБ. Писать в parquet или npz, **не в JSON**.

### 4.5 Корпус

Две части, обе обязательны, меряют **разное**.

**A — разнообразие. 500 запросов × ~80 токенов ответа.** Максимально несхожие короткие
запросы: код, математика, проза, диалог, факты, перевод, рассуждение, инструкции,
творчество, техподдержка, медицина, право, кулинария, спорт, история. ≥ 15 доменов, ≥ 30
запросов на домен, внутри домена — разные темы.
→ насколько велико пространство маршрутов.

**B — устойчивость режима. 20 диалогов × 5 ходов × ~200 токенов.** Связные сессии внутри
домена с естественной сменой регистра (объяснение → код → таблица → оговорки).
→ как долго живёт режим и как выглядят переходы.

Итого ≈ 60 тыс. токенов. Промпты **сгенерировать заранее и сохранить в файл** — один и тот
же корпус прогоняется через все модели, иначе сравнение A/A′ и B/B′ бессмысленно.

## 5. Симуляция кэша — главный расчёт

Полностью офлайн по собранной трассе. Быстро, можно гонять десятки конфигураций.

### 5.1 Модель кэша

Единица: `(layer, expert)` или `(layer, expert, band)` для MoE, `(layer, band)` для dense.
Размер единицы в параметрах берётся из конфига модели.

```
M = бюджет как ДОЛЯ ОТ ОБЩЕЙ МАССЫ FFN/MoE-параметров
    сканировать M ∈ {1, 2, 3, 5, 7, 10, 15, 20, 30, 50} %
```

### 5.2 Политики — все четыре

| Политика | Описание | Роль |
|---|---|---|
| **STATIC-TOPK** | заполнить самыми частыми по всей трассе, не менять | **нижняя граница** |
| **LRU** | классика | базовая линия |
| **LFU-decay** | частота с затуханием, окно ~100 токенов | простая адаптивная |
| **EPOCH** | заморожен на 15 токенов; на границе пересобрать по спросу за прошедшую эпоху | целевая |

**Сравнение STATIC-TOPK против остальных — половина ценности замера.** У MoE балансировка
нагрузки выравнивает маржинальную частоту экспертов по построению, поэтому STATIC ожидаемо
даст `q ≈ M` (линейно, бесполезно). **Если адаптивные политики его не обходят заметно —
условной структуры нет, и вся схема держится на воздухе.** Это самый дешёвый способ убить
идею рано.

У dense такого артефакта нет, поэтому там STATIC может оказаться неожиданно силён — что само
по себе результат (значит есть стабильное ядро).

### 5.3 Что считать

```
q            доля обслуженных активаций
q_by_layer   с разбивкой по слоям — ранние и поздние ведут себя по-разному
miss_burst   распределение длин серий промахов подряд
churn        единиц заменено за эпоху / размер кэша
```

`churn` критичен: при `churn → 1` кэш перестраивается целиком каждую эпоху, и по PCIe это
не пролезет независимо от `q`.

### 5.4 Прогрев отдельно от установившегося режима

```
первые 10 % трассы  — холодный старт
последние 50 %      — установившийся режим   ← отчётное число
```

Разница — цена прогрева.

## 6. Длина и число маршрутов

То, что просили назвать явно.

### 6.1 Длина персистентности маршрута

```
o_k = |active(t) ∩ active(t+k)| / |active(t)|         медиана по трассе, k = 1..64
L_persist = наименьшее k, при котором медиана o_k < 0.5
```

Это и есть «длина пути» в практическом смысле: сколько токенов маршрут держится, прежде чем
сменится наполовину. Прямо задаёт разумную длину эпохи.

### 6.2 Эффективное число маршрутов

```
H_l = H(active_set_{l+1} | active_set_l)        условная энтропия, бит, по каждому слою
N_eff = 2^(Σ_l H_l)
```

Ориентиры из предварительного расчёта: при `H ≈ 0.2–0.5` бит/слой пространство компактно;
при `H ≈ 1.0` эффективное число маршрутов ~10⁷ и библиотека не поможет.

**График `H_l` по слоям построить обязательно** — ранние слои почти наверняка отличаются от
поздних, и это скажет, где вообще принимаются решения.

### 6.3 Насыщение

```
unique единиц                     vs число обработанных запросов
unique переходов (sig_l → sig_{l+1}) vs то же
unique полных путей (hash всей последовательности по слоям) vs то же
```

Плато или линейный рост.

### 6.4 Концентрация продолжений

Для каждого узла — распределение исходящих переходов по убыванию:

```
медиана p₁,  медиана (p₁+p₂),  медиана (p₁+p₂+p₃)
```

Прямо отвечает, сколько ветвей держать в теневом буфере.

## 7. Побочный замер: зазор у среза роутера (только MoE)

```
gap = logit[ранг k] − logit[ранг k+1]        k = top-k модели
```

Отчёт: гистограмма по слоям, квантили 5 / 25 / 50 %.

Зачем: рантайм планирует смещать роутер к резидентным экспертам. Смещение переворачивает
выбор там, где `gap < κ`. Квантиль 5 % задаёт максимально допустимое `κ`. Если разрывы
велики — смещение бесполезно и опираться надо только на догрузку.

---

## 8. Контроль квантования — обязательный раздел отчёта

Прогнать **один и тот же корпус** через B (fp16) и B′ (4-bit), и через A (4-bit) и A′ (int8).
Сравнить попарно:

| Метрика | Допустимое расхождение |
|---|---|
| `q` при каждом `M` | < 3 п.п. |
| `L_persist` | < 15 % |
| `N_eff` | < 2× |
| число уникальных единиц | < 10 % |

Если расхождение больше — **полосы слишком мелкие.** Увеличить `s` вдвое и повторить.
Записать, при каком `s` метрики сошлись. Это число само по себе полезно: оно говорит,
на какой гранулярности структура устойчива.

## 9. Формат отчёта

Один markdown + каталог с графиками и сырыми csv.

**Первая строка отчёта — одно число:**

```
q при M = 5 %, политика EPOCH, модель OLMoE, установившийся режим = ____
```

Дальше:

1. Таблица `q(M, policy)` — 10 значений `M` × 4 политики, по каждой модели.
2. График `q` от `M`, логарифмическая ось `M`, четыре кривые.
3. Вердикт по таблице §0.
4. `churn` при `M = 5 %`, EPOCH.
5. `L_persist` и распределение `o_k` (§6.1).
6. `H_l` по слоям и `N_eff` (§6.2).
7. Три кривые насыщения (§6.3).
8. Медианы `p₁`, `p₁+p₂`, `p₁+p₂+p₃` (§6.4).
9. Квантили `gap` (§7).
10. **Таблица контроля квантования (§8).**
11. Отдельно — то же для dense-моделей, с выводом по плотному пути.

**Честно указать:**

- какие модели, какая квантизация, сколько токенов реально собрано;
- как найдены модули роутера и FFN (имена, интроспекция) — если угадывались, сказать прямо;
- при каком размере полосы метрики стали устойчивы к квантованию;
- где пришлось отступить от задания и почему;
- всё, что вызвало сомнения в корректности трассы.

Если замер не получился — так и написать. **Неполный честный отчёт полезнее полного, где
часть чисел получена не тем способом, что заявлено.**

## 10. Порядок работ

```
1. Интроспекция модели: найти модули роутера (MoE) и gate/up (dense).
   Проверить на 10 токенах, что снимаются ВСЕ логиты роутера, а не top-k,
   и что band_mass считается по правильной оси.
   → ПОКАЗАТЬ РЕЗУЛЬТАТ ДО ПОЛНОГО ПРОГОНА
2. Сгенерировать и сохранить корпус (A + B), один на все модели
3. Прогон B (Qwen3-1.7B fp16) — самый быстрый, отладка всего конвейера
4. Симулятор кэша, четыре политики, десять размеров
5. Прогон B′ (4-bit) → контроль квантования § 8
6. Если метрики разошлись — увеличить полосу, вернуться к шагу 3
7. Прогон A (OLMoE 4-bit) — основной, MoE
8. Прогон A′ (int8 на CPU) — контроль
9. Метрики §6, §7
10. Отчёт
11. (если останется время) C и D
```

Шаг 1 — точка, где легче всего обесценить весь замер: если хук встанет **после** отсечения
top-k, трасса потеряет «почти выбранных», а именно они несут условную структуру.
Обнаружится это только в конце.

Шаг 6 — не пропускать. Без контроля квантования числа из 4-bit прогонов недоказуемы.

## 11. Ограничения окружения

- 1660 Super 6 ГБ, 24 ГБ RAM. Компилятора C/C++ нет, всё на Python.
- `bitsandbytes` для 4-bit/int8, `transformers`, `torch`, `pyarrow`/`numpy`.
- Скорость прогона не важна, важна корректность трассы.
- **LM Studio не подходит:** его OpenAI-совместимый API отдаёт токены и logprobs выхода,
  логитов роутера и скрытых состояний — нет. Только HF transformers с хуками.
- Если модель не влезает даже с 4-bit — уменьшить и сказать об этом в отчёте.

## 12. Чего делать НЕ надо

- Не строить граф, PTG, кластеризацию, метрику похожести траекторий. Для этого замера они
  не нужны. Метрика `D(trace₁, trace₂)` — отдельная задача, и go/no-go снимается без неё:
  достаточно точной идентичности единиц и политики вытеснения.
- Не мерить perplexity, качество ответов, скорость генерации.
- Не оптимизировать скорость сбора трассы.
- Не подгонять размер полосы под желаемый результат. `s` выбирается один раз по §3.1 и
  корректируется только по критерию устойчивости §8.
