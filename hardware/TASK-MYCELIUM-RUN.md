# Задание: прогон Mycelium 8.9.2 на локальных моделях

Отдельная работа, не продолжение зондов по весам. Другой код, другая гипотеза.

**Что проверяется:** даёт ли термодинамически управляемая мультиагентная оркестрация
качество выше, чем те же модели без неё.

---

## 0. Зачем это, и почему предыдущие замеры были не о том

Три предыдущих задания измеряли отбор контекста по негэнтропии. Это оказалось механизмом,
которого в Mycelium нет. Проверено по коду:

```python
# blackboard.py:247
def compute_thermodynamics(self, block_id, final_answer, ...):
    H_old = self.effective_entropy(block_id)
    block = self.upsert(block_id, final_answer, ...)      # ← ОТВЕТ, не контекст
    delta_H = H_old - H_new
```

`G_B` строится из **ответа, который система конструирует**. `ΔH` меряет, стал ли ответ
структурнее. `Φ > 0` гейтит Depth Loop. `select()` выбирает блок ответа, над которым надо
ещё поработать. Контекст же извлекается обычным ретривером (`memory.search`: FAISS-косинус
+ `topology_bias` из Physarum).

То есть термодинамика Mycelium — это **распределение вычислительного усилия по траектории
построения ответа**, а не поиск. Мерить надо её, и мерить end-to-end.

---

## 1. Единственное число, ради которого всё делается

```
E_score = Q(Y_syn) − max_i Q(Y_i)
```

Качество синтеза минус качество лучшего отдельного кандидата. Положительное `E_score` —
операционное определение эмерджентности в этой системе (`scorer.py:272`).

| `E_score` | Вывод |
|---|---|
| ≥ +0.10 устойчиво | синтез бьёт лучшего одиночку, оркестрация работает |
| +0.02…+0.10 | эффект есть, сравнивать с best-of-N |
| ≈ 0 | синтез не добавляет ничего |
| < 0 | синтез **портит**, лучше брать лучшего кандидата |

## 2. Критическая проверка ДО всякого прогона

`scorer.py:154`:

```python
if sys.platform == 'win32' and os.getenv('MYCELIUM_ALLOW_WINDOWS_CODE_EXEC') != '1':
    return min(self._q_code(code_text), 0.3)
```

**На Windows без флага код никогда не исполняется, `q_env` зажата в ≤ 0.3.**

А `q_env` — множитель притока негэнтропии: `d_eS = −ρ·ΔH·q_env`. Весь термодинамический
контур поехал бы на почти-константе, и замер выглядел бы работающим.

```
1. установить MYCELIUM_ALLOW_WINDOWS_CODE_EXEC=1  (или запускать в WSL)
2. подать заведомо рабочее решение → убедиться, что q_env = 1.0
3. подать заведомо сломанное      → убедиться, что q_env ≤ 0.4
4. подать бесконечный цикл        → убедиться, что срабатывает timeout, q_env = 0.1
```

**Если q_env не различает эти три случая — дальше не идти.** Это тот же класс дефекта,
что дважды обнулял предыдущие замеры.

генерации будет низкой, это свойство железа, обходить не пытаться.

## 5. Условия. Пять, и четвёртое обязательно

| # | Условие | Что выключено |
|---|---|---|
| **M** | полный Mycelium | ничего |
| **M−Φ** | без гейта живости | Depth Loop идёт всегда до лимита шагов |
| **M−λ** | без контроля хаоса | `K_ACT` зафиксирован на среднем, PID отключён |
| **M−HC** | без гиперцикла | равные квоты кастам G/C/S |
| **BoN** | **best-of-N без оркестрации** | всё: N генераций теми же моделями, отбор по `Q_ext` |

**`M − BoN` — главный разрыв.** Без него измерим «мультиагентность помогает» (известно), а
не «термодинамика помогает» (вопрос).

`N` в BoN подобрать так, чтобы **бюджет токенов совпадал** с полным Mycelium. Считать
фактически потраченные токены в M и задать `N` под них. Иначе сравнение нечестное.

## 7. Диагностика: работает ли термодинамика вообще

Отдельно от `E_score`. Возможен исход «качество выросло, но термодинамика ни при чём» —
его надо уметь отличить.

```
1. Φ > 0 хоть когда-нибудь?
   В соседнем замере на контексте Φ > 0 не выполнялось НИ РАЗУ при ρ=1, q_env=0.5.
   Если и здесь всегда Φ < 0 — гейт нерабочий, и M ≡ M−Φ по построению.

2. λ_L покидает диапазон [−0.1, +0.1]?
   Если нет, PID не срабатывает и M ≡ M−λ.

3. Квоты каст x уходят от 1/3?
   Если нет, гиперцикл не работает и M ≡ M−HC.

4. corr(Φ, задача решена) и corr(ΔH, задача решена)
   Связана ли термодинамика с исходом вообще.

5. Депт-луп: как часто запускается, меняет ли ответ, улучшает ли q_env
```

**Если пункты 1–3 показывают, что механизмы не активируются, — абляции измерят ноль, и
это надо сказать прямо, а не выдавать за отрицательный результат по существу.**

## 8. Оценка времени — считать по длине контекста, не по одной цифре

В соседней работе оценка была занижена вчетверо, потому что бралась скорость префилла на
2048 токенах (155 ток/с), а на 4096 она уже 45 ток/с.

```
измерить фактическую скорость генерации на 10 вызовах ДО прогона
считать: задач × условий × шагов × (K_ACT генераций + критика + синтез) × токенов / скорость
```

Грубый ориентир: 30 задач × 5 условий ≈ 6–10 часов. **Сначала смоук на 3 задачах × 5
условий** — он даст реальную скорость и вскроет дефекты. Ориентировочно 40–60 минут.

**При каждом запуске указывать ориентировочное время.**

## 11. Отчёт

Первая строка — одно число:

```
E_score, полный Mycelium, среднее по 30 задачам = ____
```

Дальше:

```
таблица: условие × (q_env, E_score, E_total, токенов, секунд)
разрыв M − BoN при равном бюджете токенов          ← ГЛАВНОЕ
разрывы M − M−Φ, M − M−λ, M − M−HC                 ← что именно даёт вклад
диагностика §7: активировались ли механизмы
распределения Φ, λ, квот каст по шагам
```

Обязательные разделы, как в предыдущих трёх отчётах:

- что реально прогнано, с числами;
- где отступили от задания и почему;
- что вызывает сомнение в корректности;
- **что не запустилось с первого раза и что оказалось причиной.**

Неполный честный отчёт полезнее полного, где часть чисел получена не тем способом, что
заявлено. Если гейт закрыл прогон — отчёт на одну страницу, и это будет самый полезный
исход.

## 12. Чего НЕ делать

- Не переписывать Mycelium. Задача — прогнать существующий код, а не улучшить его.
- Не менять коэффициенты (`w_*`, `α`, `τ`, пороги). Они авторские; если что-то выглядит
  неверным — сообщить, не править.
- Не подменять `q_env` на LLM-судью. Только исполнение тестов.
- Не использовать одну модель в трёх ролях.
- Не начинать полный прогон до обоих гейтов.
