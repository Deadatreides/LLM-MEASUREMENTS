## Для запихивания — ниже обрыва памяти

### З1. Стриминг экспертов явным чтением, кэш слотов и заполнение волнами — llama.cpp PR #25294

* **Статус:** открыт с 4 июля 2026, ревью мейнтейнеров нет.
* **Механизм:**
  - кэш из `n_slots` срезов на слой на устройстве;
  - перевод номеров экспертов в слоты после top-k;
  - промахи дочитывает пул потоков `pread`, с O_DIRECT мимо страничного кэша;
  - вытеснение по затухающей «горячести» с LRU при равенстве;
  - когда убатч задевает больше экспертов, чем слотов, эксперты считаются волнами по
    `(n_slots − k)/2`, остальное маскируется, выходы суммируются.
* **Замер** (GLM-5.2 254 ГБ на 128 ГБ унифицированной памяти): заполнение 1.06 → 5.58 т/с (5.3×),
  ответ 0.87 → 2.08 т/с против `mmap + --cpu-moe`.
* **Проблемы из обсуждения:**
  - волны расходятся с эталоном по мере длины ответа — порядок накопления меняет argmax на
    пограничных токенах;
  - нужен пол кэша `3·k`;
  - только один контекст на модель;
  - на тёплом кэше Linux O_DIRECT медленнее буферизованного чтения.
* **Форки на его основе:**
  - aldubl — промежуточный ярус ОЗУ: 3.71 т/с заполнения против 2.06;
  - ServeurpersoCom — раздел видеопамяти;
  - xpire — `--moe-stream-window`: W слотов на слой целиком, подкачка строго по порядку слоёв.
* **Тот же принцип в C-движках** kimi-k3-in-c и glm-5.2-in-c: `pread`/O_DIRECT, LRU-кэш,
  `POSIX_FADV_DONTNEED` против разрастания страничного кэша.
* **У нас:** нет. Это прямое лечение обрыва из PREFILL-DEFICIT.md (заполнение 0.19×, 7.7 ГиБ чтения
  на убатч), а у 120b этот режим по построению. Нужен путь для Windows: `FILE_FLAG_NO_BUFFERING`
  или `ReadFile` по выровненным блокам.

### З2. Загрузка объединения экспертов один раз на слой — glm-5.2-in-c

* Для пакета токенов берётся объединение выбранных экспертов слоя, каждый читается один раз.
* Вместе с окном по слоям (З1, xpire) это и есть послойное заполнение из разбора 13 сентября.
* **У нас:** нет.

### З3. Горячие эксперты, закреплённые в ОЗУ — llama.cpp PR #26414 и обсуждение #25469 «HotPin»

* **Статус:** открыт с 1 августа 2026.
* **Механизм:** частоты по `ffn_moe_topk`, `mlock` N горячих в ОЗУ, плотные части закрепляются первыми.
* **Замер:** заполнение 24.4 → 37.5 т/с, ответ 2.0 → 3.0 т/с (i9-13900KF + RTX 4090, 152 ГБ ОЗУ).
* **На Windows** жалуются на ошибки `VirtualUnlock`.
* **У нас:** есть закрепление `MYC_PIN`; прежние замеры шли в режиме выше обрыва.

### З4. Сжатие KV сильнее q4_0 без потери качества

* **TurboQuant** (Google, 2025): типы `turbo3`/`turbo2` для `-ctk/-ctv` в форке openalchemy/llama.cpp,
  обсуждение llama.cpp #20969. Около 5× при 3 битах «без потери качества» на Qwen; требует FA и CUDA.
* **Недавнее в точности, старое в 3–4 битах** (quant.cpp, чистый C, 401★): последние 128 токенов в
  FP32, остальное после случайного преобразования Адамара — скаляры Ллойда–Макса. На Llama 3.2 3B
  контекст вырос в 6.9× при +3.8 % перплексии.
* **Преобразование Адамара для KV** в ik_llama.cpp: PR 1033, 1034, 1527; Q4_0 KV с низкой
  перплексией — PR 1547, 1556.
* **У нас:** есть только q8_0/q4_0. На 65 тыс. KV занимает 1.54 ГиБ и выталкивает эксперты 21 слоя
  из 24 — сжатие вернёт карту экспертам.

### З5. KV на диске и повторное использование между запросами

* glm-5.2-in-c пишет KV на диск: 182 КБ на токен.
* В llama.cpp есть `cache_prompt` и сохранение слота.
* **У нас:** есть от апстрима, но в замерах целевого режима не использовалось. Для длинного контекста
  это отказ от повторного заполнения.

## Для скорости

### С1. Перепаковка экспертов CPU под нашей раскладкой — проверено в дереве

* В апстриме есть `CPU_REPACK` с ядром `mxfp4_8x8_q8_0` для AVX2.
* Но парсер `-ot` знает только типы буферов устройств по умолчанию («CPU», «CUDA0»), поэтому при
  `--fit`, `-ot` и `-ncmoe` эксперты ложатся в обычный буфер CPU (`CPU_Mapped`).
  **Перепакованное ядро на наших 67 % экспертного счёта не работает.**
* В ik_llama.cpp то же решает `-rtr`. По ik, перепакованные тензоры нельзя унести на карту при
  заполнении, так что заполнение станет медленнее.
* Перепакованное нельзя отобразить в память — только для моделей, помещающихся в ОЗУ.
* Выигрыш на Zen 1 неизвестен: у неперепакованного MXFP4 уже есть AVX2-ядро.
* Проверка дешёвая: разрешить `CPU_REPACK` в `-ot` и замерить ответ и заполнение.

### С2. Кэш экспертов на карте по LRU — llama.cpp PR #27861

* **Статус:** черновик с 28 августа 2026.
* **Устройство совпадает с нашим Б2:**
  - тензоры-спутники со слотами и нулевым слотом-пустышкой;
  - перевод номеров через `get_rows`;
  - хостовая `mul_mat_id` пропускает кэшированных и обнуляет строки, два выхода складываются;
  - только декодирование, асинхронные заливки с лимитом на шаг.
* **Замеры:** +15…+40 % ответа (Qwen3.8 на 2×3090: 18.4 → 24.2 т/с при 48 слотах, ~4.1 ГиБ);
  вместе с MTP 1.8–1.9×. По их трассам статической головы почти нет (top-32: 10 % против 6.2 %
  равномерного), выигрыш даёт временная локальность.
* **Ловушки из ревью:**
  - одинаковые номера пустышки ломают пакетные CUDA-ядра при n_tokens > 8;
  - несвежие таблицы между убатчами;
  - нет синхронизации перед шагом кэша;
  - все слоты заняты заливкой при медленной шине;
  - хостовая `mul_mat_id` тратит подготовку и барьеры даже на пропущенных экспертах.
* **У нас:** Б2 со статичным набором сеанса (1.24× / 1.05×), Б2.1 не сделан. Брать LRU и лимит
  заливок, обходить перечисленные ловушки.

### С3. Умное урезание экспертов (SER) — ik_llama.cpp PR 239

* **Правило:** всегда top-Kmin; эксперты между Kmin и K берутся, только если `p_i > t·p_0`.
* **Замеры ik:** DeepSeek-Lite — +12 % ответа за +1.6 % перплексии, +5–7 % за +1.1 %; гибрид CPU+GPU,
  5 экспертов вместо 6 — «почти 20 %».
* **У нас:** только глобальный `expert_used_count`. По нашему разложению каждый активный эксперт
  стоит ~20 мс на токен на 16 тыс.; у gpt-oss top-4, так что цену по качеству мерить на корпусе.

### С4. Спекуляция без модели-черновика

* **Какие есть:**
  - n-gram (ik PR 1261) и суффиксная (ik PR 1646);
  - n-gram + MTP + грамматика одним проверочным пакетом (glm-5.2-in-c);
  - модель-черновик (Deltafin, Rust).
* **При стриминге экспертов** проверочный пакет читает объединение экспертов один раз — чтения на
  токен становится меньше.
* **У нас:** есть MTP (срабатывает редко) и файлы `llama-lookup`. Суффиксной нет.

### С5. Слияние up и gate экспертов — ik `--merge-up-gate-experts`

* Одна `mul_mat_id` вместо двух, меньше квантования входа и барьеров потоков на CPU.
* Граф апстрима уже умеет `ffn_gate_up_exps`; файлу gpt-oss нужна побитово точная перекладка.
* Выигрыш в ik пока не измерен.

## Что другие намерили так же, как мы

* **glm-5.2-in-c:**
  - рост ОЗУ поднял попадание кэша с 2 до 61 %, а скорость не изменилась — упор в счёт;
  - рост видеопамяти скорость поднимает;
  - межслойная подкачка по роутеру подняла попадание 58 → 62 %, но снизила скорость;
  - перекрывающееся чтение с диска вредило.
* **Обсуждение llama.cpp #18758:**
  - на тёплом кэше `mmap` быстрее O_DIRECT;
  - явное чтение срезов на +13–14 % быстрее страничных промахов;
  - раскладка файла ускорила холодное чтение в 2.23× — но у модели с 512 мелкими экспертами. Это
    совпадает с выводом ревизии: раскладка решает на мелких единицах.
* **PR #25294:** побитовое совпадение со стримингом держится только на коротких ответах.
