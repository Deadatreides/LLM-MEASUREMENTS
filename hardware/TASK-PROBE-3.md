# ЭТАП 0. Диагностика-фильтр. Без инференса, минуты

Это главная перестройка задания. Вопрос «находит ли негэнтропийный отбор нужный блок»
решается на голом PPR, без генерации.

```
для каждой пары (иголка, позиция):
    раздробить стог на блоки           абзацы по 6 предложений, как в отчёте 2
    G_B = BlockGraph().build(блок, task_type)
    P   = g.transition_matrix()
    v   = g.personalization_vector(ВОПРОС, task_type)
    π   = run_ppr(P, v, alpha=0.85)
    J   = 1 − H(π)/ln(n)

    найти блок, содержащий иголку
    записать его РАНГ по J среди всех блоков
```

**Метрика-фильтр:**

```
R = P(блок с иголкой попал в верхнюю треть по J)
случайный отбор даёт R = 1/3 по построению
```

| `R` | Что делать |
|---|---|
| **≥ 0.60** | отбор работает, **этап 2 запускать** |
| 0.40 – 0.60 | слабо, этап 2 запускать в сокращённом виде (только условия A/B/C) |
| **≤ 0.40** | **отбор случаен. ЭТАП 2 НЕ ЗАПУСКАТЬ.** Сообщить и остановиться |

Дополнительно в том же проходе, всё бесплатно:

```
распределение J по блокам: среднее, std, размах
корреляция J с «содержит иголку»: точечно-бисериальная
то же для Φ = |d_eS| − d_iS,  d_eS = −ρ·ΔH·q_env,  d_iS = L_r·(π_r − π̄)²
    L_r = число рёбер G_B блока,  q_env = 0.5,  ρ = 1
    → отсекает ли фильтр Φ>0 блок с иголкой (это была бы катастрофа) или мусор
```

**Оговорка к постановке, обязательная.** Вектор персонализации строится по лексическому
пересечению с вопросом. Если иголка содержит слова вопроса, отбор вырождается в поиск по
ключевым словам, и `R` будет высоким по неинтересной причине. Поэтому:

> **Иголка обязана быть перефразирована так, чтобы не делить ни одного содержательного
> слова с вопросом.** Проверить это программно: пересечение множеств `_keywords(иголка)` и
> `_keywords(вопрос)` должно быть пустым. Иголки, не проходящие проверку, — переписать.

Без этого весь этап C измеряет обычный лексический ретривер.

# ЭТАП 1. Калибровка стога. GPU, ~30 минут

**Риск, который надо снять до основного прогона:** «потеря внимания в середине» описана на
крупных моделях. Покажет ли её Qwen3-1.7B на 6k — неизвестно. Если U-кривой нет, измерять
нечего и все четыре часа уйдут впустую.

```
только условие A (полный линейный контекст)
5 иголок × 5 позиций {5, 30, 50, 70, 95 %} × 3 размера стога {2000, 4000, 6000}
= 75 испытаний, ≈ 300 тыс. токенов префилла ≈ 32 мин при 155 ток/с
```

**Критерий:** глубина U = `min(acc) / max(acc)` по позициям.

| Глубина U | Размер стога |
|---|---|
| ≤ 0.7 | годится, брать наименьший такой |
| 0.7 – 0.85 | слабая U, брать наибольший размер |
| > 0.85 на всех размерах | **U-кривой нет.** Сообщить; этап 2 переформулировать как чистый замер качества при сжатии контекста, без утверждения про «середину» |

Выбранный размер `H` фиксируется и идёт в этап 2. Всё остальное считать от него.

# ЭТАП 2. Основной прогон. GPU, бюджет 5 часов

## 2.1 Условия — четыре, третье обязательно

| | Условие | Что проверяет |
|---|---|---|
| A | полный линейный контекст `H` | базовая U-кривая |
| B | дробление + отбор по **негэнтропии**, бюджет `Bud` | заявленный эффект |
| **C** | дробление + **случайный** отбор, тот же `Bud` | **контроль** |
| D | дробление + отбор по **косинусу к вопросу** | отделяет негэнтропию от «любого разумного отбора» |

**К механизму относится только разрыв `B − C`.** Без C положительный результат не значит
ничего: сжатие само по себе двигает U-кривую. `B − D` отвечает, нужна ли именно
негэнтропия, а не обычный ретривер.

## 2.2 Развёртка по бюджету — это и есть «размер кэша»

Бюджет отбора — прямой аналог размера кэша из частей A предыдущих заданий. Разворачивать:

```
Bud ∈ { H/6, H/3, H/2 }      для условий B и C
D — только при Bud = H/3     (иначе не влезаем по времени)
```

Даёт кривую «точность от бюджета» по каждому условию — то же, чем была `q(M)` для весов.

## 2.3 Размер прогона и как он считается

```
токенов на (иголка × позиция) = H  +  2·(H/6 + H/3 + H/2)  +  H/3
                              = H  +  2H       +  H/3   =  3.33·H

бюджет 5 ч при 155 ток/с = 2.79 млн токенов префилла
число испытаний = 2.79e6 / (3.33·H) / 5 позиций
```

При `H = 4000`: **≈ 42 иголки** × 5 позиций. Существенно больше, чем 25 в отчёте 2.
При `H = 6000`: ≈ 28 иголок. При `H = 2000`: ≈ 84.

Позиций **пять**, не семь: `{5, 30, 50, 70, 95 %}`. U-кривая по пяти точкам читается, а
освободившееся время лучше потратить на иголки и на развёртку по бюджету.

## 2.4 Многошаговый поднабор — «качество», а не только «поиск»

10 из иголок сделать **двойными**: два факта в разных местах стога, вопрос требует обоих.

```
позиции пары: {20 % и 80 %}, {40 % и 60 %}, {5 % и 95 %}
ответ засчитывается только при обоих фактах
```

Это проверяет то, ради чего затевалась «организационная» часть: удерживает ли отбор
**оба** нужных блока, а не один. Одноходовый поиск этого не показывает.

## 2.5 Что записывать сверх точности

По каждому испытанию:

```
позиция иголки в ИСХОДНОМ стоге
позиция иголки в СОБРАННОМ контексте после отбора        ← сдвинулась ли она из «середины»
попал ли блок с иголкой в отбор вообще                    ← отделяет «не нашли» от «не поняли»
ранг блока с иголкой по J
J выбранных блоков: среднее, std
Φ выбранных блоков
число блоков, фактически вошедших
токенов в собранном контексте (проверка, что бюджет соблюдён)
```

**Разделение «не попал в отбор» и «попал, но модель не ответила» — обязательно.** Это два
разных отказа, и лечатся они противоположным.

## 2.6 Оценка ответа

Точное вхождение подстроки. Иголка формулируется так, чтобы ответ был однозначной строкой
(код, число, редкое имя собственное). **LLM-судью не использовать.**

## 2.7 Устойчивость прогона

С учётом того, что запуски пару раз падали:

```
1. смоук на 1/50 объёма, проходящий ВЕСЬ путь до записи результата  — перед основным
2. результаты писать инкрементально (jsonl, flush после каждого испытания)
3. возобновляемость: при перезапуске пропускать уже записанные (needle_id, pos, cond, bud)
4. перед стартом печатать: свободная VRAM, свободная RAM, оценка времени, число испытаний
5. на исключении в одном испытании — записать его как failed и продолжить, не падать
```

# ЭТАП 3. Добор по весам. CPU, фоном

Всё считается по уже собранным данным либо из одних весов. Инференса не требует, GPU не
занимает.

## 3.1 Качество ранг-1 зонда — последнее недостающее число по весам

```
для каждого кластера C:  W_C ∈ R^{|C|×d_model}
Q(C) = σ₁² / Σᵢσᵢ²                    доля энергии в первом сингулярном числе
Q(k) = среднее и разброс по кластерам, при k ∈ {2,4,8,16,32}
```

Считается **из одних весов**, минуты. Смысл: зонд `ĝ_C = σ₁·|⟨v₁,x⟩|` заменяет `|C|`
скалярных произведений одним. Его точность и есть `Q`.

| `Q(4)` | Вывод |
|---|---|
| ≥ 0.70 | зонд работает, внутриэкспертная маскировка имеет смысл |
| ≈ 0.25 (= 1/\|C\|) | зонд слеп — блок неотличим от случайного, слой не строить |

Контроль: посчитать `Q` для **случайных** кластеров того же размера. Должно выйти ≈ `1/|C|`.

## 3.2 Длины серий и трафик

```
после перестановки каналов по кластерам:
    средняя и медианная длина серии подряд идущих АКТИВНЫХ кластеров, при k ∈ {4,8,16}
    сравнить с оценкой 1/(1−a_clust)
    эффективный размер транзакции = серия × размер кластера
waste(k) = a_clust(k) / p             и трафик на токен относительно k=48
```

Проверяет мой довод, что транзакции не являются ограничением и что мелкая нарезка выигрывает.

## 3.3 Незавершённое из отчёта 2


# Отчётность

Как в предыдущих двух отчётах — образец правильный, менять не нужно. Обязательно:

- что реально прогнано, с числами токенов и временем;
- где отступили от задания и почему;
- что вызывает сомнение в корректности;
- **отдельно: всё, что не запустилось с первого раза, и что оказалось причиной** — этого
  в прошлых отчётах не было, а запуски падали.

Если этап 0 закрыл этап 2 — так и написать, отчёт на одну страницу, и это будет **самый
полезный из трёх отчётов**: он сэкономит месяцы разработки контурного слоя.

Неполный честный отчёт полезнее полного, где часть чисел получена не тем способом, что
заявлено.
