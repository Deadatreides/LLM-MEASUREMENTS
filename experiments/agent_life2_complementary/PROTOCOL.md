# PROTOCOL.md — agent_life2_complementary

Написан и зафиксирован **2026-08-21, до вычисления любых чисел** (до
24 прогонов). Не переписывается задним числом — правило проекта: если
механическая корзина `COMP_*` даст на вид странный результат, он
публикуется КАК ВЫЧИСЛЕН, интерпретация добавляется рядом, явно.

## §0. Рамка

Цель — НЕ идеальная комбинация 6 моделей на HETEROSTEP. Цель — проверить
ОДИН механический рычаг, найденный `agent_life1_mechanism/reports/
REPORT_LIFE1.md`: оператор горизонтального переноса, выбирающий донора по
комплементарности покрытия слота (а не по structural/semantic similarity),
на СТАРТЕ, лишённом готовой multi-slot сборки. Опора на LIFE-1 (не
переоткрывается): similarity-SWAP_SLOT дал `slot_match≈4%`,
`loss:gain≈13.5:1`, `overlap=1.0` (материал рядом уже есть — узкое место
семантика донора, не нехватка блоков).

Изоляция: пишет только в `agent_life2_complementary/`. `arch2/` — импортом
без правок. `agent_a5_live_m/`, `agent_life1_mechanism/` — чтением и
копированием кода (не импортом), без правок. Без pip/venv. Живая сетка A5
— только чтение, новых `generate()` в этом пакете нет.

## §1. Научный вопрос и корзины

Если (1) донор slot-HGT выбирается ТОЛЬКО по комплементарности покрытия
блока, и (2) старт беден (нет готовых multi-slot заготовок в
не-эталонной популяции) — растёт ли сборка совместного покрытия
относительно режима LIFE-1 (similarity-HGT + богатый посев), и при каком
`p_slot_hgt` это устойчивее?

**Корзины** (ровно одна):

- **COMP_WORKS** — на ≥2 из 3 уровней `p`:
  - `slot_match` ≈ 1.0 (корректность реализации оператора, не находка —
    см. §2.6/Verification: если оператор перенёс слот, `Imp(donor,s)=1 ∧
    Imp(recipient,s)=0` гарантированы КОНСТРУКЦИЕЙ, так что успешный
    перенос обязан давать `slot_match=1.0`; отклонение — баг, не
    результат) **И**
  - overall `loss:gain` (по ВСЕМ операторам рождения, не только
    `TRANSFER_SLOT`) ≤ 4 **И**
  - `N_AB_first_assembly` (§2.1) И `elite_AB_share` РАСТУТ относительно
    lean-внутреннего базового уровня `p=0.10` (тот же набор 8 seed,
    парное сравнение, не число из LIFE-1 — там был богатый посев, другая
    задача)
  — **И** на выбранном `p*` знак роста `N_AB_first_assembly` (относительно
  `p=0.10`) держится на ≥6 из 8 seed.

  **Поправка пользователя от 2026-08-21, зафиксирована здесь явно**:
  первоначальный порог «mean N_AB_evolved per seed > 28.2» ОТМЕНЁН —
  28.2 это `pool(N_AB_evolved LIFE-1)/5`, число из ДРУГОГО режима (богатый
  посев, similarity-донор), некорректно как планка для lean-старта. Замена
  — внутреннее сравнение с `p=0.10` этого же пакета, см. выше.

- **COMP_PARTIAL** — `slot_match≥0.50` на ≥1 уровне `p` (т.е. хотя бы
  где-то перенос вообще случается), но рост `N_AB_first_assembly`/
  `elite_AB_share`/устойчивость по seed не дотягивают до COMP_WORKS.

- **COMP_FAIL** — иначе (при УСПЕШНОМ прогоне всех 24 клеток).

- **COMP_BLOCKED** — сетка/lean-assert/воспроизведение сломаны — только
  `BLOCKERS.md`, без корзины.

`p*` (порядок не меняется от поправки пользователя): `argmax
mean(N_A + N_AB_evolved)` среди уровней `p`, прошедших `slot_match≥0.50`
и `loss:gain≤4`; если таких нет — `argmax mean(N_AB_evolved)`;
тай-брейк → меньший `p`.

## §2. Определения (как LIFE-1, не двигать)

```
signature_s(g) = (op слота ∈ {SEQ,PAR}, sorted(model_ids CALL внутри слота))
covered(s,g)   = union по атомам слота s множества task_id панели, где атом PASS
best_single(s) = max по одиночным атомам |covered(s,·)| на панели
Imp(s,g) = 1 ⟺ |covered(s,g)| > best_single(s), иначе 0
ImpSet(g) = {s : Imp(s,g)=1}
```

A-событие: рождение `gen≥1`, `ImpSet(child) ⊃ ImpSet(parent)` и
`|ImpSet(child)| = |ImpSet(parent)|+1`. AB-генотип: `|ImpSet(g)|≥2` (НЕ
`r≥r(B3)`, НЕ имена моделей). Все счётчики механизма — ТОЛЬКО по `gen≥1`
(есть родитель); seed-происхождение/эталонный AB — отдельной строкой, не
в знаменателе (урок reference-leak, в 5-й раз).

### 2.1 Новая метрика (не в LIFE-1): `N_AB_first_assembly`

Рождение, где `|ImpSet(parent)| < 2` И `|ImpSet(child)| ≥ 2` — то есть
совместное покрытие ВОЗНИКЛО этим рождением, а не унаследовано от уже-AB
родителя. В LIFE-1 129 из 238 рождений с `Δ|ImpSet|=0` были «уже-AB
родитель передал AB-статус дальше» — без этой метрики `N_AB_evolved`
смешивает СБОРКУ с НАСЛЕДОВАНИЕМ в обоих пакетах. Не входит в
предрегистрированную формулу `p*` (та не менялась), но ЯВЛЯЕТСЯ частью
критерия COMP_WORKS (§1, по поправке пользователя).

### 2.2 Sanity (обязателен на каждой из 24 клеток)

`Imp(FORMAT)` (индекс слота 1) обязан быть 0 для ВСЕХ генотипов — на
панели один атом уже покрывает 80/80, `Imp=1` там арифметически
невозможен ни при каком подмножестве (проверено на всех 5 панелей LIFE-1).
Если хотя бы раз 1 → СТОП, баг в `Imp`, запись в `BLOCKERS.md`, дальше не
идти.

## §4. Бедный старт (`src/lean_seeds.py`)

**Важная находка разведки, меняющая исходный §2.5 задания**: `arch2.
mutate.random_genotype` НЕ МОЖЕТ производить валидные ASSEMBLE-генотипы на
реестре HETEROSTEP — его `leaf()` строит `library.attempt(...)`
(`max_tokens∈{150,320}`, швы `seam.multistep_arith`/`seam.enriched_code`),
что проваливает `is_valid` против `heterostep.Registry`
(`max_tokens` зафиксирован в 60, известен только `seam.heterostep`).
Проверено эмпирически на архиве LIFE-1: из 396 рождений всех 5 seed
только 14 были `"random"`, и НИ ОДНО не содержало ASSEMBLE — так
называемые `P_rand_assemble_*` LIFE-1 на самом деле `BUDGET(500,
STOP(...))`/голый `STOP` — не способны подтвердить ни одного слота.
Поэтому «бедный старт» строится ЯВНО из `heterostep_seeds._slot`/`.route`
(чистые конструкторы ASSEMBLE-дерева), не через `M.random_genotype`.

**Второе ограничение**: одноатомный слот (`SEQ(single model)`)
структурно НЕ МОЖЕТ иметь `Imp=1` (его покрытие ≤ `best_single` по
определению). Полностью depth-1 популяция даёт НОЛЬ валидных доноров
навсегда, и `transfer_slot` вырождается в постоянный откат на `mutate` —
эксперимент был бы бессодержателен. §2.5 задания разрешает `|ImpSet|≤1` и
требует только `assert`, что НЕ-эталонных генотипов с `|ImpSet|≥2` — 0.
Значит бедный старт ОБЯЗАН включать одноблочные генотипы (`Imp` ровно на
одном слоте), иначе научный вопрос не проверяется вовсе (LIFE-1 уже
доказал, что материал рядом есть — `overlap=1.0`; LIFE-2 проверяет, умеет
ли комплементарный канал его СОЕДИНЯТЬ, а не собирать с нуля).

**Состав `build_seeds_pop20_lean(ds, panel)`** — 20 РАЗЛИЧНЫХ
`complex_id` (не 23 имени с дедупом, как в LIFE-1 — `assert` на это ниже):

- 3 эталона (`REF_B1_route`/`REF_B2_greedy2`/`REF_B3_greedy_cover`,
  строятся детерминированным `b1_route`/`b2_route`/`b3_route` — копия
  логики `deterministic_route.py` без хэш-зависимого тай-брейка) — в
  `ev.references`, НЕ в размножающуюся популяцию (`Evolution.seed()`
  гарантирует строгое разделение по `reference_names`).
- 1 «нулевой» — чистый `b1`-маршрут (по одной лучшей одиночной модели на
  слот) — `|ImpSet|=0`.
- 13 одноблочных (панель-устойчивых, из разведки): 5 READ-Imp пар
  (`GEM+INT`, `INT+LLA`, `INT+QW3`, `INT+QWC`, `QWC+QW3`), 2 LOOKUP-Imp
  пары (`GEM+QW3`, `QW3+SML`), 6 COMPUTE-Imp пар (`GEM+INT`, `GEM+QWC`,
  `INT+QWC`, `LLA+QWC`, `QWC+QW3`, `QWC+SML`) — каждая как `b1` с ОДНИМ
  слотом заменённым на `PAR(модель1,модель2)`, остальные 3 слота — `b1`
  (одноатомные, `Imp=0`).
- 6 заполнителей без блоков — `P_single_model_x4`/`_alt` (крайние модели
  из `ds.models` на все 4 слота), `P_second_best_route` (второй элемент
  жадного порядка на каждый слот) — все `|ImpSet|=0` по построению (одна
  модель на слот).

Итого 3+1+13+6=23 имени; при коллизии `complex_id` (маловероятно, но
возможно) — добор до 20 НЕ-эталонных через дополнительные комбинации
одноблочных пар до достижения ровно 20 различных.

**Обязательные assert'ы до generation 0** (провал → `BLOCKERS.md`, evolve
не запускается):
1. `len({g["complex_id"] for g in pop.values()}) == 20` (20 различных id).
2. `all(len(imp_set(g)) <= 1 for name, g in pop.items() if name not in
   REFERENCE_NAMES)` — ноль не-эталонных с `|ImpSet|≥2`.

## §5. `transfer_slot` (`src/slot_hgt.py`) — единственный механический рычаг

```
transfer_slot(parent, rng, ctx, registry, gen) -> (child|None, report)
  donors = ctx["donors"]                      # archive ∪ alive, эталоны уже исключены
  valid(s) = [d for d in donors if Imp(s,d)=1 and Imp(s,parent)=0]
  slots = [s for s in 0..3 if valid(s)]
  если slots пуст -> M.mutate(...)            # откат, НЕ similarity-HGT
  s = rng.choice(slots)                        # равномерно по слотам (без SLOT_WEIGHTS)
  donor = rng.choice(valid(s))                 # равномерно; donor_score_fn НЕ в ctx нигде
  child = parent с children[s] := deepcopy(donor.root.children[s])
  до MAX_RETRIES при невалидности/дубликате, затем откат на M.mutate
  report = {"operator": "TRANSFER_SLOT", "donor_id":..., "slot": s, "complementary": True}
```

`ctx["donor_score_fn"]` не кладётся НИКУДА в этом пакете (оба потребителя
— `arch2.mutate.m5_horizontal_transfer` и любой скопированный
`swap_assemble_slot` — читают его через `.get(...)` и откатываются на
равномерный выбор при отсутствии ключа — проверено чтением кода). Донор
эталонов исключён тем же способом, что LIFE-1 (`ev.archive` минус
`ev.references`).

`births.jsonl` пишет КАЖДУЮ попытку (не только принятую): `gen, child_id|
null, parent_id, donor_id|null, slot|null, complementary: bool|null,
operator, delta_impset, admitted: bool`.

## §6. Факторы и константы

`p_slot_hgt ∈ {0.10, 0.20, 0.35}` × seeds `20261401..20261408` = 24
прогона. `start_pop=20` (§4), `max_gen=24`, `G_STALL=12`, `budget_per_task
=3000`, панель — единая (§3), screen — оставшиеся 20 train id той же
единой панели. Не сканируются: pop, gen, G_STALL, размер панели, алфавит,
D1/D2/D3.

**Ожидаемо и НЕ провал**: по опыту LIFE-1 (идентичный полигон, тот же
gate-механизм D1/D2/стагнация), все 24 клетки вероятно закончатся
`extinct=True` около поколения 12, и `any_complex_beats_gate` может быть
`False` во всех поколениях — это про ПЛАНКУ (сильнейший эталон), которую
LIFE-2 не трогает; интересующие метрики — `N_AB_first_assembly`,
`loss:gain`, `elite_AB_share`, они считаются независимо от того, бьёт ли
кто-то планку.
