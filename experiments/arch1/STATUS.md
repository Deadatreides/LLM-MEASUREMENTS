## Решения, принятые по ходу (важно для следующих сессий)
- Структура src/ строго повторяет уровни из API_BOUNDARIES.md §1 (storage,
  graph_core, state_engine, evidence_engine, seam_engine + src/seams/,
  model_adapter, policy, repair_planner, action_executor, budget_manager,
  orchestrator) — модуль-файл на модуль-интерфейс.
- **GraphCore не хранит state/verification_status/confidence/evidence
  claim'а как мутируемые поля.** Это осознанно оставлено STATE ENGINE и
  EVIDENCE ENGINE (этап 2) — GraphCore реализует ровно интерфейс
  API_BOUNDARIES §2, где этих методов нет. Важно для этапа 2: state
  живёт как отдельные append-only записи, привязанные к subject_id, а
  не как правка объекта Claim.
- **`superseded_by` не хранится как поле** — вычисляется по `supersedes`
  следующей версии. `parents`/`children`/`claims` — тоже не хранимые
  списки, а обход по DEPENDENCY-рёбрам. Это сохраняет Storage строго
  append-only без единого исключения (даже «установить один раз»).
- **Детекция цикла (DEPENDENCY_MODEL §5.2) реализована через явное
  условие достижимости** (`source ∈ downstream_closure(target)` в
  графе ДО добавления ребра), а не дословно по неоднозначной
  формулировке псевдокода спеки («v уже достижим из u»). Проверено
  тестами на конкретных графах, а не сверкой с текстом.
- **`add_dependency` и `collapse_scc` — два независимых метода.**
  `add_dependency` при цикле ВСЕГДА отклоняет ребро (граф не меняется)
  и пишет CYCLE_OBSERVATION; для status=HYPOTHESIS дополнительно
  сохраняет ребро как REFUTED_BY_ACYCLICITY (§5.2.a). Для
  status=CONFIRMED (§5.2.b) схлопывание SCC **не автоматическое** —
  вызывающий код должен сам вызвать `collapse_scc(claim_set)` отдельно
  после получения CYCLE_DETECTED. **Важно для этапа 4 (REPAIR PLANNER):
  именно он — тот вызывающий код, который должен реагировать на
  CYCLE_DETECTED+CONFIRMED вызовом collapse_scc.**
- Схлопнутые в SCC claim'ы не удаляются: `get_claim(member_id)`
  по-прежнему возвращает оригинал. Обход (`direct_children` и т.п.)
  прозрачно резолвит поглощённые id в id композита через внутренний
  `collapsed_of` — так «внешние рёбра переносятся на composite» без
  физической правки хранимых рёбер.
- `graph_version` = счётчик записей в Storage (seq). `graph_snapshot`
  реализован как честный replay append-log'а в свежий GraphCore —
  дёшево получить и заодно подтверждает восстановимость графа по
  версии (аудит J), хотя отдельным тестом это в этапе 1 не покрыто
  (не входит в обязательный минимум WORK_PLAN.md).

### Этап 2
- **Тип Evidence живёт в state_engine.py, не в evidence_engine.py.**
  Единственный способ не нарушить направление зависимостей
  (EVIDENCE ENGINE — уровень 3, STATE ENGINE — уровень 2; уровень 2 не
  может импортировать из уровня 3). STATE ENGINE определяет форму
  evidence, которую готов принимать (strength уже посчитана — «не
  знает, откуда взялось evidence»); EVIDENCE ENGINE импортирует этот
  тип и константы (assertion/strength/LLM-типы) снизу вверх — разрешено.
- **apply_evidence реализует только EVIDENCE_ADDED-строки таблицы
  STATE_MACHINE §2.** Переходы PROPOSED<->GENERATED и REPAIRING
  (триггеры ACTION_STARTED/ACTION_COMPLETED) не реализованы — в
  API_BOUNDARIES §3 для них нет отдельного метода, это территория
  ACTION EXECUTOR (этап 5). Субъект без истории состояний по умолчанию
  считается GENERATED — точка входа для evidence-driven переходов.
  **Важно для этапа 5**: ACTION EXECUTOR либо получит свой метод в
  STATE ENGINE, либо будет управлять этими состояниями отдельно.
- **«STALE watermark».** «Повторная проверка относительно нового
  upstream» (STATE_MACHINE §4.2) реализована так: при переходе
  CORRECT→STALE запоминается длина накопленной evidence-истории
  claim'а; дальнейшая классификация (`apply_evidence`) при вычислении
  цели смотрит только на evidence, добавленное ПОСЛЕ этой отметки.
  Старое evidence не теряется (остаётся в storage, append-only), но
  не учитывается заново — иначе STALE→CORRECT срабатывал бы просто от
  повторного вызова без реальной новой проверки. Вне STALE
  используется вся история целиком.
- **CONFLICTED→CORRECT/INCORRECT «по иерархии силы» не реализован.**
  EVIDENCE_MODEL/STATE_MACHINE не определяют порядок внутри HARD,
  нужный для разрешения конфликта двух HARD-evidence. Текущее
  поведение: CONFLICTED «липкий» — раз оба (HARD SUPPORTS и HARD
  REFUTES) когда-либо появились, дальше он таким и остаётся, что
  само по себе и есть требуемая защита от автоматического INCORRECT.
  **Открытый вопрос для будущих этапов**, если понадобится реальное
  разрешение конфликтов.
- **REJECTED возвращается только в одном явном случае** — попытка
  получить CORRECT, где единственная HARD-поддержка имеет тип
  MODEL_JUDGEMENT/SELF_JUDGEMENT (INV-S5). Остальные три
  запрещённых перехода из §2.1 (UNKNOWN→INCORRECT без REFUTES,
  STALE→INCORRECT без новой проверки, CONFLICTED→INCORRECT
  автоматически) в этом API структурно недостижимы (apply_evidence
  не принимает целевое состояние — только evidence), поэтому
  проверяются как assert внутри `_classify`/`apply_evidence`, а не
  как отдельный наблюдаемый REJECTED-исход; тесты проверяют итоговое
  состояние напрямую.
- EvidenceEngine.resolve() и StateEngine.apply_evidence содержат почти
  одинаковую логику классификации (hard_refute/hard_support) —
  сознательное дублирование, а не забытый рефакторинг: EVIDENCE ENGINE
  (уровень 3) не может вызывать StateEngine (уровень 2 не может
  зависеть от 3, и обратный вызов вверх тоже запрещён направлением
  зависимостей), поэтому каждый слой держит свою копию нужной ему
  части логики классификации.

### Этап 3
- **SEAM ENGINE зависит буквально только от Storage**, как и написано
  в API_BOUNDARIES §12. `applicable_seams(subject_id, graph_view)`
  принимает `graph_view` как duck-typed параметр (вызывает только
  `.get_claim(...)`) — никакого `import graph_core` в seam_engine.py
  нет, в отличие от state_engine.py на этапе 2, где зависимость от
  graph_core прямо задекларирована спекой. Здесь она не задекларирована
  — значит её и не вводим.
- **SOFT-швы (LLM-проверяющий) не реализованы вовсе** — прямое
  следствие WORK_PLAN.md §8 («что в ARCH-1 сознательно не входит»), не
  импровизация. `seam_class()` для всех зарегистрированных швов сейчас
  всегда `HARD`. MODEL ADAPTER (этап 5) здесь не используется.
- **exec_seam/format_seam не импортируют experiment8 через путь к
  соседнему каталогу** — логика (run_tests.py: compile+exec+прогон
  test_*; ast_checks.py: extract_code/inspect_function_source)
  скопирована и адаптирована внутрь arch1/src/seams/. exec_seam работает
  в процессе, без subprocess-изоляции run_tests.py — изоляция нужна при
  реальном исполнении недоверенного вывода модели, это забота ACTION
  EXECUTOR (этап 5), не контрольных случаев этого этапа.
  **Важно для этапа 5**: если ACTION EXECUTOR будет прогонять реально
  сгенерированный моделью код (а не контрольные случаи), рассмотреть
  возврат к subprocess-изоляции по образцу run_tests.py.
- **Цикл импорта seam_engine.py ↔ seams/\*.py разрешён отложенным
  импортом**: типы (`SeamDefinition`, `ControlCase`, статус-константы)
  в seam_engine.py; `seams/*.py` импортируют их оттуда; фабрика
  `default_seam_engine()` импортирует `seams.*` внутри функции, не на
  уровне модуля.
- **`is_trusted` по умолчанию `False`** для только что
  зарегистрированного шва (непроверенный ≠ доверенный). `evaluate()`
  всегда возвращает актуальный `is_trusted()` в `SeamResult.trusted`,
  даже когда сырой результат — `PASS`: проверено тестом на
  специально «сломанном» шве (заявляет PASS, но контрольный случай
  ожидает FAIL — self_test ловит несоответствие, is_trusted остаётся
  False, evaluate().trusted тоже False). Это и есть механическая
  реализация «недоверенный шов не может дать HARD-evidence» — не
  только текст в докстринге.
- **ERROR гарантированно не становится FAIL**: любое исключение внутри
  `check()` ловится централизованно в `SeamEngine.evaluate()`
  (и в `self_test()` отдельно, как несовпадение с ожидаемым статусом).
  Проверено на синтетическом шве, чей check() безусловно бросает
  исключение.

### Этап 4 (единственный этап с включением Opus 5, только план — код писал Sonnet)
- **Р1 (утверждено пользователем): `narrow()` — АБСОЛЮТНАЯ проверка.**
  REPAIR_MODEL §3 говорит «проверить c относительно НОВОГО состояния
  предков», но narrow() работает ДО фактического ремонта — предки ещё
  не перегенерированы. Шов проверяет c против собственного механического
  oracle, независимо от предка; PASS ⇒ unaffected ⇒ MAY_REUSE. «Новое
  состояние предков» реализовано топологическим порядком обхода, не
  относительной сверкой. **Важно для этапа 6**: когда появится реальный
  ACTION EXECUTOR, `post_repair_check` (ниже) — то место, где сверка
  РЕАЛЬНО становится относительной (против нового значения upstream,
  не против oracle).
- **Р2: тип `Cost` — в `storage.py`**, а не в `budget_manager.py`.
  `RepairPlanner` принимает `cost_estimator` как callable сверху
  (инверсия зависимостей, API_BOUNDARIES §1) — иначе уровень 5 тянул бы
  соседа по своему же уровню, что запрещено. `budget_manager.py`
  остаётся заглушкой. **Важно для этапа 5**: реальные стоимости должны
  прийти из MODEL_PROFILE/ACTION EXECUTOR, а не из плейсхолдера

### Этап 8 — ГЛАВНАЯ НАХОДКА: дефект в собственном измерении

- **Кампания 1 (этап 7) недостоверна для проверки A-1.** Пересчёт по
  сохранённому сырью показал: **59.6% первичных FAIL были ложными**

  входов ДЛЯ шва. Извлечение жило в `orchestrator.py`/`metrics/runner.py`

  о контрольных случаях для шва, но не требует их для конвейера,
  подающего швy входы — это дыра в самой спеке, не только в
  реализации.**

  воспроизводит ровно сломавший нас вход. Существующие контрольные

### Этап 8 — ВТОРАЯ НАХОДКА: шаг 1 сужения молча отключает сам механизм

Важнее первой, потому что это дефект **спецификации**, а не реализации.

- **Что обнаружено.** REPAIR_MODEL §3, шаг 1: «если есть ребро
  DATA/COMPUTATIONAL от подтверждённо-затронутого предка И значение
  предка буквально присутствует в c → c сразу в `verified`, проверку не
  запускать». Реализовано дословно по спеке. На **реальном** содержимом
  кампании 1 (origin=C4, кандидат C6, n=119) этот шаг срабатывает в
  **72.3% случаев** — то есть C6 объявляется «затронутым» и подлежащим
  регенерации, НИ РАЗУ не будучи проверенным.
- **Почему это ломает именно A-1.** `unaffected` (и значит `MAY_REUSE`,
  и значит экономия ремонта) достижим ТОЛЬКО через шаг 2 — прогон шва.
  Если шаг 1 перехватывает узел раньше, шаг сужения превращается в
  no-op: множество `unaffected` не может наполниться в принципе. Это
  объясняет околонулевой `stale_resolved_by_verify_ratio` (0.0165)
  ЛУЧШЕ, чем гипотеза «модели слабые».
- **Проверено обеими сторонами (первая гипотеза не подтвердилась —
  фиксирую честно).** На ЧИСТОМ инъекционном стенде шаг 1 НЕ
  срабатывает, и `narrow()` корректно относит C6 в `unaffected` —
  механизм A-1 демонстрируемо работает. Сначала я объяснил разницу
  «нарушением границы claim'а», но **это объяснение оказалось неверным**:
  после исправления промптов (кампания 2) частота срабатывания не
  упала, а слегка выросла (72.4% → 78.9%).
- **Настоящая причина глубже и относится к самой спеке.** По ребру
  `COMPUTATIONAL` потомок ЗАКОННО содержит значение предка — в этом и
  состоит смысл такого ребра (C6 = C4 + C5, значит значение C4 обязано
  быть в C6). Значит для арифметической цепочки условие шага 1
  выполняется ВСЕГДА, и merge-узел не может попасть в `unaffected`
  никогда — независимо от качества модели.
- **Самое существенное: шаг 1 нарушает центральный запрет самой
  архитектуры.** ARCHITECTURE.md §1: «STRUCTURAL DEPENDENCY ≠ VALIDITY
  STATE». Шаг 1 делает вывод о ВАЛИДНОСТИ («c затронут, регенерировать»)
  из СТРУКТУРНОГО факта («значение предка присутствует в c»). Он не
  различает «потомок унаследовал ОШИБОЧНОЕ значение предка» и «потомок
  содержит ВЕРНОЕ значение предка» — проверяется только присутствие.
  На инъекционном стенде испорченное значение (`57.8`) у потомка
  отсутствует → шаг 1 молчит → проверка отрабатывает; в реальности
  предок помечен origin, но его значение (`40`) верно и присутствует у
  потомка → шаг 1 срабатывает → потомок осуждён без проверки.
- **Обе находки этапа 8 — об одном и том же классе ошибки**: участок,
  который выносит суждение, не будучи проверкой. В первом случае это
  извлечение вне границы шва, во втором — структурная эвристика вместо
  evidence. Оба обходят механизм, который архитектура объявляет
  единственным законным источником суждения о валидности.
- **Направление ошибки безопасное, но цена — вся ценность.** Шаг 1
  ошибается в сторону избыточного ремонта (никогда не пропускает
  реально затронутое), поэтому корректность системы не страдает. Но
  избыточный ремонт — это ровно то, что архитектура обещала устранить;
  безопасный отказ здесь означает потерю смысла, а не мягкую деградацию.
- **Вывод для ARCH-2 (не исправлялось на этапе 8 — это изменение
  СПЕКИ, а не баг реализации; менять спеку по ходу измерения — та же
  подстройка под результат).** Возможные направления: (а) сравнивать не
  «присутствует ли значение предка», а «присутствует ли ПРЕЖНЕЕ,
  ныне опровергнутое значение предка» — то есть смотреть на diff версий
  предка, а не на его текущее содержимое; (б) допускать шаг 1 только
  когда у предка есть HARD-evidence(REFUTES) именно на то значение,
  которое присутствует у потомка; (в) отказаться от шага 1 и всегда
  проверять (дороже, но не нарушает §1). Вариант (а) выглядит наиболее
  соответствующим духу спеки, но данных для выбора нет.
- **Важно не переоценить находку.** Шаг 1 ошибается в безопасную
  сторону (избыточный ремонт, никогда не пропуск), поэтому
  КОРРЕКТНОСТЬ системы не нарушена ни в одном прогоне. Нарушена только
  экономия — но именно она и есть заявленная ценность архитектуры.

## Обновление после Эксперимента 12: контекст против оператора

**Эксперимент 12** (`trace-probe/experiment12/`, `REPORT_EXPERIMENT12.md`):
разрешает расхождение 10 vs 11 впрямую — сетка «структурный контекст
(K0 evidence-only / K1 структура без значений / K2 структура + подтверждённые
значения) x оператор (та же/другая модель)», 318 состояний коллизии
(178 арифметика, 140 код), 7 плеч, тот же переиспользованный стенд.

Результат разрешает расхождение в пользу «не структура, не оператор»:

- Смена модели БЕЗ контекста (K0O1 vs K0O0) значимо ХУЖЕ повтора той же
  моделью (p=0.0042) — не нейтральна, а отрицательна.
- Структурный контекст (K1O0/K2O0 vs K0O0) не даёт значимого выигрыша
  (p=0.108, p=0.060) и значимо ДОРОЖЕ контроля по токенам.
- Там, где промежуточные значения были подтверждены на первичной
  генерации (целевой случай гипотезы Эксперимента 11, §19) — эффект
  ровно нулевой: 0 из 34 состояний решены и в K2O0, и в K0O0.
- Структурный контекст в принципе применим редко: только 18.9% состояний
  коллизии вообще имеют хоть один подтверждённый шаг/requirement.
- Ни одно из 7 плеч не дешевле слепого 1-к-1 повтора без контекста
  (552.7 ток/успех).
- Единственный устойчивый положительный результат за три эксперимента —
  переформулировка промпта на syntactic-коллизиях (H-син, предзарегистрирована,
  93.0% против 73.9%, n=115, p=5.9e-5) — не архитектурный механизм.

## Обновление после Эксперимента 12 v2: строгий протокол, тот же вывод резче

**Эксперимент 12 v2** (`trace-probe/experiment12/REPORT_EXPERIMENT12_V2.md`,
`experiment_id=exp12-v2`) — независимая повторная кампания на ТОМ ЖЕ
датасете из 318 состояний (фаза 0 переиспользована буквально, протокол
не менялся), но с существенно более строгим протоколом измерения:
пятисоставный статус PASS/SAME_FAILURE/DIFFERENT_FAILURE/INAPPLICABLE/
UNVERIFIED (не просто PASS/FAIL), учёт регрессий и улучшений на уровне
ОТДЕЛЬНЫХ шагов/requirements, механическая dependency-vs-value-calculation
классификация арифметических ошибок (пересчёт формулы на СОБСТВЕННЫХ
значениях модели, не оракульных), явный проверяемый context manifest,
ΔK1/ΔK2(инкрементально к K1, не к K0)/Δhetero(K) для каждого уровня/
interaction effect I — все с парными bootstrap CI.

Ключевые числа v2 (согласуются с v1, но точнее и резче):
- ΔK1 (K1O0 vs K0O0) = +3.5 п.п., CI [−0.3, +7.5], не значимо.
- **ΔK2 инкрементально к K1** (K2O0 vs K1O0) = **+0.6 п.п., p=0.845** —
  подтверждённые значения САМИ ПО СЕБЕ, поверх одной только структуры,
  не добавляют практически ничего измеримого.
- Δhetero(K0) = **−8.8 п.п., значимо (p=0.0042)** — смена модели без
  контекста значимо вредит. Δhetero(K1)=Δhetero(K2)≈**−2.5 п.п., не
  значимо** — при богатом контексте смена модели перестаёт значимо
  вредить, но **не становится полезной** ни на одном уровне.
- Interaction effect I(K1)=I(K2)≈**+6.3 п.п., CI касается нуля** —
  контекст ослабляет вред от смены модели, не разворачивает его в
  выгоду. Явно проверенный и НЕ подтверждённый сильный критерий из
  задания: «CHANGE_MODEL улучшает результат только при K2» — было бы
  сильным свидетельством в пользу гипотезы Mycelium, но
  Delta_hetero(K2) отрицательна, не положительна.
- same_failure среди FAIL падает с 90.3% (K0O0) до 76.8% (K2O1), но PASS
  растёт лишь на 1.5 п.п. — диверсификация ошибки явно отделена от
  успеха, не путается с ним (задание v2, «критическое правило
  интерпретации»).
- Единственный протестированный класс задач, где CHANGE_MODEL при
  богатом контексте численно опережает SAME_MODEL — арифметические
  "value"-ошибки (n=30, на грани порога, не сильный вывод).
- Механическая dependency-vs-value классификация применима лишь к 28.7%
  арифметических коллизий этого датасета — честно отражённое
  ограничение метода.

**Итоговый вывод по всей программе экспериментов 10-12 (v1+v2)**: переход
к A-2 не рекомендуется. Мотивация для A-2 (граф зависимостей даёт
полезный repair-контекст) не подтверждена ни одной из двух независимых
измерительных кампаний Эксперимента 12. Дальнейшая работа — в сторону
промпт-инжиниринга конкретных типов коллизий (единственный устойчивый
положительный результат всей программы: переформулировка промпта на
syntax-коллизиях, 93.0% vs 73.9%, n=115, p=5.9e-5), не в сторону
графовых/архитектурных механизмов.
