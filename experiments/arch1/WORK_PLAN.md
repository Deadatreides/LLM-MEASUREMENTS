# WORK_PLAN.md — план реализации ARCH-1

**Что делаем:** вертикальный срез архитектуры на одном классе задач с механическим oracle. Не полная система — только то, что нужно, чтобы **измерить два непроверенных допущения** (ARCHITECTURE_AUDIT.md, Часть 4).

**Приоритеты (по заданию):** 1) сделать правильно → 2) уложиться в подписку $20 → 3) время.

---

## 0. Ключевые факты, определяющие весь план

### 0.1 Локальные прогоны бесплатны в токенах Claude

Генерация на GGUF-моделях идёт на вашей GTX 1660 SUPER. Это **ноль токенов Claude**. Токены тратятся только на: написание кода, отладку, анализ результатов.

**Следствие:** этап измерения (самый долгий по времени) почти ничего не стоит по подписке. Планировать нужно вокруг **кода**, а не вокруг вычислений.

### 0.2 Спецификация не влезает в контекст целиком

```
arch0/ = 392 КБ ≈ 120–140 тыс. токенов
контекстное окно = 200 тыс. токенов
```

Прочитать весь `arch0/` в одной сессии — значит съесть 60–70% окна до начала работы. **Категорически нельзя.** В каждом этапе ниже указан точный список файлов для чтения (обычно 2–4 документа, 15–40 КБ).

### 0.3 Существующий стенд переиспользуется

```
experiment9/configs/llm_client.py    98 строк   → MODEL ADAPTER почти готов
experiment9/configs/env_fix.py       42 строки  → CUDA-фикс, работает
experiment9/configs/chat_render.py   76 строк   → рендер промптов
experiment8/configs/run_tests.py                → HARD-шов исполнения
experiment8/configs/ast_checks.py               → HARD-шов структуры
```

Это экономит примерно полтора этапа. Ничего из этого переписывать не нужно.

### 0.4 Про лимиты подписки — честно

Точные квоты Claude Pro меняются и я не могу назвать их с уверенностью. Что известно устойчиво:
- 5-часовые скользящие окна;
- недельные лимиты (введены в 2025), для Pro они и есть главное ограничение при длительной работе;
- **Opus расходует бюджет кратно быстрее Sonnet** — на Pro это решающий фактор;
- Claude Code расходует больше обычного чата, потому что каждый ход пересылает контекст.

**План построен так, чтобы быть устойчивым к неопределённости лимитов:** каждый этап автономен, заканчивается рабочим состоянием на диске, и упор при исчерпании лимита не теряет прогресс. Если лимит поймали посреди этапа — см. §5.

## 1. Выбор модели и режима

### 1.1 Общее правило

**Sonnet 5 — по умолчанию на всех этапах.** Она полностью справляется с реализацией по готовой спецификации: спецификация уже написана, творческих решений почти не осталось, задача — аккуратный перевод спеки в код.

**Opus 5 — только там, где цена ошибки высока, а спека допускает толкование.** На $20-подписке это максимум 2 коротких включения за весь проект (этапы 4 и 8, только в режиме планирования, не для набора кода).

**Haiku 4.5 — для механических операций:** обновление `STATUS.md`, переименования, тривиальный boilerplate. Даёт заметную экономию на рутине.

### 1.2 Режимы Claude Code

| Режим | Когда | Зачем |
|---|---|---|
| **Plan mode** (Shift+Tab дважды) | перед каждым этапом ≥2 | получить план без исполнения, проверить его, потом выполнить. Дешевле, чем переделывать неверно написанное |
| **Обычный** (подтверждение правок) | этапы 1–3, 5 | код детерминированный, ошибки видны сразу |
| **Extended thinking** («think harder») | этап 4, точечно | самая тонкая логика (сужение области ремонта) |
| **Auto-accept** | этап 7 | прогоны, где правок почти нет |

### 1.3 Чего НЕ делать

- Не просить Claude «переосмыслить архитектуру» — она зафиксирована в `arch0/`. Любое переобсуждение спеки = потраченный бюджет впустую.
- Не использовать `/compact` — он стоит токенов и теряет детали. Использовать `/clear` между этапами (бесплатно) + `STATUS.md` для переноса.
- Не держать одну сессию на два этапа — контекст забьётся и качество упадёт.

## 2. Протокол переноса контекста между сессиями

Это самая важная механическая часть плана. Перенос — **через диск, а не через чат**. Это буквально тот же принцип, что в самой архитектуре (append-only, provenance).

### 2.1 Два постоянных файла

**`arch1/CLAUDE.md`** — создаётся на этапе 0, читается автоматически в каждой сессии. Содержит:
```markdown
# Проект: ARCH-1, реализация вертикального среза Мицелия

## Что это
Реализация по готовой спецификации в ../arch0/. Спека authoritative —
её НЕ переобсуждаем, только реализуем.

## Жёсткие правила
1. Никаких LLM-судей. HARD-evidence только от детерминированных процедур.
2. Storage append-only: методов update/delete нет вообще.
3. Каждый модуль — со своими контрольными случаями (известный ответ).
   Модуль без прошедших контрольных случаев считается неготовым.
4. GRAPH CORE и STATE ENGINE не импортируют ничего про LLM.
5. Сырой вывод модели сохраняется ДО парсинга, всегда.

## Стек
Python 3.11, llama-cpp-python (GGUF, CUDA), без внешних зависимостей
сверх уже установленных. Никаких фреймворков.

## Где что
../arch0/          спецификация (НЕ читать целиком, только нужное)
./src/             код
./tests/           контрольные случаи
./STATUS.md        текущее состояние (читать в начале каждой сессии)
```

**`arch1/STATUS.md`** — обновляется в конце каждой сессии. Шаблон:
```markdown
# STATUS

## Последнее обновление: <дата>, этап <N>

## Готово
- [x] Этап 1: GRAPH CORE — src/graph_core.py, 12/12 контрольных случаев
- [ ] Этап 2: ...

## Текущий этап: <N>
Что сделано в этой сессии:
Что осталось до критерия готовности:

## Решения, принятые по ходу (важно для следующих сессий)
- <решение> — <почему>

## Известные проблемы / отложенное
- <что> — <почему отложено>

## Следующий шаг (буквально первая команда следующей сессии)
```

### 2.2 Начало каждой сессии — фиксированные 3 шага

```
1. /clear
2. Прочитать: arch1/CLAUDE.md + arch1/STATUS.md          (~3–4 тыс. токенов)
3. Прочитать спеки ТОЛЬКО для текущего этапа (список в §3)
```

Не читать: отчёты экспериментов, `EXPERIMENTAL_BASIS.md`, `ARCHITECTURE_AUDIT.md`, документы других этапов. Обоснования решений уже вшиты в спеку — повторно их выводить не нужно.

### 2.3 Конец каждой сессии — фиксированные 2 шага

```
1. Прогнать контрольные случаи этапа, зафиксировать результат
2. Обновить STATUS.md (можно Haiku — это механическая операция)
```

### Этап 3. SEAM ENGINE + фреймворк самопроверки швов

**Цель:** механические швы и — главное — механизм, который ловит ошибки в самих швах.

Это **самый важный этап по критерию «сделать правильно»**. По данным проекта: все шесть найденных за девять экспериментов дефектов проверяющих правил были пойманы контрольными случаями и **ни один — на реальных данных**.

**ВХОД:**
```
CLAUDE.md + STATUS.md                              4 КБ
arch0/SEAM_MODEL.md                               15 КБ  ← основной
experiment8/configs/run_tests.py                   готовый код
experiment8/configs/ast_checks.py                  готовый код
                                          итого ≈ 9 тыс. токенов
```

**ВЫХОД:**
```
src/seam_engine.py      реестр швов, evaluate(), seam_class,
                        self_test(), is_trusted()
src/seams/exec_seam.py     обёртка вокруг run_tests.py (HARD)
src/seams/format_seam.py   парсинг секций (HARD)
src/seams/numeric_seam.py  сверка чисел (HARD)
tests/seam_control_cases/  для КАЖДОГО шва: заведомо верный вход,
                           заведомо неверный вход, неприменимый вход
```

**Ключевое требование:** шов, не прошедший `self_test`, помечается `is_trusted = false` и **не может** производить HARD-evidence. Это проверяется автоматически.

**Модель/режим:** Sonnet 5. Plan mode обязателен — структура контрольных случаев важнее кода.

**Оценка:** ~500 строк · выход ~18 тыс. токенов · 1–2 сессии · **3–4 часа**

**ГОТОВО:** каждый шов проходит все три типа своих контрольных случаев; недоверенный шов доказуемо не может дать HARD.

**⚠ Первый настоящий гейт.** Если контрольные случаи ловят ошибки в ваших швах уже здесь — это **успех механизма**, а не задержка. Так и должно быть.

### Этап 4. REPAIR PLANNER — три множества и шаг сужения

**Цель:** самая тонкая логика: `candidate_affected` → сужение проверкой → `repair_set`.

**ВХОД:**
```

arch0/REPAIR_MODEL.md                             21 КБ  ← основной
arch0/COLLISION_MODEL.md                          11 КБ

```

**ВЫХОД:**
```

src/repair_planner.py    candidate_affected(), narrow(), build_plan(),
                         сравнение стратегий, STOP-условия
src/policy.py            RuleBasedPolicy по REPAIR_MODEL §4.2
tests/injection_harness.py   ← перенести методику из experiment9
tests/test_repair.py
```

**Инъекционный стенд — переиспользовать эксперимент 9.** Там уже отработана схема: заморозить корректный граф → инъецировать ровно одну ошибку в известную точку → сравнить предсказанную область с независимо построенной истиной. Логика в `experiment9/metrics/injection9.py` и `ground_truth9.py`. Не изобретать заново — адаптировать.

**Контрольные случаи:**
```
1. инъекция в терминальный узел → область = {он сам}
2. инъекция в корень → область = весь граф
3. инъекция в ветвь A → ветвь B НЕ затронута
4. merge-узел затрагивается только со стороны повреждённой ветви
5. narrow() переводит узел в unaffected ТОЛЬКО по evidence
6. план всегда содержит FULL_RETRY в alternatives_considered
7. повтор плана → REPAIR_OSCILLATION → STOP
8. хеш состояния повторился → REPEATED_STATE → STOP
```

**Модель/режим:** **здесь единственное оправданное включение Opus 5.**
```
1. Opus 5 + plan mode, 20–40 минут: обсудить ТОЛЬКО логику narrow() —
   как именно разделять verified / unaffected / unknown.
   Это место, где спека допускает толкование и где ошибка дорога.
2. Переключиться на Sonnet 5 для написания кода по утверждённому плану.
```
Не писать код на Opus — это перерасход бюджета без выигрыша.

**Оценка:** ~450 строк · выход ~20 тыс. токенов (из них ~4 тыс. на Opus) · 1–2 сессии · **3–5 часов**

**ГОТОВО:** 8/8 контрольных случаев на инъекционном стенде. **Ни одного вызова LLM на этом этапе** — вся логика проверяется детерминированно.

### Этап 7. Измерительный прогон

**Цель:** получить данные для ответа на 4 вопроса из `ARCHITECTURE_AUDIT.md §5.4`.

**ВХОД:** `CLAUDE.md + STATUS.md` ≈ 4 тыс. токенов. Больше ничего.

**ВЫХОД:**
```

metrics/measurements.json
```

**Конфигурация прогона:**
```
20 задач × 3 модели × 4 seed = 240 генераций   (как в эксп. 9)
+ ветка A: граф задан вручную (из schema9.py)
+ ветка B: граф выведен автоматически
```

**Что измеряем:**
| Вопрос | Метрика |
|---|---|
| Даёт ли сужение экономию? | `stale_resolved_by_verify_ratio` |

**Дисциплина запусков** (проверена в экспериментах 1–9): фоновый запуск через механизм задач, последовательно по моделям, проверка VRAM до и после. Не запускать две модели параллельно на 6 ГБ.

### 4.2 Про полный расход токенов

Приведённые «тыс. токенов» — это **полезный выход** (написанный код и текст). Это то, что я могу оценить надёжно.

Полный расход в Claude Code выше в разы, потому что каждый ход пересылает контекст. Порядок величины: **суммарный вход за сессию обычно в 10–30 раз больше выхода**, но кэширование промпта существенно снижает реальную стоимость повторяемой части.

**Практический вывод: расход определяется числом ходов, а не объёмом кода.** Отсюда правила экономии в §6.

## 5. Что делать при исчерпании лимита

План специально нарезан так, что упор в лимит не теряет прогресс.

```
Лимит пойман ПОСЛЕ этапа   → всё на диске, /clear, ждать окно, начать следующий
Лимит пойман ВНУТРИ этапа  → 1. немедленно обновить STATUS.md (можно Haiku,
                                это дёшево)
                             2. записать в «Следующий шаг» буквальную команду
                             3. /clear, ждать окно
                             4. новая сессия читает CLAUDE.md + STATUS.md
                                и продолжает — контекст восстанавливается
                                за ~4 тыс. токенов
```

**Никогда не «дожимать» этап на исходе лимита.** Обрыв посреди правки файла — худший из возможных исходов: состояние на диске несогласованно, а контекст потерян.

**Признак приближения к лимиту:** ответы начинают приходить заметно медленнее либо появляется предупреждение. При первом признаке — сразу шаг 1 из списка выше.

## 6. Правила экономии бюджета

Отсортированы по величине эффекта.

1. **Не читать `arch0/` целиком.** Список файлов на этап — в §3. Это разница между 14 тыс. и 130 тыс. токенов на старте сессии.

2. **Plan mode перед этапами 1, 3, 4, 6.** Неверно написанный модуль стоит вдвое: написать + переписать. План стоит десятую часть.

3. **Проверять кодом, а не рассуждением.** Не «посмотри на этот вывод и скажи, правильно ли» — а `python run_checks.py`. Локальное исполнение бесплатно, рассуждение о выводе стоит токенов и менее надёжно.

4. **Правило трёх ходов при отладке.** Если баг не найден за три хода — остановиться, добавить печать промежуточных значений, запустить локально, вернуться с фактами. Спираль отладки вслепую — главный пожиратель бюджета.

5. **`/clear`, а не `/compact`.** Очистка бесплатна, сжатие стоит токенов и теряет детали. Переносить через `STATUS.md`.

6. **Haiku на рутину:** обновление `STATUS.md`, переименования, форматирование.

7. **Не просить пересказ спеки.** Она написана. Если что-то непонятно — прочитать конкретный раздел, а не просить объяснить.

8. **Один этап — одна сессия.** Смешение двух этапов забивает контекст и роняет качество на втором.
