# trace-probe / experiment

Контролируемое исследование вариативности локальных языковых моделей:
насколько сильно меняется вывод ОДНОЙ и той же модели при независимых
повторных генерациях, а также при изменении temperature / top_p /
формулировки промпта? Насколько сильно при этом меняется именно паттерн
ошибок, а не только поверхностный текст?

Это инфраструктура сбора данных, а не готовый вывод. Фактические результаты
и их интерпретация — в `REPORT.md`.

## Зафиксированные решения по объёму эксперимента (не молчаливые)

- **Только GGUF, один локальный GPU (NVIDIA GTX 1660 SUPER, 6 ГБ VRAM),
  через llama-cpp-python.** Модели в формате transformers/safetensors из
  `../models/` (OLMoE-1B-7B-0924, Qwen3-0.6B, Qwen3-1.7B,
  granite-3.1-1b-a400m-base) исключены по прямому указанию пользователя, а
  не потому что не запустились. См. `configs/models.json` -> `excluded_models`.
- Найдено 8 пригодных GGUF-моделей; все 8 прошли smoke test. См.
  `configs/models.json` -> `models` и `configs/smoke_test2_results.json`.
- У одной модели (`smollm2-360m-instruct-noimpl-q5_k_m`) нет встроенного
  chat-шаблона, и даже при вручную подставленном ChatML-шаблоне того же
  семейства модель выдаёт вырожденный/повторяющийся текст независимо от
  формулировки промпта. Это проверено экспериментально, а не предположено
  — см. заметку в `models.json` — и оставлено в эксперименте как
  полноценный отрицательный результат.

## Структура каталогов

```
experiment/
  tasks/tasks.jsonl          9 фиксированных задач, 3 домена (математика/логика/код), объективный ground truth
  prompts/prompts.jsonl      3 варианта формулировки промпта (P1/P2/P3) x 3 домена
  configs/
    models.json              реестр моделей + исключения, с причинами
    conditions.json           5 условий генерации (сетка temperature x top_p)
    env_fix.py                 process-local фикс сломанной переменной окружения CUDA_PATH
                                (см. комментарии в файле про первопричину)
    chat_render.py            ручной рендеринг chat-шаблона через jinja2 (по модели)
    extraction.py              regex-извлечение ответа/кода, текстовые характеристики
    verification.py           объективная проверка по доменам (математика/логика/код)
    verify_code.py             изолированный воркер выполнения кода с таймаутом
    run_batch.py               раннер для одной модели (грузит модель один раз, крутит очередь задач)
    run_parallel.py            оркестратор: N моделей параллельно, затем слияние шардов
    reverify.py                 переприменяет verification.py к сохранённому RAW (без затрат GPU)
    enrich_index.py            добавляет output_text_hash в объединённый индекс (для diversity)
    search.py                  CLI-фильтр по компактному индексу -> RUN_ID'ы
  runs/
    index.jsonl                 компактный индекс, ОДНА СТРОКА НА ОДИН ЗАПУСК (схема ниже)
    index.<model_id>.jsonl      шарды по моделям (пишутся вживую run_batch.py)
    index_enriched.jsonl        index.jsonl + output_text_hash (производный, пересчитываемый файл)
    raw/<run_id>/result.txt      точный сырой вывод модели
    raw/<run_id>/meta.json       отрендеренный промпт, параметры генерации, usage
  metrics/                       результат работы compute_metrics.py
  REPORT.md
```

## Воспроизведение конкретного запуска

Каждая строка `runs/index.jsonl` содержит `model_id`, `model_version`,
`quantization`, `architecture`, `prompt_id`, `prompt_text_hash`,
`temperature`, `top_p`, `top_k`, `seed`, `max_tokens`, `condition_id` и
`repeat_index`. Имея это плюс `configs/models.json` и
`prompts/prompts.jsonl`, можно точно восстановить промпт и вызов генерации
для любого RUN_ID; сам вывод при этом ещё и сохранён дословно в
`runs/raw/<run_id>/`.

`seed` задаётся явно на каждый повтор (`seed == repeat_index`), в том числе
при T=0. Это сделано намеренно: при T=0 семплирование — argmax, и seed
формально не должен влиять на результат, поэтому 5 "повторов" при T=0 — это
одновременно и проверка того, действительно ли этот backend детерминирован
при T=0 (см. REPORT.md), а не априорное предположение об этом.

## Известные ограничения (продублированы в REPORT.md)

- Всего 9 фиксированных задач (требование "небольшой фиксированный набор")
  — это даёт устойчивое число повторов на ячейку (5), но ограниченный охват
  по задачам. Выводы о том, КАКИЕ именно задачи модель склонна проваливать,
  не следует обобщать за пределы этих 9 задач.
- `HAS_CONTRADICTION` всегда `null` (сознательно не вычислялось): это не
  определяется надёжно простыми regex-методами, а LLM-judge в этом
  эксперименте не использовался (см. ограничение в исходном ТЗ).
- `HAS_EXPLICIT_UNCERTAINTY` / `HAS_SELF_CORRECTION_LANGUAGE` — это
  keyword-эвристики, а не семантическое понимание — считать слабым
  сигналом, не более.
- Проверка для `math`/`logic` требует, чтобы модель выдала строку вида
  `Final answer: <x>` (по инструкции в промпте), иначе используется
  последняя непустая строка как fallback. Модели, которые ни разу не
  выходят на разбираемую финальную строку, получают FORMAT_ERROR — это
  реальный, значимый результат для эксперимента (способна ли модель вообще
  соблюдать формат?), а не шум измерения.
