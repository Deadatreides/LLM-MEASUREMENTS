# REPORT_PIPELINE — artifact pipeline vs monolithic best-of-N (English version)

English translation of [`REPORT_PIPELINE.md`](REPORT_PIPELINE.md) (Russian original). If the two disagree,
the original wins.

Roles used throughout:

| role | what it is |
|---|---|
| **A1** | contract |
| **A2** | tests, generated by the model |
| **A3** | implementation, generated by the model |
| **A4** | repair (patch) |

The **seam** is the mechanical check that runs the A2 tests against the A3 code. **Reference** means the
hand-written reference implementation and reference tests of each task; they are never generated by a
model.

---

Hypothesis under test: a structured pipeline (CONTRACT → TESTS / IMPLEMENTATION → mechanical seam →
PATCH) solves more tasks and catches errors better than plain best-of-N at a comparable budget.

**Result: the hypothesis was not confirmed.** At a comparable token budget, best-of-N (especially N = 8)
consistently solves more tasks than any pipeline variant. The A2↔A3 mechanical seam rejects correct code
more often than it catches real errors. Below are the data and the specific diagnosis of why — not an
attempt to rescue the hypothesis by interpretation.

---

## 1–4. Baseline N = 1/2/4/8

Pooled over 4 models, 24 task-model pairs.

| N | calls | avg tokens per task | solved rate |
|---|---|---|---|
| 1 | 1 | 314 | 0.833 |
| 2 | 2 | 604 | 0.833 |
| 4 | 4 | 1226 | 0.875 |
| 8 | 8 | 2473 | **0.958** |

The baseline grows monotonically with N and does not plateau within N ≤ 8.

Scoring note (`metrics/compute_metrics2.py`): a baseline task counts as solved if **any** of its N
samples passes the reference tests, i.e. pass@N.

## 5–7. Pipeline variants

| variant | calls (avg) | tokens (avg) | task-level solved rate | coverage |
|---|---|---|---|---|
| PIPELINE_1 (A1+A2+A3, no repair) | 3.00 | 1384 | 0.875 | 4 models, 24 task-model pairs |
| PIPELINE_2 (+1 repair) | 3.79 | 1808 | 0.916 | 4 models, 24 task-model pairs |
| PIPELINE_2R2 (+2 repairs) | 4.11 | 1606 | 1.000 | qwen3-1.7b only, 6 tasks |
| PIPELINE_3 (shared A1/A2 + 3×A3) | 5.00 | 1722 | 1.000 | qwen3-1.7b only, 6 tasks |

PIPELINE_2R2 and PIPELINE_3 were run only on the main model (qwen3-1.7b), as the more expensive
variants. They were not scaled to all 4 models to save budget — a deliberate decision, see §13 below.

## 8–10. Calls, tokens, time

- Total LLM calls in the whole experiment: **785** (0 generation failures).
- Total output tokens: **137,887**; input tokens: **190,551**.
- Total generation time (serial-equivalent): **2132.8 s ≈ 35.5 min**. Wall time was shorter thanks to
  parallel processes in phase 2: 3 models at once, ~3.8 of 6.1 GB VRAM.
- 192 baseline samples + 168 pipeline attempts = 360 "task-solving units".

## 11. Solved rate — direct comparison at a comparable budget

**Budget-matched (by tokens).**
- Baseline N = 4 (1226 tokens) gives **0.875**. That is statistically the same as PIPELINE_1 (1384
  tokens, also 0.875), but the baseline spends **fewer tokens** on it.
- Baseline N = 8 (2473 tokens) gives 0.958. That is above the ceiling PIPELINE_2 reaches even at 1808
  tokens (0.916).
- **At a comparable or smaller token budget, the baseline never loses to the pipeline on solved rate.**

**Call-matched (by number of calls).**
- PIPELINE_1 (3 calls, 0.875) slightly beats the nearest baseline by number of calls (N = 2, 0.833).
- It almost reaches N = 4 (0.875) with one call fewer.
- This is the only place where the pipeline shows a small advantage, and only when comparing by number
  of calls, not by tokens. The two ways of comparing give different answers, so both are shown.

## 12. Error detection rate

Pooled over all pipeline attempts (168 attempts, all variants, all models): among attempts where A3 is
objectively wrong (by the reference), the share caught by the A2↔A3 mechanical seam (`drift_caught_rate`)
ranges from **0.67 to 1.0**, depending on model and variant. This is a deceptively good number — see §15
(false reject) and the main finding below.

## 13. A2 mutation score

The average mutation score of the generated A2 suites is **0.965** (n = 168, range by model 0.833–1.0).
The mutants are purely mechanical, made from the reference implementation. At first glance this means
"the tests are good". **That is misleading** — see the main finding below.

## 14. Repair (A4)

- Attempts with at least one repair: **67** of 168 (40%).
- Of those, 50 were "false rejects": the original implementation was ALREADY correct by the reference,
  and the A2↔A3 seam rejected it wrongly. **0 of these 50** turned into a regression
  (`PATCH_REGRESSION_RATE = 0.0` in every model and variant). Repair at least does not break what
  already worked.
- The remaining 17 were real A3 errors. Repair fixed **1 of 17** (`PATCH_SUCCESS_RATE ≈ 0.06` on
  average, 0.0 for 3 of the 4 models). **Repair almost never fixes real bugs** in this configuration.

## 15. False accept / false reject

| model | false_reject_rate (seam wrongly rejected a correct A3) | false_accept_rate (seam wrongly accepted a wrong A3) |
|---|---|---|
| llama-3.2-1b | 0.92–1.0 | 0.0 |
| qwen2.5-coder-1.5b | 0.71–0.78 | 0.0 / — |
| qwen3-1.7b (best model) | 0.47–0.65 | 0.0–0.33 |
| smollm2-360m-bartowski (weak) | 1.0 | 0.0 |

**False reject dominates in all 4 models without exception**, including the best one (qwen3-1.7b).
False accept is rare but not zero: 0.33 for qwen3-1.7b in PIPELINE_2; a concrete example is below.

## Main finding: why — A2 itself is wrong 77% of the time

Direct check: feed a **known-correct** reference implementation of the task to the A2 tests. If the
tests are good, they must accept it.

- **129 of 168 (76.8%)** generated A2 test suites **rejected the known-correct reference
  implementation**.
- Of the A2 suites whose mutation score was perfect (1.0, n = 155), **126 (81%) still rejected** the
  correct reference code.

This is the key methodological result, and the direct answer to question 3 in §28 of the spec, below.
**A high mutation score does not mean the tests are correct with respect to the task's real
specification.** A mutation score only shows the ability to tell the original code from a mechanically
broken version, not that the asserts themselves are right. A2 systematically invents private, wrong or
too-narrow expectations (see the example below) that have nothing to do with the real behaviour described
in the task.

### Concrete example (CASE 3 / CASE 5, section 10 of the spec)

`qwen3-1.7b-q4_0-unsloth--CODE_04--PIPELINE_2--a1` (task count_vowels):

A3 (implementation):
```python
def count_vowels(s):
    vowels = {'a', 'e', 'i', 'o', 'u'}
    return sum(1 for char in s if char in vowels)
```
The bug: it does not lowercase the string, so it does not count uppercase vowels
(`count_vowels('HELLO')` returns `0` instead of `2`).

A2 (tests) contain `test_mixed_case` with the string `"AaEeIiOoUu"`. It holds exactly one lowercase vowel
of each kind, so the bug **happens not to show**: even without case handling the sum matches, 5. No A2
test checks a string of ONLY uppercase vowels.

Result:
- `seam_a2_reference_status = MECHANICAL_FAIL` — A2 is bad in principle, it does not accept even the
  correct reference;
- but `initial_seam_a2_a3 = MECHANICAL_PASS` — A2 consistently "accepted" the buggy A3;
- and `initial_reference_status = MECHANICAL_FAIL` — an external verifier with the test
  `count_vowels('HELLO') == 2` would have caught the bug.

**Because the internal seam said PASS, repair never even started.** The pipeline would have quietly
counted the task as solved if not for the independent reference verifier. This is exactly the
"dangerous collision" from §10/§21 of the spec — not hypothetical, actually observed.

## 16–19. Mutations / drift / regression — summary

- **DRIFT_RATE** (share of attempts where A3 is objectively wrong): 0.0–0.39 depending on the model.
  Models write correct code more often than correct tests.
- **DRIFT_CAUGHT_RATE**: 0.67–1.0. Its denominator consists mostly of real errors, which are rare, so
  it does not offset the false rejects.
- **CASE2 (A2 bad, A3 good)** is by far the dominant class in all 4 models: 7–14 of 18 attempts per
  model for PIPELINE_1/2.
- **CASE3 (both bad, but the seam passes consistently)** and **CASE5 (the seam passes, the reference
  does not)** were recorded for qwen3-1.7b — 1 case, analysed above. Rare, but not zero, and this is the
  only model where any false accept was observed at all.
- **PATCH_REGRESSION_RATE = 0.0** everywhere — the only unambiguously positive result for the pipeline:
  repair does not break code that already works.

## Answers to the 4 questions (section 28 of the spec)

**1. Do A1/A2/A3 really produce more independent errors than N plain answers?**
No, the opposite. The pipeline's errors are strongly correlated around ONE point of failure — the A2
role (test generation). CASE2 ("A2 bad") is the overwhelming majority of all observed inconsistencies in
all 4 models. This is not a diversified set of independent errors but one systematic, reproducible
source of noise.

**2. Does the mechanical seam really turn this variability into a higher solved rate?**
No. At a comparable token budget, the pipeline's solved rate does not exceed baseline best-of-N for any
of the 4 models (see §11). The seam formally "works" — the mutation score is high and some real errors
are caught — but the net effect on the final solved rate is either neutral or negative, because the
false rejects almost always outweigh the benefit.

**3. How often is the verifier artifact A2 itself wrong?**
Very often: **76.8%** of generated test suites reject the known-correct reference implementation. This
is the main quantitative result of the whole experiment.

**4. What does one successfully repaired wrong result cost, compared with extra plain sampling?**
- Repair fixed 1 real error out of 17 (≈6%), at an average of ~501 tokens per A4 call (416.7 input +
  84.2 output, n = 77 A4 calls).
- One extra baseline sample costs ~180–430 tokens (range over the 4 models at N = 8). Going from N = 1
  to N = 8 raises the pooled solved rate from 0.833 to 0.958.
- So one extra best-of-N "shot" at a comparable price yields more new solutions than one repair pass.
  **In this experiment, extra plain sampling is cheaper and more effective than one repair pass.**

## Limitations

- **Small task set.** 6 tasks, all code, inherited from experiment 1 and extended. Conclusions about
  specific tasks do not generalise further.
- **Partial model coverage.** PIPELINE_2R2 and PIPELINE_3 were run on only one (the best) model. This is
  a deliberate budget cut, allowed by section 13 of the spec, and stated explicitly, not hidden.
- **Temperature fixed at 0.3, not 0.0, for ALL calls.** This is a deliberate departure from a literal
  "T = 0". At T = 0 this backend behaved almost deterministically in experiment 1, which would have
  starved best-of-N of real candidate diversity and biased the comparison in the pipeline's favour.
  T = 0.3 is still a "low fixed temperature", allowed by section 18 of the spec, and gives both modes
  the same source of variability.
- **A4 patches only the IMPLEMENTATION (A3), never the TESTS (A2).** This is a deliberate simplification
  of the repair role. Section 9 of the spec allows either, but patched tests are an order of magnitude
  harder to verify mechanically. It partly explains the low PATCH_SUCCESS_RATE: when the root of the
  problem is in A2 and only A3 may be fixed, there is often nothing to fix.
- **Candidate selection in PIPELINE_3 is purely mechanical:** the first candidate that passes the A2↔A3
  seam, otherwise the first in order. No LLM judge and no manual selection.
- **Reference tests and reference implementations were written by hand and self-checked.** This
  includes a bug of my own, found and fixed during preparation: see `tasks/tasks_pipeline.py`, task
  CODE_06, and the test `test_spaces_not_stripped` in CODE_01.

## Final check (section 30 of the spec)

- **The reference verifier is independent of the LLM.** `reference_tests` were written by hand, run
  through `configs/run_tests.py`, and were never generated by a model.
- **A2 does not receive A3, and A3 does not receive A2.** Confirmed in the code: `gen_tests` and
  `gen_implementation` in `configs/runner2.py` take only the task and A1 as input.
- **A4 receives only real mechanical signals** — traceback and failing test names, not an abstract
  "check again". See `failure_report_text()`.
- **The mutation score is computed automatically, without an LLM** (`configs/ast_mutator.py` +
  `configs/run_tests.py`).
- **RAW of all artifacts is saved:** 785 folders in `runs/raw/` and 785 records in `artifacts.*.jsonl`,
  matched 1:1.
- **Every artifact has an `artifact_id`.** Every pipeline run has a `run_id` linking A1/A2/A3(s)/A4(s)
  through `parent_artifact_ids`.
- **All 785 LLM calls have a token cost:** `input_tokens` / `output_tokens` are filled in every record;
  0 generation failures.
- **Baseline and pipeline were compared two ways** — by number of calls and by tokens (§11). The results
  differed, so both are shown.
- **A2 errors are separated from A3 errors** from the start: `seam_a2_reference_status` and
  `initial_reference_status` are separate fields.
- **False accept is separated from false reject:** `MISSED_DANGEROUS` and `FALSE` are different drift
  categories.
- **Patch regression is measured explicitly:** `repair_regressed`, `patch_regression_rate` = 0.0
  everywhere.
- **No LLM-as-a-judge was used anywhere.**
- **No artificial errors were injected.** Mutations were applied only to copies of the reference
  implementation for mutation testing, never to model outputs.
- **No cherry-picking.** Candidate selection in PIPELINE_3 is mechanical, and the whole dataset,
  including all the "bad" cases, was kept and went into the metrics.
- **Negative results are not hidden** — this whole report is about the hypothesis not being confirmed,
  and why.

## Summary (no architecture proposals)

1. **Models used:**
   * qwen3-1.7b-q4_0-unsloth — main model, full coverage;
   * llama-3.2-1b-instruct-q4_0, qwen2.5-coder-1.5b-instruct-q4_0,
     smollm2-360m-instruct-bartowski-q5_k_m — weak / medium / coder, reduced coverage.

   All GGUF, on the same GPU backend as in experiment 1.
2. **Tasks used:** 6, code domain — CODE_01..CODE_06. The first 3 come from experiment 1; 3 more of the
   same type were added. Each has a REFERENCE_IMPLEMENTATION and REFERENCE_TESTS.
3. **Pipeline runs executed:** 168.
   * PIPELINE_1 and PIPELINE_2: 4 models × 6 tasks × 3 independent attempts = 72 each.
   * PIPELINE_2R2 and PIPELINE_3: 1 model × 6 tasks each.
   * Plus 192 baseline samples: best-of-8 × 4 models × 6 tasks.
4. **Baseline solved rate:** 0.833 (N = 1) → 0.958 (N = 8), pooled over 4 models.
5. **Pipeline solved rate:** 0.875 (no repair) → 0.916 (1 repair), pooled over the same 4 models. 1.0 for
   PIPELINE_2R2/PIPELINE_3, but on one model only.
6. **Error detection rate:** 0.67–1.0 by model, but devalued by the high false reject rate.
7. **A2 mutation score:** 0.965 on average — yet 76.8% of these A2 suites still reject known-correct
   code (the main finding).
8. **Repair success:** ≈6% (1 of 17 real errors fixed).
9. **Regression rate:** 0.0% — repair never breaks working code.
10. **Tokens:** 137,887 output + 190,551 input = 328,438 in total, 785 LLM calls.
11. **Time:** 2132.8 s (35.5 min) of total generation time, serial-equivalent. Wall time was shorter
    thanks to parallel processes in part of the run.
12. **Main collision types:**
    * the overwhelming majority is CASE2 — the A2 tests are wrong, the A3 implementation is right — a
      false reject of correct code;
    * rare, but recorded: CASE3/CASE5 — tests and implementation "agreed" with each other consistently
      but wrongly; the seam gave a false sense of correctness, and only the external reference caught
      it.
13. **Limitations:** see the section above — small task set, partial model coverage for the expensive
    variants, fixed T = 0.3, A4 patches only the implementation.
14. **RAW and INDEX:**
    * `trace-probe/experiment2/runs/raw/` — 785 folders, RAW text + meta.json per artifact;
    * `trace-probe/experiment2/runs/{baseline,pipeline_runs,artifacts,seams}.<model_id>.jsonl` —
      compact indexes;
    * summary metrics — `trace-probe/experiment2/metrics/metrics2_summary.json`, published here as
      [`metrics/metrics2_summary.json`](metrics/metrics2_summary.json).

    The raw runs are not in this repository; see the top-level README.
