# Эксперимент 6 — ERROR STATE / ALLOCATION / MARGINAL COMPUTE

**Примечание по нумерации.** В присланном задании эксперимент был озаглавлен «ЭКСПЕРИМЕНТ 5», но так как папка `experiment5` уже занята предыдущим (энтропийным) экспериментом, вся работа выполнена в папке `experiment6`, и везде далее (файлы, префиксы) используется номер 6. Содержательно это прямое продолжение логики «Эксперимент 5» из задания — просто следующий по счёту в общей последовательности папок проекта.

## 0. Вопрос

Не «полезна ли энтропия», а: **можно ли по наблюдаемому состоянию задачи (первые k генераций) рационально распределить следующий вычислительный бюджет** — и если да, то какая часть замкнутого цикла OBSERVE→CLASSIFY→ALLOCATE→EXECUTE→VERIFY→UPDATE→STOP/REDIRECT реально даёт выигрыш, а какая нет.

## 1. Данные и методология

- **Unit** = (task_id, model_id, temperature). 6 задач (CODE_01…CODE_06) × 2 модели (qwen3-1.7b-q4_0-unsloth, llama-3.2-1b-instruct-q4_0) × 3 температуры (0.0, 0.5, 1.0) = **36 units**.
- Для каждого unit «наблюдение» — это **первые 8 генераций** (seeds 1–8) из уже имеющегося пула эксперимента 5 (N=16 на unit). Дальнейшие данные (seeds 9–16, другая температура, другая модель) переиспользованы из эксперимента 5 **без единой новой генерации** — только нарезка (re-slicing) уже посчитанного.
- Единственная новая генерация — рукав **CHANGE_PROMPT** (альтернативный «reasoning-first» промпт, 288 генераций: 6 задач × 2 модели × 3 температуры × 8 seeds, 0 ошибок, 0 дублей) и **claim-level локальный retry** (8 генераций для одного диспутного утверждения).
- **Anti-leakage**: классификатор состояния (`state_classifier.py`) видит **только** первые 8 генераций своего unit. Ни Oracle@16, ни данные других рукавов (SAME_MODEL/SWITCH_MODEL/CHANGE_TEMPERATURE/CHANGE_PROMPT) не участвуют в классификации — они используются **только постфактум**, чтобы оценить, было ли решение хорошим.
- **Иерархия корректности**: LEVEL 0 — механическая (pytest, `run_tests.py`); LEVEL 1 — детерминированная семантическая (regex-классификаторы claims, никогда генерация не является доказательством самой себя); LEVEL 2 (независимая/вероятностная) в данном эксперименте не задействована отдельно — она используется только на claim-уровне через independent-continuation (см. §6).
- **Классификация ошибок E0–E10** (`configs/error_taxonomy.py`): E0=CORRECT (mechanical pass), E1=SYNTAX/TIMEOUT, E2=NameError/undefined, E4=прочий runtime, E5=TEST_FAILURE (содержательная), E6=TEST_FAILURE с тривиально пустым телом (pass/... /raise NotImplementedError), E10=UNKNOWN (не удалось извлечь код — код никогда не сворачивается молча в CORRECT/INCORRECT). E3/E7/E8/E9 помечены как неприменимые к этому кодовому домену либо производные на уровне состояния.
- **TRAIN/TEST по задачам** (не по seed/модели): TRAIN = CODE_01…CODE_04 (24 unit), TEST = CODE_05, CODE_06 (12 unit). Пороги классификатора состояний зафиксированы заранее (0.75 для «доминирования», 0.5 для unknown_rate, ±30% для two-way conflict) и **не подбирались** ни под train, ни тем более под test.

## 2. Классификатор состояний (S1–S6)

Признаки считаются **только** из первых 8: `pass_at_k`, `oracle_at_k`, `oracle_at_half` (из первых 4), `growth_half_to_k = oracle_at_k − oracle_at_half`, `dominant_cluster_share`, `n_unique_clusters`, `h_sem_bits`, `n_eff_clusters`, `two_way_conflict` (ровно 2 кластера, ни один <30%, один из них CORRECT).

Дерево решений (фиксированное, без подбора):
1. `unknown_rate_k ≥ 0.5` → **S5_UNKNOWN**
2. `dominant_cluster_share ≥ 0.75` и доминант = CORRECT → **S1_CONFIDENT_CORRECT** (действие: STOP)
3. `dominant_cluster_share ≥ 0.75` и доминант = ошибка → **S3_CONFIDENT_WRONG** (действие: SWITCH_MODEL)
4. иначе (неуверенность): `two_way_conflict` → **S6_CONFLICT** (SWITCH_MODEL); `growth_half_to_k > 0` → **S2_UNCERTAIN_PRODUCTIVE** (SAME_MODEL); иначе → **S4_NOISY** (STOP)

**Наблюдаемое распределение по 36 units:**

| Состояние | n | Действие |
|---|---|---|
| S1_CONFIDENT_CORRECT | 28 | STOP |
| S3_CONFIDENT_WRONG | 3 | SWITCH_MODEL |
| S4_NOISY | 4 | STOP |
| S6_CONFLICT | 1 | SWITCH_MODEL |
| S2_UNCERTAIN_PRODUCTIVE | **0** | SAME_MODEL |
| S5_UNKNOWN | **0** | CHANGE_PROMPT |

**Честное ограничение методологии.** `growth_half_to_k` в этих данных — грубый бинарный признак (Oracle@4 против Oracle@8, оба ∈{0,1}), и он оказался **вырожден до 0.0 на всех 36 unit** без единого исключения. Это не позволило когда-либо провести классификатор через ветку S2_UNCERTAIN_PRODUCTIVE — состояние «неопределённость, которая продуктивно растёт» просто ни разу не сработало как отдельная ветка при данном признаке, независимо от того, существует ли оно в реальности. Аналогично S5_UNKNOWN не встретился ни разу — на использованных 6 задачах кодовые ответы либо парсились, либо явно проваливали тест, случаев «код не извлекается» с частотой ≥50% не было. По прямому требованию задания (запрет подбирать пороги после просмотра данных) эти пороги **не были задним числом смягчены**, чтобы искусственно населить S2/S5 — это репортится как ограничение, а не скрывается.

## 3. Claim-level: локальный retry vs полный retry (H6)

Диспутное утверждение `CODE_01/C7_EDGE_SPACES` (qwen3-1.7b, T=0.5) — задокументированное «слепое пятно» модели ещё в экспериментах 3–4.

| | n | CORRECT | avg output tokens/gen | tokens/success |
|---|---|---|---|---|
| Полный retry всей спецификации (A1, из эксп. 3/4, переиспользовано) | 28 | 1 (3.6%) | 198.5 | ≈5515 |
| Локальный retry только этого утверждения (новая генерация) | 8 | 4 (50%) | 44.75 | ≈89.5 |

**≈60× выигрыш по стоимости успеха** при локальном retry конкретного claim вместо перегенерации всего артефакта. Это самый чистый и сильный результат эксперимента.

## 4. Действие по состоянию: точечные разборы

### S3_CONFIDENT_WRONG (H5: SWITCH_MODEL лучше SAME_MODEL при системной ошибке)

Из 3 unit в состоянии S3 **только один** имел реально нулевой `oracle_before` (`CODE_04/llama-3.2-1b-instruct-q4_0/T0.0`) — у двух других oracle_before уже был 1.0 (повезло поймать единичный правильный ответ в первых 8), поэтому delta_oracle=0 для любого действия там тривиален (потолок уже достигнут) и не тестирует H5.

Единственный информативный случай:

| Действие | Δoracle | tokens |
|---|---|---|
| SAME_MODEL | 0.0 | 2832 |
| SWITCH_MODEL | **+1.0** | 1642 |
| CHANGE_TEMPERATURE | +1.0 | 2911 |
| CHANGE_PROMPT | 0.0 | — |

SWITCH_MODEL и CHANGE_TEMPERATURE оба вывели unit из систематической ошибки, SAME_MODEL и CHANGE_PROMPT — нет. SWITCH_MODEL сделал это за **наименьшее число токенов**. Second look на бюджетно-сопоставленных S3-unit'ах из TRAIN (см. ниже) подтверждает то же направление на независимом срезе:

| Unit | D-действие (SWITCH_MODEL) Δoracle / tokens | SAME_MODEL Δoracle / tokens |
|---|---|---|
| CODE_01/llama/T0.0 | 0.0 / 1690 | 0.0 / 5600 |
| CODE_04/llama/T0.0 | **+1.0 / 1642** | 0.0 / 2832 |

Кросс-валидируется независимым выводом эксперимента 5, где этот же unit был задокументирован как «systematic trap» для llama-3.2-1b. **H5 поддержана, но на n=1 клиновом случае** — статистически тонко, нужно больше «настоящих» S3 с oracle_before=0 для уверенного вывода.

### S4_NOISY / S6_CONFLICT (H3/H4)

Все 5 unit (4×S4 + 1×S6) показали delta_oracle=0.0 **для всех действий без исключения**. Однако корневая причина — **эффект потолка**: у всех пятерых `oracle_before` уже был 1.0 к моменту классификации (pass@8 в диапазоне 0.25–0.625 — хотя бы один правильный ответ уже был в первых 8). То есть delta_oracle=0 здесь **механически гарантирован** структурой метрики (Oracle — это max, а не среднее), а не является чистым свидетельством «диверсификация не помогает, когда действительно есть что искать». H3 (высокая энтропия + растущий oracle → положительная отдача) вообще не тестируема — S2 не встретился ни разу. H4 (высокая энтропия + низкий прирост = шум) получает лишь частичную, смешанную с потолочным эффектом поддержку.

## 5. Сравнение политик

5 политик, каждая применяется к одному и тому же outcome-таблице (36 unit): **A_ALWAYS_SAME_MODEL**, **B_FIXED_TEMPERATURE** (всегда меняет температуру), **C_DIVERSIFY** (SWITCH_MODEL если pass@8<1, иначе STOP), **D_STATE_AWARE** (действие по таблице S1–S6), **RANDOM** (контроль).

### Весь набор (n=36)

| Политика | final Oracle | final Pass | Δoracle (сред.) | tokens (сумма) | stop_rate | switch_rate |
|---|---|---|---|---|---|---|
| A_ALWAYS_SAME_MODEL | 0.972 | 0.823 | 0.000 | 82 540 | 0.00 | 0.00 |
| B_FIXED_TEMPERATURE | 1.000 | 0.852 | 0.028 | 80 662 | 0.00 | 0.00 |
| C_DIVERSIFY | 1.000 | 0.903 | 0.028 | 28 643 | 0.64 | 0.36 |

| RANDOM | 0.972 | 0.819 | 0.000 | 54 395 | 0.39 | 0.11 |

### TEST split (held-out задачи CODE_05/CODE_06, n=12) — задачи, на которых пороги ни разу не подгонялись

| Политика | final Oracle | tokens | utility/token |
|---|---|---|---|
| A | 0.958 | 51 489 | 0.0 |
| B | 1.000 | 50 567 | 2e-05 |
| C | 1.000 | 14 666 | 6.8e-05 |

| RANDOM | 0.958 | 43 035 | — (худший Δpass) |

**Ключевая интерпретация (без приукрашивания).** D_STATE_AWARE не выигрывает за счёт «умного» выбора среди сложных состояний — таких unit слишком мало (S2=0, S3=3, S5=0, S6=1). Выигрыш почти целиком объясняется **точным распознаванием уже решённых unit (S1, 28/36) и выбором STOP** (stop_rate 0.83–0.89), тогда как A/B/RANDOM тратят токены безусловно на всех 36. Это не «умное распределение вычислений между трудными случаями», а **дешёвое и надёжное распознавание того, где вычисления вообще не нужны**. Единственное клиновое подтверждение содержательной маршрутизации в трудном состоянии — S3-кейс из §4 (n=1).

## 6. Проверка H1–H8

| Гипотеза | Вердикт | Комментарий |
|---|---|---|
| H1: состояние предсказывает предельный выигрыш | **Поддержана с оговоркой** | В основном отражает детекцию «уже решено» (потолок), а не тонкую дифференциацию среди неуверенных состояний |
| H2: низкая энтропия + доминирующая ошибка → низкая отдача SAME_MODEL | **Поддержана** | n=1 чистый случай (§4), направление устойчиво |
| H3: высокая энтропия + растущий oracle → положительная отдача | **Не тестируема** | S2_UNCERTAIN_PRODUCTIVE не встретился ни разу (0/36) — признак growth_half_to_k вырожден |
| H4: высокая энтропия + низкий прирост = шум | **Частично поддержана, спутана эффектом потолка** | Все S4/S6 unit уже имели oracle_before=1.0; delta_oracle=0 механически гарантирован структурой метрики |
| H5: SWITCH_MODEL > SAME_MODEL при систематической ошибке | **Поддержана**, но n=1 содержательный случай | Кросс-валидировано независимым выводом эксперимента 5 |
| H6: локальный retry claim > полный retry артефакта | **Сильно поддержана** | ≈60× по стоимости успеха |
| H7: STATE_AWARE > ALWAYS_SAME_MODEL при равном бюджете | **Поддержана**, но не в буквальной формулировке | Не «то же самое дешевле», а «то же/лучше при 5–15× меньшем бюджете» — нужно фиксировать именно эту формулировку |
| H8: STATE_AWARE > простая температурная политика (B) | **Поддержана** | ≈15× меньше токенов на TRAIN, лучший Δpass |

## 9. Финальный архитектурный гейт

Не «стоит ли строить Мицелий» — а какой **минимальный**, оправданный именно этими данными кусок цикла OBSERVE→CLASSIFY→ALLOCATE→EXECUTE→VERIFY→UPDATE→STOP/REDIRECT имеет право на существование:

1. **Внедрять**: детектор «уже решено» (`dominant_cluster_share ≥ 0.75` с доминантом CORRECT → STOP). Это единственный элемент, подтверждённый на статистически весомой подвыборке (28/36) и дающий измеренную, воспроизведённую на held-out TEST-задачах экономию 5–15× бюджета без потери итогового качества.
2. **Не внедрять пока**: полноценную маршрутизацию действий (SAME_MODEL vs SWITCH_MODEL vs CHANGE_TEMPERATURE vs CHANGE_PROMPT) для состояний S2/S3/S5/S6 как production-логику — данных категорически недостаточно (0, 3, 0, 1 unit). Направление H5 (SWITCH_MODEL при системной ошибке) выглядит многообещающе и заслуживает прицельного следующего эксперимента, но не готово быть «правилом».
3. **Внедрять отдельно и независимо от state-машины**: декомпозицию артефакта до уровня claim перед retry (H6) — это не требует S1–S6 вообще, работает как самостоятельный механизм и даёт наибольший измеренный эффект во всём эксперименте (≈60×).
4. **Не внедрять**: `growth_half_to_k` в текущем виде — признак не сработал ни разу, его нужно переопределить (например, непрерывная доля новых уникальных кластеров, а не бинарный Oracle-скачок) прежде чем повторно тестировать H3/H4.

Следующий эксперимент, если он будет, должен: (а) целенаправленно набрать больше unit с genuine oracle_before=0 в состоянии S3 (не «уже решено задним числом»), чтобы дать H5 настоящую статистическую силу; (б) протестировать STOP-детектор и claim-level декомпозицию на **новых**, не use для подбора порогов задачах — именно так, как того требует финальный пункт задания, без повторной подгонки.
