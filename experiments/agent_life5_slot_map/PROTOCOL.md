## 0. Рамка (не сужать)

## 1. Решение: опциональный evolve — ДА (подтверждено пользователем)

Задание явно гейтит Phase B.2 подтверждением: «Если заказчик
подтверждает GPU/время». Спрошено через AskUserQuestion в этой же
сессии (plan mode, до какого-либо числа этого пакета) — пользователь
выбрал **«Phase B + optional evolve»**. Зафиксировано здесь до запуска:
Phase B.2 ВКЛЮЧЕНА — 4 новых seed (`20261801..20261804`), чистый
default-канал (без единого registry-кода-пути, даже отключённого),
на скопированной сетке LIFE-4 (`max_gen=32`/`G_STALL=20`, то же окно,
что уже подтверждено рабочим).

Данные пула:
- **Обязательно**: `agent_life3_block_live/runs/life3_{with,ctrl}_s*`
  (6+6) + `agent_life4_block_fix/runs/life4_{with,ctrl}_s*` (6+6) = 24
  прогона. Проверено (эта сессия, до этого файла): все 24 директории
  целы (archive/summary/blocks/heredity/births присутствуют), все 24
  `summary.json["panel"]` **побайтово идентичны** (80 задач) — пул
  одной панелью/`best_single` корректен, без per-package различий.
- **Опционально (включено)**: 4 новых `life5_default_s2026180{1..4}`
  прогона — сетка скопирована byte-identical из
  `agent_life4_block_fix/metrics/live_grid/` (md5 проверен до первого
  числа), 0 новых `generate()`.
- Замечено заранее (важно для интерпретации §3, не порог): 12 из 24
  обязательных прогонов — это CTRL-плечи LIFE-3/4, где block registry
  был выключен ВСЕГДА — они уже являются точным экземпляром Phase-A
  дефолта. Обязательный пул — не чисто «старый код с мёртвым registry».

Эти 4 опциональных прогона НЕ смешиваются с обязательным пулом 24 —
считаются отдельным кросс-чеком (см. §3), корзины §4 вычисляются
ТОЛЬКО по обязательному пулу.

## 2. Phase A — дефолт (код, не наука)

`src/default_channel.py` — единственный evolve-путь для Phase B.2:
- `p_slot_hgt = 0.35`
- `transfer_slot` = комплементарный донор (`slot_hgt.py`, копия
  LIFE-2/3/4 БЕЗ ИЗМЕНЕНИЙ)
- `donor_score_fn` отсутствует в `ctx`
- `references` исключены из донора (`ev.references`)
- lean-старт: 0 non-ref `|ImpSet|>=2` (тот же assert, что LIFE-2/3/4)
- **НЕТ** registry блоков, **НЕТ** `p_block_insert`, **НЕТ** ветки
  `BLOCK_INSERT` в диспетчере вообще (не пустой словарь для симметрии,
  как в CTRL LIFE-3/4 — буквально два исхода: `roll<0.35` ->
  `transfer_slot`, иначе -> `mutate`)

## 3. Phase B — карта слотов (основная наука, обязательна, CPU)

`src/unfold_metrics.py` — Imp-core, копия `agent_life4_block_fix/src/
metrics_lib.py`'s unfold-функций (`slot_models` разворачивает
`cx.`-composite-CALL рекурсивно через `registry.get(mid)["genotype"]
["root"]`, семантика = `arch2/runner.py`'s исполнение). Не скопированы
A1-A5-специфичные функции (не нужны — LIFE-5 не строит A1-A5, §0
non-goals).

Для каждого archive genotype (все 24+4 прогона), для каждого слота
`s∈{READ,FORMAT,LOOKUP,COMPUTE}`:
- `signature = (op, sorted(set(unfold(slot_models(...)))))` —
  **дедуп через `set()`**, не просто `sorted()` от списка (LIFE-4's
  `BLOCKERS.md` "Находка 1" описала это как шумный, но безвредный для
  Imp баг — новый код, не обязан быть побайтовой копией, исправлено
  здесь при первой возможности)
- `Imp(s) = len(covered_set(...)) > best_single[s]` — вычисляется РОВНО
  ОДИН РАЗ на различную `(slot, signature)` пару (кэш), не пересчитывается
  на каждое вхождение — Imp это чистая функция сигнатуры при
  фиксированной панели/сетке (подтверждено §1)
- `carrier` = `complex_id` (дедуп ГЛОБАЛЬНО по пулу — если один и тот же
  `complex_id` встречается в нескольких прогонах, это буквально один и
  тот же генотип, не два носителя, см. LIFE-4's находку про сходимость)
- `n_seed_appeared` = число РАЗЛИЧНЫХ `run_id`, где сигнатура встретилась
  хотя бы раз с `Imp=1` — метрика, которая automatически поймала бы
  LIFE-3/4's LOOKUP-сходимость, если бы существовала тогда
- `median_L`/`max_L` — лайфспан на КАЖДОЕ вхождение (не дедуп по
  carrier — лайфспан это свойство прогона, не содержимого)

Два прохода агрегации: **gen>=0** (весь архив, включая ~20 общих
детерминированных lean-seed на прогон — доминирует сырые счётчики
тривиально) и **gen>=1** (только эволюционировавшее — научно значимое).
Корзины §4 считаются по gen>=1.

**Sanity-гейт (блокирующий)**: `Imp(FORMAT)` должен быть `False` для
КАЖДОГО генотипа во всём пуле (одна модель насыщает FORMAT 80/80,
структурно невозможно побить) — единственное нарушение означает, что
unfold/Imp сломан, стоп до любой корзины.

Дополнительно (не входит в §3.1 обязательно, но дёшево и прямо полезно
для проверки воспроизводимости): те же агрегаты раздельно по пакету
(life3-only vs life4-only) — "воспроизведена ли сигнатура на >=2
seed/пакета" становится прямым чтением, не ручным диффом, как в LIFE-4.

Δ Imp на рождение (НОВОЕ — прежние пакеты трекали Δ только по всему
`ImpSet`, не по слоту): для каждого admitted birth, для КАЖДОГО слота
отдельно, `+1` если `Imp(child,s) > Imp(parent,s)`, `-1` если наоборот.

## 4. Корзины карты (предрегистрировано, не двигать после чисел)

Per-slot (READ/LOOKUP/COMPUTE; FORMAT — только sanity), на обязательном
пуле 24, gen>=1:

- **`MAP_COVERAGE_GAP`**: `N_signatures_with_Imp=1 <= 1` **И** суммарно
  `n_carriers < 5` на этом слоте.
- **`MAP_STABILITY_GAP`**: `>=3` Imp-сигнатур на слоте, но
  `median_L < 2` **ИЛИ** (все, кроме одного outlier'а, имеют
  `n_carriers < 3`).
- **`MAP_LOOKUP_ONLY`** (сводная строка, не per-slot): единственный слот
  с Imp-сигнатурой, воспроизводимой на `>=2` seed/пакета — LOOKUP;
  READ/COMPUTE такой воспроизводимости не показывают.
- **`MAP_MIXED`**: разные слоты попадают в разные корзины — отчёт
  обязан разнести их, не схлопывать в одну строку.
- **`MAP_BLOCKED`**: архивы недоступны/повреждены, ИЛИ FORMAT sanity
  проваливается.

Precedence вычисления сводной строки: если LOOKUP-условие выполнено ->
`MAP_LOOKUP_ONLY`; иначе если корзины по слотам различаются ->
`MAP_MIXED`; иначе — общая корзина слотов; если ни один слот не
классифицирован — `MAP_BLOCKED`.

Вердикт вычисляется один раз механически по обязательному пулу 24;
опциональный кросс-чек (4 прогона) НЕ пересчитывает и не переопределяет
эту корзину — используется только как корробарация/расхождение,
изложенное рядом.
