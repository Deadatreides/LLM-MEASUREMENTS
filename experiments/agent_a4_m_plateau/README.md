# agent_a4_m_plateau

Пакет A4: калибровка `p_cross` до плато/верхней рабочей точки, ТОЛЬКО
archive-метрики для claim'ов (не snapshot), вердикт одной из трёх корзин.

## Запуск единой командой

```bash
python agent_a4_m_plateau/scripts/run_all.py
```

### Порядок работы

1. `scripts/verify_baselines.py`: проверка B1=0.4600, B2=0.5800, B3=0.7000
   (r и c) на HETEROSTEP train grid; также пишет `metrics/verify.json`.
2. 12 эволюционных прогонов: 4 номинальных уровня `p_cross` ∈ {0.50, 0.65,
   0.80, 0.90} × 3 seed (20261101, 20261102, 20261103), `start_pop=20`, до 32
   поколений, `G_STALL=16`. Фактически применяемая вероятность
   `effective_p_cross = min(p_cross, 0.75)` (`min_frac_local=0.25`) — см.
   `BLOCKERS.md`: `p_cross ∈ {0.80, 0.90}` дают ОДИНАКОВЫЙ
   `effective_p_cross=0.75` и потому дают побитово идентичные результаты
   при совпадающем seed — это не баг, а ожидаемое следствие клэмпа,
   зафиксированное в отчёте.
3. Для каждого прогона — ТОЛЬКО archive-метрики решают вердикт (переоценка
   всего архива на ПОЛНОЙ 100-задачной train-сетке против канонических чисел
   B1/B2/B3, эталоны исключены и из метрик, и из донорского пула для
   рекомбинации). Snapshot считается и публикуется отдельно, «для истории».
4. `metrics/summary.json` (12 прогонов), `metrics/curve_m.json` (J(p_cross),
   m*, плато, V3_HIT, вердикт-корзина).
5. Отчёт — `reports/REPORT_A4.md` (пишется отдельно после `run_all.py`).

Полный прогон занимает ~10 минут (0 GPU, offline replay).
