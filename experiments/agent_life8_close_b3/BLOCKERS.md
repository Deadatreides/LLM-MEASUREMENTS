## Найдено и исправлено ДО первого реального evolve-числа

1. **`run_all.py`'s `import ceiling as CEIL` резолвился в НЕСВЯЗАННЫЙ
   `arch2/ceiling.py`, а не в собственный `src/ceiling.py` пакета.**
   `live_dataset.py`'s собственный модульный код вставляет `ARCH2`/`ROOT`
   в позицию 0 `sys.path` (нужно, чтобы достать `arch2`'s модули) — это
   сдвигает `src/` пакета НИЖЕ `arch2/` для ЛЮБОГО последующего голого
   `import`. Совпадение имени с УЖЕ СУЩЕСТВУЮЩИМ, никак не связанным
   `arch2/ceiling.py` (обнаружен только этой сессией — не было причин
   знать о нём раньше) привело к `AttributeError: module 'ceiling' has
   no attribute 'compute_ceiling'` на самом первом прогоне `run_all.py`,
   ДО Phase 1 (крах внутри Phase 0, до единого реального evolve-числа).
   Явно проверено: это ЕДИНСТВЕННАЯ коллизия имён во всём пакете (все
   9 остальных собственных/скопированных имён модулей сверены против
   полного листинга `arch2/*.py` и `<ROOT>/*.py` — коллизий нет).
   Исправлено: `ceiling.py` теперь грузится по прямому пути файла
   (`importlib.util.spec_from_file_location`, тот же приём, что уже
   применялся для `verify_seams.py`) — не зависит от порядка `sys.path`.
   Повторный прогон прошёл Phase 0 идентично (числа совпали bit-for-bit
   со значениями, полученными при ручной проверке до исправления).

2. **Собственная forensic-функция `run_all.py::forensic_best_vs_baselines`
   воспроизвела уже однажды исправленный (LIFE-4) баг
   "composite-call-blindness"**: `ML.slot_models(children[s], None)` с
   `registry=None` молча пропускает любой `cx.*`-CALL внутри слота (не
   разворачивает его), возвращая для такого слота пустой/неполный список
   моделей. Обнаружено ПОСЛЕ завершения полной кампании: forensic-таблица
   первой версии показала "организм решает 33, только организм — 0" при
   `best_test_metrics.r=0.49` (49 задач) для ТОГО ЖЕ генотипа — несходимость
   49 vs 33 указала на недосчёт. Прямая трассировка (`traces/.../
   final:test_best`) подтвердила: лучший генотип Phase 1 (`cx-e7b946`)
   решает COMPUTE-слот на задаче `HS_006` через `CALL_COMPOSITE
   cx.cx-b653ef` → `cx.cx-fd948f` → `cx.cx-9c9fe0` (трёхуровневая
   вложенность) — рутинное поведение arch2 (ЛЮБОЙ допущенный в архив
   генотип автоматически адресуем как `cx.<его complex_id>`), НЕ имеет
   отношения к block registry/BLOCK_INSERT, которые P5 исключает из
   этого пакета. **Важно: сама кампания (отбор/смерть/HGT/stall) этим
   багом НЕ затронута** — `orchestrator.py::run_cell`'s собственный
   `imp_fn` всегда использовал полноценный `reg = HSTEP.Registry()`
   (прямая живая регистрация, не пост-хок аудит); баг был исключительно
   в ОТДЕЛЬНОЙ, ОТЧЁТНОЙ функции, добавленной этой сессией, никогда не
   использовавшейся для selection/death/stall.

   Дальнейшая проверка вскрыла и ВТОРУЮ проблему в ТОЙ ЖЕ функции: даже
   с реальным registry (`ML.build_audit_registry`, тот же приём, что уже
   использует `metrics_lib.py::process_run`), `slot_models`'s обход
   `CALL_COMPOSITE` возвращает модели СО ВСЕХ 4 слотов вложенного
   генотипа (READ/FORMAT/LOOKUP/COMPUTE), а не только с "соответствующего"
   слота — потому что вложенный `cx.*` в слоте 3 разворачивается в ЦЕЛЫЙ
   независимый 4-слотовый ASSEMBLE, а не в одну альтернативную модель для
   ЭТОГО ОДНОГО слота (подтверждено прямым чтением трассы: PAR-ветка слота
   3 предлагает "весь другой генотип целиком, оцени его as a unit" как ОДНУ
   из своих ветвей — семантика значительно мощнее, чем "ещё одна модель на
   этот шаг"). Статическая реконструкция "какие модели покрывают этот слот"
   через `ds.cells` в принципе ненадёжна при наличии вложенных composite
   ссылок. Исправлено переходом на уже готовые, авторитетные, трассо-
   основанные результаты: `arch2.fitness.resolved_set`/`load_results`

### Forensic (исправленная версия, см. выше)

Лучший генотип Phase 1 (`cx-e7b946`, seed 20262202, panel-выбранный,
`best_test_r=0.49`) НЕ идентичен ни B2, ни B3 bit-for-bit — это
действительно ДРУГАЯ структура, не переоткрытие эталона. Но на test:
49 задач и организм, и B3 решают ОБА; 2 задачи решает ТОЛЬКО B3; **0
задач организм решает такого, чего не решает и B3**. Множество решённых
организмом задач — строгое подмножество решённого B3. Организм исследует
структурно иные сборки, но ни разу не находит покрытие ЗА пределами того,
что уже даёт простой жадный greedy-cover (B3) — прямое, количественное
подтверждение корзины `B3_STACK` (не просто "не дотянул", а "структурно
не выходит за пределы уже известного стека"), а не артефакт узкой выборки
(тот же паттерн для best-panel-selected генотипа единственной лучшей
Phase-1 клетки — не выборочная случайность одного seed).

**Не исследовано здесь (вне рамок задания — P5/§0 запрещают)**: почему
именно organism не выходит за пределы B3's покрытия — механизм отбора
