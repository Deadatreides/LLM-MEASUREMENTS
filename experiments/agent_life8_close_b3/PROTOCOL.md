# PROTOCOL.md — agent_life8_close_b3

Написано ДО первого evolve (Phase 0's ceiling — единственные числа,
посчитанные до записи этого файла, и они CPU-only, детерминированы по
уже существующей сетке, не evolve). Не переписывается после того, как
числа увидены — интерпретация в BLOCKERS.md/REPORT_LIFE8.md, не сюда.

## 0. Рамка

Семь пакетов (LIFE-1..7) подтвердили complementary slot-HGT и, последним,
stall-from-improvement как продуктовый default — но НИ ОДИН ни разу не
пересчитал итоговую силу маршрута `r` против канонических B1/B2/B3
(самый повторяемый открытый пункт памяти проекта после LIFE-7). LIFE-8
закрывает именно это, одним проходом: сначала честно измерить потолок
(сборка vs язык), потом тратить бюджет в порядке от дешёвого к дорогому
(CPU-организм → CPU-склейка → только если всё ещё нужно — живой добор
языка).

Пишем только в `agent_life8_close_b3/`. Читаем `arch2/`, все
`agent_life2..7_*`, `agent_a5_live_m/`, `experiment11/`, `experiment14/`
— без правок. Grid: REUSE (копия LIFE-7, md5-проверена), 0 новых
`generate()` на исходных 6 моделях.

**Не сравнивать stall/Pareto/GATE в этом пакете** (P5) — организм
зафиксирован раз и навсегда.

## P1–P7

Задание ссылается на эту нумерацию, но определяет явно только P4 —
доопределено здесь из структуры задания (тот же приём, что LIFE-3's
самоопределённые R1-R4).

- **P1**: переиспользование сетки корректно — копия LIFE-7 (сама
  цепочка byte-identical копий с LIFE-3, `GEN_SEED=150002`/
  `SPLIT_SEED=20260821`) — это ТОТ ЖЕ сплит, на котором считаются
  B1/B2/B3/UNION; 0 новых `generate()` на исходных 6 моделях.
- **P2**: UNION — корректно определённый потолок: задача UNION-решена,
  если НЕЗАВИСИМО на каждом шаге хотя бы одна из моделей PASS-ит клетку
  этого шага. Это лучшее, чего МОГЛА БЫ достичь идеальная посегментная
  сборка с данным пулом моделей — верхняя граница, которую ни один
  реальный ASSEMBLE-генотип не может превысить (ASSEMBLE фиксирует ОДИН
  набор моделей на слот, не ретроактивно-идеальный выбор на задачу).
- **P3**: `GAP_LANG` (UNION_test − B3_test) — часть нехватки B3 до
  100%, которую НИКАКОЕ качество сборки не исправит (пул просто не
  покрывает некоторые шаги). `GAP_STACK` (B3_test − B2_test) — прокси
  того, насколько важен сам стек 3-vs-2, отдельно от языка.
- **P4** (дано дословно заданием): не добирать модели, пока не
  показано, что запас UNION-vs-B3 переживает лучшую попытку сборки —
  сначала качество сборки, потом язык.
- **P5**: "организм" ЗАФИКСИРОВАН на весь пакет как LIFE-7's
  подтверждённый default — комплементарный slot-HGT (`p=0.35`) +
  stall-from-improvement (`G_STALL=20`), обычная смерть D1/D2. БЕЗ
  Pareto-survival, БЕЗ gate-based stall, БЕЗ slot-safe mutate, БЕЗ
  carrier immunity, БЕЗ block registry. Этот пакет не пересматривает
  отбор (§0/§5 задания явно запрещают сравнивать stall/Pareto/GATE) —
  он только спрашивает, закрывает ли УЖЕ решённый механизм B3 при
  лучшем посеве или более богатом языке.
- **P6**: "склейка" Фазы 2 никогда не должна вручить организму готовое
  покрытие уровня B3 — ни один посевной генотип не несёт `|ImpSet|>=3`
  на gen 0 (гарантировано конструкцией: каждый glue-генотип — это
  однослотовая инъекция поверх baseline `b1`, тот же паттерн, что
  `lean_seeds.py` уже использует, просто с более длинным списком
  моделей на слот — проверено явным assert'ом, не просто заявлено).
- **P7**: отбор кандидат-моделей Фазы 3 полностью детерминирован
  (сортировка по id, первые K≤4, никогда "лучшие по интуиции") —
  обязательство против смещения, не оптимизация под результат; и как
  только Фаза 3 начата, цель — НОВЫЙ потолок (B3'/UNION' на расширенном
  алфавите), не старый B3 — честно сдвигать ворота, не держать старую
  лёгкую цель.

## Зафиксированные поправки после ревью пользователя (дословно, не
## только подразумеваются веткованием)

1. **`F1_FAIL` + 0 кандидатов Фазы 3 → `B3_FAIL`, отчёт, стоп** — ни
   Фаза 2, ни evolve Фазы 3 не запускаются. Выход из ветки гейтится
   ИСКЛЮЧИТЕЛЬНО `F1_FAIL`, не количеством кандидатов (которое всё
   равно проверяется — 0, подтверждено этой сессией — но только для
   записи в отчёт, не для решения о выходе).
2. **`LANG_POOR` → Фаза 2 пропущена → проверка кандидатов Фазы 3 →
   корзина `B3_CEILING`** при пустых/бесполезных кандидатах, **никогда
   `B3_STACK`** (`B3_STACK` требует именно `LANG_RICH`). Не путать эти
   две корзины в `classify_final`.
3. **Фаза 2 ОБЯЗАТЕЛЬНА при `LANG_RICH` и не `F1_B3`/`F1_FAIL`** —
   одинаково для `F1_NEAR` И `F1_MID`. `F1_NEAR` нигде не трактуется
   как "уже почти B3, можно выходить" — ни в ветвлении, ни в тексте
   отчёта; разница между `F1_NEAR`/`F1_MID` — только диагностическая
   метка для отчёта, не сокращение пути.
4. **17 донор-генотипов Фазы 2 идут ТОЛЬКО в `ev.archive`/`ev.
   genotypes`, НИКОГДА в `ev.population`, ни в какой момент прогона.**
   Проверено этой сессией (не только заявлено): D1/D2/`select_elite`/
   `_reserve_niches` перебирают `self.population`/`survivors`,
   производные от неё, никогда `self.archive` напрямую — генотипы,
   присутствующие только в `archive`/`genotypes`, структурно инертны
   для смерти/элиты. Явная runtime-проверка (не только design-claim):
   после каждого поколения assert, что 17 исходных donor id НИКОГДА не
   пересекаются с `ev.population`.
5. **`HSTEP.MODEL_IDS` патчится ТОЛЬКО внутри кода Фазы 3, никогда
   раньше.** Фаза 1 и Фаза 2 полностью завершаются (все `Evolution`/
   `Registry` построены и отработали) до того, как код Фазы 3
   (единственное место, трогающее `HSTEP.MODEL_IDS`) вообще запускается
   — заражения 6-модельных клеток не может произойти. Это свойство
   последовательного однопроцессного дизайна (Фаза 0→1→2→3 в одном
   `run_all.py`), не отдельный процесс — но сам патч живёт в ОДНОЙ
   явно помеченной функции `model_expansion.py::patch_model_ids`,
   никогда не на уровне импорта модуля и никогда не достижим из кода
   Фазы 1/2.

Также подтверждено ревью, без изменений плана: не сканировать `models/`
на незарегистрированные `.gguf` (раскрыть в BLOCKERS.md как "есть на
диске, не в registry, не брали"); не возвращать Pareto "на всякий
случай" (P5 абсолютен); не считать brute-force 1296 комбинаций —
`ceiling.py`'s B1/B2/B3/UNION достаточен.

## Phase 0 — потолок (готово ДО этого файла, числа зафиксированы)

Посчитано на panel и на test (`src/ceiling.py`):

| | r_panel | r_test |
|---|---|---|
| B1 | 0.3125 | 0.27 |
| B2 | 0.525 | 0.46 |
| B3 | 0.6125 | 0.51 |
| UNION | 0.6125 | 0.57 |

`GAP_LANG = 0.57 − 0.51 = 0.06`. `GAP_STACK = 0.51 − 0.46 = 0.05`.
Порог `GAP_LANG_THRESHOLD = 0.05` (не двигать после чисел, как и
задание требует).

**`GAP_LANG = 0.06 ≥ 0.05` → `LANG_RICH`.** Реальный запас существует —
UNION заметно выше B3 на СУЩЕСТВУЮЩИХ 6 моделях, так что если Фаза 1 не
закроет B3 сразу, Фаза 2 (склейка, не добор языка) обязательна следующим
шагом (поправка #3).

**Важная методологическая заметка (не путать регимы)**: эти B1/B2/B3
числа — с ЖИВОГО сплита (LIFE-3..7's `GEN_SEED=150002`/
`SPLIT_SEED=20260821`), НЕ то же самое, что "канонические" r=0.46/0.58/
0.70 из памяти проекта (та память — про OFFLINE `experiment14` сплит
ДО A5, другой режим целиком, не сравнимы напрямую). Память будет
скорректирована по итогам этого пакета.

## Phase 1 — организм на 6 моделях

`src/orchestrator.py::run_cell(ds, panel, screen, seed, out_dir,
phase="F1")` — LIFE-7's `WITH_B` вариант дословно (P5). 8 seed
`20262201..20262208`.

`R = mean(best_test_r)` по 8 seed; `Δ` против B1/B2/B3/UNION, знак
(sign) считается по числу seed, где `best_test_r` строго больше
соответствующего эталона (paired, по позиции seed) — простой mean+sign,
не CI (`F.paired_delta_r` рассчитан на сравнение ДВУХ ЖИВЫХ прогонов
внутри одного эксперимента с бутстрэпом по общим task_id; здесь один
операнд — фиксированное число (эталон), не распределение с тем же
`experiment_id`, так что CI-версия не композируется чисто без
дополнительной работы — решено ДО прогона, не после: mean+sign).

`classify_f1`:
```
F1_B3   : R > B3_test AND sign(vs B3) >= 6/8   -> package ends, B3_DONE
F1_NEAR : B3_test - R <= 0.03 AND R > B2_test   -> Phase 2 MANDATORY (поправка #3)
F1_MID  : else, R > B1_test                     -> Phase 2 MANDATORY (поправка #3)
F1_FAIL : R <= B1_test                          -> B3_FAIL немедленно (поправка #1)
```

## Phase 2 — склейка (только если `F1_NEAR`/`F1_MID` И `LANG_RICH`)

Подтверждено этой сессией прямым запуском, не предположено: `lean_
seeds.find_robust_pairs` на этой же сетке/панели находит РОВНО те же
4 (READ) + 2 (LOOKUP) + 4 (COMPUTE) = 10 двух-модельных PAR Imp=1 пар,
что карта LIFE-5, и `build_seeds_pop20_lean`'s "источник 1" уже строит
посвящённый посев под КАЖДУЮ из них (`P_single_slot_{kind}_{i}`) —
буквальное повторное добавление этих 10 было бы no-op. Настоящая новая
ценность — 17 ДРУГИХ PAR-сигнатур Imp=1 из карты LIFE-5 (3-5-модельные
комбинации, которые механизм `lean_seeds.py` из одних пар построить не
может): 3 на READ, 4 на LOOKUP, 10 на COMPUTE (`src/glue_seeds.py`,
читает `agent_life5_slot_map/metrics/per_slot_signatures.json` напрямую).

`lean-20 (20) + 17 новых = 37 > pop=24` — по собственному fallback
задания: **население остаётся неизменным lean-20** (pop=20, как в Фазе
1); все 17 новых генотипов вставляются НАПРЯМУЮ в `ev.archive`/`ev.
genotypes` (поправка #4) БЕЗ добавления их id в `ev.population` — так
`transfer_slot`'s `ctx["donors"]` видит их как валидных доноров с
поколения 0, но они никогда не конкурируют/размножаются/умирают как
члены популяции сами. Каждый — `|ImpSet|==1` по построению, проверено
`assert_glue_donors_single_slot` (P6).

6 seed `20262211..20262216`. `R2 = mean(best_test_r)`, sign ≥5/6.
```
F2_B3 : R2 > B3_test AND sign >= 5/6   -> package ends, B3_DONE
F2_NO : иначе                           -> Phase 3 (даже при LANG_RICH —
                                            склейка не добила не значит
                                            «сдаться»)
```

## Phase 3 — добор языка (только если не `F1_B3`/`F2_B3`)

`src/model_expansion.py::find_candidate_models`: `sorted(experiment11
registry) - {текущие 6}`, первые K≤4 (P7). **Подтверждено этой сессией
прямым чтением `experiment11/configs/model_registry.py`: этот список
пуст** (реестр содержит РОВНО те же 6 моделей, что уже используются, ни
одной больше — 7-й кандидат `Phi-3.5-mini-instruct-Q4_0_4_8` физически
на диске, но исключён из реестра самим `experiment11` из-за
несовместимого формата квантизации с установленным llama-cpp-python).
→ **`CLOSE_NEED_MODELS`** немедленно, без GPU-затрат. Код при этом
написан ОБЩО (реально перечитывает реестр, не хардкод `[]`) — останется
верным, если реестр когда-либо вырастет.

Если бы кандидаты БЫЛИ: собрать grid только для новых моделей (`new_
model × 4 kinds × train∪test`, отдельный файл `new_models_grid.json`,
исходные 6-модельные файлы не открываются на запись), floor = 80% от
`4*K*n_tasks`; патчить `HSTEP.MODEL_IDS` (поправка #5, только здесь);
пересчитать B1'/B2'/B3'/UNION' на расширенном алфавите (P7 — цель с
этого момента B3', не старый B3); lean-посев искать ЗАНОВО на новой
сетке (не копировать карту LIFE-5 — покрытие изменилось); 6 seed
`20262221..20262226`.
```
F3_B3  : R3 > B3'_test AND sign >= 5/6            -> B3_DONE
F3_OLD : R3 > старого B3_test, но не > B3'_test    -> B3_LANG
F3_NO  : иначе                                     -> ни то ни другое
```

## Итоговая корзина (§5 задания, вычисляется один раз, механически)

```
B3_DONE     : F1_B3 or F2_B3 or F3_B3
B3_LANG     : F3_OLD
B3_CEILING  : (Фаза 3 не достигнута ИЛИ CLOSE_NEED_MODELS) AND LANG_POOR
B3_STACK    : LANG_RICH AND F2_NO AND (CLOSE_NEED_MODELS or F3_NO)
B3_FAIL     : F1_FAIL (Фаза 3 не спасает — подтверждено: реестр пуст)
              OR floor генерации Фазы 3 не выполнен
B3_BLOCKED  : инфраструктура (копия сетки / смоук)
```

Given `LANG_RICH` уже подтверждён (Phase 0): при пустом реестре
кандидатов итоговые исходы этого конкретного прогона — **DONE / STACK /
FAIL** (не CEILING, поскольку `LANG_POOR` не выполнено; не LANG,
поскольку Фаза 3 не запускает evolve при пустых кандидатах) — это
нормальный, предсказанный расклад, не дыра плана.

`Next` строка выбирается механически из корзины, без обсуждения.
