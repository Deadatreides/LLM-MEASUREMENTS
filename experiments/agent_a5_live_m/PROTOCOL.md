# PROTOCOL.md — agent_a5_live_m

Написан и зафиксирован **2026-08-20, до первого вызова `generate()`**. Не
переписывается задним числом; если предрегистрированное правило вердикта
(§6) даст результат, который на вид выглядит неверно интерпретированным —
вердикт остаётся КАК ВЫЧИСЛЕН, интерпретация добавляется рядом, явно.

Четвёртый пакет поверх ASSEMBLE (`arch2/`, 5-й цикл), после `agent_a2_
assemble_budget/`, `agent_a3_mstar/`, `agent_a4_m_plateau/` — все три
работали ИСКЛЮЧИТЕЛЬНО offline-replay поверх `experiment14/runs14/
train_grid.json` и ни разу не звали настоящую модель. Этот пакет закрывает
прямой вопрос: держится ли результат под настоящими живыми вызовами, на
свежем независимом сплите, при отборе на полном/фиксированном сигнале, а
не на ротирующемся срезе 15-20 задач.

## §0. Изоляция

Пишет только в `agent_a5_live_m/`. Читает (не правит) `arch2/*`,
`experiment14/*`, `experiment11/configs/model_registry.py`,
`agent_a2_*/a3_*/a4_*` — только как источник паттернов для копирования, не
импорта (правило изоляции пакетов `agent_aN` друг от друга). Никаких pip/
venv/conda: окружение уже установлено глобально; при нехватке модуля —
запись в `BLOCKERS.md`, не самостоятельная установка.

## §1. ЖЁСТКОЕ определение LIVE для этого пакета (зафиксировано пользователем)

Live = ВСЕ метрики/фитнес этого пакета строятся ТОЛЬКО из `generate()`
через `experiment11/configs/model_registry.py` на задачах НОВОГО сплита
(§2). Запрещено как источник r/c/вердикта: чтение
`experiment14/runs14/train_grid.json` (и `test_grid.json`, если появится),
чтение любого `arch2` offline-replay grid, подстановка чисел A2/A3/A4.

Разрешено и обязательно: один раз заполнить
`agent_a5_live_m/metrics/live_grid/` вызовами `generate()` (кэш пустой на
старте кампании), затем и baselines, и все 5 эволюционных прогонов читают
ТОЛЬКО этот live_grid. Повторный `generate()` для уже успешно записанной
ячейки `(task_id, kind, model_id)` запрещён — это не «недостаточно live»,
это единственный способ уложиться в заявленный бюджет 1-2 часа GPU (сравнимо
по объёму с тем, как `experiment14/runs14/train_grid.json` сам был построен
живыми вызовами один раз: 2400 ячеек за 517с, `experiment14/runs14/
train_console.log`). Если `live_call_log.jsonl` не растёт во время
эволюции (шаг 4) — это ОЖИДАЕМО, не провал: все ячейки уже получены на
шаге 2.

## §2. Тестбед и сплит

Задачи — генератор `experiment14/tasks/heterostep.py`, импорт напрямую (НЕ
через `arch2/heterostep.py`, которое хардкодит старые seed'ы внутри
`Dataset.__init__` — вызывает `_tasks14.build_tasks()`/`split(...)` без
аргументов; проверено чтением файла).

- `N_TASKS = 200` — `build_tasks(n=200, seed=GEN_SEED)`.
- `GEN_SEED = 150001` (не пересекается с exp14's 140001).
- `SPLIT_SEED = 20260820` (не пересекается с exp14's 20260819) —
  `split(list(task_ids), seed=SPLIT_SEED)` → TRAIN=100, TEST=100.
- Ни одна TEST-задача не участвует в выборе маршрута/элиты/p_cross/моделей
  ни на каком шаге.
- 6 моделей эксп. 11 (`experiment11/configs/model_registry.MODEL_IDS`),
  без изменений.
- Параметры генерации: `temperature=0.5, top_p=1.0` (везде); шаговые вызовы
  `max_tokens_step=60`; целостные вызовы B0 `max_tokens_whole=200` (как
  плечо A эксп. 14).
- `LIVE_SEED_BASE = 5000` (не пересекается с exp14's 3000, arch2 E1's 2000).
- 3 шва — `experiment14/seams.py` (`numeric_seam`, `token_seam`,
  `check_step`, `whole_seam`), импорт без изменений. RESOLVED цепочки = PASS
  на каждом шаге (ASSEMBLE, SPEC.md §31).

## §3. Формула детерминированного per-ячейка seed

`seed = LIVE_SEED_BASE + stable_hash(task_id, kind, model_id) % 10**6`, где
`stable_hash` — **не** встроенный Python `hash()` (тот рандомизирован по
процессу для строк, `PYTHONHASHSEED`, не воспроизводим между прогонами), а
`int(hashlib.sha256(f"{task_id}|{kind}|{model_id}".encode()).hexdigest(), 16)
% 10**6` — детерминированное прочтение той же спецификации. Зафиксировано
здесь ДО первого вызова.

## §4. Живая сетка (шаг 2, единственная тяжёлая фаза `generate()`)

Модель-мажорный обход (тот же порядок, что доказанно быстр в
`experiment14/harness.py::run_train_grid`: 2400 ячеек за 517с на этой
машине): для каждой из 6 моделей — загрузка один раз, затем все
`(task_id, kind)` пары для ВСЕХ 200 задач (TRAIN∪TEST). Upstream для
зависимых шагов (COMPUTE зависит от READ/LOOKUP) — ПОДТВЕРЖДЁННЫЙ оракул, не
собственный ответ модели (та же дисциплина, что `run_train_grid`, строка
167: `upstream[step["name"]] = step["oracle"]`).

Каждый вызов дописывает одну строку в `metrics/live_call_log.jsonl`
(timestamp, model, task_id, step/kind, seed, n_in, n_out, ms, path_to_raw)
немедленно. После каждой модели — атомарная перезапись
`metrics/live_grid/{train,test}_grid.json` (резюмируемо: уже записанные
ячейки не перевызываются при перезапуске).

Цель: 200×4×6 = 4800 строк. Приёмочный минимум при вынужденной остановке:
≥ 6×4×120 = 2880 строк — ниже этого честный `BLOCKERS.md` объясняет
причину, недостача никогда не маскируется как полный прогон.

## §5. Baselines B0-B3 (шаг 3, чтение живой сетки, без новых вызовов для B1-B3)

B1/B2/B3 вычисляются функцией от данных (`arch2/heterostep_seeds.py::
b1_route/b2_route/b3_route`, импорт без изменений — читает только
`ds.models`/`ds.cells[...]["status"]`, не зависит от того, какими seed'ами
построен датасет) на `live_dataset`, а не хардкодятся числами A2/A3/A4.
Маршрут учится ТОЛЬКО на TRAIN, применяется на TEST без переобучения
(запрет hindsight).

B0 — лучшая ОДИНОЧНАЯ модель на целостном плече (не зафиксированная заранее
qwen3 — решено данными, тот же принцип, что и для B1-B3): live-вызов
`whole_prompt` для всех 6 моделей × 100 TRAIN (600 вызовов, выбор победителя
только по TRAIN), затем победитель — на 100 TEST (100 вызовов) для
held-out отчёта. Кэш — `metrics/live_grid/whole_grid.json` (отдельно от
шаговой сетки: другая форма промпта/бюджет токенов).

## §6. Эволюция (шаг 4, 5 независимых seed)

- `arch2.evolve.Evolution`, `arch2.genotype`, `arch2.mutate`, `arch2.runner`
  — импорт без изменений.
- `custom_reproduce`/`swap_assemble_slot` — КОПИЯ (не импорт) из
  `agent_a4_m_plateau/src/` с донор-пулом, исключающим `ev.references`
  (урок A3→A4, `orchestrator.py:150-160`).
- `p_cross = 0.60` фиксировано (не сканируется в этом пакете).
  `min_frac_local=0.25` → `effective_p_cross = min(0.60, 0.75) = 0.60` —
  клэмп НЕ включается на этом уровне (в отличие от A4, где 0.80/0.90 оба
  клэмпились к 0.75 и стали побитово идентичны) — фиксируется явно, чтобы
  не удивлять позже.
- **Фиксированная панель вместо ротации**: `control_slices=[panel_80]`
  (список длины 1 ⇒ `gen % 1 == 0` всегда — та же самая identical
  80-задачная панель на каждом поколении; механизм уже существует в
  `evolve.py:371` без единой правки). `screen_ids` = оставшиеся 20 TRAIN
  задач, не входящие в панель. И панель, и screen — подмножества TRAIN
  (100 задач); TEST не участвует в конструкции `Evolution` вовсе. Панель
  зафиксирована в `metrics/train_panel.json` до генерации 0.
- `pop=20` (состав — копия `build_seeds_pop20` A4, эталоны + структурно
  разные затравки), `max_gen=24`, `G_STALL=12`, `budget_per_task=3000`
  (унаследовано от A4 — достаточно для B3-подобных генотипов, тратящих до
  ~1550 токенов на отдельные задачи).
- Seeds: `20261201, 20261202, 20261203, 20261204, 20261205` — ровно 5, не
  меньше.
- Каждая оценка генотипа — попадание в `HeterostepBackend` (импорт без
  изменений) поверх `live_dataset.cells`, т.е. lookup в уже построенной
  живой сетке. Новых `generate()`-вызовов на этом шаге не ожидается.

## §7. Финальная оценка (шаг 5)

`archive_genotypes = [g for cid,g in ev.archive.items() if cid not in
set(ev.references)]` (тот же фильтр, что и для донор-пула — устраняет
класс дефекта, трижды всплывавший в A2→A3→A4). Полная TRAIN (100) и полная
TEST (100) оценка через `ev.evaluate(...)` (импорт без изменений,
резюмируемо по построению — уже записанные пары (комплекс,задача)
пропускаются). Топ-3 архива по `r` на full TRAIN (тай-брейк — меньший `c`)
+ B0-B3 — все прогоняются на full TEST. Парный bootstrap
(`arch2.fitness.paired_delta_r`/`bootstrap_efficiency`, импорт без
изменений, `n_boot=10000`) против B1 и против B3, с CI95.

Обязательная таблица snapshot (панель, `ev.generations[-1]["scores"]`) vs
archive (full TRAIN) для топ-3 — закрывает находку A3 про завышение
snapshot-вердиктов.

## §8. Предрегистрированные вердикт-корзины (ровно одна, считается по TEST)

**LIVE_ROUTE_WINS** ⟺ (на ≥4 из 5 seed: точечный ΔR(best_complex,B1) > 0 И
нижняя граница CI95 ≥ 0) И (на ≥4 из 5 seed: r(complex) ≥ r(B2) − 0.02).

**LIVE_PARTIAL** ⟺ на ≥3 из 5 seed точечный ΔR vs B1 положителен, но CI
пересекает 0, либо результат нестабилен между seed (ровно случай 3-из-5).

**LIVE_NULL** ⟺ иначе. Явно допустимый, не проваленный исход.

Обязательная строка вне корзины: mean ΔR vs B3 на TEST + CI95; запрет
формулировки «победили B3», если CI включает 0.

- `|live_call_log|` после шага 2 ≥ 6×4×120=2880 (цель 4800) — иначе
  `BLOCKERS.md`.
- Ни одного `open()` на `experiment14/runs14/*.json` или любой `arch2`
  offline-grid путь нигде в `src/`/`scripts/` этого пакета — проверяется
  вручную перед публикацией отчёта.
- Смоук (шаг 1) — до шага 2, обязателен.
- Если недоступны GPU/модели — только `BLOCKERS.md` с фактом, без
  offline-подмены.
- После шага 7: проверка, что ни один топ-архивный генотип не совпадает
  побитово (r,c) с эталоном B1/B2/B3 — сигнатура утечки донор-копирования
  (найдено в A3/A4); здесь структурно невозможна (донор-пул уже исключает
  эталоны), но проверяется и фиксируется явно по конвенции проекта.
