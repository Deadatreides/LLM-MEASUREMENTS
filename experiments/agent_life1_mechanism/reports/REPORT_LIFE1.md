# REPORT_LIFE1 — универсальный механизм сборки/наследственности/отбора

Спека: `PROTOCOL.md` (определения `Imp`/A/AB, пороги `MECH_*`, ветка Phase
B — зафиксированы до вычисления любых чисел). Кампания: инструментированный
CPU-replay поверх уже собранной живой сетки `agent_a5_live_m/metrics/
live_grid/` — **0 новых вызовов `generate()`**. Артефакты:
`metrics/lineage_audit.json`, `metrics/runs_instrumented/life1_s<seed>/
{archive.json,heredity.jsonl,summary.json,births.jsonl}` (5 seed,
20261201-05).

## 1. Рамка

Вопрос — не «какой маршрут лучше на 6 моделях HETEROSTEP», а какой
универсальный механизм (сборка блоков / горизонтальный перенос / отбор)
стабильно производит **совместное покрытие независимых блоков**. Полигон
HETEROSTEP+6 моделей — измерительный инструмент; результаты формулируются
в терминах slot/block/donor/coverage/archive (§6), маршрут-числа A5
(`REPORT_LA5.md`) используются только как источник данных, не как цель.

Ключевое методологическое решение (см. также «Находки» ниже): `agent_a5_
live_m` не сохранил родословную (`ev.edges`/`ev.archive`/`ev.generations`
никогда не писались на диск), поэтому Phase A здесь — не чтение
сохранённых логов, а **доказанно побитово идентичный повторный прогон**
(Gate R1/R2 ниже), инструментированный так, как `arch2/run_arch2.py`
делает это по умолчанию, а A5 — пропустил.

## 2. Gate R (воспроизводимость субстрата)

**R1**: единственный источник недетерминизма между отдельными запусками —
`heterostep_seeds._greedy_order`'s `set()`+`max()` тай-брейк (READ: точная
ничья 98/100 между `internvl3-2b-q4_k_m` и `qwen2.5-coder-1.5b-instruct-q4_0`
на первом шаге, ещё ничья на втором — 6 вариантов; FORMAT/LOOKUP/COMPUTE без
ничьих). Полный перебор всех 6 вариантов (`src/deterministic_route.py`)
нашёл **ровно один**, чьи 3 эталонных `complex_id` совпадают с
восстановленными из трасс архивного прогона A5 (seed 20261201: B1=
`cx-7b8668`, B2=`cx-7ddd67`, B3=`cx-df47df`) — совпадение **сразу**, без
неоднозначности.

**R2**: полный инструментированный повтор всех 5 seed A5 (20261201-05) на
найденном варианте. Результат — **5/5 точных совпадений** множества
`complex_id` архива с именами файлов `agent_a5_live_m/runs/a5_live_s<seed>/
cx-*.jsonl` (95/99/102/98/96 — совпадают с `archive_size` из
`agent_a5_live_m/metrics/per_seed_*.json`).

**Вывод: субстрат Phase A доказанно тот же прогон, что дал вердикт
`LIVE_ROUTE_WINS` в `REPORT_LA5.md`.** Не пересоздан «эквивалентный»,
а воспроизведён побитово.

**Побочная находка — исправление `agent_a5_live_m/BLOCKERS.md` находки 1.**
Та цитирует структуру B2's READ как `PAR(qwen2.5-coder, internvl3)`. Это
структура из УДАЛЁННОГО диагностического перепрогона (`runs_diag*`),
который взял **другую** ветку тай-брейка. Архивный прогон (доказано здесь
Gate R1/R2) имеет `B2 READ = PAR(internvl3, llama-3.2-1b)`. Вывод A5's
находки 1 («лидеры кластеруются на уровне B2, легитимно, не донор-копия»)
остаётся верным — правка касается только конкретной структуры,
процитированной как пример, не общего вывода.

## 3. Phase A: аудит

Определения — `PROTOCOL.md` §1: `Imp(s,g)=1` ⟺ покрытие слота `s` строго
больше, чем у лучшего одиночного атома на панели; A-событие — рождение,
где `ImpSet` выросло РОВНО на один слот (superset); AB-генотип —
`|ImpSet|≥2`. Считается только по эволюционным рождениям (`gen≥1`,
есть родитель) — затравочные AB (`P_par_*`, по 5 из 19 не-эталонных
затравок КАЖДОГО seed'а, по построению) публикуются отдельно, не
смешиваются со знаменателем (урок reference-leak, теперь в 5-й раз).

## 4. Корзина MECH_* (PROTOCOL.md §2, механически)

```
N_A = 7 (пул) < 10  →  MECH_UNKNOWN
```

Порог не сдвигался после того, как числа стали видны (запрещено
`PROTOCOL.md`). Формально пакет не может выбрать один из трёх механизмов —
но диагностика ниже (углублённый audit, обязательный по ветке
MECH_UNKNOWN/MIXED) показывает ПОЧЕМУ N_A так мал, и это само по себе
содержательный результат.

### 4.1 Почему N_A мал — распределение Δ|ImpSet| по 381 эволюционному рождению

| Δ|ImpSet| | рождений | доля |
|---|---|---|
| **0** (не изменилось) | 238 | 62% |
| **+1** (A-событие) | 7 | 1.8% |
| **−1** (потерян слот) | 135 | 35% |
| **−2** | 1 | 0.3% |

Прирост на 2+ слота за одно рождение — **0 случаев**. Из 238 «не
изменилось» — 129 это AB-генотип, унаследовавший AB-статус БЕЗ нового
события (родитель уже был AB, слот, дававший это, не тронут). Значит
совместное покрытие в архиве держится в основном ПЕРЕДАЧЕЙ уже
достигнутого состояния через рождения, которые его не трогают, а не
активным наращиванием — рост (+1) в **19 раз** реже потери (−1).

### 4.2 По оператору — где именно теряется и где приобретается

| оператор | n | gain | loss | unchanged | loss/gain |
|---|---|---|---|---|---|
| M1 (замена молекулы) | 106 | 0 | 35 | 71 | ∞ |
| M2 (сдвиг параметра) | 17 | 0 | 0 | 17 | — (сетка параметров вырождена для CALL, см. ниже) |
| M3 (структурный) | 58 | 0 | 7 | 51 | ∞ |
| M5 (arch2's горизонтальный перенос) | 40 | 1 | 8 | 31 | 8:1 |
| M6 (компрессия в композит) | 8 | 0 | 5 | 3 | ∞ |
| **SWAP_SLOT** (оператор A5, `p_cross=0.60`) | **152** | **6** | **81** | 65 | **13.5:1** |

M2 не даёт ни прироста, ни потери: сетка параметров CALL в HETEROSTEP —
одна точка (`temperature/prompt/seed_slot/max_tokens` зафиксированы), M2
может только сдвигать BUDGET-лимит, что не трогает `ImpSet`.

**Главная находка**: `SWAP_SLOT` — оператор, СПЕЦИАЛЬНО добавленный A5 для
межслотовой рекомбинации — даёт БОЛЬШЕ всего и приростов (6 из 7 A-событий
в пуле), И больше всего потерь (81 из 173 суммарных потерь по всем
операторам). Отношение потеря:прирост для него — 13.5:1, хуже, чем у M5
(8:1), и структурно хуже, чем у операторов, которые вообще не переносят
между слотами (M1/M3/M6 дают только потери, 0 приростов, потому что не
СПОСОБНЫ давать прирост межслотовой сборки по конструкции — это ожидаемо,
не находка).

**Почему `SWAP_SLOT` теряет так часто**: он выбирает донора по
skeleton/semantic-similarity (`donor_score_fn`, унаследовано из arch2's M5
без изменений) — то есть по тому, НАСКОЛЬКО ПОХОЖ донор целиком на
элитных особей, а не по тому, лучше ли КОНКРЕТНО ПЕРЕНОСИМЫЙ СЛОТ у донора,
чем у реципиента. Прямое измерение: из 152 применений `SWAP_SLOT`, только
**6 (4%)** оказались `slot_match` — случаем, когда у донора
`Imp(перенесённый_слот)=1`, а у реципиента `Imp(тот_же_слот)=0` (§ таблица
выше, `N_M5_slot_match`). В 96% случаев донор выбран без учёта того, несёт
ли он что-то ЛУЧШЕЕ именно в этом слоте — отсюда 13.5:1 потерь.

## 6. Переносимое правило (без имён моделей)

> В системе с языком «блок = слот, донор = архивный/живой конкурент,
> отбор = Парето по (r,−c,u)», оператор горизонтального переноса,
> **выбирающий донора по структурному/фенотипическому сходству ЦЕЛОГО
> кандидата, слепой к тому, превосходит ли донор реципиента ИМЕННО в
> переносимом блоке**, даёт перенос с высоким отношением потерь к
> приростам (наблюдалось 13.5:1) — потому что бóльшая часть переносов
> случайна относительно локальной пользы конкретного блока. Прямое,
> измеримое предсказание: замена критерия выбора донора на
> **комплементарное покрытие блока** (донор допустим для переноса блока
> `s` только если `Imp(s, donor)=1 ∧ Imp(s, recipient)=0`) должна поднять
> долю `slot_match`-переносов с ~4% к значению, близкому к 100% по
> построению, и по прямому следствию — снизить отношение потерь к
> приростам для этого оператора. Это не проверено (Phase B не запускался,
> §5) — это точное, фальсифицируемое предсказание для следующего пакета,
> сформулированное ДО его прогона.

Второе, более слабое наблюдение: совместное покрытие блоков (`overlap=1.00`
во всех seed) НЕ является узким местом само по себе — независимые блоки
постоянно сосуществуют в живой популяции. Узкое место — именно
неселективность оператора переноса, не отсутствие материала для переноса.

## 7. Не заявляется

- **Не заявляется**, что горизонтальный перенос — единственная причина
  малого N_A; M1/M3/M6 тоже дают только потери (по конструкции — они не
  умеют комбинировать слоты вовсе), это не сравнение «SWAP_SLOT хуже
  остальных», а «SWAP_SLOT — единственный, кто МОГ БЫ, и делает это плохо».
- **Не заявляется** превосходство предложенного правила (§6) — оно не
  проверено интервенцией в этом пакете.
- **Не заявляется** перенос механизма за пределы полигона HETEROSTEP+6
  моделей — гипотеза сформулирована в общих терминах (§6), но проверена
  только здесь.
- **Не заявляется** ослабление находок `REPORT_LA5.md`/`agent_a5_live_m/
  BLOCKERS.md` — только точечное исправление одной цитируемой структуры
  (§2), сам вывод A5 подтверждён независимо этим пакетом.
- `arch2/` и другие `agent_aN` пакеты не изменялись; в этом пакете не
  было ни одного вызова `generate()`.
- `MECH_UNKNOWN` — явно допустимый исход по PROTOCOL.md, не провал задания.

## 8. Дальше

**Рекомендация с высокой уверенностью** (обоснована §4.2, не гипотеза
вслепую): следующий пакет должен реализовать РОВНО один рычаг —
комплементарный-по-покрытию выбор донора для `SWAP_SLOT` (точно рычаг
`MECH_RECOMB` из `PROTOCOL.md` §4, `transfer_slot`) — и измерить те же
метрики (`Δ N_AB`, `Δ P(B|A)`, loss:gain по оператору) на новых seed
(20261301-05), не трогая ничего другого. Это не по формальной корзине
(та вышла `MECH_UNKNOWN`), а по прямому количественному диагнозу §4.2,
который можно опровергнуть измерением.

Что стоит добавить в логи, если этот класс аудита будет повторяться:
per-birth diff (какой ИМЕННО слот изменился) для M1/M3/M6, не только для
`SWAP_SLOT` — сейчас это восстанавливается постфактум структурным диффом
дерева (сделано здесь для Imp, не для общего «что изменилось»), но нативная
запись в `births.jsonl` избавила бы от необходимости передиффовывать деревья
в каждом новом audit-пакете.
