## 5. Статические наблюдения по коду

### 5.1 Production scoring не равен lab scoring

В `orchestrator.py:357` `acceptance_probe` по умолчанию `None`, а в `orchestrator.py:632` gate используется только если probe явно подставлен. В обычном `run_step` финальная оценка идет через `self.scorer.q_env(final_answer, task_type)` без тестов.

В `core/scorer.py:216` есть `q_env_fine`, но она возвращает полезный test-ratio только при наличии тестов и разрешенного sandbox-исполнения. На Windows без `MYCELIUM_ALLOW_WINDOWS_CODE_EXEC=1` кодовый execution feedback ограничен защитным путем.

Вывод: лабораторные цифры из `lab/run_experiment.py` не являются поведением обычного `main.py` без специальной подмены scorer/probe.

### 5.2 `_split_into_blocks` есть, но основной depth-loop фактически монолитный

`orchestrator.py:965` содержит `_split_into_blocks`, однако `orchestrator.py:1010` запускает `_run_depth_loop` поверх `initial_answer` и `draft_texts`, а внутри используется один `block_id` вида `step-N`.

Это совпадает с документацией: блочная blackboard-идея описана, но не доведена до реальной работы по AST/функциям.

### 5.3 DPO-пары могут быть межзадачными

`core/memory.py:409` реализует `SQLiteStore.get_pairs`: выбираются top/bottom traces по `e_total`. По статическому чтению нет ограничения, что chosen/rejected относятся к одной и той же задаче.

`agents/trainer.py` использует этот источник для DPO-данных. Значит DPO-обучение может сравнивать разные задачи, что плохо согласуется с preference learning для одного prompt.

### 5.4 Phi в гиперцикле остается математически инертным

В `core/hypercycle.py:77` начинается update. `phi` вычисляется и ограничивается `phi_min`, но затем входит как общий знаменатель для всех каст, после чего вектор нормализуется. Общий множитель сокращается.

Это уже зафиксировано в `tests/test_mechanisms.py:116` и `FIX_PLAN.md:102`, то есть не новая гипотеза, а подтвержденное состояние.

### 5.5 Композитный `QualityScorer.score()` не подключен к основному контуру

`core/scorer.py:355` содержит `score()` с весами и composite quality, но в `orchestrator.py` основной шаг использует отдельные `q_ext`, `q_env`, `EmergenceMetric.compute_base` и ручную сборку reward.

Это подтверждает пункт `FIX_PLAN.md:604`: часть конфигурационных весов качества сейчас фактически не управляет поведением.

### 5.6 Search отключен корректно

В `config/settings.yaml` `search.enabled: false`. В `orchestrator.py:445` `search_task` не создается, если search отключен.

Для read-only/offline этапа это важно: внешний поиск не должен случайно стартовать.

### 5.7 Инициализация и запуск пишут состояние

`MyceliumOrchestrator.__init__` создает каталоги `logs`, `swarm/*`, `data`, загружает/готовит bandit/memory/blackboard/search. Runtime-пути также пишут telemetry, SQLite, FAISS, graph, bandit state и эволюционные артефакты.

Поэтому на этом этапе корректно было не запускать код и тесты.

### 5.8 Версионные подписи расходятся

В заголовках кода встречается `Σ_v8.5`, `README.md` начинается с `Σ_v8.8.1`, runtime log в `orchestrator.py:380` пишет `Mycelium v8.9 initialized`, `opencode_bridge.py` указывает v8.9.2.

Это не функциональный дефект, но ухудшает восстановление состояния проекта.
