## Что выяснилось по ходу и меняет план

**1. Φ в гиперцикле инертен, правка «убрать alpha из Φ» бесполезна.** `x_new[c] = x[c]·(1+a·k[c]·x_prev)/(1+a·Φ)` — знаменатель ОБЩИЙ для всех каст, а следующая строка делит на `sum(x_new)`, и общий множитель сокращается точно. Значит `Φ`, `phi_min` и вся защита «от деления на нулевое Φ» из аудита v8.5 не влияют ни на что. Проверено численно: `phi_min` 0.05 против 0.9 даёт совпадение до 1e-12. **Из плана Ш2.3 этот пункт убран**, остались мутация и Multinomial.

**2. Ш2.3 бесполезен до Ш1.3.** Симуляция на измеренном разрыве каталитических констант (`max(k)−min(k) = 0.084`, из `hypercycle_k` прогона) показывает: правки не помогают. Помогают при разрыве ~0.54 — а такой даёт только переход с `q_ext` на `q_env`, у которого динамический диапазон в **6.4 раза** шире (0.800 против 0.125). Порядок жёсткий: сначала Ш1.3, потом замерить фактический разрыв, потом Ш2.3.

**3. λ_L телескопируется — это не показатель Ляпунова.** `Σ ln(dᵢ/dᵢ₋₁) = ln(d_последн/d_первое)`, то есть величина определяется **двумя граничными дельтами окна из двадцати**, а путь между ними не влияет вообще. Те же 40 дельт в другом порядке дают −0.808 вместо +0.599. Наблюдавшийся диапазон [−2.089, +0.155] — в основном шум границ. Добавлен флаг `fix.lyapunov_regression`: наклон МНК по всем точкам окна.

**4. Коэффициентов PID не хватает даже с исправленным интервалом.** При `kp=0.5, ki=0.1`, затухании интеграла 0.97 и устойчивом λ_L≈0.6 нужно **шесть** срабатываний, чтобы `round(6+u)` сдвинулся на единицу. При интервале 10 это 50 шагов, при исходном 50 — 250. Коэффициенты не трогал: это отдельная правка после замера, чтобы не менять две вещи разом.

**5. `granite-3.1-1b-a400m-base` — это `granitemoe`.** Обнаружено отсечкой MoE. 400M активных параметров из 1B, и bnb до слитых экспертов не дотягивается. Второй независимый повод убрать её из пула, помимо отсутствия chat_template.

**6a. Пер-агентная награда вырождалась из-за шкалы q_env, а не из-за числа генераторов.** Формула `_q_code_safe`:

```python
return 1.0 if ratio == 1.0 else max(0.4, ratio * 0.8)
```

схлопывает **всё с `ratio ≤ 0.5` ровно в 0.4**. Черновик, прошедший 0 тестов из 4, и черновик, прошедший 2 из 4, неразличимы. Замерено на прогоне: 0.4 — это 12 из 20 черновиков; из 7 шагов с одинаковой наградой пять были «обе 0.4», и только две — честная ничья «обе решили верно».

Проверка на контролируемом наборе из пяти решений с разной долей пройденных тестов: `q_env` даёт **3 различных значения из 5**, непрерывный `q_env_fine` — **5 из 5**.

| решение | q_env | fine |
|---|---|---|
| 4/4 | 1.000 | 1.000 |
| 3/4 | 0.600 | 0.787 |
| 2/4 | **0.400** | 0.575 |
| 1/4 | **0.400** | 0.362 |
| 0/4 | **0.400** | 0.150 |

Решение: `code_detail()` — один запуск песочницы, сырой результат; `q_env` строит из него **прежнюю** шестиуровневую шкалу (сравнимость с прошлыми прогонами сохранена), `q_env_fine` — непрерывную для награды. Порядок смыслов сохранён: синтаксическая смерть (0.0) хуже, чем «0 из N тестов» (0.15).

**6b. Критики получали оценку синтезатора**, то есть для бандита были неотличимы от него. Добавлен `fix.critic_loo`: пересинтез без критики каждого критика, `r_j = 0.5 + (q(итог) − q(итог без j))`. Это и есть marginal contribution из «Анализа Sigma_v6.7». Цена — по одному вызову синтеза на критика; на GGUF это +30–50 % ко времени шага, при API-пуле было бы неприемлемо.

После обеих правок награды разошлись: `coder15_b=0.678 smol360=0.616 qwen3_17=0.801`, LOO даёт `qwen05=0.500 smol17=1.000`.

**6c. Награда пер-агентная, но не пер-ролевая — а шкалы у ролей разные.** Найдено на прогоне `sh1_30` при проверке гейта 1.

| роль | шкала награды |
|---|---|
| G | абсолютное качество черновика, 0.15…1.0 |
| S | `0.5 + (синтез − лучший черновик)` — центрировано на 0.5 |
| C | `0.5 + (итог − итог без этой критики)` — тоже на 0.5 |

Одна `mu` на агента смешивает три разные шкалы, и ранжирование начинает зависеть от того, **какие роли агент чаще играл**, а не от того, насколько он хорош в роли, под которую его сейчас отбирают. Наблюдалось прямо: `mu(qwen3_17)=0.616` выше `mu(coder15_a)=0.599`, при одиночном baseline 0.569 против 0.684. Нижние три агента при этом легли верно (ρ = +0.714) — сигнал уже нёс информацию, путался только верх.

Решение — `fix.per_role_mu`: `mu_role` / `sigma_role` / `calls_role` по паре (агент, роль). Это не усложнение: `bandit.select` **и так** вызывается по одной касте за раз (`allowed_roles=['G']`), то есть состояние приводится к тому, как оно уже используется. Пер-ролевая статистика сохраняется в `bandit_state.json` — иначе терялась бы при каждом перезапуске, а оркестратор создаётся заново на каждое условие.

Три теста: что скалярная `mu` **переставляет** сильного и слабого генератора при разных пропорциях ролей, что пер-ролевая порядок восстанавливает, и что она переживает save/load.

**7. Пять падающих тестов в `test_operational_hardening.py` — доэксплуатационные.** Нет пакетов `schedule` и `fastapi`; `groq` отсутствует в локальном пуле, поэтому `_record_provider_results` пропускает неизвестный id; один падал на `open()` без кодировки. Кодировку починил, остальное — окружение и конфиг, к правкам отношения не имеет. Сейчас 22 зелёных, 4 красных.

## Ф1.1 Рантайм: чем гонять кванты без LM Studio

Проверил окружение: Python 3.11.9, torch 2.13.0+cu126, GTX 1660 SUPER 6144 МиБ, RAM 23.9 ГБ, драйвер 571.96. `bitsandbytes 0.50.0` **установлен**. `llama_cpp` — нет. `nvcc` — нет, то есть компилировать нечем, нужен готовый wheel.

Три варианта, и два из них тупики:

| Вариант | Вердикт |
|---|---|
| **transformers + GGUF** | тупик. В transformers 5.x GGUF разжимается в fp32 при загрузке (`modeling_gguf_pytorch_utils.py:791`) — установлено в собственном MoE-зонде, `trace-probe/HONESTY.md` §7. Экономии памяти ноль |
| **transformers + bitsandbytes NF4** | **рабочий, ноль установок.** bnb уже стоит. Для плотных моделей `load_in_4bit` подменяет `nn.Linear` на `Linear4bit` — проверено там же (§7: у плотных работает, у слитых MoE-экспертов нет; у нас все плотные) |
| **llama-cpp-python + GGUF** | лучше по памяти и скорее быстрее на Turing, но требует установки готового wheel (`--extra-index-url https://abetlen.github.io/llama-cpp-python/whl/cu124`). Риск нештатный, компилятора нет. **Апгрейд фазы 2**, не фазы 1 |

**Выбор фазы 1 — bnb NF4.** Обоснование не «удобнее», а «меньше диффа»: `lab/llm_server.py` продолжает работать целиком — с микро-батчингом, остановкой по закрытому код-блоку и HTTP-формой, которую `call_model` уже умеет. Тот же харнесс дал 240 записей и 0 падений; менять его в фазе, где узкое место — математика, а не ток/с, значит менять инструмент измерения одновременно с измеряемым.

Две правки в `llm_server.py`, обе локальные:

1. `_ensure_loaded`: добавить `quantization_config=BitsAndBytesConfig(load_in_4bit=True, bnb_4bit_quant_type='nf4', bnb_4bit_compute_dtype=torch.float16)`, `device_map={'': 0}`.
2. **Удалить своп.** `_on_gpu`, `.to('cuda')/.to('cpu')` и `STATS['swaps']` уходят: 4-битные bnb-слои нельзя надёжно перемещать между устройствами, и именно поэтому кванты и позволяют держать все модели резидентно. Это не потеря, а то, ради чего кванты и берутся: своп сейчас 1.0–2.8 с, первая загрузка с диска 30–35 с.

Что теряется от отказа от свопа: ничего. Что теряется от bnb вместо GGUF: место на **диске** — bnb квантует при загрузке, на диске остаются fp16 safetensors (~8 ГБ на четыре новых модели). Если диск важнее скорости внедрения — это и есть аргумент за GGUF в фазе 2.

Отдельно поправить в **коде**, а не в обёртке харнесса: таймаут. Сейчас 600 с выставляется снаружи, в `lab/run_experiment.py`, то есть тестируется конфигурация, отличная от штатной. Перенести в `models.yaml` как `timeout: 600` на модель.

## Ф1.2 Модели: 4 новых, все без гейта

Требование не «шесть штук», а: **6 агентов** (заполнить `alloc {G:2, C:2, S:2}` при K_ACT=6), **≥3 семейства** (чтобы `D_sem` перестал быть 0.072), **≥4 уровня качества** (чтобы μ было что разделять) и **контролируемые пары** — одно семейство, известный разрыв. Пары важнее числа: они дают чистый ответ на «Thompson разделяет по качеству или по стилю».

| # | Репозиторий | fp16 диск | NF4 VRAM | Роль в замере |
|---|---|---|---|---|
| 1 | `Qwen/Qwen2.5-Coder-1.5B-Instruct` | ~3.1 ГБ | ~1.1 ГБ | сильный на коде — верх μ |
| 2 | `Qwen3-1.7B` — **уже скачан** | есть | ~1.2 ГБ | сильный общий; преемственность со старым baseline |
| 3 | `HuggingFaceTB/SmolLM2-1.7B-Instruct` | ~3.4 ГБ | ~1.2 ГБ | средний, третье семейство, инструкт-тюн вместо базовой granite |
| 4 | `HuggingFaceTB/SmolLM2-360M-Instruct` | ~0.7 ГБ | ~0.3 ГБ | **пара к #3**: то же семейство, разрыв 1.7B/360M |
| 5 | `Qwen/Qwen2.5-0.5B-Instruct` | ~1.0 ГБ | ~0.5 ГБ | **пара к #1**: Qwen2.5, разрыв 1.5B/0.5B; низ μ |

Итого VRAM при NF4 ≈ **4.3 ГБ** + KV при ctx 2048 → влезает в 6144 МиБ с запасом, **все пять резидентно, свопа нет**. Диск: ~8.2 ГБ новых загрузок.

Пять моделей → 5 агентов; шестой — дубликат #1 с другим `temp_offset`. Все — ungated, HF-логин и принятие лицензий не нужны. Llama-3.2 и Gemma-2 сознательно не берутся: оба семейства gated, а Gemma-2 вдобавок не имеет роли `system` в шаблоне, а `call_model` её всегда отправляет.

**Роли — всем шести `[G, C, S]`.** Не расписывать вручную: M−swap показал, что раскладка ролей не тот рычаг, а Thompson с гиперциклом должны разложить сами. Иначе Ш0.1 не проверяет ничего.

**`provider` — свой на каждую модель** (`local_qwen_coder`, `local_smol17`, …), тогда `max_per_provider: 2` снова что-то значит.

**`granite-3.1-1b-a400m-base` выводится из пула.** Базовая модель без chat_template в роли критика — не «слабый агент», а шум в роли, от которой зависят `mean_e_by_caste` и вся критика для синтезатора.

**Существующие fp16 не удалять** (`models/Qwen3-1.7B`, `Qwen3-0.6B`, `granite-*`): понадобятся, чтобы воспроизвести старый baseline при сомнениях в сравнимости.

## Ф1.3 Протокол работы: два уровня прогона

Полный прогон — 8 условий × 30 задач — занял 6 ч 34 мин. Итерировать на таком цикле нельзя. Два уровня:

| Уровень | Состав | Время | Когда |
|---|---|---|---|
| **smoke** | 10 задач, условия M + BoN-G | ~25–40 мин | после каждой правки |
| **gate** | 30 задач, полный набор условий | ~6 ч, ночью | только на границах Ш0/Ш1/Ш2 |

Итерации — на smoke, гейты — на gate. Smoke не годится для решений о ±2 SEM, он годится ровно для одного: **не сломалось ли и активировался ли механизм**. Проба инвариантов (Ш0.3) применима к smoke целиком, потому что «K_ACT принял >1 значения» не требует статистики.

Что делает это осуществимым: `lab/run_experiment.py:480-481` пишет `f.write(...)` + `f.flush()` **на каждую запись**. Значит частичный прогон читается на ходу, и незачем ждать конца, чтобы понять, что пошло не так. Это условие протокола, а не удобство — если добавляются поля, они должны писаться там же, на шаге, а не агрегироваться в конце.

Разделение обязанностей:
* прогоны запускаются в фоне, с чекпоинтом на задачу, так чтобы обрыв не обесценивал сделанное;
* после каждого прогона — проба инвариантов и дельта к предыдущему замеру, а не «всё ок»;
* какие поля добавить в запись — решается по ходу, от вопроса, который возник; поэтому телеметрия и растёт из диалога, а не проектируется заранее.

Честное ограничение: шестичасовой прогон нельзя наблюдать непрерывно. Отсюда требование к чекпоинтам и к тому, чтобы каждая запись была самодостаточной — это не перестраховка, а следствие того, кто и как читает лог.

### Ш0.1 Пул моделей: 6 разных вместо 3×3 реплики

**Зачем.** В условии M на шаге ровно **2 кандидата** (alloc G=2), и это две реплики одной модели с одной температурой. В **25 из 30** задач их `q_env` совпадает до значения, `D_sem = 0.072`. Ниши, fitness sharing, max-2-per-provider и дискриминация Thompson в такой конфигурации не имеют предмета. Ответ на вопрос «трёх моделей мало?» — да, но дело не только в числе.

**Три правки, по возрастанию цены:**

1. **Температура на реплику (бесплатно, делать первым).** Сейчас `bandit.get_temperature()` возвращает одно значение на весь шаг, и все реплики получают `temperature`, `temperature*0.8`, `temperature*0.7` по касте — внутри касты одинаково. Достаточно дать каждой реплике свой оффсет в `models.yaml` (`temp_offset: -0.15 / 0 / +0.15`) и умножать на него в `call_model`. Это даёт дисперсию внутри касты без скачивания чего-либо. Проверить на 5 задачах: `len(set(q_env_candidates))` должно стать > 1 в большинстве шагов.

2. **Заменить granite-3.1-1b-a400m-base.** Это **базовая** модель без chat_template; отчёт §9.8 отмечает, что она пересказывает задание. Критик, который не умеет критиковать, — это не «слабый агент в пуле», это шум в роли, от которой зависит `mean_e_by_caste` и вся критика для синтезатора. Замена одной модели здесь важнее добавления четвёртой.

3. **Расширить пул.** Конкретный проверенный состав — в §Ф1.2 выше: пять моделей, ~4.3 ГБ VRAM при NF4, все резидентно, все ungated, две контролируемые пары внутри семейств. Критерий отбора важнее числа: нужны **инструкт-тюны с заметно разным качеством на одном типе задач**, иначе μ бандита нечего разделять. Каждую модель перед включением в пул прогнать в одиночку: 30 эталонных решений MBPP (должны дать 1.0) и 10 задач соло — это и есть baseline из замера ниже.

4. **Каждую модель — своим `provider`.** Все агенты сейчас `provider: local`, поэтому `max_per_provider` пришлось поднять с 2 до 9, и ограничение стало нефункциональным. Если завести `provider: local_qwen17`, `local_llama32` и т.д., `max_per_provider: 2` снова начинает что-то значить, и rate-limit guard становится проверяемым. Token bucket при `max_rpm: 999` не мешает.

**Замер до перехода:** прогнать одиночный baseline каждой модели (30 задач, без оркестрации) — таблица «модель → q_env → solved». Без неё нельзя будет сказать, разделил ли Thompson модели правильно: не с чем сверять.

**Критерий прохода Ш0.1:** `len(set(q_env_candidates)) > 1` в ≥ 70 % шагов; известен одиночный baseline каждой модели пула.

### Ш0.2 Переформулировать критерий эмерджентности

`E_score = Q_syn − max_i Q_i` на дискретной шестиуровневой шкале почти не может быть положительным: в **14 из 30** задач M лучший кандидат уже дал `q_env = 1.0`, там `E_score ≤ 0` по построению. Считать:

* **главное** — агрегатный `q_env` и `solved` против BoN-G при равном бюджете **по всем токенам, включая prompt** (сейчас считаются только completion, и фора у BoN больше заявленных 7 %);

* **новая величина: recovery rate** — доля задач, где хотя бы один кандидат имел `q_env = 1.0`, а финальный ответ — нет. Это прямая мера потерь селектора, и в M она уже видна: task 159 `cand=[0.4, 1.0] → final 0.4`, task 164 `cand=[0.533, 1.0] → final 0.5`. Две задачи из 30, где правильное решение было получено и потеряно. Эту величину надо гнать в ноль, и она чувствительнее, чем `q_env`.

## Ш1. Сигнал

Здесь основной ожидаемый эффект. Пять правок, каждая локальная.

### Ш1.1 Единицы бюджета (R3) — одна строка

`orchestrator.py:604`: `budget=self.budget_tokens / 3600` — это токенов **в секунду** (222), подставляется как бюджет **шага**. `min(cost/budget, 1) == 1.0` в **197 из 198** шагов; cost-член — константа −0.1213, это **86.6 %** средней `E_total`.

**Проверка:** дисперсия `cost/budget` по прогону > 0; ни один шаг не на клипе 1.0.

### Ш1.2 Тесты в контур (R2)

`run_step` вызывает `self.scorer.q_env(final_answer, task_type)` **без** `tests` (`orchestrator.py:543`). При `tests=None` → 0.7 на Linux или `min(_q_code, 0.3)` на Windows. Весь контур работает по `_q_code` — эвристике, антикоррелирующей с истиной (corr от −0.139 до −0.422).

* Провести `tests` до `q_env` штатным путём, а не подменой скорера в харнессе (`TestAwareScorer` из `lab/run_experiment.py` — костыль для замера, в проде его нет).
* Там, где тестов нет, **не возвращать 0.7**. Возвращать `None` и исключать член из формулы: отсутствие сигнала не должно выглядеть как средний сигнал. Это отдельный класс дефекта — он уже дважды обнулял замеры (отчёт §9.2: без pytest `_q_code_safe` молча возвращал 0.0 для всех решений, включая правильные, и выглядел рабочей метрикой).
* Для задач без готовых тестов — генерировать проверки из условия или property-based; но это **после** Ш1, отдельным шагом.

### Ш1.3 Пер-агентная награда (R1) — главная правка

`_build_bandit_rewards` (`orchestrator.py:710-735`) раздаёт всем агентам шага одно число. Доказательство, что это убивает всё: после калибровки μ = 0.4988 и σ = 0.3570 **у всех девяти агентов до 4-го знака** — granite (базовая, выдаёт мусор) и Qwen3-1.7B неразличимы. Отсюда же: все энергии сходятся к одной точке ≈ 4.5, между death=0 и split=8.1 → **0 событий death/split за весь лог**; `k_i` каст почти не расходятся.

Ввести marginal contribution — то, что было прописано в «Анализе Sigma_v6.7» как `ΔE_i = E_total(с i) − E_total(без i)`, и дёшево аппроксимируется без пересчёта:

| Каста | Награда |
|---|---|
| Генератор i | `q_env(draft_i)` — свой собственный, уже считается на строке 453 и сейчас выбрасывается |
| Синтезатор | `q_env(Y_syn) − max_i q_env(draft_i)` — ровно та величина, которую система и объявляет целью |
| Критик j | `q_env(Y_syn) − q_env(Y_syn без критики j)` — leave-one-out по уже собранным критикам; при 2 критиках это один дополнительный дешёвый вызов синтеза на шаг |

Если один дополнительный вызов на шаг дорого — на первом проходе дать критикам общую награду синтезатора, но **генераторам обязательно свою**. Половина эффекта — уже в этом: генераторов больше всего, и именно их качество определяет `oracle`.

Всё остальное (μ_i, σ_i, энергии, `k_i` гиперцикла, LinUCB) начинает работать автоматически — оно и было спроектировано под этот вход.

### Ш1.4 LinUCB обновлять сыгранной рукой (R1b)

`bandit.py:342-344`: `chosen_temp = self.temp_bandit.select(ctx)` — обновляется рука, которая лучшая **сейчас**, а не сыгранная. Самоподтверждающийся контур, контрфактика не собирается. Прокинуть `temperature` из `run_step` в `bandit.update`.

Заодно два знаковых дефекта из R10, они здесь же: `samples[aid] = np.random.normal(...) * latency_penalty` — для отрицательного сэмпла штраф работает как бонус; `rank_noise = uniform(0,0.1) * probs` — больше всего шума достаётся лидеру, задумано было наоборот.

### Ш1.5 Пороги на квантили (каскад R3)

`flow_threshold = 0.7`, `evolution_threshold = 0.8` откалиброваны под шкалу `E_total`, которой нет. Из-за этого `PhysarumGraph.add_flow` не создал **ни одного** flow-ребра, а git-коммит эволюции не срабатывал никогда. ### Ш1.6 Traceback обратно в синтез — вне очереди

Обоснование — прогон **M−swap**. Гипотеза «синтезатор слабее генератора, поэтому не может улучшить» проверена и **отвергнута**: с Qwen3-1.7B на синтезе `E_score` остался отрицательным (−0.049), 0 положительных из 30, причём места для улучшения было **больше** (22 задачи с запасом против 16, потолок достигнут в 8/30 против 14/30).

Значит дело в процедуре. Промпт синтезатора (`orchestrator.py:488-497`) — «combine the drafts and address all critique points», и **ни слова о том, что именно неверно**, потому что этого никто не знает: `q_env` в синтез не передаётся. Синтезатор решает «объедини тексты», а не «исправь ошибку». Естественный исход — воспроизвести самый уверенный черновик; при попытке объединить два разных получается склейка, ломающая парсинг: **все 5 регрессов в M — это 0.4 → 0.2, то есть SyntaxError**, а не ошибка логики.

Правка: после `q_env` черновиков передавать синтезатору не только тексты, но и результат исполнения — какой черновик прошёл сколько тестов, и текст ошибки. Зависит от Ш1.2, поэтому здесь, а не раньше. Дешевле любого другого пункта Ш3–Ш4 и адресует единственный результат, который держится во всех восьми условиях.

**Тесты Ш1:** юнит на `_build_bandit_rewards` (разные награды на разные касты); юнит на конверсию бюджета; интеграционный из Ш0.4 (μ расходятся) должен позеленеть.

**Прогон Ш1:** M, BoN-G, M−fixed на новом пуле, 30 задач. Плюс абляция `M−reward` (вернуть общую награду) — она измеряет вклад именно Ш1.3.

**ГЕЙТ Ш1** (все четыре):
1. `spread(μ)` между лучшей и худшей моделью пула > 0.1, и порядок μ согласуется с одиночным baseline из Ш0.1;
2. `#flow_edges > 0`, дисперсия `cost/budget > 0`;
3. `recovery rate` снизилась относительно baseline;
4. `q_env(M) − q_env(BoN-G)` вышел за ±2 SEM хоть в какую-то сторону.

**Если гейт не пройден — стоп.** Дальше не идти. Это будет означать, что оркестрация не даёт ничего сверх параллельного сэмплирования даже с исправленным сигналом и разнородным пулом, и Ш2–Ш4 не имеют смысла. Результат содержательный, его надо зафиксировать, а не обходить.

### Ш2.4 Термодинамика — сначала решить, нужна ли

Три независимых обнуления:

1. **Порядок операций** — `_run_depth_loop` кладёт `final_answer` в блок до `compute_thermodynamics` → ΔH ≡ 0 → Φ ≡ 0. Закрыто флагом `depth.thermo_causal_fix`, по умолчанию выключен. Включить.
2. **Модуль стирает знак** — `Φ = |d_eS| − d_iS`. Φ>0 получается одинаково при упорядочивании и при деградации. В контрфактике отчёта Φ = 0.50035 возникла при ΔH = −0.5003, то есть при **росте** энтропии, и 3 из 4 приведённых примеров — с ΔH < 0. Φ измеряет величину изменения, не пользу. Убрать модуль: `Φ = ρ·ΔH·q_env − d_iS`.
3. **d_iS ≡ 0 по масштабу** — `π_r = max(0,ΔH)/c_r · q_env`, `c_r = max(1, tokens_used) ≈ 900`. При ΔH ~ 0.1 получается π_r ~ 1e-4, `d_iS ~ 1e-8·edges ≈ 0`. Не делить на абсолютное число токенов — нормировать на средний расход.

Плюс: `alive` не читается **нигде**; `effective_entropy` умножает H блока на topology_bias из графа памяти, что принцип §9.1 собственного `ARCHITECTURE.md` прямо запрещает («Смешивание G_B и G_M запрещено»).

**Но перед этим — решить, нужен ли контур вообще.** Свидетельств, что он несёт полезный сигнал, пока нет: `corr(Φ, solved)` в условиях с 2–3 ненулевыми Φ даёт **−0.141, −0.172, +0.187, +0.358** — знак случайный, это шумовой пол корреляции, а не измерение. ## Ш3. Память и контекст на PTG

### Ш3.0 Что PTG действительно даёт, и чего не даёт

**Не даёт.** PTG не закрывает R1 (пер-агентная награда), R2 (execution feedback), R3 (единицы бюджета), R5 (константы гиперцикла), R6 (сэмплирующий PID). Это те пять, которые объясняют измеренный ноль. Поставить PTG раньше Ш1 — значит добавить хорошо сделанный слой поверх контура, который не различает granite от Qwen, и получить тот же ноль с более красивой памятью.

**Про «тупую нарезку» — проверил, и вывод против моей же первой догадки.** Гипотеза «`[:800]` рубит код-блок посередине, синтезатор видит битый код и выдаёт битый» на текущих данных **не подтверждается**: длины черновиков в M — медиана 347 символов, максимум 1503, за 800 выходят **5 из 60**; из 7 регрессов только один (task 158) имел черновики длиннее 800. `_fit_model_context` при ctx=2048 на MBPP тоже не срабатывал — промпты не доходили до бюджета. То есть слепая нарезка — **латентный** дефект, а не причина измеренных провалов. Честно сказать это надо, иначе PTG продаётся под ложным предлогом.

Где она перестаёт быть латентной:
* `context_from_memory = '\n'.join(f"[past] {p['answer'][:200]}" for p in past)` — работает **всегда**, 200 символов от каждого из 5 прошлых ответов. Это не контекст, это обрубки;
* `_truncate_words` при превышении бюджета вырезает **середину** промпта и вставляет `...[truncated]...` — на реальном API-пуле (24 модели, ответы по 2–4 КБ, ctx 8192) и на задачах сложнее MBPP это будет срабатывать постоянно;
* `critiques = '\n'.join(r['text'][:400] for r in c_ok[:2])` — критика третьего критика отбрасывается целиком, независимо от содержания.

**Даёт (реально).**

| Механизм PTG | Что заменяет в Мицелии |
|---|---|
| `Archive` + типизированные рёбра `continues/reinforces/contradicts/fixes/refines/supersedes` | `PhysarumGraph` (R8): рёбра между **соседними по времени** трассами, не создающиеся никогда, PPR от **прошлой** задачи, без анти-коагуляции |
| Anti-coagulation CASE A–E, `_local_semantic_density` | ровно то требование «не дать графу превратиться в полносвязную кашу» из `глубина/гемини 3.txt`, которое в Мицелии решено одной константой `competition_decay: 0.02` |
| `reinforces` вместо дедупликации | сейчас похожие трассы либо дубли, либо ничего |
| `assemble_context_snapshot(seeds, char_budget)` — greedy по приоритету, дедуп по id, разрешение `supersedes`, relations на 1 хоп, `provenance`, `context_entropy` | `[:200]/[:800]/[:400]` и вырезание середины |
| `search_branch_first` | `faiss.search` + PPR от `_last_trace_id` |
| `find_unresolved()` — головы веток без продолжения | ничего. Это и есть цель для депт-лупа из Ш4 |
| `resolve_supersession` | ничего |

`context_entropy = −Σ p·log p` по нормированным `final_weight` включённых чанков — это осмысленная величина («снапшот однобокий или размазан»), в отличие от H(π) по AST одного ответа. **Но** она измеряет контекст, а не ответ. Подставлять её вместо энтропии блока — значит повторить ту же ошибку, из-за которой система платит за удаление кода. Использовать как диагностику и как вход в приоритет retrieval — да; как гейт депт-лупа — нет.

### Ш3.1 Шим эмбеддера — обязателен, делать первым

`ptg_core.Archive.__init__` жёстко ставит `self.embedder = Embedder()` (строка 1138) — LM Studio, без точки инъекции. Два независимых препятствия:

1. **Разные пространства.** Мицелий использует BGE-m3 + E5-small → 1408d через `sentence_transformers`. PTG-документация прямо предупреждает: модель обязана совпадать, косинус между разными пространствами бессмыслен. Два эмбеддера в одной системе — гарантированная тихая порча.
2. **VRAM.** 6 ГБ. `PTG_EMBEDDER.md` §9.2 документирует реальный инцидент **на этом же железе**: embedding-модель при ctx 8192 требует ~8.4 ГБ, батч из 17 текстов обрабатывался 121 секунду, LM Studio выгрузил рабочую модель посреди сборки. Держать LM Studio с эмбеддером рядом с тремя генерирующими моделями на 1660S нереально.

**Решение:** duck-typed шим, подменяющий `archive.embedder` **после** конструктора. Требуемая поверхность (по факту использования в `ptg_core`): `.embed(texts) -> np.ndarray (N, dim)` нормированные, `.dim`, `.model`, `.backend`, `.test_connection(preferred_model=None) -> True`, `.fallback_used`, `.probe_error`. Внутри — `memory.embedder.encode` Мицелия. Порядка 30 строк, `ptg_core.py` не трогается.

Кэшировать вектор запроса: Мицелий уже посчитал `task_vec`, `search_branch_first` посчитает его второй раз (47 мс на CPU).

**Проверка:** `Archive` строится на 20 синтетических атомах через шим, `save()` → новый процесс → `load_if_exists()` → `search_branch_first` возвращает осмысленный порядок. Плюс проверить, что `embedder_dim` в `meta_tree.json` записался как 1408, и что жёсткая остановка при смене модели (ПАТЧ 18) не срабатывает ложно.

### Ш3.2 PTG вместо PhysarumGraph

Программная вставка поддерживается: `_add_atom(atom)` — это то, что `build()` зовёт на каждый атом, и ПАТЧ 16 уже использует его напрямую для синтетических атомов структуры проекта (строка 1501). Форма атома: `{id, file, order, question, answer, text, confidence, timestamp, vec, session_id, source_path, filename, folder_path}`. Векторы должны быть нормированы — `np.dot` используется как косинус.

Отображение:

| Мицелий | PTG-атом |
|---|---|
| `prompt` | `question` |
| `final_answer` | `answer` |
| `prompt + answer` | `text` |
| `f"step-{step}"` | `file` / `source_path` (сентинел, как `__project_structure__`) |
| `task_vec` | `vec` |
| `e_total` / `q_env` | `confidence` |

Заменить в `Memory`: `faiss.search + ppr_search` → `search_branch_first`; `add_flow` → `_add_atom` (решение continues/reinforces принимает PTG по матрице CASE, а не порог `e_total > 0.7`, которого никогда не бывает).

**Что при этом уходит и это нормально:** Levy flight и `_compute_pagerank` живут внутри `decay_all()`, который зовётся раз в 100 добавлений и на 30-шаговых прогонах не срабатывал **никогда**. Терять нечего.

**Что надо удержать:** append-only PTG не удаляет узлы, `nodes.json` грузится целиком (§15: streaming не реализован). Для прогонов на 30–5000 шагов это не проблема; для бессрочной работы — тот же класс дефекта, что растущий без вытеснения `SemanticBlackboard.blocks`. Зафиксировать как известное ограничение с порогом (например, ротация архива по эпохам), не делать вид, что решено.

**Замер:** латентность вставки и поиска на шаге. Бюджет — десятки мс, а не секунды. `_add_atom` делает traverse по всем ветвям; при тысячах ветвей это перестанет быть бесплатным, измерить на 1000 атомах до интеграции.

### Ш3.3 Контекст для синтезатора и генератора через `assemble_context_snapshot`

Это прямой ответ на вопрос про PTG и отбор контекста по дереву.

* **Генератору** вместо `context_from_memory` (5 обрубков по 200 символов) — снапшот с явным `char_budget`, посчитанным из `ctx − max_tokens` конкретной модели, а не из общего `_fit_model_context`. Seeds — результат `search_branch_first(task)`.
* **Синтезатору** — снапшот, в который черновики и критика входят как **атомы с типизированными рёбрами** (Ш3.4), а не как склеенная строка. Приоритет включения у PTG уже правильный: сначала seeds полностью, потом `supersedes`-разрешение, потом `contradicts/fixes/refines` на 1 хоп, потом lineage превью. При нехватке бюджета режется хвост, а не середина осмысленного текста.
* `truncated_by_budget` и `context_entropy` — в телеметрию. Первое покажет, как часто бюджет реально жмёт (сейчас это неизвестно вообще), второе — не свалился ли контекст на один узел.

**Проверка:** абляция `M−ptgctx` (снапшот против нынешней склейки) на одинаковом пуле и бюджете. Именно эта абляция и отвечает, стоило ли оно того. Ожидание честное: **на MBPP эффект близок к нулю**, потому что бюджет там не жмёт (§Ш3.0). Гнать эту абляцию надо на задачах, где контекст реально большой — иначе она измерит шум.

### Ш3.4 Типизированные рёбра из вывода критика

Работа критика — «identify logical errors, gaps and contradictions». Результат уходит в строку `critiques` и исчезает. У PTG для этого есть ровно те типы рёбер: `contradicts`, `fixes`, `refines`, `supersedes`.

Минимальная версия без парсинга свободного текста: критик отвечает структурированно (`{target: draft_id, relation: contradicts|refines|fixes, claim: ...}`), из этого строятся рёбра между атомами черновиков. Тогда:

* синтезатор получает не «вот три мнения», а граф «черновик A противоречит B в этом месте, C уточняет A»;
* `edges_by_type("contradicts")` даёт список неразрешённых конфликтов — вход для Ш4;
* `resolve_supersession` даёт «последнюю правду» по цепочке правок вместо накопления версий.

Это то место, где PTG перестаёт быть заменой памяти и становится тем, чего в Мицелии не было вообще.

### Ш3.5 Code-PTG для задач типа `code`

`code_ptg_v2` импортирует тот же `Archive` и добавляет структурные рёбра `contains/calls/implements/tests/imports` **напрямую, в обход эмбеддинг-графтинга** — обоснованно: для кода источник истины есть (AST), гонять детерминированный факт «A вызывает B» через косинусный порог — понижение качества.

Применение: на задачах, где есть окружающий код (не MBPP-однострочники), генератор получает не «весь файл, обрезанный по бюджету», а `deps(target)` / `risks(target)` — только реально связанные карточки. Это самостоятельная ценность, но она проявится только на задачах с проектным контекстом. **На MBPP не даст ничего** — там нет проекта. Поэтому: реализовывать после того, как появится второй корпус с проектными задачами, не раньше.

**Гейт Ш3:** `M−ptgctx` замерена на корпусе, где бюджет реально жмёт; латентность вставки/поиска в пределах десятков мс; шим не подмешивает второе эмбеддинг-пространство (проверено `embedder_dim == 1408` в `meta_tree.json`).

## Ш4. Стигмергия

Это то, что спроектировали в обсуждениях и не реализовали. Гипотеза о эмерджентности проверяется **здесь**, а не в Ш1–Ш3. До этого шага все механизмы просто приводятся в рабочее состояние.

Из «Анализа Sigma_v6.7», раздел «что оставить»: **marginal contribution** (сделано в Ш1.3) и **execution feedback** (Ш1.2) — предпосылки. Дальше:

### Ш4.1 Блоки вместо монолита

`_split_into_blocks` в `orchestrator.py` **написан и не используется**: депт-луп работает с одним блоком `step-N`, содержащим весь ответ. Вернуть: ответ → набор блоков (AST-функции), у каждого своя H, свой счётчик неудач.

### Ш4.2 Агенты выбирают блок

`P(агент i → блок r) ∝ x_каста · Ẽ_i · exp(H_r/T) · exp(−n_r/3)` — из `глубина/meta2.txt`. Рой слетается туда, где больно, вместо переписывания всего ответа. Цель для выбора — `find_unresolved()` + `edges_by_type("contradicts")` из Ш3.

Важное предупреждение из того же «Анализа Sigma_v6.7» — что выкинуть, и что **до сих пор не выкинуто**:

| Предписано выкинуть | Состояние |
|---|---|
| `entropy = 1 − mean(cos)` | выкинуто в v8.9 (заменено PPR) ✓ |
| `prob = exp(H/T)` без центрирования | **осталось** в `blackboard.probabilities` ✗ |
| `while total_entropy > 0.15` | выкинуто ✓ |
| **выбор одного `chosen_block` на всех** | **осталось**: `select([block])` при единственном блоке ✗ |
| **entropy-score, независимый от качества** | **осталось** ✗ |

Ш4.2 обязан закрыть три оставшихся, иначе он воспроизведёт ровно ту ошибку, от которой предупреждали: «Система должна вознаграждать снижение неопределённости в проблемных блоках… Иначе selector начнёт культивировать хаос».

### Ш4.3 DPO-пары внутри одной задачи

`SQLiteStore.get_pairs` сортирует все трассы по `e_total` и парит `rows[i]` с `rows[mid+i]`: `prompt` берётся у chosen, а `rejected` — ответ на **другую задачу**. Обучение «предпочитай тему A теме B». Переписать на пары из кандидатов одного шага — их теперь несколько и у каждого есть свой `q_env` из Ш1.3.

Ночной DPO ни разу не запускался, так что до Ш4 это чистая теория. Не начинать, пока Ш1 не даст осмысленную награду.

## Ш5. Уборка

Ноль эффекта на качество, но снимает ложные сигналы «механизм есть».

* Дубликат `call_model` (`orchestrator.py:105-113`) — мёртвый, затирается вторым определением на строке 114.
* `QualityScorer.score()` — **не вызывается нигде**. Композитная `Q = w_ext·Q_ext + w_env·Q_env + w_cons·consistency − w_lat·lat − w_cost·cost + w_info·ΔI` со всеми весами из конфига мертва целиком. Либо подключить в Ш1.3, либо удалить вместе с весами.
* `consistency()`, `NoveltySignal`, `precision_obs`, `HybridEmbedder.set_search_priority` (метод скопирован не в тот класс) — то же решение.
* `sigma_min = np.sqrt(cfg['sigma_min']**2)` — тождество через abs.
* `main.py:218` — `schedule.every(1).hours` вне охраны `if schedule is None` → падение на старте без пакета `schedule`.
* `SemanticBlackboard.blocks` (блок на шаг, без вытеснения), `LeakyIntegrator.history` (безлимитный список) — ограничить.
* `rho_bar = 1/len(self.blocks)` → по мере накопления блоков ρ всех сползает к клипу 0.01.
* `LeakyIntegrator`: gain = `1 − decay` = 0.0015 против 0.0117 по спеке; вклад `0.0015·ΔI ≈ 1e-6`, на 4 порядка ниже проектного. Аудит v8.5 предписал `0.051·clip(ΔI·100, −1, 1)` — не применено. Решить: применить или снять член.

## Порядок и точки остановки

```
Ш0  ──► новый baseline на новом пуле (старые числа несравнимы)
     │
Ш1  ──► ГЕЙТ: μ разделились? recovery rate упала? разрыв с BoN-G вышел за 2 SEM?
     │        нет ──► СТОП. Зафиксировать результат, не обходить.
     │        да  ──► дальше
Ш2  ──► проба инвариантов зелёная, абляции стали осмысленны
     │        + решение по термодинамике: M vs M−Φ
Ш3  ──► PTG: шим ─► память ─► контекст ─► типизированные рёбра
     │        абляция M−ptgctx на корпусе, где бюджет жмёт
Ш4  ──► стигмергия. Здесь и только здесь проверяется исходная гипотеза
Ш5  ──► уборка, параллельно чему угодно
```

Три вещи, которые нельзя делать в обратном порядке:

1. **Ш0.1 перед всем.** Иначе Thompson дискриминирует между репликами одной модели — то есть между шумом, — и любой результат Ш1 нечитаем.
2. **Ш1 перед Ш3.** PTG поверх контура с одинаковой наградой даст тот же ноль с более красивой памятью.
3. **Симуляция гиперцикла перед правкой гиперцикла** (Ш2.3). 20 строк, минута счёта, и они бы сэкономили весь путь до сюда.

Про число моделей, коротко: скачивать стоит, но сначала сделать Ш0.1 п.1 (температура на реплику, бесплатно) и п.2 (заменить базовую granite на инструкт-тюн). Критерий отбора — **разное качество на одном типе задач**, не разнообразие ради разнообразия: μ бандита должно иметь что разделять, и разделение надо сверять с одиночным baseline каждой модели.
