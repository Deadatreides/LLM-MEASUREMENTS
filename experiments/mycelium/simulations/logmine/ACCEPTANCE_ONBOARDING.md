# Часть C. Офлайн-пересчёт приёмки

## C.0. Сверка — и почему она важнее результата

Тесты корпуса уже разбиты на именованные `test_0/test_1/test_2`, поэтому
по-ассертный результат берётся парсингом `pytest -v`, расщеплять файл не нужно.

Прежде чем считать что-либо, харнесс сверен с прогоном: восстановленная `q_env`
против записанной в `sh2_200` по всем 1387 текстам.

```
сопоставлено 1387, расхождений 1 = 0.07 %
```

Единственное расхождение — задача 462, `product(lst, repeat=len(lst))`:
экспоненциальная по времени, в прогоне уложилась в 10 с (`q_env` 0.4), у меня
при восьми параллельных воркерах не уложилась в 20 с (`timeout`, 0.1). Это
артефакт параллелизма, а не разницы в семантике.

**Первая версия сверки не прошла: 85 % расхождений.** Причина была у меня —
в `pytest` флаги `-v` и `-q` вместе, и `-q` гасит `-v`, из-за чего построчных
`::test_0 PASSED` не появлялось и всё превращалось в `no_tests_ran`. Без этой
сверки я бы получил «гейт не даёт ничего» на сломанном харнессе. Это ровно
класс ошибок из `HANDOFF §3.3`, и ловится он только тем, что величина сверяется
с известной.

## C.1. Цена расщепления ассертов (§B.2)

`test_0` → приёмка, `test_1` и `test_2` → оценка.

```
solved по трём ассертам (историческое): 58/200 = 29.0 %
solved по двум оценочным:               64/200 = 32.0 %
дрейф +3.0 п.п.,  вверх 6 задач, вниз 0
```

Порог §B.2 — 3–4 п.п. Дрейф **на нижней границе порога**: сравнение с
`sh2_200` формально остаётся возможным, но все числа части D должны
публиковаться на двухассертной шкале, с явным указанием, что 29.0 % старой
шкалы соответствуют 32.0 % новой.

Направление дрейфа единственно возможное: убрав ассерт, задачу нельзя сделать
труднее — 6 задач вверх, 0 вниз.

**Оговорка, которой в задании нет.** §B.2 предлагает запасной вариант: «если в
промпте задачи уже виден пример-ассерт — использовать его, тогда расщепление не
нужно». Здесь этот вариант не существует: в `corpus200` **все три ассерта видны
в промпте у всех 200 задач**, и это ровно те же ассерты, что в тест-файле.
Отдельного примера, не входящего в оценку, нет. Расщепление — единственный
способ, и §B.2 применён в основной редакции.

**Что расщепление делает с наградой** (§D просил проверить):

```
вырожденность q_env_fine по черновикам:
   по трём ассертам: 116/198 = 58.6 %   (в логе прогона 58.0 % — сходится)
   по двум оценочным: 120/198 = 60.6 %
цена: +2.0 п.п. вырожденных шагов
```

Расщепление ухудшает различимость награды, но на 2 п.п., а не в разы. Брать
приёмочный ассерт «из промпта вместо расщепления» нельзя (см. выше), так что
эти 2 п.п. — неизбежная цена.

*Здесь я сначала померил не то:* сравнивал **состав** пройденных ассертов
вместо их **доли**. Состав тоньше доли, и на нём расщепление ложно выглядело
улучшением (64.1 % → 60.6 %). В награду идёт `q_env_fine = 0.15 + 0.85·ratio`,
то есть доля; на ней расщепление ожидаемо ухудшает.

## C.2. Насколько силён сам приёмочный ассерт

Поскольку все три ассерта видны в промпте, кандидат, захардкодивший примеры,
проходит приёмку, не решив задачу. Это внутренний потолок одноассертного гейта,
и он измерен:

```
кандидатов, прошедших test_0:            422
из них проваливших test_1 и test_2:       76 = 18.0 % [14.6 %, 22.0 %]
```

Восемнадцать процентов прошедших приёмку — не решения. Гейт всё равно
окупается (ниже), но его потолок задан этим числом, и увеличением числа
приёмочных ассертов он двигается только за счёт оценочной шкалы.

## C.3. Трёхступенчатый гейт (§B.3)

Пул кандидатов шага: 2 черновика + до 4 синтезов (основной + LOO-пересинтезы)
+ пост-депт-лупный итог, медианно 7.

```
ступень 1 (импортируется):  оставляет медианно 7
ступень 2 (test_0 прошёл):  оставляет медианно 2; никто не выжил на 87 шагах
ступень 3: argmax q_ext среди выживших (результат ступени 2 бинарен, поэтому
           решает тай-брейкер)
```

Запасной ход, которого в §B.3 нет и который пришлось определить: если ступень 2
не оставила никого (87 шагов из 200), выбираем `argmax q_ext` среди
импортируемых; если и таких нет — среди всех. Иначе на 43 % шагов гейт не
определён.

```
solved на шкале из двух ассертов:
   фактический выбор (s_ok[0] + депт-луп):     64/200 = 32.0 %
   гейт, пул = черновики+синтезы+итог:         93/200 = 46.5 %   (+14.5 п.п.)
   гейт, пул по §B.3 без итога:                93/200 = 46.5 %   (+14.5 п.п.)
   оракул по всему произведённому:             97/200 = 48.5 %

f2 = P(взятое не проходит | проходящее было), n = 97
   было:  0.3402 [0.2536, 0.4390]
   стало: 0.0412 [0.0162, 0.1013]      порог 0.11 ВЗЯТ (верх ДИ 0.101)
```

Гейт добирает 14.5 из 16.5 доступных п.п. — то есть 88 % разрыва приёмки.
Вариант «без итога» даёт то же самое: пост-депт-лупный ответ не приносит
ничего, чего не было бы в синтезах.

## C.5. BoN-G — посчитать нельзя, и это надо чинить в части D

`run_experiment.py` пишет для BoN-G только `q_env_candidates` и
`q_ext_candidates` — списки чисел. **Текстов кандидатов нет**, поэтому
по-ассертно пересчитать ветку невозможно, и `f1` после гейта не считается ни
при каких допущениях.

Что считается: потолок ветки на двухассертной шкале, границами по шкале `q_env`
(значение 0.5333 = 2 из 3, но какой именно провалился — неизвестно):

```
потолок BoN-G: от 67.8 % (только заведомо решённые) до 75.4 % (все спорные — в плюс)
точечная оценка переносом условных долей из M: 70.1 %
   (из M: при 2 из 3 провалившийся — приёмочный в 30.2 % случаев)
```

**Требование к части D:** сохранять тексты кандидатов BoN-G. Иначе §B.4
(«одинаковый механизм приёмки в обеих ветках, из одной функции») останется
непроверяемым ровно в той ветке, против которой идёт сравнение, — а §B.4
прямо предупреждает, что односторонняя починка обесценивает вывод.

## §3. Gemma — системная роль: опасение снимается чтением шаблона

В шаблоне Gemma нет роли `system`, но он **сам** складывает её в первый
пользовательский ход:

```jinja
{%- if messages[0]['role'] == 'system' -%}
    {%- set first_user_prefix = messages[0]['content'] + '\n\n' -%}
    {%- set loop_messages = messages[1:] -%}
```

То есть предписанное §3 «складывать инструкцию в начало первого
пользовательского сообщения» делать руками **не надо** — и не надо ничего
менять в `llm_server.py`. Из трёх возможных поведений (сложит / молча отбросит /
упадёт) реализовано первое, самое безопасное. Проверено на отрендеренном
промпте: инструкция видна внутри `<start_of_turn>user`.

Стоп: `eos_token_id = 1` (`<eos>`), а ход заканчивается `<end_of_turn>`. Это
выглядело как риск, но смоук показал `finish_reason=stop` **3 из 3** —
llama.cpp относит `<end_of_turn>` к end-of-generation. Мусора после кода нет.

## §4. Llama — своё, без правок

Системная роль поддерживается и раскладывается в
`<|start_header_id|>system<|end_header_id|>`. `eos_token_id = 128009` — это
`<|eot_id|>`, то есть терминатор хода, а не `<|end_of_text|>`; остановка
работает, `finish_reason=stop` 3 из 3.

Шаблон подставляет дату (`Today Date: 11 Aug 2026`) в системный блок. На
результат не влияет, но делает промпт невоспроизводимым между днями — если
понадобится точное воспроизведение, дату надо фиксировать.

## §3/§4. Двойной BOS — нет ни у одной

Проверено на уровне токенов, а не текста. `Jinja2ChatFormatter` подставляет
`bos_token` как **пустую строку** (BOS детокенизируется в `''`), а llama.cpp
добавляет ровно один BOS при токенизации:

```
Gemma:  первые 4 токена [2, 105, 2364, 107]          BOS один
Llama:  первые 4 токена [128000, 128006, 9125, 128007]  BOS один
```

# Что дальше и чего не хватает

**Часть D (прогон приёмки) разблокирована**, но перед запуском нужно два
изменения в `lab/run_experiment.py`, оба следуют из этой работы:

1. **сохранять тексты кандидатов BoN-G** — иначе ветка снова непроверяема
   (§C.5), и требование §B.4 нельзя будет подтвердить;
2. **писать в запись шага результат каждой ступени гейта** и то, что выбрали бы
   `s_ok[0]` и `argmax q_ext` — §D просит сравнивать старую и новую приёмку
   внутри одного прогона, а не между прогонами.

Сама правка приёмки в `orchestrator.py:577` и в BoN **не сделана**: §B.4
требует один общий механизм из одной функции для обеих ветвей, и это правка
контура, а не разбора. Офлайн-подтверждение, ради которого §C и ставился,
получено — величина эффекта известна заранее (+14.5 п.п., f2 = 0.041), и если
прогон разойдётся с ней, это само по себе находка.

**Отборочный прогон пула** (`TASK_POOL_CANDIDATES`, ~2061 вызов) технически
разблокирован смоуком, но `lab/pool_candidates.py` из §Реализация ещё не
написан, и обе задачи конкурируют за одну видеокарту. Порядок из
`TASK_ACCEPTANCE` («приёмка → пул») я не менял.

**Незакрытое:** конфаунд квантования (§1) — решение за вами, докачивать ли
`Llama-3.2-1B-Instruct-Q5_K_S` до прогона.
