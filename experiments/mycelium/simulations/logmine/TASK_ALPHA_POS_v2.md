# Поправки к заданию на замер alpha_pos

Исходное задание — `TASK_ALPHA_POS.md` (в `simulations/files.zip`). **В замысле
замера не изменилось ничего.** Схема опыта, сетка длин по степеням четвёрки,
парный анализ МакНемара, расчёт мощности, правило решения из §6 — всё в силе.
Новых симуляций перед замером не нужно, и логи к нему отношения не имеют: он
про контекст, а не про пул, а лестница расширения в Мицелии не запускалась ни
разу, так что данных всё равно нет.

Ниже — только две поправки, обе следуют из перебора логов `sh2_200`
(`LOG_MINING.md`), и обе живут в коде, а не в постановке. Реализация:
`lab/alpha_pos.py`.

---

## Поправка 1. Грейдер свой и бинарный, `q_env` не переиспользовать

**Что нашли в логах.** 40.6 % всех замеров `q_env` прогона схлопнуто в одно
значение 0.4: формула `max(0.4, ratio·0.8)` (`core/scorer.py:322`) делает
неразличимыми все исходы от «0 тестов из N» до «половина». Для парного
МакНемара это смертельно: тест живёт на несогласованных парах, а схлопнутая
шкала превращает часть настоящих несогласий в согласия и уносит мощность.

**Что делать.** Грейдер — свой, отдельный, бинарный. Точное совпадение
уникального кода, как в исходном задании; ничего сверх этого.

`lab/alpha_pos.py` **намеренно не импортирует `core.scorer`**. Функция
`grade(text, code)` — двенадцать строк: вытащить `[A-Z]{2}-\d{4}`, сравнить с
ожидаемым, вернуть 0 или 1. Регистр не важен, положение в ответе не важно,
частичное совпадение — это 0.

Проверено на восьми случаях, включая `CF-6377XX` → 0 и `Ответ — CF-6377.` → 1.

Формат кода выбран так, чтобы не читаться словом: две согласные из набора без
гласных плюс четыре цифры. Иначе модель может «угадать» правдоподобное
сочетание, и контроль угадывания начнёт ловить не то.

## Поправка 2. Ретраи на transient и отдельный лог срывов

**Что нашли в логах.** В прогоне `sh2_200` — 108 сорванных вызовов
(`Transient server error`), это около 3 % от общего числа. В непарной схеме
3 % срывов стоят 3 % мощности. **В парной — дороже:** элемент участвует во всех
трёх условиях, и сорванный вызов в одном условии выбивает элемент целиком, то
есть теряется тройка, а не одна ячейка. При 100 элементах на точку сетки
потеря десяти элементов — это переход из «отличаем пороговый профиль от
никакого с вероятностью 0.91» в «0.85».

**Что делать.**

* до `MAX_RETRY = 5` попыток с экспоненциальным откатом (2 с, удваивается);
  различаются `transient` (5xx, таймаут, разрыв соединения) и `fatal`;
* **каждый** срыв — строкой в отдельный файл `lab/data/alpha_pos_failures.jsonl`
  с элементом, длиной, условием, номером голоса, номером попытки и типом;
* элемент, у которого срыв не устранился ретраями, помечается `broken` и
  выбрасывается из анализа **во всех условиях явно**, с подсчётом в отчёте, а
  не молча;
* `--analyze` печатает число срывов по типам и сколько из них стоили элемента.

Так потеря мощности видна как число, а не как необъяснимая разница `n` между
условиями.

## Что ещё стоит в коде и чего в задании не было

Эти пункты не меняют постановку, но без них парность рассыпается.

**Кеш префикса сломан явно.** §3 исходного задания требует «следить, чтобы не
срабатывало кеширование префикса». В llama.cpp кеш работает по общему префиксу,
а условия A и B на одном и том же отвлекающем тексте различаются только
положением одной вставки — то есть делят длинный общий префикс. В каждый
промпт первой строкой ставится уникальный `[ref <nonce>]`, разный для каждого
из трёх голосов. Это ломает совпадение префикса с первого токена.

**Контроли записываются с `L = 0`.** Потолок и угадывание считаются один раз на
элемент, а не на каждую длину, и лежат под отдельным ключом. Иначе анализ не
знает, под какой длиной их искать.

**Джиттер позиции.** Условие A — доля 0.45…0.55 равномерно, условие B —
0.00…0.05, как в §3. Фактическая доля пишется в запись.

**Порядок вызовов перемешан** по всему плану целиком (элементы × длины ×
условия), иначе прогрев и своп модели ложатся на условия неравномерно.

**Фактическое число токенов** берётся из `usage.prompt_tokens` ответа сервера,
а не оценивается: `--chars-per-token` только для сборки, в запись идёт то, что
реально посчитал токенизатор.

## Что проверить до прогона

`python lab/alpha_pos.py --preflight` — не делает ни одного вызова модели,
пока не проверит остальное.

**Первое уже выстрелило.** На сетке 4096/16384/65536 нужно ~210 000 символов
отвлекающего текста, а во всех `.md` проекта их 144 000. Абзацы начнут
повторяться примерно в полтора раза, и факт снова выделится контрастом — ровно
то, чего материал должен избегать. Нужен корпус побольше: либо добавить в
`--distractor` тексты из `<WORKDIR>\сайты\идеи\эмерджментная сборка\`, либо
опустить верхнюю точку сетки.

**Второе — контекст сервера.** `n_ctx` задаётся при старте `llm_server.py` и
общий для всех моделей. Для верхней точки 65536 сервер надо поднимать с
`--n-ctx 65792 --max-resident 1`. На 6 ГБ VRAM у `1.5B-q4` KV-кеш при ctx 65536
это порядка 1.9 ГБ плюс ~1.1 ГБ весов — влезает, но впритык. Если не влезет,
сетка сдвигается на 2048/8192/32768: шаг ×4 сохраняется, а смысл сетки (эффект
может отсутствовать на коротком окне и быть резким на длинном) — тоже.

**Объём.** 110 элементов × (3 длины × 3 условия + 2 контроля) × 3 голоса =
**3630 вызовов**. Исходная оценка §4 давала 2700 без контролей; контроли
добавляют 660, отсев по §3 съедает 10–20 элементов.

## Запуск

```bash
python lab/llm_server.py --port 8077 --n-ctx 65792 --max-resident 1
```

```bash
python lab/alpha_pos.py --preflight
```

```bash
python lab/alpha_pos.py --n-items 110 --grid 4096,16384,65536
```

```bash
python lab/alpha_pos.py --analyze
```

Прогон устойчив к обрыву: запись построчная с `fsync`, повторный запуск
подхватывает сделанное по ключу (элемент, длина, условие).
