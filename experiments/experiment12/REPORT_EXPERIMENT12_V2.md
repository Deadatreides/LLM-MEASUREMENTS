## 1. Постановка

Проверить экспериментально, возникает ли преимущество Mycelium не от самого факта смены модели, а от передачи следующему оператору **структурированного и механически подтверждённого** состояния задачи. Факторизация 3×2: три уровня контекста (K0 flat / K1 structure / K2 confirmed) × два режима оператора (O0 та же модель / O1 другая модель) = 6 плеч, плюс седьмое отдельное плечо `K0O0_promptB` (предзарегистрированная проверка H-син, перенесённая из предыдущей итерации). 318 состояний коллизии (178 арифметика, 140 код), 6 моделей, тот же стенд, что во всех предыдущих экспериментах проекта. Не реализовывались ни оркестратор, ни bandit, ни PTG, ни автоматическая декомпозиция — только измерение.

## 3. PASS/SAME_FAILURE/DIFFERENT_FAILURE/INAPPLICABLE/UNVERIFIED/ERROR

Пятисоставный статус (задание v2) реализован в `outcome_classification.py`, сравнивает сигнатуру ошибки retry с исходной (не текст, а структурированные `details`: имя+значение финального шага для арифметики, множество имён провалившихся requirements для кода). **UNVERIFIED встретился 0 раз из 2226** — механические швы этого стенда либо однозначно сравнивают с оракулом, либо возвращают INAPPLICABLE (нарушение формата); пути «формат в порядке, но сравнение недостоверно» в этой конструкции нет. Это архитектурное свойство, проверенное юнит-тестом на искусственном случае (классификатор СПОСОБЕН вернуть UNVERIFIED), и честно отражённая в реальных данных частота — не дефект, как и 0% UNKNOWN в предыдущих экспериментах проекта. **ERROR — 0 раз** (конвейер не падал на всех 2226+1320 вызовах).

## 4. SAME_FAILURE и DIFFERENT_FAILURE

Ключевая метрика — доля FAIL-исходов, при которых воспроизводится **та же самая** коллизия (`same_failure_rate_of_fails`, знаменатель — только FAIL, не все попытки):

| плечо | доля SAME среди FAIL |
|---|---|
| K0O0 | 90.3% |
| K0O1 | 87.6% |
| K1O0 | 83.4% |
| K1O1 | 81.7% |
| K2O0 | 81.2% |
| K2O1 | **76.8%** |

Монотонное снижение от K0O0 к K2O1 — и контекст, и смена модели независимо снижают точное повторение исходной ошибки. **Это не переинтерпретируется как успех** (см. §15, критическое правило) — снижение SAME_FAILURE на 13.5 п.п. (90.3%→76.8%) сопровождается ростом PASS всего на 1.5 п.п. (32.1%→33.6%), то есть подавляющее большинство «диверсифицированных» ошибок остаются ошибками, просто другими (DIFFERENT_FAILURE растёт с 5.3% до 10.1% — почти весь выигрыш от снижения SAME_FAILURE уходит в DIFFERENT_FAILURE, не в PASS).

\* `other` (127 из 178 арифметических состояний, 71.3%) — состояния, где пересчёт подтипа невозможен: хотя бы один шаг, от которого зависит финальный, сам получил статус INAPPLICABLE (неоднозначная строка/пропуск) на первичной генерации, и подстановка его значения в формулу невозможна. **Честное ограничение метода**: механическая dependency/value-классификация применима лишь к 28.7% арифметических коллизий этого датасета (51 из 178 = 21 dependency + 30 value) — для большинства отказов причина смешанная/неопределима на уровне одного шага.

Два содержательных наблюдения:
- **syntax**: K0O1 same_failure среди FAIL = 47.8% (см. полный JSON) — почти в 3 раза выше, чем K0O0 (18.3%). Смена модели НЕ диверсифицирует syntax-ошибки так, как диверсифицирует другие типы: слабые модели в этом пуле склонны к ОДНОТИПНОМУ формату отказа (усечённый код) независимо от того, какая именно модель выбрана — отсюда и провал PASS rate при смене модели именно на этом типе (73.9%→48.7%).
- **other/value**: единственные два bucket-а, где CHANGE_MODEL (O1) численно ОПЕРЕЖАЕТ SAME_MODEL (O0) при обогащённом контексте — `other`: K1O1 20.5% vs K1O0 14.2%; `value`: K1O1/K2O1 16.7% vs K1O0 3.3%/K2O0 10.0%. `value` (n=30) на грани порога — направление интересное, но выборка мала для сильных выводов (см. §12).

## 14. Проверка отсутствия leakage

Три независимых линии защиты, все подтверждены на полной кампании (не только на пилоте):
1. **По конструкции**: `context_builder.build_prompt()` не принимает retry-результат как параметр — утечка future-информации архитектурно невозможна, не только проверена постфактум.
2. **check_no_leak на числовые значения**: K1/K2 structure text сверяется с запрещённым множеством значений (регресс-тест на баг границ чисел с пилота v1 — короткий вариант типа `"3"` больше не ложно матчится внутри `"320.0"`).
3. **context_manifest.py**: структурная проверка готового текста промпта (маркер структуры отсутствует в K0, присутствует в K1/K2; исходный артефакт присутствует дословно) — 0 нарушений на 1272 K1/K2-записях (пилот v1) + повторно на всех 2226 записях полной кампании.

**Предполётный чек-лист (§ обязательный sanity check задания, все 6 пунктов) пройден и на пилоте, и на полной кампании**: `sanity_checklist.overall_ok = true` в `action_outcomes_full.json` — K0 без структуры, K1 структура без значений, K2 только подтверждённые значения, O0/O1 промпт побайтово идентичен, context manifest без нарушений, все 318 collision_id присутствуют во всех 7 плечах.

## 15. Критическое правило интерпретации — проверка по данным

Задание прямо запрещает засчитывать успех по снижению same_failure или по росту разнообразия ответов. Проверка явно:

- **«K2 уменьшил same_failure» ≠ успех**: same_failure среди FAIL упал с 90.3% (K0O0) до 76.8% (K2O1) — реальный эффект, но PASS вырос всего на 1.5 п.п. (§4) — диверсификация ошибки не конвертируется в решение задачи.
- **«CHANGE_MODEL увеличил разнообразие ответов» ≠ успех**: DIFFERENT_FAILURE растёт с ростом контекста/сменой модели (5.3%→10.1%), но это по-прежнему FAIL, не PASS.
- **Если K2 улучшает SAME MODEL так же, как CHANGE MODEL → ценность в контексте, не в рое**: НЕ подтверждено буквально в эту сторону — K2 численно улучшает CHANGE_MODEL (K0O1→K2O1: +10.4 п.п.) сильнее, чем SAME_MODEL (K0O0→K2O0: +4.1 п.п.), что ближе к следующему пункту.
- **Если CHANGE_MODEL улучшает результат ТОЛЬКО при K2 → сильное свидетельство в пользу идеи**: НЕ подтверждено — Δhetero(K2) = −2.5 п.п. (§10), CHANGE_MODEL не улучшает результат ни при каком уровне контекста, он лишь перестаёт значимо ВРЕДИТЬ. Взаимодействие реально (§11), но это ослабление вреда, не появление пользы — качественно другой, более слабый результат, чем требуется для подтверждения идеи.
- **Если ни один вариант не улучшает PASS относительно K0/O0 → гипотеза не подтверждена, к сложной архитектуре переходить нельзя**: частично применимо — K1O0/K2O0 численно выше K0O0, но ни один прирост не значим на предрегистрированном тесте (§8–9), и НИ ОДНО из 7 плеч не бьёт экономическую планку слепого повтора (§5).

## 16. Что эксперимент ДОКАЗЫВАЕТ

- Подтверждённые промежуточные значения (K2) не дают измеримого собственного вклада поверх одной только структуры (K1): ΔK2 инкрементально = +0.6 п.п., p=0.845 (§9).
- Смена модели без контекста значимо вредит (p=0.0042); с обогащённым контекстом вред статистически исчезает, но в пользу не превращается ни на одном уровне (§10).
- Есть измеримое, статистически пограничное взаимодействие между контекстом и сменой модели (§11) — контекст смягчает вред от переключения модели, направление устойчиво воспроизводится (то же +6.3 п.п., что независимо получалось и для K1, и для K2).
- Единственный явный, хорошо обеспеченный данными (n=115≥100, p=5.9×10⁻⁵) положительный эффект во всей серии экспериментов — переформулировка промпта на syntax-коллизиях, не архитектурный механизм.
- Диверсификация ошибки (снижение same_failure, рост different_failure) — реальный, измеримый, но НЕ равный успеху эффект; корректно отделён от роста PASS во всех разделах отчёта.
- Механическая dependency/value-классификация арифметических ошибок работоспособна, но применима лишь к 28.7% реальных отказов этого датасета — честное ограничение метода, не молчаливо обойдённое.
- Регрессии (сломанные ранее исправные шаги) редки и не различают плечи (2–4% для всех 7) — ни одно плечо не является систематически более разрушительным.

## 17. Что эксперимент НЕ ДОКАЗЫВАЕТ

- НЕ доказывает, что структурированный контекст (в любом варианте K1/K2) даёт практически значимый прирост PASS — все приросты в пределах CI, включающего ноль или касающегося его.
- НЕ доказывает и не опровергает окончательно ценность гетерогенности моделей саму по себе — при K0 она значимо вредит, при K1/K2 эффект неотличим от нуля в обе стороны (недостаточная мощность на конкретно этом сравнении, не доказанный ноль).
- НЕ доказывает причинный механизм различия «other»/«value» подтипов (где CHANGE_MODEL при богатом контексте численно опережает SAME_MODEL) — n=30 для value слишком мало для причинных выводов, это наблюдение, не результат.
- НЕ говорит ничего о задачах вне класса «многошаговая арифметика + функция на Python с независимыми requirements» — датасет специально сконструирован для этого эксперимента, обобщение на другие типы задач не проверялось.
- НЕ доказывает, что автоматический вывод декомпозиции (A-2) бесполезен — эксперимент проверяет ценность УЖЕ ГОТОВОЙ, вручную заданной структуры и подтверждённых значений; вопрос "стоит ли её выводить автоматически" остаётся отдельным и по-прежнему неизмеренным (что и являлось точкой входа в этот эксперимент).

## Итог

Пять из шести критериев интерпретации задания (§15) указывают в одну сторону: структурированный, механически подтверждённый контекст в том виде, в каком он реализован здесь, не даёт практически значимого самостоятельного выигрыша, а гипотеза «CHANGE_MODEL полезен именно при K2» не подтверждена — обнаружено только смягчение вреда, не появление пользы. Единственный устойчивый, хорошо обеспеченный данными положительный результат за всю программу экспериментов 10–12 — переформулировка промпта под конкретный тип коллизии (syntax), не архитектурный механизм. Переход к более сложной архитектуре на основании гипотезы Mycelium **не обоснован** этими данными.
