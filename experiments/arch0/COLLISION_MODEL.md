# COLLISION_MODEL.md — коллизии

## 1. Определение и главное разграничение

```
COLLISION := наблюдаемое несовместимое состояние двух или более
             артефактов / claims / evidence
```

```
COLLISION ≠ ERROR
```

- **COLLISION** — факт наблюдения: «эти два наблюдения не могут быть верны одновременно». Это утверждение о **несовместимости**.
- **ERROR** — утверждение о том, что конкретный элемент **неверен**. Требует evidence силы HARD против конкретного участника.

Коллизия говорит «здесь что-то не сходится», но **не говорит, кто именно неправ**. Переход от коллизии к ошибке требует отдельного шага локализации и достаточного evidence.

### 1.1 Почему это разделение обязательно

Три независимых основания:

1. **F12** — задокументирован случай, где внутренний шов дал PASS при реальной ошибке. Обратный случай (шов дал FAIL при правильном артефакте) наблюдался ещё чаще: **F9/F11** — сгенерированный верификатор отвергал заведомо правильный эталон в большинстве случаев, false reject доминировал у всех моделей. Если бы «шов сказал FAIL» автоматически означало «артефакт неверен», система бы систематически чинила исправное.

2. **F16** — конфликт между источниками не означает, что верный ответ рядом; для сильной модели он скорее указывал на систематическую слепую зону.

3. **F31** — даже когда ошибка реальна, участник, у которого сработала проверка, не обязательно является её причиной.

Отсюда: коллизия — вход в процесс локализации, а не вердикт.

## 2. Типы коллизий

| Тип | Что наблюдается | Типичный источник | Автоматически ⇒ ошибка? |
|---|---|---|---|
| `MECHANICAL_FAILURE` | HARD-шов дал FAIL (тест упал, число не сошлось) | `SEAM_EXECUTION`, `SEAM_CONTRACT` | нет — но evidence силы HARD против конкретного участника обычно есть |
| `CONTRACT_VIOLATION` | артефакт не соответствует объявленному интерфейсу | `SEAM_CONTRACT` | нет |
| `INTERNAL_INCONSISTENCY` | внутри одного артефакта утверждения противоречат друг другу | `SEAM_CONSISTENCY` | нет |
| `CROSS_ARTIFACT_INCONSISTENCY` | два артефакта требуют взаимоисключающего | `SEAM_CONSISTENCY` | нет |
| `SOURCE_DISAGREEMENT` | независимые источники дали несовместимые результаты по одному claim | `SEAM_CONFLICT` | **нет — особо** (F16) |
| `DEPENDENCY_VIOLATION` | downstream не согласуется с текущей версией upstream | `SEAM_DEPENDENCY` | нет — это чаще всего `STALE`, а не ошибка |
| `EVIDENCE_CONFLICT` | по одному subject есть HARD-evidence в обе стороны | `SEAM_EVIDENCE` | нет — требует разбирательства, оба источника подозрительны |
| `FORMAT_VIOLATION` | вывод не соответствует output_contract | `SEAM_FORMAT` | да, для утверждения о формате (но не о содержании) |
| `DRIFT` | новая версия разошлась с предыдущей за пределами разрешённого | `SEAM_DRIFT` | нет |
| `UNVERIFIABLE_CONFLICT` | противоречие есть, но средств установить, кто прав, нет | любой при `oracle_availability = NONE` | нет — терминально `UNKNOWN` |

### 2.1 `EVIDENCE_CONFLICT` — особый случай

Когда два **HARD** источника противоречат друг другу, система **не выбирает победителя по иерархии**. Оба помечаются как подозрительные, claim переходит в `CONFLICTED`, и порождается диагностическая задача уровня инфраструктуры.

Основание — F45 и F44: дефекты проверяющих правил реальны и встречались многократно; конфликт двух жёстких проверок — типичный симптом того, что **одна из проверок сломана**, а не того, что claim «сложный». Автоматический выбор победителя замаскировал бы баг инфраструктуры под свойство данных.

## 3. Локализация origin

```
FUNCTION localize(collision, graph):
    participants ← collision.participants
    defective ← {c ∈ participants : ∃ HARD evidence(REFUTES, c)}

    IF defective == ∅:
        # никто не опровергнут жёстко — коллизия есть, ошибки нет
        collision.origin ← null
        collision.status ← LOCALIZED_AS_UNDECIDED
        RETURN

    roots ← root_origins(defective, graph)     # см. DEPENDENCY_MODEL.md §6.2

    IF |roots| == 1:
        collision.origin ← roots[0]
        collision.origin_confidence ← HIGH
    ELSE IF |roots| > 1:
        collision.origin ← roots            # MULTIPLE_LOCAL
        collision.origin_confidence ← HIGH  # каждый локализован чисто
    ELSE:
        collision.origin ← null             # ERROR_GLOBAL
        collision.origin_confidence ← NONE
```

**Критично (F31):** `roots` вычисляется **через граф предков**, а не по признаку «у кого сработала проверка». Наивная версия была реализована и дала неверный результат на контрольном случае: каскадный claim, чей текст согласован с неверной предпосылкой, тоже не проходит абсолютную проверку и выглядит как самостоятельный дефект.

**Наблюдение по реальным данным (F39):** класс `ERROR_GLOBAL` (`roots` пусто) не встретился ни разу; `MULTIPLE_LOCAL` встречался часто. Это означает, что ветка «несколько независимых корней» — не экзотика, а основной случай, и планировщик обязан её обрабатывать как норму, а не как ошибку.

## 4. Severity

`severity` — **не** оценка «насколько всё плохо», а указание, блокирует ли коллизия выдачу результата:

| Severity | Смысл |
|---|---|
| `BLOCKING` | затрагивает claim, от которого зависит финальный результат задачи, и есть HARD evidence(REFUTES) |
| `MAJOR` | затрагивает результат, но нет HARD evidence — только конфликт/неопределённость |
| `MINOR` | затрагивает claim вне пути к финальному результату |
| `INFORMATIONAL` | наблюдение зафиксировано, влияние на результат не установлено |

Вычисляется структурно: достижимость финального claim из участников коллизии + сила доступного evidence. Никакой эвристики «важности».

## 5. Что происходит с коллизией дальше

```
COLLISION
   │
   ├─ origin определён ──────► AFFECTED_REGION ──► REPAIR_PLAN   (REPAIR_MODEL.md)
   │
   ├─ origin не определён ───► либо запрос дополнительного evidence,
   │  (LOCALIZED_AS_UNDECIDED)  либо ACCEPTED с честным UNKNOWN
   │
   └─ нет средств проверки ──► UNRESOLVABLE (терминально, не авария)
```

### 5.1 Приоритизация: чего архитектура НЕ делает

Соблазнительно: «есть коллизия → значит сюда надо потратить бюджет».
Экспериментально это **не подтверждено и скорее опровергнуто** (F16): в точках конфликта вероятность найти верный ответ была ниже, чем в бесконфликтных.

Что подтверждено надёжнее (F15): **отсутствие** коллизии — хороший признак «сюда тратить не нужно».

Поэтому:
- отсутствие коллизий на claim → законное основание не тратить на него бюджет;
- наличие коллизии → основание **локализовать и спланировать**, но **не** автоматическое основание тратить больше вычислений;
- решение о тратах принимается планировщиком по стоимости и типу коллизии (REPAIR_MODEL.md §4), а не по факту наличия конфликта.

## 6. Защита от бесконечного цикла

Каждая коллизия несёт `iteration_count`. Правила остановки — в REPAIR_MODEL.md §7. Ключевые:

- повтор состояния: хеш (состояние графа + план ремонта) уже встречался → `UNRESOLVABLE`;
- осцилляция: план N и план N−2 совпадают → `UNRESOLVABLE`;
- лимит итераций на коллизию;
- исчерпание бюджета.

Все четыре — **нормальные** терминальные исходы, приводящие к `STOP` с указанием причины, а не к аварии.
