# INVARIANTS.md — архитектурные инварианты

Каждый инвариант: формулировка, проверка, экспериментальное основание, что ломается при нарушении.

Инварианты делятся на **проверяемые автоматически** (assert в коде / линтер / CI) и **процедурные** (соблюдаются дисциплиной разработки). Процедурные отмечены явно — притворяться, что они проверяются машиной, было бы самообманом.

---

## I-1. `EVERY_ARTIFACT_HAS_PROVENANCE`

**Формулировка.** Каждый артефакт, claim, evidence и dependency несёт заполненный `provenance`: кто создал, каким оператором, из каких входов, когда.

**Проверка (авто).**
```
∀ x ∈ {artifacts, claims, evidence, dependencies}:
    x.provenance ≠ null ∧ x.provenance.created_by ≠ null ∧ x.provenance.input_refs ≠ null
```

**Основание.** F45: за проект не менее шести дефектов проверяющих правил обнаружены пересчётом по сохранённым данным. Без provenance невозможно отличить ошибку модели от ошибки инфраструктуры.

**При нарушении.** Диагностика становится невозможной; любая аномалия списывается на «модель плохая».

---

## I-2. `NO_SILENT_OVERWRITE`

**Формулировка.** Никакое содержимое не перезаписывается. Изменение = новая версия со ссылкой на предыдущую.

**Проверка (авто).** Storage не имеет методов `update`/`delete`. Линтер импортов + отсутствие соответствующих методов в интерфейсе.

**Основание.** F37+F38 совместно: область ремонта определяется проверкой, и проверка может ошибиться в обе стороны; откат обязан быть возможен. Плюс F45.

**При нарушении.** Невозможен откат (аудит J); теряется история решений ремонта.

---

## I-3. `EVERY_STATE_CHANGE_IS_VERSIONED`

**Формулировка.** Каждое изменение состояния порождает `STATE_RECORD` с `from`, `to`, `trigger`, `graph_version`.

**Проверка (авто).** STATE ENGINE — единственный путь изменения `state`; он всегда пишет запись. Assert: число записей = числу переходов.

**Основание.** Требуется для детекции повторяющегося состояния (STOP-условие `REPEATED_STATE`) и для отката.

**При нарушении.** Бесконечный цикл ремонта становится необнаружимым.

---

## I-4. `UNKNOWN_IS_NOT_ERROR`

**Формулировка.** `UNKNOWN` не превращается автоматически ни в `INCORRECT`, ни в `CORRECT` — ни внутри графа, ни на границе API.

**Проверка (авто).**
```
запрещённый переход: UNKNOWN → INCORRECT без evidence(assertion=REFUTES)
запрещённый переход: UNKNOWN → CORRECT   без evidence(assertion=SUPPORTS, strength=HARD)
API: get_state() возвращает unknown_claims отдельным полем
```

**Основание.** F43 (UNKNOWN устойчиво возникает), F44 (доля UNKNOWN сильно зависит от калибровки проверок — то есть часть «неизвестности» есть свойство инфраструктуры, а не ответа).

**При нарушении.** Либо ложные ошибки и лишний ремонт, либо молчаливая выдача непроверенного как проверенного.

---

## I-5. `STALE_IS_NOT_INCORRECT`

**Формулировка.** `STALE` означает «прежнее доказательство больше не применимо», а не «неверно». Переход `STALE → INCORRECT` требует **новой** проверки относительно нового upstream.

**Проверка (авто).**
```
запрещённый переход: STALE → INCORRECT без нового evidence(REFUTES),
                     созданного ПОСЛЕ смены версии upstream
```

**Основание.** F37 (граф систематически шире фактически необходимого ремонта) + F38 (но примерно треть реальных случаев действительно каскадирует). Без этого различения система вынуждена выбирать между «чинить всё» и «надеяться».

**При нарушении.** Теряется главный механизм экономии; система скатывается к полному пересчёту (то есть к тому, что F46 уже признал неконкурентным).

---

## I-6. `AFFECTED_SUBGRAPH_IS_NOT_MRS`

**Формулировка.** `candidate_affected_set` — верхняя граница, а не план ремонта. Между ними обязателен шаг сужения через проверку.

**Проверка (авто).**
```
∀ repair_plan: plan.region.verified_affected_set ≠ null
               ∧ (plan.repair_set ⊆ plan.region.candidate_affected_set)
               ∧ шаг narrow() был выполнен либо явно пропущен с указанием причины
```

**Основание.** F34 (recall = 1.0 — граница безопасна), F37 (precision ≈ 0.47 — граница избыточна), F42 (реально нужна примерно половина claims задачи).

**При нарушении.** Систематическая перегенерация заведомо корректного.

---

## I-7. `DEPENDENCY_IS_NOT_SIMILARITY`

**Формулировка.** Зависимость создаётся только из выраженного отношения. Семантическое сходство, соседство в тексте и совпадение чисел без прослеживаемого происхождения дают максимум `UNKNOWN_DEPENDENCY` со статусом `HYPOTHESIS`.

**Проверка (авто).**
```
∀ dep: dep.status == CONFIRMED ⇒ ∃evidence с типом
       {MECHANICAL, STATIC_ANALYSIS, EXECUTION, EXTERNAL_DATA, HUMAN}
∀ dep, созданная эвристикой сходства: dep.status == HYPOTHESIS
```

**Основание.** F40 (скрытая и ложная зависимость различимы, но эвристика проверена только на полярных случаях — сила WEAK).

**При нарушении.** Ложные рёбра → лишний ремонт и ложные каскады; при этом ошибка невидима, потому что граф «выглядит правдоподобно».

---

## I-8. `COLLISION_IS_NOT_AUTOMATIC_ERROR`

**Формулировка.** Коллизия — наблюдаемая несовместимость. Она не назначает виновного автоматически.

**Проверка (авто).**
```
запрещённый переход: CONFLICTED → INCORRECT без разрешающего evidence
collision.origin вычисляется через root_origins() (граф предков), а НЕ
    по признаку «у кого сработала проверка»
```

**Основание.** F31 (нисходящий claim, согласованный с неверной предпосылкой, тоже проваливает проверку и выглядит самостоятельным дефектом — наивная атрибуция была реализована и дала неверный результат), F16 (конфликт не указывает, где истина), F9/F11 (проверка ошибается в обе стороны).

**При нарушении.** Ремонт нацеливается на симптом вместо причины.

---

## I-9. `LLM_JUDGEMENT_IS_NOT_HARD_ORACLE`

**Формулировка.** Evidence типов `MODEL_JUDGEMENT` и `SELF_JUDGEMENT` никогда не имеют силы `HARD` и не могут быть единственным основанием для `CORRECT` или `INCORRECT`.

**Проверка (авто).**
```
∀ claim: state == CORRECT ⇒ ∃evidence e:
    e.assertion == SUPPORTS ∧ e.strength == HARD ∧
    e.evidence_type ∉ {MODEL_JUDGEMENT, SELF_JUDGEMENT}
```

**Основание.** F9 (сгенерированный моделью верификатор отверг заведомо правильный эталон в большинстве случаев), F10 (внутренняя «строгость» не означает корректность), F11 (false reject доминировал у всех моделей), F12 (задокументирован обратный случай: внутренняя проверка дала PASS при реальной ошибке, и ремонт не запустился).

**При нарушении.** Ровно сценарий F12 — молчаливое закрытие задачи с ошибкой.

---

## I-10. `AGREEMENT_IS_NOT_INDEPENDENCE`

**Формулировка.** Согласие нескольких генераций получает силу в зависимости от **оси независимости**; согласие по оси `SEED`/`TEMPERATURE`/`PROMPT` — слабое. Ни при каком количестве слабых evidence claim не становится `CORRECT`.

**Проверка (авто).**
```
∀ evidence типа MULTI_SOURCE_AGREEMENT: independence_axis ≠ null
∀ evidence: strength ≤ max_strength_for_axis(independence_axis)
resolve(): накопление WEAK никогда не даёт CORRECT
```

**Основание.** F1 (ошибка повторяется при повторе той же конфигурации примерно в 3 случаях из 4 при базовой частоте ~1 из 10), F5 (температура растит поверхностное разнообразие сильнее смыслового), F7 (смена промпта не дала независимости — опровергнуто), F6 (смена модели — сильнейшая ось), F14/F17 (полное согласие при полной неправоте наблюдалось).

**При нарушении.** Систематическая ошибка одной модели маскируется под «уверенность».

---

## I-11. `EVERY_ACTION_HAS_COST`

**Формулировка.** Каждое действие имеет `estimated_cost` до выполнения и `actual_cost` после. Графовый анализ и проверки — тоже действия со стоимостью.

**Проверка (авто).**
```
∀ action: status == PLANNED   ⇒ estimated_cost ≠ null
∀ action: status == COMPLETED ⇒ actual_cost ≠ null
```

**Основание.** F41 (анализ измеримо стоит; перебор MRS растёт как 2^n), F47 (локальное не всегда дешевле).

**При нарушении.** Невозможно сравнить стратегии → возврат к догме «локально = дёшево», которую F47 опровергает.

---

## I-12. `EVERY_PLAN_COMPARES_ALTERNATIVES`

**Формулировка.** План ремонта обязан содержать ≥2 рассмотренные стратегии, включая `FULL_RETRY`.

**Проверка (авто).**
```
∀ plan: |plan.alternatives_considered| ≥ 2 ∧ FULL_RETRY ∈ plan.alternatives_considered
```

**Основание.** F46 (артефактный pipeline не превзошёл плоский best-of-N при равном токенном бюджете), F47, F25.

**При нарушении.** Архитектура повторяет ошибку, уже измеренную в старом Мицелии: тратить бюджет на структуру вместо генераций и проигрывать простому baseline.

---

## I-13. `NO_MERGE_OF_PROVENANCE`

**Формулировка.** При объединении claims (`MERGE`, схлопывание SCC) происхождения слагаемых **сохраняются раздельно**, а не сливаются в одно.

**Проверка (авто).**
```
∀ composite claim: provenance.input_refs содержит ВСЕ исходные claim_id
∀ исходный claim: state == SUPERSEDED (не удалён)
```

**Основание.** Без этого невозможно понять, какая часть композита была причиной коллизии — то есть теряется локализация, ради которой существует декомпозиция (F29).

---

## I-14. `SEAM_CLASS_BY_PROCEDURE`

**Формулировка.** Шов относится к `HARD` только если его процедура детерминирована и не содержит вызова языковой модели. Классификация по процедуре, а не по намерению.

**Проверка (авто).** Реестр швов: `seam_class == HARD ⇒ check_procedure не вызывает ModelAdapter`.

**Основание.** F9–F12. Плюс отдельный случай: исполнение **сгенерированных моделью** тестов даёт HARD-evidence относительно вопроса «соответствует ли реализация этим тестам», но SOFT относительно «корректна ли реализация» (SEAM_MODEL.md §2.2).

---

## I-15. `UNTRUSTED_SEAM_CANNOT_PRODUCE_HARD_EVIDENCE`

**Формулировка.** Шов, не прошедший свои контрольные случаи, не может производить evidence силы `HARD`.

**Проверка (авто).** `seam.is_trusted == false ⇒ evidence.strength ≤ MODERATE`.

**Основание.** F44 (за-строгие правила давали ложный UNKNOWN 32% при корректных ответах), F45 (шесть найденных дефектов классификаторов, все обнаружены контрольными случаями, ни один — на реальных данных).

**При нарушении.** Баги инфраструктуры превращаются в «ошибки модели» и запускают ремонт исправного.

---

## I-16. `RAW_IS_ALWAYS_PERSISTED`

**Формулировка.** Сырой вывод оператора сохраняется **до** попытки разбора и при любом исходе, включая провал парсинга.

**Проверка (авто).** В `ActionExecutor.execute` запись `RUN` предшествует разбору; assert на порядок.

**Основание.** F45.

---

## I-17. `POLICY_CANNOT_WRITE`

**Формулировка.** Слой политики выбирает из готового множества и не имеет доступа на запись в граф, состояние и evidence.

**Проверка (авто).** Интерфейс `Policy` не принимает ссылок на записывающие сервисы; линтер импортов.

**Основание.** Требование §33 задания (router должен быть заменяемым) + чистота уровней (ARCHITECTURE.md §3). Дополнительно — опыт старого Мицелия: там контур отбора был перемешан с исполнением, и починка отбора потребовала отдельного большого аудита.

---

## I-18. `CORE_IS_MODEL_AGNOSTIC`

**Формулировка.** `GRAPH CORE` и `STATE ENGINE` не зависят ни от какой конкретной реализации LLM.

**Проверка (авто).** Линтер импортов в CI; нарушение = ошибка сборки.

**Основание.** Требование L аудита; F3/F4/F25 (операторы различаются настолько, что привязка ядра к одному из них исказила бы всё).

---

## I-19. `NO_GLOBAL_QUALITY_SCORE` *(процедурный)*

**Формулировка.** В архитектуре нет единой скалярной величины «качество/уверенность», агрегирующей разнородные сигналы и участвующей в решениях.

**Проверка.** Процедурная — при ревью. Автоматически проверяется частично: отсутствие такого поля в схемах данных.

**Основание.** F18 (метрика, сильно коррелирующая с общим выигрышем, не коррелирует с предельным — r ≈ 0.002), F19 (близкая энтропия при разных нужных действиях), и прямое измерение в старом Мицелии: скалярная агрегированная оценка была **анти**коррелирована с истиной (ρ = −0.429), тогда как разделённая по ролям давала +0.771. Смешивание шкал не просто теряло сигнал — оно его портило.

---

## I-20. `FROZEN_STRUCTURE_BEFORE_GENERATION` *(процедурный)*

**Формулировка.** Схема декомпозиции, правила швов и правила зависимостей фиксируются до генерации содержимого и не переписываются под наблюдённый результат.

**Проверка.** Процедурная: версия схемы записывается в `provenance`; изменение схемы = новая версия decomposition, старая сохраняется.

**Основание.** Методология всех девяти экспериментов. Содержательная причина: при перестройке графа после наблюдения результата понятия `origin` и `affected region` теряют смысл — граф начинает объяснять уже известный ответ вместо предсказания области влияния.

---

## I-21. `STOP_IS_A_NORMAL_OUTCOME`

**Формулировка.** Остановка — штатный исход с обязательным указанием причины, а не аварийное завершение.

**Проверка (авто).** `task.state ∈ {STOPPED, RESOLVED} ⇒ stop_reason ≠ null`.

**Основание.** F20/F21 — детектор «здесь ничего делать не нужно» дал основную измеренную экономию бюджета; это самое ценное действие в системе, и оно не должно выглядеть как отказ.
