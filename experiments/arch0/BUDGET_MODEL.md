# BUDGET_MODEL.md — бюджет

## 1. Бюджет — самостоятельный объект

Не параметр, не счётчик внутри оркестратора. Отдельная сущность со своим жизненным циклом, потому что от неё зависят решения планировщика ремонта (какую стратегию выбрать) и STOP-условия.

```
BUDGET {
  budget_id
  token_budget   / token_spent   / token_reserved
  time_budget    / time_spent    / time_reserved
  call_budget    / call_spent    / call_reserved
  model_budget   : {model_id → лимит вызовов}     # для дорогих/ограниченных операторов
  retry_budget   / retry_spent
  policy_on_exhaustion ∈ {STOP, DEGRADE, ASK_HUMAN}
}

COST { tokens, time_sec, calls, model_id }
```

**Reserve/commit.** Действие сначала резервирует оценку, затем фиксирует факт. Это нужно, чтобы параллельные ветви (CONTEXT: параллелизм по независимым claims) не перерасходовали общий бюджет.

## 2. Что считается расходом

| Статья | Токены | Время | Учитывается? |
|---|---|---|---|
| `GENERATE` / `REGENERATE` / `PATCH` | да | да | да |
| `VERIFY` через HARD-шов | 0 | да | **да** |
| `VERIFY` через SOFT-шов | да | да | да |
| Построение графа, обход, распространение STALE | 0 | да | **да** |
| Вычисление affected region | 0 | да | **да** |
| Планирование ремонта | 0 | да | **да** |
| Точный MRS перебором | 0 | **растёт как 2^n** | **да, с жёстким лимитом** |

**Графовый анализ не бесплатен** (требование §22 задания). Экспериментально он мал (F41: доли миллисекунды на случай для графа из 6 узлов), но полный перебор подмножеств масштабируется экспоненциально — это измеренный факт, а не опасение. Поэтому:

```
IF размер candidate_set > MRS_BRUTE_FORCE_LIMIT:
    точный MRS не вычисляется, используется приближение (REPAIR_MODEL.md §5.3)
```

## 3. Оценка стоимости до выполнения

```
FUNCTION estimate(action, model_profile, context):
    IF action не вызывает модель:
        RETURN COST{tokens: 0, time_sec: profile.mean_internal_time, calls: 0}

    input_tokens  ← len(rendered_context)                    # известно точно
    output_tokens ← model_profile.mean_output_tokens(scope)  # оценка по наблюдениям
    RETURN COST{
        tokens: input_tokens + output_tokens,
        time_sec: model_profile.mean_latency(scope),
        calls: 1,
        model_id: action.model_id
    }
```

**`model_profile` обязателен со `scope`.** Оценка «средняя длина ответа модели X» без учёта типа артефакта и промпта бессмысленна: F25 зафиксировал случай, где одна модель при непривычном формате retry-промпта срывалась в многословность настолько, что локальный ремонт становился **дороже полной плоской генерации**. Профиль без scope не поймал бы этого.

При `sample_size` ниже порога оценка помечается `LOW_CONFIDENCE`, и планировщик обязан заложить запас.

## 4. Обязательное сравнение стратегий

Ключевое требование раздела и прямое следствие F46/F47.

```
FUNCTION compare_strategies(region, collision, task, budget) -> [ {strategy, cost, feasible} ]:
    FULL_RETRY    : перегенерировать задачу целиком (плоско, без графа)
    LOCAL_REPAIR  : Σ cost(entry) по repair_set
    VERIFY_FIRST  : Σ cost(VERIFY) по candidate_set
                    + Σ cost(REGENERATE) по ожидаемой доле провалов проверки
    MODEL_SWITCH  : LOCAL_REPAIR, но другой оператор
    PROMPT_SWITCH : LOCAL_REPAIR, но другой prompt_profile
```

### 4.1 Почему `FULL_RETRY` обязателен в сравнении

| Факт | Что он запрещает предполагать |
|---|---|
| F46: артефактный pipeline не превзошёл плоский best-of-N при равном токенном бюджете | что структурированный путь «сам по себе» экономичнее |
| F47: локальный ремонт не всегда дешевле; знак экономии менялся | что «локально» = «дёшево» |
| F25: экономика ремонта модель-специфична (у одной модели существенная экономия, у другой отрицательная) | что экономику можно оценить без профиля конкретного оператора |
| F28: декомпозиция сама стоит дороже и не улучшает качество ответа | что граф оправдывает себя качеством |

Вывод, зафиксированный архитектурно: **выгода графового подхода — в локализации и в возможности не трогать заведомо целое (F29, F35, F42), а не в автоматической дешевизне.** Поэтому дешевизна каждый раз проверяется, а не постулируется.

### 4.2 Инвариант

```
EVERY_PLAN_COMPARES_ALTERNATIVES:
    ∀ repair_plan: |plan.alternatives_considered| ≥ 2
                   ∧ FULL_RETRY ∈ plan.alternatives_considered
```
Проверяемый assert. План, не сравнивший себя с полным пересчётом, отвергается планировщиком.

## 5. Учёт «сколько уже вложено»

Опасность: чем больше вложено в ветку, тем сильнее соблазн вложить ещё.

Правило: **уже потраченный бюджет не влияет на оценку следующего действия.** Решение принимается только по ожидаемому эффекту и остаточному бюджету. Единственное исключение — счётчики итераций/ретраев, которые работают как жёсткие ограничители, а не как аргумент «уже почти получилось».

Основание — F1: при устойчивой ошибке повтор той же конфигурации воспроизводит ту же ошибку с высокой вероятностью. «Ещё одна попытка тем же способом» — статистически плохая ставка, независимо от того, сколько уже потрачено.

## 6. Исчерпание бюджета

```
ON budget.remaining < минимума для любого допустимого действия:
    SWITCH task.budget.policy_on_exhaustion:
        STOP      → task.state ← STOPPED, stop_reason ← BUDGET_EXHAUSTED
        DEGRADE   → отдать текущее состояние графа с явной разметкой:
                    что CORRECT, что UNKNOWN, что STALE, какие коллизии открыты
        ASK_HUMAN → REQUEST_EVIDENCE(HUMAN) на открытые коллизии
```

`DEGRADE` — не «выдать лучшее, что есть». Это **выдать состояние графа честно**, с сохранением статусов. Инвариант `UNKNOWN_IS_NOT_ERROR` действует и здесь: при исчерпании бюджета `UNKNOWN` не превращается ни в успех, ни в провал.

## 7. Метрики, которые стоит собирать (для будущего router)

Не участвуют в решениях ARCH-0, но логируются, чтобы позже строить политику на данных, а не на убеждениях:

| Метрика | Зачем |
|---|---|
| `cost_per_resolved_collision` | сравнение стратегий постфактум |
| `cost_of_verification / cost_of_regeneration` по типам claim | проверка допущения «VERIFY дешевле» (OQ-STALE) |
| `over_repair_ratio` = \|repair_set\| / \|истинно необходимое\| | измеримо только там, где истина устанавливаема |
| `stale_resolved_by_verify_ratio` | доля STALE, снятых дешёвой проверкой, — прямая мера пользы механизма §4 STATE_MACHINE |
| `cost_by_independence_axis` | окупается ли `CHANGE_MODEL` относительно эффекта |
| `graph_analysis_time / total_time` | контроль, что анализ не съедает выигрыш |

`stale_resolved_by_verify_ratio` — важнейшая: именно она покажет, реализовалась ли на практике экономия, ради которой введено состояние `STALE`. В эксп. 9 предпосылка измерена (F37: избыточность графа велика), но сама экономия через VERIFY-механизм **не измерялась живьём** (OQ-MRS, OQ-STALE).
