# DEPENDENCY_MODEL.md — граф зависимостей

## 1. Определение

```
DEPENDENCY := (source_claim, target_claim, dependency_type, evidence, confidence, status)
```

Читается: «истинностное значение `target` **опирается на** истинностное значение `source`». То есть если `source` окажется неверным, прежнее обоснование `target` перестаёт быть применимым.

**Направление фиксировано:** `source → target` означает поток обоснования вниз. Обход при поиске области влияния идёт **по направлению рёбер** (от origin к потомкам).

---

## 2. Типы зависимостей

| Тип | Смысл | Достаточное основание | Пример |
|---|---|---|---|
| `LOGICAL` | target следует из source логически | явная импликация в структуре задачи | «все A суть B» → «этот A есть B» |
| `COMPUTATIONAL` | target арифметически/алгоритмически вычислен из source | source входит в формулу target | subtotal_A + subtotal_B → total |
| `DATA` | target использует значение, объявленное в source | совпадение конкретного значения с прослеживаемым происхождением | «цена = 20» → «2 × 20 = 40» |
| `CONTRACT` | target обязан соответствовать интерфейсу, объявленному в source | source — спецификация, target — реализация | сигнатура → реализация |
| `CAUSAL` | source задаёт условия применимости target | рамка задачи определяет применимый метод | «две категории» → «метод для категории A» |
| `DERIVATION` | target — шаг вывода из source | target объявлен как применение source | «метод: P×r×t» → «500×0.04×3» |
| `FORMAT` | target обязан иметь форму, заданную source | явный контракт формата | схема → экземпляр |
| `OTHER` | не подходит ни под один тип, но связь обоснована | обязательно заполненный `evidence` | |
| `UNKNOWN_DEPENDENCY` | **есть основания подозревать связь, но она не установлена** | подозрение зафиксировано, но не подтверждено | два claim используют одно неявное допущение |

### 2.1 `UNKNOWN_DEPENDENCY` — обязательный тип

Это не «мусорная корзина», а требование §14 задания и следствие F40.

Правило: если система обнаружила основание подозревать зависимость, но не может её подтвердить, она **обязана** создать ребро с типом `UNKNOWN_DEPENDENCY` и статусом `HYPOTHESIS`, а не «молча считать claims независимыми».

Влияние на алгоритмы:
- в распространении `STALE` такие рёбра **участвуют** (безопасность);
- в вычислении `candidate_affected_set` — **участвуют**;
- при планировании ремонта потомки по таким рёбрам попадают в `unknown_set`, а не в `verified_affected_set`;
- их приоритет проверки ниже, чем у подтверждённых рёбер.

## 3. Что является достаточным основанием, а что — только гипотезой

Это ядро требования «не превращать semantic similarity в dependency» (§3, §15 задания; экспериментально — F40).

### 3.1 Достаточное основание (`status = CONFIRMED`)

Ребро считается подтверждённым, только если выполняется хотя бы одно:

| Основание | Тип evidence |
|---|---|
| **Структурное объявление**: декомпозиция по зафиксированной схеме прямо задаёт связь (например, «шаг вычисления зависит от объявленного метода») | `MECHANICAL` |
| **Прослеживаемое значение**: конкретное значение из source буквально появляется в target, и его происхождение прослежено, а не просто совпало | `MECHANICAL` / `STATIC_ANALYSIS` |
| **Проверяемая подстановка**: изменение source механически меняет проверяемый результат target | `EXECUTION` |
| **Внешне заданный контракт**: связь объявлена в спецификации задачи или человеком | `EXTERNAL_DATA` / `HUMAN` |

### 3.2 Только гипотеза (`status = HYPOTHESIS`)

| Наблюдение | Почему не достаточно |
|---|---|
| Тексты claims похожи / содержат одни слова | F40, §15: семантическое сходство ≠ зависимость |
| В обоих claims встречается одно и то же число | прямо проверено: совпадающее число при несвязанном контексте — не зависимость |
| Claims идут подряд в артефакте | соседство ≠ связь (прямой запрет §3 задания) |
| Модель заявила, что связь есть | `MODEL_JUDGEMENT` — никогда не hard evidence (F9–F14) |

**Правило подозрения (следствие F40).** Совпадение нетривиального значения **плюс** пересечение содержательного контекста → создать `UNKNOWN_DEPENDENCY` со статусом `HYPOTHESIS`. Совпадение значения **без** пересечения контекста → **не создавать ребро**, но зафиксировать наблюдение в диагностике.

Оговорка о силе основания: F40 имеет силу WEAK — эвристика проверена только на полярных случаях. Поэтому она порождает **только гипотезы**, никогда не `CONFIRMED`, и её порог является параметром конфигурации, а не константой архитектуры. См. OQ-3.

### 3.3 Как зависимость подтверждается

```
HYPOTHESIS ──► CONFIRMED   при появлении evidence из §3.1
HYPOTHESIS ──► REFUTED     при контрпримере: source изменён, а проверяемый
                           результат target доказуемо не изменился
CONFIRMED  ──► DISPUTED    при появлении evidence, противоречащего существованию связи
```

**`REFUTED` рёбра не удаляются** — иначе теряется объяснение прошлых решений ремонта.

### 3.4 Конфликтующие evidence о зависимости

Хранятся все, ребро получает `status = DISPUTED`. `DISPUTED` ребро ведёт себя как `HYPOTHESIS` (участвует в безопасном верхнем пределе), но помечает потомков как `unknown_set`.

### 3.5 Альтернативные рёбра

Допускаются. Между одной парой claims может существовать несколько рёбер разных типов (например, `DATA` и `CONTRACT`) — они не конфликтуют, а описывают разные аспекты связи. При обходе они схлопываются в «есть связь»; при диагностике различаются.

## 4. Свойства графа, подтверждённые экспериментально

| Свойство | Подтверждение |
|---|---|
| Транзитивное замыкание вниз от origin даёт **точную и полную** область потенциального влияния | F34: 120/120 точных совпадений с независимо построенным ground truth, recall = 1.0, ноль пропущенных зависимостей |
| Независимые ветви **не загрязняются** | F35: 0 из 80 случаев |
| Merge-узел (in-degree > 1) не требует особого механизма | F36 |
| Область влияния — **верхняя граница**, а не минимальный ремонт | F37: precision ≈ 0.47, over-repair в большинстве случаев |
| Различить «свой дефект» от «унаследованного» **нельзя** поклеймной механической проверкой; нужен граф происхождения | F31 |

**F31 — важнейшее следствие для реализации.** Наивная логика «claim не прошёл свою проверку ⇒ это его собственная ошибка» **неверна**: нисходящий claim, согласованный с неверной предпосылкой, тоже не проходит проверку на абсолютную истину и выглядит как самостоятельный дефект. Отличить корень от симптома можно только через структуру графа (см. §6).

## 5. Циклы

### 5.1 Проблема

Основная модель — DAG, и все подтверждённые свойства (§4) получены на ациклических графах (OQ-6: циклы экспериментально не проверялись). Но реальные рассуждения могут порождать взаимозависимость («A следует из B, B следует из A»).

### 5.2 Выбранный механизм: детекция при вставке + схлопывание SCC

```
ON попытке добавить ребро (u → v):
    если v уже достижим из u ... то есть, если добавление создаёт цикл:
        1. НЕ добавлять ребро в основной DAG
        2. Создать запись CYCLE_OBSERVATION {u, v, обнаруженный путь}
        3. Классифицировать:
           a) если ребро имеет status=HYPOTHESIS  →  пометить REFUTED_BY_ACYCLICITY,
              зафиксировать в диагностике, НЕ схлопывать
           b) если ребро имеет status=CONFIRMED   →  схлопнуть SCC:
              - все claims цикла заменяются одним composite claim
                с atomicity = INDIVISIBLE_BLOCK
              - внутренняя структура сохраняется в его content и в provenance
              - внешние рёбра переносятся на composite
              - исходные claims получают state = SUPERSEDED (не удаляются)
```

### 5.3 Обоснование выбора

Рассмотренные варианты и почему выбран именно этот:

| Вариант | Отклонён, потому что |
|---|---|
| Запретить такую dependency вовсе | молчаливо теряет реальное отношение; нарушает требование «не делать вид, что циклов не существует» |
| Оставить общий граф с циклами | ломает **все** экспериментально подтверждённые свойства: транзитивное замыкание перестаёт завершаться корректно, теряется понятие origin, F34/F35/F36 больше не применимы |
| Итеративный блок с фиксированной точкой | требует механизма сходимости, для которого нет ни экспериментальных данных, ни оракула сходимости; это отдельный исследовательский вопрос, а не архитектурное решение ARCH-0 |
| **Схлопывание SCC (выбрано)** | сохраняет ацикличность → сохраняет все подтверждённые свойства; цикл не игнорируется, а становится **явно видимым** объектом (`INDIVISIBLE_BLOCK`); цена — потеря локализации внутри блока, и она честно отмечена в данных |

**Цена решения зафиксирована явно:** внутри `INDIVISIBLE_BLOCK` локализация невозможна, ремонт только целиком. Это ухудшение, но оно **измеримо и видно** (размер блока — прямой индикатор качества декомпозиции), в отличие от вариантов, где проблема прячется.

**Ограничение честности:** OQ-6 — циклы не тестировались экспериментально. Механизм спроектирован так, чтобы **не разрушать** проверенное ядро, но сам он остаётся непроверенным.

## 6. Алгоритмы

### 6.1 Транзитивное замыкание вниз (candidate affected set)

```
FUNCTION downstream_closure(origin, graph):
    reverse_index ← предвычисленный индекс: claim → [прямые потомки]
    seen ← ∅
    frontier ← [origin]
    WHILE frontier не пуст:
        cur ← pop(frontier)
        FOR each child в reverse_index[cur]:
            IF ребро(cur→child).status ≠ REFUTED AND child ∉ seen:
                seen ← seen ∪ {child}
                push(frontier, child)
    RETURN seen
```
Сложность: O(V + E) при предвычисленном индексе. Подтверждено как точное (F34).

### 6.2 Определение корневых origin (root origins)

Прямая реализация вывода F31: собственный дефект claim **не** делает его корнем, если он достижим из другого дефектного claim.

```
FUNCTION root_origins(defective_claims, graph):
    roots ← ∅
    FOR each c в defective_claims:
        ancestors ← upstream_closure(c, graph)
        IF ancestors ∩ defective_claims == ∅:
            roots ← roots ∪ {c}
    RETURN roots
```

**Почему именно так:** попытка определять корень по признаку «его собственная проверка провалилась» была реализована и **дала неверный результат** на контрольном случае (F31) — каскадный claim помечался как независимый дефект. Корректная реализация обязана смотреть на предков.

### 6.3 Классификация ошибки

```
FUNCTION error_class(claim, defective, roots, graph):
    IF claim ∉ defective:            RETURN NO_ERROR
    IF claim.state == UNKNOWN:       RETURN UNKNOWN
    IF claim ∈ roots:                RETURN ERROR_LOCAL
    RETURN ERROR_DEPENDENCY
```

Плюс отдельные классы, наблюдавшиеся в реальных данных (F39):
- `MULTIPLE_LOCAL` — |roots| > 1, каждый локализован чисто;
- `ERROR_GLOBAL` — дефект есть, но `roots` пусто или не определяется (в реальных данных не наблюдался ни разу, но класс сохранён для полноты).

## 7. Метрики качества графа (для диагностики, не для решений)

| Метрика | Что показывает |
|---|---|
| `branching_factor` (max out-degree) | насколько граф действительно ветвится (если 1 — это цепочка, и выгода от независимых ветвей отсутствует) |
| `dependency_depth` | длина максимального пути; растёт → растёт каскадный риск |
| `merge_in_degree` | сколько ветвей сходятся |
| `unknown_dependency_ratio` | доля неподтверждённых рёбер; высокая → область влияния будет часто уходить в `unknown_set` |
| `indivisible_block_size` | размер схлопнутых SCC; растёт → теряется локализация |
| `hypothesis_ratio` | доля `HYPOTHESIS` рёбер |

Эти метрики **не участвуют в принятии решений** — они диагностические. Основание для осторожности: F19 (скалярная метрика не определяет действие) и общий запрет на «магический global score».
