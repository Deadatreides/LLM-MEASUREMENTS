# CONTEXT_MODEL.md — что именно получает модель

## 1. Принцип

**Модель никогда не получает весь граф.** Контекст строится **под конкретное действие** из явно перечисленных источников.

Требование §25 задания. Экспериментальное основание — F25: у одной из моделей непривычный формат контекста вызвал срыв в многословность, из-за которого локальный ремонт стал дороже полной генерации. Контекст — не «чем больше, тем лучше», а параметр с собственной ценой и собственными режимами отказа.

---

## 2. Слои контекста

| Слой | Что содержит | Когда включается |
|---|---|---|
| `TASK_CONTEXT` | исходная формулировка задачи | почти всегда |
| `ARTIFACT_CONTEXT` | содержимое конкретных артефактов (версионно) | когда действие работает с существующим артефактом |
| `CLAIM_CONTEXT` | формулировка целевого claim и его соседей по артефакту | `EXPAND`, узкий `REGENERATE` |
| `DEPENDENCY_CONTEXT` | **только прямые upstream** целевого claim, в их текущих версиях | когда цель зависит от чего-либо |
| `EVIDENCE_CONTEXT` | результаты проверок (что именно провалилось) | ремонт по конкретной коллизии |
| `REPAIR_CONTEXT` | что именно требуется изменить и что менять **запрещено** | `PATCH`, `REGENERATE` в рамках плана |

---

## 3. Сборка контекста по действию

```
FUNCTION build_context(action, graph) -> Context:
    ctx ← ∅
    SWITCH action.type:

      GENERATE:
        ctx += TASK_CONTEXT
        ctx += DEPENDENCY_CONTEXT(прямые upstream целевого claim, текущие версии)
        ctx += output_contract из prompt_profile
        # НЕ включать: соседние ветви, историю версий, evidence

      REGENERATE (в рамках плана ремонта):
        ctx += TASK_CONTEXT
        ctx += DEPENDENCY_CONTEXT(прямые upstream, ТЕКУЩИЕ версии)
        ctx += REPAIR_CONTEXT{
                 что менять: целевой claim,
                 что НЕ менять: claims с necessity ∈ {MAY_REUSE, DO_NOT_TOUCH}
               }
        ctx += EVIDENCE_CONTEXT(что именно провалилось) — ТОЛЬКО если HARD
        # НЕ включать: предыдущую неверную версию (см. §4)

      PATCH:
        ctx += ARTIFACT_CONTEXT(текущая версия целиком)
        ctx += REPAIR_CONTEXT(локализованная область)
        ctx += EVIDENCE_CONTEXT(HARD-результат проверки)

      VERIFY через SOFT-шов:
        ctx += проверяемый артефакт
        ctx += эталон/контракт, относительно которого проверяем
        # НЕ включать: кто произвёл артефакт, прошлые вердикты (см. §5)

      DECOMPOSE:
        ctx += TASK_CONTEXT
        ctx += ARTIFACT_CONTEXT(разбиваемый артефакт)
        # НЕ включать: остальной граф

    IF size(ctx) > operator.context_capacity * SAFETY_MARGIN:
        применить стратегию сокращения (§6)
    RETURN ctx
```

## 4. Что сознательно НЕ попадает в контекст

### 4.1 Предыдущая неверная версия при `REGENERATE`

**Не включается по умолчанию.**

Основание — F1: ошибка привязана к паре (оператор, задача) и воспроизводится в ~3 случаях из 4 без всякой подсказки. Показ модели её же предыдущего неверного ответа не имеет экспериментального подтверждения как средство исправления, а риск закрепления той же ошибки прямой.

Исключение: `PATCH`, где изменение по определению делается **над** существующим текстом.

**OQ-CTX-1:** влияние показа предыдущей неверной версии на исправление ошибки в этой архитектуре не измерялось. Помечено как открытый вопрос, а не решено умолчанием.

### 4.2 Соседние независимые ветви

Не включаются. Основание — F35: ветви структурно независимы; их содержимое не нужно для генерации и лишь увеличивает стоимость и риск дрейфа.

### 4.3 Собственные прошлые вердикты при `VERIFY`

При SOFT-проверке модель не получает информацию о том, кто произвёл артефакт и какие вердикты выносились раньше.

Основание — F9/F11: оператор в роли верификатора уже систематически смещён (в этих данных — в сторону ложного отказа). Добавление информации о происхождении артефакта создаёт дополнительный канал смещения, который нечем скорректировать.

### 4.4 Полная история версий

Не включается. Доступна для аудита и отката, но не подаётся в модель — стоимость линейно растёт, польза не подтверждена.

## 5. Изоляция при проверке

```
ИНВАРИАНТ CTX-1:
  контекст SOFT-проверки НЕ содержит:
    - идентификатор оператора, произведшего проверяемый артефакт
    - прошлые вердикты по этому артефакту
    - информацию о том, что артефакт уже был отвергнут/принят
```

Цель — не дать одному и тому же оператору «согласиться с собой» через контекст. Это частичная мера: она не делает `SELF_JUDGEMENT` сильнее (сила остаётся `WEAK` по EVIDENCE_MODEL.md §2), но убирает наиболее очевидный канал корреляции.

## 6. Стратегия сокращения при переполнении

Порядок отбрасывания (от наименее к наиболее ценному):

```
1. EVIDENCE_CONTEXT слабых (SOFT) проверок
2. CLAIM_CONTEXT соседей по артефакту
3. ARTIFACT_CONTEXT родителей, не являющихся прямыми upstream
4. детализация DEPENDENCY_CONTEXT (оставить только значения, убрать обоснования)

НИКОГДА не отбрасывается:
   - TASK_CONTEXT
   - output_contract
   - прямые upstream целевого claim
   - REPAIR_CONTEXT (что менять / что не менять)
```

Если после всех сокращений контекст не помещается — действие возвращает `CONTEXT_OVERFLOW`, и планировщик обязан выбрать другой путь (например, `DECOMPOSE` цели или оператора с большим `context_capacity`). Молчаливое обрезание запрещено: оно порождает ошибки, неотличимые от ошибок модели.

---

## 7. Контекст фиксируется в provenance

Каждое действие сохраняет `input_context_ref` — **что реально ушло в модель**, а не «что предполагалось отправить».

Основание — F45: дефекты обнаруживались пересчётом по сохранённому сырью. Без записи фактического контекста невозможно отличить «модель ошиблась» от «мы отправили не то».

## 8. Открытые вопросы

- **OQ-CTX-1** — влияние показа предыдущей неверной версии (см. §4.1).
- **OQ-CTX-2** — оптимальная глубина `DEPENDENCY_CONTEXT`: включать только прямых upstream или транзитивных предков. Архитектура выбирает **только прямых** (минимальный достаточный по структуре графа), но это не измерялось.
- **OQ-CTX-3** — влияние формата контекста на многословность оператора (наблюдалось у одной модели, F25) не изучено систематически.
