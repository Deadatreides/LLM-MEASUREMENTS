# SEAM_MODEL.md — швы

## 1. Определение

**SEAM** — наблюдаемая граница между состояниями/артефактами/claims, на которой возможна проверка совместимости.

Шов **не является** проверкой «правильности вообще». Шов проверяет **конкретное отношение** между конкретными участниками. Из этого следует главное ограничение: шов не создаётся из соседства — только из выраженного отношения (то же требование, что и для dependency, §7 задания).

```
SEAM := (seam_type, seam_class, participants, check_procedure) → EVIDENCE
```

Шов **производит evidence**, а не состояние. Перевод claim в `CORRECT`/`INCORRECT` делает STATE ENGINE на основании силы полученного evidence (STATE_MACHINE.md §2). Это разделение обязательно: оно не даёт «шов сказал PASS» автоматически стать «claim корректен» — ровно тот механизм, который в эксп. 2 привёл к молчаливому закрытию задачи с ошибкой (F12).

## 2. Классы швов: HARD / SOFT / UNKNOWN

Это разделение — центральное в документе и напрямую следует из F9–F14.

| Класс | Определение | Может ли один давать `CORRECT` | Примеры |
|---|---|---|---|
| **HARD** | существует объективная, детерминированная, воспроизводимая процедура проверки, не зависящая от суждения модели | **да** | выполнение тестов, точное сравнение чисел, AST-разбор, проверка схемы |
| **SOFT** | есть только модельное или эвристическое свидетельство | **нет, никогда** | «модель считает, что реализация соответствует спецификации» |
| **UNKNOWN** | данных для проверки недостаточно / процедура неприменима | нет | нет oracle для утверждения |

### 2.1 Жёсткое правило

```
SOFT seam НИКОГДА не переводит claim в CORRECT.
SOFT seam МОЖЕТ:
  - породить COLLISION (сигнал «посмотрите сюда»)
  - перевести claim в CONFLICTED
  - понизить confidence
  - инициировать запрос более сильного evidence
SOFT seam НЕ МОЖЕТ:
  - закрыть проверку
  - разрешить коллизию
  - служить единственным основанием для REJECTED/INCORRECT
```

**Обоснование по данным:**
- F9: сгенерированный моделью верификатор отверг заведомо правильный эталон в 76.8% случаев — то есть SOFT-шов в роли решающего давал бы массовые ложные отказы;
- F11: false reject доминировал у всех моделей, включая лучшую;
- F12: обратный случай тоже реален — SOFT-шов сказал PASS при настоящей ошибке, и ремонт не запустился;
- F10: внутренняя «строгость» SOFT-шва (высокий mutation score) не коррелирует с его внешней корректностью.

Иными словами: SOFT-шов ошибается в обе стороны, и его ошибки **не случайны**, а систематичны. Он полезен как **привлечение внимания**, вреден как **арбитр**.

### 2.2 Классификация не по намерению, а по процедуре

Шов относится к HARD **только** если его `check_procedure` детерминирована и не содержит вызова языковой модели. Если процедура включает вызов модели в любой роли — шов SOFT, независимо от того, насколько «объективно» сформулирована задача для модели.

Отдельно: артефакт типа `TESTS`, **сгенерированный моделью**, при исполнении даёт `EXECUTION`-evidence — процедура исполнения детерминирована, но **предмет проверки произведён моделью**. Такой шов классифицируется как:
- **HARD относительно вопроса** «соответствует ли реализация этим тестам»;
- **SOFT относительно вопроса** «корректна ли реализация».

Это разделение прямо описывает конфигурацию, породившую F9/F12, и не даёт спутать два вопроса.

## 3. Типы швов

| Тип | Что проверяет | Типичный класс | Экспериментальный статус |
|---|---|---|---|
| `SEAM_CONTRACT` | соответствие артефакта объявленному интерфейсу/спецификации | HARD, если контракт машинно-проверяем (сигнатура, схема); иначе SOFT | подтверждён (AST-проверка сигнатуры, эксп. 8) |
| `SEAM_EXECUTION` | результат исполнения/вычисления | HARD | подтверждён (эксп. 1, 2, 8) |
| `SEAM_CONSISTENCY` | взаимная непротиворечивость двух артефактов (текст утверждает одно — вычисление делает другое) | HARD, если оба формализуемы | **F33: механизм проверен на искусственных случаях, но ни разу не сработал на реальных данных.** Полезность на реальных данных не подтверждена (OQ-2) |
| `SEAM_DEPENDENCY` | согласованность downstream с текущей версией upstream | HARD, если значение прослеживается | подтверждён (эксп. 9: именно этот шов делает STALE осмысленным) |
| `SEAM_EVIDENCE` | взаимная совместимость самих evidence по одному subject | HARD (сравнение метаданных детерминировано) | новый, не проверялся отдельно |
| `SEAM_FORMAT` | соответствие вывода объявленному output_contract | HARD | подтверждён (парсинг секций, 94.4% полных разборов, F27) |
| `SEAM_DRIFT` | расхождение новой версии артефакта с предыдущей за пределами разрешённой области | HARD | частично (мутационный/дрифт-анализ эксп. 2) |
| `SEAM_CONFLICT` | расхождение между независимыми источниками по одному claim | HARD (сравнение классификаций детерминировано), но **интерпретация ограничена** | подтверждён как детектор (F32: 14 реальных конфликтов, невидимых плоскому режиму), но **как сигнал для распределения бюджета — ненадёжен** (F16) |

### 3.1 Отдельно про `SEAM_CONFLICT`

Этот шов даёт наиболее ценную информацию, которой нет в плоском режиме (F32), и одновременно требует наибольшей осторожности в интерпретации:

- **Что он надёжно означает:** «здесь независимые источники разошлись» — это факт, наблюдаемый механически.
- **Чего он НЕ означает:** «здесь правильный ответ близко». F16 прямо опровергает: для сильной модели вероятность найти верный ответ в точке конфликта была существенно **ниже**, чем там, где конфликта нет. Конфликт чаще указывает на систематическую слепую зону.
- **Что надёжнее:** отсутствие конфликта как индикатор «сюда можно не тратить бюджет» (F15).

Поэтому `SEAM_CONFLICT` порождает коллизию типа `SOURCE_DISAGREEMENT` (COLLISION_MODEL.md), но **не** повышает автоматически приоритет затрат на этот claim.

### 3.2 Обязательный учёт независимости в `SEAM_CONFLICT`

Шов обязан записывать в evidence `independence_axis` (DATA_MODEL.md §6). Согласие или расхождение двух генераций одной модели с одним промптом и разными seed — **почти не информация** (F1: ошибка повторяется в ~75% случаев; F5: растёт поверхностное разнообразие, а не разнообразие режимов ошибки).

```
сила сигнала SEAM_CONFLICT по оси:
  SEED         → минимальная  (F1)
  TEMPERATURE  → низкая       (F5: поверхностное разнообразие ≫ разнообразие ошибок)
  PROMPT       → низкая       (F7: в этих данных не лучше, чем другой seed)
  MODEL        → наивысшая    (F6: минимальная доля тихого согласия на ошибке)
  EXTERNAL     → наивысшая
```

Это ранжирование **не является** численной константой — это порядок, подтверждённый F6/F7 на одном наборе данных, и он подлежит перепроверке при смене класса моделей.

## 4. Жизненный цикл шва

```
DECLARED (объявлен при декомпозиции: известно, между чем проходит)
   │
   ▼
APPLICABLE / INAPPLICABLE  (есть ли всё нужное для проверки)
   │
   ▼
EVALUATED → PASS / FAIL / ERROR
   │
   ▼
EVIDENCE создано (с типом, силой, воспроизводимостью, осью независимости)
   │
   ▼
STATE ENGINE решает, меняется ли состояние
```

**`INAPPLICABLE` — не отказ.** Это нормальный исход, ведущий claim в `UNVERIFIED` (не в `UNKNOWN` и тем более не в `INCORRECT`). Различение важно: F44 показал, что смешение «проверка неприменима» и «результат неизвестен» искажает картину состояния графа на десятки процентов.

**`ERROR` (сама процедура проверки сломалась) — отдельный исход**, не равный `FAIL`. Он даёт evidence типа `UNKNOWN`, а не `REFUTES`. Основание — F45: дефекты проверяющих правил реальны и встречались в проекте многократно; система, трактующая сбой проверки как «claim неверен», превращает свои баги в ложные ошибки модели.

## 5. Контроль качества самих швов

Прямое следствие F44 и F45: **проверяющие правила сами являются источником ошибок**, причём систематических.

Архитектура обязана предусматривать:

1. **Контрольные случаи с заранее известным ответом.** Для каждого HARD-шва — набор входов, где ожидаемый результат известен по построению (включая заведомо корректный и заведомо некорректный вход). Шов, не проходящий свои контрольные случаи, помечается `seam.trusted = false` и **не может** производить evidence силы HARD.

   Основание: в этом проекте все обнаруженные дефекты классификаторов были найдены именно так (F45), и ни один — на реальных данных.

2. **Мониторинг доли `INAPPLICABLE`.** Резкий рост — сигнал, что шов за-строг (ровно ситуация F44: 32% ложного UNKNOWN из-за за-строгих правил распознавания).

3. **Запрет на подстройку под результат.** Изменение шва после просмотра реальных результатов допустимо только при одновременном условии: контрольные случаи пересчитаны и остались неизменными. Это процедурное требование, унаследованное из методологии экспериментов.

## 6. Что шов НЕ делает

| Не делает | Почему |
|---|---|
| Не выносит вердикт о состоянии | разделение seam → evidence → state (F12) |
| Не создаётся из соседства claims | требование §7 задания |
| Не агрегируется в общий «score согласованности» | нет экспериментального основания; запрет на magic global score |
| SOFT-шов не закрывает проверку | F9, F10, F11, F12 |
| Не считает повтор одной модели независимым источником | F1, F5, F7 |
