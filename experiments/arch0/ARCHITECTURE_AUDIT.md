## Часть 1. Проверка A–L (§36 задания)

Для каждого вопроса: траектория через архитектуру и честный вердикт.

### A. Можно ли представить простой «привет»?

```
TASK("привет", class=EXPLANATION, risk=LOW)
 → DECOMPOSITION_GATE: нет ни одного потенциального HARD-шва → NO_DECOMPOSE
 → 1 ARTIFACT (EXPLANATION), 1 CLAIM (ATOMIC)
 → DEPENDENCY GRAPH: 0 рёбер
 → SEAM: применимых нет → claim.state = UNVERIFIED
 → COLLISION: нет
 → STOP(NO_COLLISION_AND_NO_VERIFICATION)
 → API отдаёт результат с явным маркером UNVERIFIED
```

**ДА.** Стоимость графовой машинерии здесь близка к нулю (гейт срабатывает до построения). Важно: система **не притворяется**, что проверила — `UNVERIFIED` доезжает до потребителя (I-4).

### B. Можно ли представить объяснение бинома Ньютона?

```
ARTIFACTS: A1_STATEMENT (формулировка теоремы)
           A2_FORMULA   (общий вид разложения)
           A3_DERIVATION(вывод/обоснование)
           A4_EXAMPLE   (конкретное разложение, напр. (a+b)^4)
CLAIMS:    C1 формулировка   C2 формула   C3 шаги вывода   C4 числовой пример
DEPS:      C1→C2 (CAUSAL), C2→C3 (DERIVATION), C2→C4 (COMPUTATIONAL)
SEAMS:     C4 — HARD (символьное/численное раскрытие проверяемо)
           C2 — HARD (сверка с известной формулой, EXACT_MATCH)
           C3 — SOFT или UNKNOWN (корректность изложения вывода)
           C1 — UNKNOWN (педагогическое качество формулировки)
```

**ДА, но с расщеплением.** Часть claims получает `CORRECT` механически (формула, числовой пример), часть остаётся `UNVERIFIED` (ясность изложения). Это ровно режим `oracle_availability = PARTIAL`, и он обрабатывается штатно: ошибка в примере локализуется и чинится точечно, не затрагивая формулировку.

**Что архитектура здесь НЕ может:** сказать, что объяснение хорошее. Она может сказать, что оно математически непротиворечиво и пример верен. Это честное ограничение, а не обход вопроса.

### C. Сложная математическая задача?

**ДА.** Это основной проверенный класс. Многошаговая задача → цепочка `DERIVATION`/`COMPUTATIONAL` claims, HARD-швы на числовых шагах. Подтверждено эксп. 8 и 9: локализация работает (F29, F34), независимые ветви сохраняются (F35).

### D. Код?

**ДА.** `A1_CONTRACT` → `A2_EDGE_CASES` → `A3_IMPLEMENTATION`; `SEAM_EXECUTION` через исполнение эталонных тестов = HARD; `SEAM_CONTRACT` через AST = HARD.

**Ключевая деталь:** артефакт `TESTS`, произведённый моделью, — обычный артефакт со своим состоянием, а **не** оракул (F9: такие тесты отвергали заведомо правильный эталон в большинстве случаев). Он даёт HARD-evidence на вопрос «соответствует ли реализация этим тестам» и SOFT на вопрос «корректна ли реализация» (I-14).

### E. Задача без oracle?

**ДА, в ограниченном смысле.** Режим `graph consistency only` (EVIDENCE_MODEL.md §6): можно фиксировать структурные несовместимости, локализовать конфликт, определять незатронутые ветви; нельзя утверждать `CORRECT`.

**Честное ограничение:** экономика при этом деградирует — `VERIFY` без oracle стоит как генерация, и механизм `STALE`→`VERIFY`→`MAY_REUSE` теряет смысл (FM-13). Архитектурно корректно, экономически не проверено (**OQ-4**, крупнейший пробел).

### F. Несколько независимых ветвей?

**ДА, и это сильнейшее место.** F35: 0 загрязнений из 80 контролируемых случаев. `downstream_closure` структурно не заходит в соседние ветви; всё вне `candidate_affected_set` получает `DO_NOT_TOUCH`.

### G. Общий upstream claim?

**ДА.** F34/F36: при изменении общего корня оба поддерева корректно попадают в область влияния; merge-узел не требует особого механизма. Проверено на всех 20 задачах эксп. 9 (сохранение структурного размера области при инъекции в корень).

### H. Конфликт двух независимых источников?

**ДА.** `SEAM_CONFLICT` → коллизия `SOURCE_DISAGREEMENT` → оба claim `CONFLICTED`.

**Критично, что архитектура здесь НЕ делает:** не выбирает победителя большинством и не повышает автоматически приоритет трат на конфликтный claim. Основание — F16: конфликт указывает скорее на систематическую слепую зону, чем на близость истины; F15: надёжнее обратный сигнал («нет конфликта → можно не тратить»).

При двух HARD-источниках в конфликте (`EVIDENCE_CONFLICT`) подозреваются **оба**, включая саму инфраструктуру проверки (F45).

### I. Сохраняется ли правильная работа после локального ремонта?

**ДА, механизм есть; проверен частично.**
- `DO_NOT_TOUCH` для всего вне области влияния (F35);
- `post_repair_check` проверяет неизменённые claims, достижимые из области ремонта (REPAIR_MODEL.md §6);
- обнаруженная скрытая зависимость материализуется как ребро.

**Ограничение:** проверка возможна только там, где есть HARD-шов. В эксп. 9 скрытых зависимостей post-hoc не найдено, но граф там был задан заранее корректно.

### J. Можно ли откатить состояние?

**ДА.** Append-only хранилище, версионирование всех сущностей, `STATE_RECORD` на каждый переход, `graph_snapshot(graph_version)`, `rollback` переключает указатель без удаления (I-2, I-3).

### K. Можно ли остановить бессмысленный retry?

**ДА, четырьмя независимыми ограничителями:** `REPEATED_STATE` (хеш графа+плана), `REPAIR_OSCILLATION` (план N = план N−2), `MAX_ITERATIONS`, `BUDGET_EXHAUSTED`. Плюс правило «уже потраченное не влияет на оценку следующего действия» (BUDGET_MODEL.md §5).

Дополнительно: `NO_EXPECTED_GAIN` опирается на самый надёжный подтверждённый сигнал (F15/F20) и не опирается на опровергнутый (F16).

### L. Можно ли заменить модель без изменения core?

**ДА.** `GRAPH CORE` и `STATE ENGINE` не импортируют ничего связанного с LLM (I-18, проверяется линтером в CI). `ModelAdapter` возвращает сырьё и не парсит. Смена модели затрагивает только уровень 4.

---

### Итог части 1

**Все двенадцать проверок пройдены.** Три (B, E, I) пройдены **с явно названными ограничениями**, которые зафиксированы в документах, а не обойдены.

## Часть 2. Проблемы старого Мицелия (§37 задания)

Источник фактов: `mycelium/RESULTS.md` (прогон `sh2_200`, 200 задач MBPP, 400 записей), `mycelium/lab/REPORT.md`, `mycelium/READ_ONLY_STAGE1_REPORT.md`. Всё ниже — измеренные результаты того проекта, не реконструкция.

### OLD-1. Оркестрация проиграла простому best-of-N на 23 п.п. при равном бюджете

**Измерено:** `solved M = 29.0%` против `BoN-G = 52.0%` при 1080 против 1154 токенов. Причина названа прямо: пул кандидатов у baseline лучше **до всякого отбора** — 8.4 генерации сильнейшей модели против 2 черновиков смешанного пула. Бюджет уходил на критику и синтез вместо сэмплов.

**НОВЫЙ МЕХАНИЗМ:** `EVERY_PLAN_COMPARES_ALTERNATIVES` (I-12) — план обязан сравнить себя с `FULL_RETRY`, иначе отвергается планировщиком. Плюс `EVERY_ACTION_HAS_COST` (I-11).

**ПОЧЕМУ НЕ ПОВТОРИТСЯ ТАК ЖЕ:** структурно невозможно построить план, который тратит бюджет на надстройку, не сравнив его с прямой генерацией. Это assert, а не рекомендация.

**Честная оговорка:** это не гарантирует выигрыша — это гарантирует, что проигрыш будет **виден в момент планирования**, а не обнаружен через 200 задач. Независимо: F46 подтвердил тот же эффект в эксп. 2 на других задачах, то есть проблема воспроизводима и не была особенностью того пула.

### OLD-2. Синтез не улучшал результат

**Измерено:** из 200 задач `E_score_ext` был `>0` только в **6**, `<0` в 53, `=0` в 141. Вывод самого проекта: «синтез либо воспроизводит лучший черновик, либо портит его».

**НОВЫЙ МЕХАНИЗМ:** действия `VOTE`/`SYNTHESIZE` **отсутствуют в пространстве действий** (ACTION_MODEL.md §5). Их нет не по вкусу, а по данным — F14/F16/F17 независимо подтвердили то же самое в новых экспериментах.

**ПОЧЕМУ НЕ ПОВТОРИТСЯ:** нет сущности, которая могла бы это сделать. Комбинирование результатов заменено на локализацию расхождения (`SEAM_CONFLICT`) без выбора победителя.

### OLD-3. Скалярная агрегированная оценка была анти-коррелирована с истиной

**Измерено:** `ρ(скалярная mu, baseline) = −0.429`, тогда как разделённая по ролям — `+0.771`. Формулировка отчёта: «смешивание шкал ролей не просто теряет сигнал, оно его портит».

**НОВЫЙ МЕХАНИЗМ:** `NO_GLOBAL_QUALITY_SCORE` (I-19). Профиль оператора ведётся **по scope** (artifact_type × task_class × prompt_profile × sampling), а не одним числом. Профиль без scope запрещён структурой данных (DATA_MODEL.md §13).

**ПОЧЕМУ НЕ ПОВТОРИТСЯ:** в схеме данных нет поля, куда такой скаляр можно было бы положить, и нет решения, которое его читало бы. Подкреплено независимо: F18 показал, что метрика, сильно коррелирующая с общим выигрышем (r≈0.89), может не коррелировать с предельным (r≈0.002).

### OLD-4. Принудительное «вечное исследование» съедало бюджет

**Измерено:** `σ_min = 0.2` гарантировал, что сильнейшая модель получала лишь 40.2% вызовов; остальное уходило слабым моделям (baseline 0.48–0.50 против 0.684 у сильнейшей).

**НОВЫЙ МЕХАНИЗМ:** нет ни bandit, ни принудительной доли исследования. Выбор оператора — правило политики по типу коллизии (REPAIR_MODEL.md §4.2), политика не может расширять множество кандидатов (I-17), и каждое действие проходит бюджетный контроль.

**ПОЧЕМУ НЕ ПОВТОРИТСЯ ТАК ЖЕ:** нет компонента, который тратит бюджет по априорному расписанию независимо от состояния задачи.

**Честная оговорка:** отказ от исследования — это тоже риск (можно застрять на одном операторе). Он купируется не квотой, а `REPEATED_STATE`/`REPAIR_OSCILLATION` и правилом приоритета `CHANGE_MODEL` при устойчивой ошибке (F6/F22). Насколько такая замена работает — **не измерено**.

### OLD-5. Пороговые механизмы никогда не срабатывали

**Измерено:** `entropy_threshold` не отсекал ничего (медиана `H_norm` 0.93 против порога 0.08); квоты каст ни разу не сдвинулись (равновесие 0.017 против порога 0.083); `death/split` — 0 событий; `hypercycle_multinomial` пришлось выключить, он стоил 16.7 п.п. solved.

**НОВЫЙ МЕХАНИЗМ:** FM-17 — каждый механизм имеет счётчик срабатываний; нулевой счётчик за значимый объём диагностируется явно. Плюс архитектура **не содержит** порогов на агрегированных величинах: решения принимаются по типу состояния и наличию evidence, а не по преодолению скалярного порога.

**ПОЧЕМУ НЕ ПОВТОРИТСЯ ТАК ЖЕ:** уменьшено число мест, где порог вообще нужен, а оставшиеся (лимиты итераций, бюджет) — не статистические, а жёсткие ограничители, чьё срабатывание не зависит от калибровки под данные.

**Независимое подтверждение проблемы:** F26 в новых экспериментах — состояние «продуктивная неопределённость» не наблюдалось ни разу в трёх независимых прогонах, потому что признак был операционализирован так, что вырождался. То есть мёртвые механизмы возникают легко, и без счётчиков их не видно.

### OLD-6. Контур управления был перемешан с исполнением

**Наблюдение:** починка отбора потребовала отдельного большого восстановительного аудита (`AUDIT_RESTORE.md`, `FIX_PLAN.md`); дефекты жили в системе через несколько прогонов; часть кода оказалась мёртвой (`QualityScorer.score()`).

**НОВЫЙ МЕХАНИЗМ:** строгие уровни с однонаправленными зависимостями (API_BOUNDARIES.md §1, §12), `POLICY_CANNOT_WRITE` (I-17), `CORE_IS_MODEL_AGNOSTIC` (I-18), проверка линтером импортов в CI.

**ПОЧЕМУ НЕ ПОВТОРИТСЯ ТАК ЖЕ:** политика физически не может изменить граф; её замена не затрагивает уровни 0–3.

### OLD-7. Ключевые дефекты обнаруживались поздно и большими блоками

**Наблюдение:** прогресс по прогонам `base_30 → sh1_30 → sh2_30 → sh2_200` показывает, что корректность контура отбора (`ρ` от +0.143 до +0.771, «лидер верен» — только на четвёртом прогоне) устанавливалась через серию больших запусков.

**НОВЫЙ МЕХАНИЗМ:** контрольные случаи с заранее известным ответом для каждого HARD-шва; шов без прохождения self-test не может производить HARD-evidence (I-15). Плюс `RAW_IS_ALWAYS_PERSISTED` (I-16) — перепроверка без перегенерации.

**ПОЧЕМУ НЕ ПОВТОРИТСЯ ТАК ЖЕ:** F45 — в новых экспериментах **все шесть** найденных дефектов проверяющих правил были обнаружены именно контрольными случаями и **ни один** — на реальных данных. Механизм эмпирически результативен.

### Чего мы про старый Мицелий утверждать не можем

Прямо по требованию §37 («если данных недостаточно — так и написать»):

- **Не можем утверждать, что оркестрация проигрывает в принципе.** Сам отчёт `RESULTS.md` фиксирует честную границу: в том пуле была одна доминирующая модель (решала 47% задач в одиночку), а замысел исходил из пула разнородных моделей сопоставимой силы. На таком пуле баланс мог быть иным.
- **Не можем утверждать, что термодинамический/гиперцикловый контур бесполезен.** Отчёт фиксирует, что он ожил (`Φ` ненулевая в 28 из 30, `λ_L` стал измеримой величиной с медианой около нуля), но связь с исходом на достаточном объёме **не измерена**. Новая архитектура его не содержит — не потому, что он опровергнут, а потому, что нет данных, оправдывающих его включение.
- **Не можем утверждать, что причина провала — только состав кандидатов.** Это объяснение самого отчёта, и оно подкреплено (2.0 против 8.4 кандидатов на шаг), но альтернативные объяснения на тех данных не исключались.
- **Не можем утверждать, что новая архитектура выиграет у best-of-N.** Она этого и не обещает: F28 прямо показал, что декомпозиция не улучшает качество ответа. Она обещает **локализацию и управляемость ремонта** — и именно это, а не качество, должно измеряться дальше.

## Часть 3. Проверка на скрытые «магические» компоненты (§38)

Проверка: каждое решение отнесено к уровню, и ни одно не отдано «искусственному интеллекту вообще».

| Решение | Уровень | Проверено |
|---|---|---|
| нужна ли декомпозиция | STRUCTURAL (гейт) | детерминированный, DECOMPOSITION_MODEL.md §4 |
| границы claims | STRUCTURAL при схеме / MODEL без неё | помечается `boundary_source`; при MODEL → только HYPOTHESIS |
| существует ли зависимость | EVIDENCE | §3 DEPENDENCY_MODEL, типизированные основания |
| валиден ли claim | EVIDENCE + STATE | таблица переходов, порог HARD_ENOUGH |
| что затронуто | STRUCTURAL (граф) + EVIDENCE (сужение) | два явных шага |
| что чинить | STATE + POLICY | necessity детерминирована; выбор действия — политика |
| каким оператором | POLICY | заменяемый слой, правила задокументированы |
| содержание артефакта | MODEL | помечено `probabilistic`, не может дать CORRECT |
| когда остановиться | STATE + BUDGET | детерминированные STOP-условия |

**Найдено одно место, требующее явной пометки, и оно помечено:** вывод границ claims в отсутствие заранее заданной схемы — вероятностный, зависит от модели, и все порождённые им рёбра получают статус `HYPOTHESIS`, а не `CONFIRMED` (DECOMPOSITION_MODEL.md §2). Это **самый слабый шов архитектуры**, см. Часть 4.

Скрытых эвристик с необъяснённым поведением не найдено. Глобального score нет (I-19).

## Часть 4. Главный риск архитектуры

Формулируется отдельно, потому что он существеннее всех остальных.

> **Вся ценность архитектуры (локализация → экономия ремонта) держится на корректности графа. Все экспериментальные подтверждения этой ценности получены на графах, заданных заранее человеком и корректных по построению. Качество автоматически выведенного графа не измерялось ни разу.**

Цепочка зависимости:
```
F28: декомпозиция НЕ улучшает качество ответа и стоит дороже
  ⇒ она оправдана ТОЛЬКО экономией ремонта
F37/F38: экономия ремонта требует шага сужения через проверку
  ⇒ OQ-STALE: этот шаг никогда не запускался живьём
F34/F35: локализация точна
  ⇒ но измерено на графах, заданных заранее (OQ-DEC-1)
```

Если автоматически выведенный граф окажется существенно хуже заданного, или если шаг сужения не даст экономии на практике — архитектура превращается в чистую надбавку к стоимости. Это ровно тот исход, который уже был измерен в старом Мицелии (OLD-1) и подтверждён независимо (F46).

**Это не аргумент против реализации.** Это аргумент за то, что **первый же этап реализации обязан измерить именно это**, а не строить полную систему в надежде, что предпосылка верна.

```
ARCHITECTURE_STATUS = READY_FOR_IMPLEMENTATION
```

Блокирующих внутренних противоречий не найдено. Все двенадцать проверок A–L пройдены. Каждое архитектурное решение либо выводится из зафиксированного факта, либо помечено как OPEN QUESTION.

### 5.1 Подтверждённые экспериментами архитектурные инварианты

Эти свойства можно использовать как основания, а не как надежды:

1. **Транзитивное замыкание вниз по DAG даёт полную и безопасную область потенциального влияния** — recall = 1.0, ноль пропущенных зависимостей на 120 контролируемых случаях с независимой разметкой (F34).
2. **Независимые ветви не загрязняются** — 0 нарушений из 80 (F35). `DO_NOT_TOUCH` вне области влияния безопасен.
3. **Merge-узлы не требуют специального механизма** (F36).
4. **Область влияния строго шире минимально необходимого ремонта** — обязателен шаг сужения (F37, precision ≈ 0.47 при recall = 1.0).
5. **Сужать по умолчанию нельзя** — существенная доля реальных ошибок каскадирует (F38).
6. **Различить корень и симптом можно только через граф предков**, не поклеймной проверкой (F31).
7. **Декомпозиция даёт локализацию, а не качество, и стоит дороже** (F28, F29, F42).
8. **Ошибки LLM систематичны**: повтор той же конфигурации воспроизводит ошибку (F1) — повтор не является независимой проверкой.
9. **Смена модели — сильнейшая ось независимости** из проверенных (F6, F8, F22).
10. **Суждение модели о корректности ненадёжно в обе стороны** и не может быть жёстким оракулом (F9, F10, F11, F12).
11. **Отсутствие конфликта — надёжный сигнал «не тратить»; наличие конфликта — ненадёжный сигнал «тратить»** (F15, F16).
12. **Энтропия не предсказывает ценность следующего вычисления** (F18, F19).
13. **Проверяющая инфраструктура сама систематически ошибается**; дефекты ловятся контрольными случаями, а не реальными данными (F44, F45).
14. **Наибольшая измеренная экономия — от корректного распознавания «здесь ничего делать не нужно»** (F20, F21).

### 5.3 Непроверенные места

- **OQ-4 (крупнейший).** Поведение всей механики на задачах **без механического oracle**. Все факты получены там, где oracle был.
- **OQ-DEC-1.** Качество автоматически выведенной декомпозиции.
- **OQ-STALE / OQ-MRS.** Реальная экономия от шага сужения; близость приближения к истинному MRS на реальных каскадных ошибках.
- **OQ-1 (F26).** Существует ли операционализируемый сигнал «здесь дополнительная выборка ещё даёт новое». Три независимых эксперимента его не нашли.
- **OQ-2 (F33).** Полезность `SEAM_CONSISTENCY` на реальных данных.
- **OQ-6.** Циклические зависимости.
- **OQ-COMPLEX.** Графы существенно большего размера.
- **OQ-CTX-1..3.** Состав контекста: показ предыдущей неверной версии, глубина `DEPENDENCY_CONTEXT`, влияние формата на многословность.
- **PATCH по сигналу HARD-шва** — измерялся только по сигналу SOFT-шва (F13), где показал низкую эффективность.

### 5.4 Минимальный следующий этап реализации

**Не строить всю систему.** Первый этап должен проверить главное допущение (Часть 4), потому что при его провале остальное не имеет смысла.

**ARCH-1: вертикальный срез на одном классе задач с механическим oracle.**

Объём:
```
ВКЛЮЧИТЬ:
  GRAPH CORE           полный (версионирование, обходы, детекция цикла)
  STORAGE              append-only, сырьё
  STATE ENGINE         полная таблица переходов + распространение STALE
  EVIDENCE ENGINE      типы, силы, оси независимости
  SEAM ENGINE          только HARD-швы + обязательные контрольные случаи
  REPAIR PLANNER       три множества + шаг сужения + сравнение стратегий
  ACTION EXECUTOR      GENERATE / REGENERATE / VERIFY / STOP
  POLICY               фиксированные правила (RuleBasedPolicy)
  MODEL ADAPTER        существующий GGUF-стенд

НЕ ВКЛЮЧАТЬ:
  router, bandit, PTG, SOFT-швы, PATCH, DECOMPOSE как действие модели,
  параллельность, MERGE, задачи без oracle
```

**Что этап обязан измерить (это его единственная цель):**

| Вопрос | Метрика | Что означает провал |
|---|---|---|
| Даёт ли шаг сужения экономию? | `stale_resolved_by_verify_ratio`; доля `STALE`, снятых `VERIFY` без регенерации | близко к нулю → A-1 ложно → механизм `STALE` бесполезен, архитектура теряет главный источник экономии |
| Дешевле ли граф-ремонт полного? | `cost(LOCAL_REPAIR) / cost(FULL_RETRY)` по реальным коллизиям | ≥1 систематически → повторение OLD-1/F46 |
| Насколько выведенный граф хуже заданного? | сравнить локализацию на одних задачах: граф задан вручную против выведенного | существенно хуже → A-2 ложно, нужен отдельный эксперимент по декомпозиции |
| Работают ли контрольные случаи швов? | число дефектов швов, пойманных self-test против пойманных на реальных данных | если реальными данными ловится больше — механизм I-15 не работает |

**Критерий перехода к ARCH-2:** первые два вопроса дали положительный ответ на статистически осмысленной выборке. Если нет — **не расширять систему**, а вернуться к эксперименту по конкретному провалившемуся допущению.

Это прямое применение урока OLD-1: там расширение системы продолжалось при неизмеренной базовой предпосылке, и цена ошибки составила несколько крупных прогонов.
