# DECOMPOSITION_MODEL.md — декомпозиция задачи

Центральная часть ARCH-0 (§23–24 задания).

---

## 1. Процесс

```
TASK
 → ARTIFACT PLAN        какие самостоятельные результаты нужны
 → CLAIM EXTRACTION     какие проверяемые утверждения внутри каждого
 → DEPENDENCY INFERENCE что от чего зависит
 → SEAM GENERATION      где проходят проверяемые границы
```

Каждый шаг производит структуру, которая **фиксируется до начала генерации содержимого** и не переписывается задним числом под результат.

Это процедурное требование, унаследованное из методологии экспериментов: во всех прогонах схема декомпозиции замораживалась до генерации. Причина не формальная — при перестройке графа после наблюдения результата теряется смысл понятий origin и affected region: граф начинает объяснять уже известный ответ, а не предсказывать область влияния.

---

## 2. Кто принимает решение о декомпозиции

Три уровня, строго разделённые:

| Решение | Уровень | Детерминизм |
|---|---|---|
| **Нужна ли декомпозиция вообще** | STRUCTURAL (гейт §4) | детерминированный |
| **Какая схема артефактов применима** | STRUCTURAL (реестр схем) | детерминированный |
| **Содержимое артефактов и claims** | MODEL | вероятностный |
| **Границы claims внутри артефакта** | STRUCTURAL при наличии схемы; MODEL при её отсутствии | смешанный, помечается |

**Ключевое:** когда границы claims выводит модель, результат помечается `boundary_source = MODEL` и рассматривается как **гипотеза о структуре**, а не как факт. Все выведенные так рёбра получают `status = HYPOTHESIS`.

Обоснование: во всех экспериментах, где граф был задан заранее и корректно (эксп. 8, 9), свойства локализации подтвердились полностью (F34, F35). Свойства графа, **выведенного моделью автоматически**, не измерялись ни разу — это OQ-DEC-1, крупный открытый вопрос.

## 3. Альтернативные декомпозиции

Допускаются. Одна задача может иметь несколько схем разбиения.

```
DECOMPOSITION {
  decomposition_id, task_id, schema_ref
  artifacts: [...], claims: [...], dependencies: [...]
  status ∈ {ACTIVE, ALTERNATIVE, SUPERSEDED}
  quality_indicators: {...}     # §6
}
```

**Как выбирается активная:**
1. Если есть заранее зафиксированная схема для `task_class` — она приоритетна (детерминированный путь).
2. Иначе — по структурным индикаторам качества (§6), а **не** по «оценке качества моделью».
3. Альтернативы сохраняются со статусом `ALTERNATIVE`, не удаляются.

**AMBIGUOUS-декомпозиция.** Если два разбиения одинаково допустимы и индикаторы не различают их — обе сохраняются, активной становится **более крупнозернистая** (меньше рёбер = меньше риск ложных зависимостей), а факт неоднозначности фиксируется. Требование §2 задания: не выбирать молча.

## 4. Гейт: DECOMPOSE ONLY IF BENEFIT > COST

Главное правило. Формальная структура (не численная калибровка — для неё нет данных).

### 4.1 Почему гейт обязателен

| Факт | Следствие |
|---|---|
| F28 | декомпозиция **не улучшает** качество ответа: Oracle идентичен плоскому режиму, Pass@1 даже слегка ниже, токенов существенно больше |
| F46 | артефактный pipeline не превзошёл плоский best-of-N при равном токенном бюджете |
| F29 | но декомпозиция даёт то, чего плоский режим не может: локализацию ошибки в подмножество claims |
| F42 | и реальная область ремонта — обычно часть задачи, почти никогда не вся |

Вывод: **декомпозиция — инструмент локализации и экономии ремонта, а не улучшения качества.** Значит, она оправдана только там, где локализация действительно понадобится.

### 4.2 Структура функции

```
BENEFIT(decomposition) складывается из:
   independence_gain      — возникают ли реально независимые ветви
                            (F35: только они дают гарантию «не трогать»)
   verifiability_gain     — появляются ли HARD-швы, которых не было
                            в монолите (без них локализация нечем не подтверждается)
   localization_gain      — насколько сужается ожидаемая область ремонта
                            относительно всей задачи (F29, F42)
   repair_saving_expected — ожидаемая экономия при ремонте
                            = P(ошибка) × (cost_full_retry − cost_local_repair)
   parallelism_gain       — можно ли считать ветви параллельно

COST(decomposition) складывается из:
   extra_tokens           — структурированный вывод дороже (F28)
   extra_calls            — если артефакты генерируются раздельно
   graph_overhead         — построение, обход, распространение состояния (F41)
   context_loss_risk      — риск, что фрагмент, лишённый контекста,
                            будет хуже (F24: узкий вопрос вне контекста
                            систематически ухудшал результат для
                            конфликтных claims)
   wrong_decomposition_risk — риск ложных или пропущенных зависимостей
```

### 4.3 Правило гейта

```
FUNCTION should_decompose(task, candidate_schema, profiles, budget) -> bool:
    # Обязательные условия (все должны выполняться)
    IF нет ни одного потенциального HARD-шва в схеме:
        RETURN false          # локализация будет нечем подтверждена
    IF схема не порождает ни одной независимой ветви
       AND глубина цепочки ≤ 2:
        RETURN false          # нечего локализовать: линейная короткая цепь
    IF task.risk_level == LOW AND ожидаемая P(ошибка) низка:
        RETURN false          # ремонт скорее всего не понадобится

    RETURN BENEFIT > COST     # с явно записанными компонентами
```

**Важно:** первое условие — не формальность. Декомпозиция без HARD-швов даёт красивый граф, в котором **все claims останутся `UNVERIFIED`**, и никакой локализации не произойдёт. Это была бы чистая надбавка к стоимости (F28) без единственной выгоды, ради которой она вводится.

### 4.4 Что НЕ является критерием

| Не критерий | Почему |
|---|---|
| **Число токенов в claim** | прямой запрет §23; критерий — вычислительная независимость и отдельная проверяемость |
| «Задача выглядит сложной» | не операционализируемо |
| «Больше claims = лучше контроль» | F28: стоимость растёт сразу, локализация — только если есть швы и ветви |
| Оценка моделью | уровень MODEL не принимает структурных решений (ARCHITECTURE.md §3) |

## 5. Когда прекращать дробление

```
STOP_DECOMPOSITION если выполняется любое:
  1. У получившегося claim нет собственного применимого seam
     (проверять его отдельно нечем → отдельная единица бессмысленна)
  2. Claim нельзя перегенерировать без полного контекста соседа
     (это фрагмент, а не независимая единица — DATA_MODEL.md §3.1)
  3. Два кандидата не имеют раздельного истинностного значения
     → MERGE в COMPOSITE (DATA_MODEL.md §3.2)
  4. Дробление не уменьшает ожидаемую область ремонта
  5. Дальнейшее дробление порождает цикл → SCC-схлопывание
     (DEPENDENCY_MODEL.md §5)
```

**Неделимый claim** получает `atomicity = INDIVISIBLE_BLOCK`: локализация внутрь не заходит, ремонт только целиком, и это **явно помечено** как точка потери локализации, а не замаскировано.

## 6. Индикаторы качества декомпозиции

Наблюдаемые, структурные. Диагностические — **не участвуют в принятии решений напрямую**, кроме гейта §4.

| Индикатор | Плохой признак | Обоснование |
|---|---|---|
| `parse_stability` | низкая доля полных разборов при повторной декомпозиции | F27: 94.4% — достижимый ориентир при фиксированном формате |
| `hard_seam_coverage` | доля claims без HARD-шва велика | без швов нет локализации (F29) |
| `unknown_dependency_ratio` | много неподтверждённых рёбер | область влияния будет часто уходить в `unknown_set` |
| `indivisible_block_size` | большие схлопнутые блоки | потеря локализации |
| `branching_factor` = 1 | граф — линейная цепь | нет независимых ветвей → нет главной выгоды (F35) |
| `expected_repair_fraction` | близка к 1 | ремонт всё равно затронет всю задачу → декомпозиция не окупается (ср. F42: реально ~половина) |
| `unverifiable_ratio` | доля `UNVERIFIED` claims велика | см. F44: но сначала проверить, не за-строги ли швы, а не списывать на задачу |

### 6.1 Обнаружение плохой декомпозиции по ходу

```
Признаки, наблюдаемые уже во время работы:
  - область ремонта систематически равна всей задаче
    → границы claims не отражают реальные зависимости
  - post_repair_check регулярно находит HIDDEN_DEPENDENCY
    → пропущенные рёбра (REPAIR_MODEL.md §6)
  - claims регулярно оказываются CONFLICTED без разрешения
    → границы разрезали неразделимое
  - доля INAPPLICABLE швов растёт
    → сначала проверить швы (F44!), потом винить декомпозицию
```

**Порядок диагностики важен.** F44 зафиксировал: за-строгие проверяющие правила давали ложный `UNKNOWN` в 32% случаев при полностью корректных ответах. То есть первым подозреваемым при росте неопределённости должна быть **инфраструктура проверки**, а не декомпозиция и не модель.

### 6.2 Исправление

```
IF плохая декомпозиция обнаружена:
    создать НОВУЮ decomposition (не править существующую)
    старая → status = SUPERSEDED, сохраняется
    перенести переиспользуемые артефакты по совпадению content_hash
```

Инвариант `NO_SILENT_OVERWRITE` действует и здесь: граф не перестраивается на месте.

## 7. Наблюдение о природе ошибок, влияющее на декомпозицию

F30: во всех прогонах на этом классе задач корневая ошибка **ни разу** не оказалась в claim о выборе метода — при том, что задачи специально строились вокруг методологической ловушки. Реальные ошибки были исполнительскими (значения, арифметика, реализация).

**Как это использовать:** это наблюдение, а не закон, и оно ограничено классом задач (арифметика/код, модели ≤1.7B). Оно означает, что для этого класса задач детализация «метод» приносит меньше локализационной пользы, чем детализация «вычисление». Оно **не должно** зашиваться как правило — но может быть учтено в схемах декомпозиции для конкретного `task_class` и подлежит перепроверке на других классах.

## 8. Открытые вопросы

- **OQ-DEC-1 (крупный).** Все подтверждённые свойства локализации получены на графах, **заданных заранее человеком и корректных**. Качество автоматически выведенной моделью структуры не измерялось. Пока `boundary_source = MODEL` даёт только гипотезы.
- **OQ-DEC-2.** Численная калибровка гейта §4 не проводилась — заданы структура и обязательные условия, но не веса.
- **OQ-DEC-3.** Поведение на графах существенно большего размера (наблюдались 4–8 claims) неизвестно (см. COMPLEXITY.md).
- **OQ-DEC-4.** Перенос наблюдения F30 на другие классы задач не проверялся.
