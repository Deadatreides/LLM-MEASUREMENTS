# MODEL_INTERFACE.md — модель как вычислительный оператор

## 1. Главный тезис

**Модель — не агент и не роль. Модель — заменяемый вычислительный оператор.**

Один и тот же чекпоинт при разных промптах, температурах и типах артефакта — это **разные операторы** с разными наблюдаемыми характеристиками. Это не стилистическое утверждение, а прямое следствие данных:

- F3: влияние температуры на accuracy разнонаправленно **по моделям** (у большинства хуже при T=1.0, у одной — монотонно лучше);
- F4: влияние формулировки промпта тоже разнонаправленно (у одних моделей +0.18, у других −0.24 на том же изменении);
- F25: даже экономика локального ремонта у одной модели положительна, у другой отрицательна на тех же задачах.

Профиль вида «модель X умная» усредняет ровно то, что усреднять нельзя.

---

## 2. Разделение сущностей

```
MODEL              — чекпоинт (веса), неизменяемый идентификатор
MODEL_CONFIGURATION— как загружен (квантизация, контекст, backend)
PROMPT_PROFILE     — шаблон + output_contract
SAMPLING_CONFIG    — temperature, top_p, top_k, seed, max_tokens
TASK_ROLE          — для чего вызывается (какой artifact_type производит)

OPERATOR := (MODEL, MODEL_CONFIGURATION, PROMPT_PROFILE, SAMPLING_CONFIG, TASK_ROLE)
```

**Профилирование ведётся по OPERATOR, а не по MODEL.**

Отдельная деталь из данных: в эксп. 1 две разные конверсии **одного и того же номинального чекпоинта** (SmolLM2-360M) дали радикально разные результаты — одна работала, другая показала accuracy около нуля из-за отсутствующего chat-шаблона. Поэтому `MODEL_CONFIGURATION` входит в идентичность оператора, а не считается технической деталью.

## 3. MODEL_PROFILE

```
MODEL_PROFILE {
  profile_id
  operator_ref: {model_id, model_config_id, prompt_profile_id, sampling_config, task_role}
  scope:        {artifact_type, task_class}

  # наблюдаемые характеристики — НЕ оценочные ярлыки
  artifact_success_rate      : доля произведённых артефактов, доведённых до CORRECT
  error_classes              : {класс ошибки → частота}
  verification_success_rate  : доля случаев, когда оператор в роли VERIFY дал верный вердикт
  repair_success_rate        : доля успешных ремонтов
  format_reliability         : доля соблюдения output_contract
  mean_output_tokens         : для оценки стоимости
  mean_latency
  context_capacity
  known_failure_modes        : [enum]

  sample_size                : обязательно
  last_updated
}
```

### 3.1 Обязательные поля и почему

| Поле | Почему обязательно |
|---|---|
| `scope` | F3, F4, F25 — характеристики не переносятся между типами артефактов и конфигурациями |
| `sample_size` | отличить «плоха на этом типе» от «видели один раз»; при малом n профиль помечается `LOW_CONFIDENCE` |
| `error_classes` | F1: ошибки систематичны и привязаны к (модель, задача) — важен не процент, а **какие именно** ошибки повторяются |
| `format_reliability` отдельно от `artifact_success_rate` | F27 + F44: сбой формата и содержательная ошибка — разные вещи с разной стоимостью ремонта |
| `verification_success_rate` отдельно от `artifact_success_rate` | F13: способность произвести артефакт и способность проверить чужой — **разные способности с разной надёжностью** |
| `mean_output_tokens` в scope | F25: срыв в многословность при непривычном формате наблюдался и менял знак экономии ремонта |

### 3.2 Чего в профиле нет

- Нет скалярного «рейтинга качества». Нет экспериментального основания; F18/F19 показали, что агрегированные скаляры не предсказывают того, ради чего вводятся.
- Нет «специализации» как декларации («эта модель — критик»). Роль определяется тем, что оператор реально делает, и его измеренным `verification_success_rate`, а не назначением.

### 3.3 Известные режимы отказа как первоклассные данные

`known_failure_modes` заполняется наблюдениями, а не предположениями. Наблюдавшиеся в экспериментах:

| Режим | Наблюдение |
|---|---|
| `SYSTEMATIC_TASK_BLIND_SPOT` | F1, F17: конкретная (модель, задача) даёт устойчиво неверный результат, полное согласие при полной неправоте |
| `VERBOSITY_UNDER_UNFAMILIAR_FORMAT` | F25: срыв в многословность при непривычном формате |
| `FORMAT_DRIFT` | F27: редко, но воспроизводимо |
| `SHARED_BLIND_SPOT_ACROSS_FAMILIES` | F23: слепая зона, общая для нескольких семейств — смена модели не помогает |
| `OVER_STRICT_VERIFICATION` | F9, F11: в роли верификатора систематически отвергает верное |

Последняя строка важна: это режим отказа **оператора в роли проверяющего**, и он наблюдался у всех проверенных моделей, включая лучшую.

## 4. Интерфейс адаптера

```
interface ModelAdapter:
    capabilities() → {context_capacity, supports_seed, supports_logprobs, ...}
    generate(rendered_prompt, sampling_config) → {
        raw_text, input_tokens, output_tokens, wall_time_sec, failed, error
    }
```

**Требования:**
1. Адаптер **не парсит** результат. Он возвращает сырьё. Разбор — задача вызывающего слоя (это отделяет ошибку модели от ошибки парсера — F45).
2. Адаптер **не выносит суждений** о качестве.
3. Core (`GRAPH CORE`, `STATE ENGINE`) не импортирует адаптер. Проверка L аудита: замена модели не затрагивает ядро.
4. Опциональные возможности (`supports_logprobs`) объявляются, но **не требуются**. Отдельно: в эксп. 5 включение полного логирования логитов замедлило генерацию примерно в 29 раз и **измеримо возмущало сэмплирование** (F: REPORT5) — то есть механизм наблюдения менял наблюдаемое. Поэтому такие возможности по умолчанию выключены и включаются только явно, в диагностических режимах.

## 5. Гетерогенный пул

Архитектура обязана поддерживать:
- одну модель многократно;
- одну модель с разными температурами;
- одну модель с разными prompt_profile;
- несколько моделей;
- смешанный пул.

**Но:** ни одна из этих конфигураций не даёт автоматической независимости вызовов. Ось независимости фиксируется в evidence (EVIDENCE_MODEL.md §4) и определяет максимальную силу, которую может иметь согласие.

Отдельное подтверждённое наблюдение в пользу гетерогенности: F8 — смешанный пул на равном бюджете превзошёл лучшую одиночную модель, потому что разные модели закрывают разные слепые зоны. Это **не** аргумент за голосование; это аргумент за то, что `CHANGE_MODEL` — сильный рычаг при устойчивой ошибке (F22).

## 6. Интерфейс для будущего router

Router в ARCH-0 **не реализуется**. Но граница под него зафиксирована, и она чистая:

```
interface Policy:
    select(
        state_snapshot   : {граф-состояние, коллизии, области влияния},
        task             : {class, risk_level, oracle_availability},
        candidate_actions: [Action]      # уже отфильтрованы по предусловиям и бюджету
        model_profiles   : [ModelProfile],
        budget           : Budget
    ) → selected_action
```

**Жёсткие требования к границе:**

1. **Policy не имеет доступа к записи в граф.** Она только выбирает из готового множества. Всё изменение состояния идёт через STATE ENGINE по evidence.
2. **Policy не может расширить множество кандидатов.** Множество формирует REPAIR_PLANNER по структурным правилам.
3. **Policy заменяема целиком.** В ARCH-0 — фиксированные правила (REPAIR_MODEL.md §4.2). Позже — обучаемый router. Смена не требует изменений в GRAPH CORE, STATE ENGINE, EVIDENCE ENGINE.
4. **Решения policy логируются вместе с исходом**, чтобы правила можно было пересматривать по данным.

### 6.1 Почему router откладывается

Не из осторожности, а по данным: F21 прямо зафиксировал, что основная измеренная ценность state-aware политики пришлась на распознавание «здесь ничего делать не нужно», а трудные состояния были слишком редки, чтобы делать вывод о качестве маршрутизации между ними. Строить обучаемый выбор между действиями, о сравнительной пользе которых пока n = 1..4 (F22, F23, F24) — значит обучать на шуме.

Сначала механика собирает данные о парах (состояние → действие → исход). Потом на них можно строить политику.

## 7. Отношение к PTG

```
PTG ──(optional)──► CONTEXT BUILDER / MODEL_PROFILE
```

- Core работает при полностью отключённом PTG.
- PTG может поставлять: прошлые решения, прошлые провалы, паттерны, профили операторов.
- **PTG не является источником истины о текущем claim.** Evidence из PTG получает тип `EXTERNAL_DATA` (если это объективная запись, например «этот тест на этой задаче падал») или `MODEL_JUDGEMENT` (если это прошлая генерация).
- Прошлый успех **не** переводит claim в `CORRECT`.

Обоснование: F17 — слепые зоны концентрированы и воспроизводимы. «Раньше так работало» на систематически проблемной паре (оператор, задача) — это ровно тот механизм, который воспроизведёт ту же ошибку и придаст ей вид подтверждения.
