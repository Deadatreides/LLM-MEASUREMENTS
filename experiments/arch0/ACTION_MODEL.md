# ACTION_MODEL.md — пространство действий

Действие — атомарная единица вычисления с явной стоимостью. Router (в будущем) выбирает **из этого пространства**; в ARCH-0 выбор делают фиксированные правила.

**Общий инвариант:** `EVERY_ACTION_HAS_COST`. Действие без заполненного `estimated_cost` не может быть запланировано; действие без `actual_cost` не может быть закрыто.

---

## 1. Сводная таблица

| Действие | Меняет граф | Вызывает модель | Основной эффект |
|---|---|---|---|
| `GENERATE` | +artifact, +claims | да | создать то, чего не было |
| `REGENERATE` | +версия artifact | да | заменить существующее |
| `VERIFY` | +evidence | нет (HARD) / да (SOFT) | получить знание о валидности |
| `PATCH` | +версия artifact (частичная) | да | точечное изменение без полной перегенерации |
| `EXPAND` | +claims | да | детализировать существующий claim |
| `DECOMPOSE` | +artifacts, +claims, +deps | да/нет | разбить единицу на части |
| `MERGE` | −claims, +composite | нет | объединить неразделимые claims |
| `REQUEST_EVIDENCE` | +evidence | нет | обратиться к внешнему источнику/человеку |
| `CHANGE_PROMPT` | (модификатор) | да | тот же оператор, другой prompt_profile |
| `CHANGE_TEMPERATURE` | (модификатор) | да | тот же оператор, другой sampling |
| `CHANGE_MODEL` | (модификатор) | да | другой оператор |
| `STOP` | закрывает задачу/коллизию | нет | нормальное завершение |

`CHANGE_*` — **модификаторы**, а не самостоятельные действия: они меняют конфигурацию оператора для `GENERATE`/`REGENERATE`/`PATCH`. Выделены отдельно, потому что экспериментально это разные по силе рычаги (F2, F3, F4, F6, F7) и их нужно различать в профилировании и в логах.

## 2. Спецификации действий

### 2.1 `GENERATE`

| | |
|---|---|
| **Вход** | claim в состоянии `PROPOSED`, контекст (CONTEXT_MODEL.md) |
| **Предусловия** | claim.state = `PROPOSED`; все upstream в состоянии ≠ `PROPOSED`; бюджет позволяет |
| **Выход** | claim → `GENERATED`, новый artifact/версия, RUN сохранён с сырым выводом |
| **Стоимость** | tokens(prompt+output), 1 call, время |
| **Режимы отказа** | нарушение output_contract → `FORMAT_VIOLATION`; пустой вывод; таймаут; превышение контекста |
| **Примечание** | производит **probabilistic** результат; сам по себе не переводит claim в `CORRECT` |

### 2.2 `REGENERATE`

| | |
|---|---|
| **Вход** | claim в `INCORRECT`/`STALE`/`CONFLICTED`, необходимость `MUST_REGENERATE` |
| **Предусловия** | все upstream claim уже в актуальной версии (топологический порядок!); claim не в `REPAIRING` |
| **Выход** | новая версия claim/artifact, старая → `SUPERSEDED` (не удаляется) |
| **Стоимость** | как `GENERATE` |
| **Режимы отказа** | воспроизведение той же ошибки (**ожидаемо**: F1, ~3 из 4 при той же конфигурации) |
| **Критично** | `REGENERATE` **без смены конфигурации** при устойчивой ошибке имеет низкий ожидаемый эффект — F1. Планировщик обязан либо сменить конфигурацию (`CHANGE_MODEL` предпочтительно, F22/F6), либо иметь основание ожидать иного результата |

### 2.3 `VERIFY`

| | |
|---|---|
| **Вход** | claim, применимый seam |
| **Предусловия** | seam.applicable; seam.trusted (прошёл свои контрольные случаи, SEAM_MODEL.md §5) |
| **Выход** | evidence; возможно смена состояния claim |
| **Стоимость** | HARD-шов: время исполнения, 0 токенов. SOFT-шов: полная стоимость вызова модели |
| **Режимы отказа** | `INAPPLICABLE` → claim в `UNVERIFIED`; `ERROR` (сама проверка сломалась) → evidence типа `UNKNOWN`, **не** `REFUTES` |
| **Ключевое** | это главное дешёвое действие; на нём построена экономия через `STALE` (STATE_MACHINE.md §4). Но см. F41/OQ-4: дешевизна не гарантирована, для SOFT-швов и задач без oracle проверка может стоить как генерация |

### 2.4 `PATCH`

| | |
|---|---|
| **Вход** | artifact, локализованная область изменения |
| **Предусловия** | область изменения определена структурно; artifact допускает частичное изменение |
| **Выход** | новая версия artifact с изменённой частью |
| **Стоимость** | обычно меньше `REGENERATE`, **но не гарантированно** |
| **Режимы отказа** | патч ломает то, что работало (в эксп. 2 наблюдался нулевой процент регрессий на 50 случаях — F13 — но выборка мала); патч не исправляет реальную ошибку (F13: 1 из 17) |
| **Оговорка** | F13 прямо показал низкую эффективность патча по сигналу ненадёжного (SOFT) шва. `PATCH` по сигналу HARD-шва отдельно не измерялся — **OQ** |

### 2.5 `EXPAND` / `DECOMPOSE` / `MERGE`

| | `EXPAND` | `DECOMPOSE` | `MERGE` |
|---|---|---|---|
| **Смысл** | добавить детализацию внутри claim | разбить на независимые единицы | объединить неразделимые |
| **Предусловие** | claim слишком крупен для локализации | `DECOMPOSITION_GATE` даёт benefit > cost | два claim не имеют раздельного истинностного значения |
| **Стоимость** | вызов модели | вызов модели + рост графа | только структурная (0 токенов) |
| **Отказ** | дробление без выигрыша локализации | неверные границы → ложные/пропущенные зависимости | потеря локализации |
| **Основание** | — | F28: декомпозиция дороже и не улучшает качество; оправдана только локализацией | DATA_MODEL.md §3.2 |

### 2.6 `REQUEST_EVIDENCE`

| | |
|---|---|
| **Вход** | claim в `UNKNOWN`/`CONFLICTED`, идентифицированный внешний источник |
| **Предусловия** | источник существует и доступен |
| **Выход** | evidence типа `EXTERNAL_DATA` или `HUMAN` (сила HARD) |
| **Стоимость** | зависит от источника; для `HUMAN` — латентность неограниченна |
| **Роль** | единственный путь разрешить `UNVERIFIABLE_CONFLICT` (COLLISION_MODEL.md §2) |

### 2.7 Модификаторы `CHANGE_*`

| Модификатор | Ожидаемый эффект | Экспериментальная сила |
|---|---|---|
| `CHANGE_MODEL` | наибольшая независимость от предыдущей ошибки | F6 (сильнейший источник независимости), F22 (никогда не хуже, иногда строго лучше), F8 (mixed-model пул превосходит лучшую одиночную модель) — **MODERATE/STRONG** |
| `CHANGE_PROMPT` | снижает повторяемость ошибки | F2 — **STRONG** для повторяемости; но F7 — **NEGATIVE** для независимости claim-уровня. Противоречие честное: F2 измерял повторяемость на задачном уровне, F7 — независимость на claim-уровне; **обобщать нельзя** |
| `CHANGE_TEMPERATURE` | увеличивает разнообразие | F5: растёт **поверхностное** разнообразие, разнообразие режимов ошибки — слабее; F3: влияние на accuracy разнонаправленно по моделям — **слабый рычаг** |

**Правило приоритета при устойчивой ошибке** (следствие F1 + F6 + F22):
```
CHANGE_MODEL  >  CHANGE_PROMPT  >  CHANGE_TEMPERATURE  >  голый REGENERATE
```
Это порядок предпочтения, а не жёсткая последовательность; он подлежит пересмотру по накопленным данным профилей.

**Контрпример, который обязателен к учёту (F23):** когда слепая зона общая для нескольких моделей, `CHANGE_MODEL` не помогает вовсе, а помогают `CHANGE_PROMPT` или `REQUEST_EVIDENCE`. Планировщик обязан не зацикливаться на смене моделей — это ловится через `REPEATED_STATE` (REPAIR_MODEL.md §7).

### 2.8 `STOP`

| | |
|---|---|
| **Предусловия** | выполнено любое STOP-условие (REPAIR_MODEL.md §7) |
| **Выход** | `task.state = STOPPED/RESOLVED`, `stop_reason` заполнен |
| **Стоимость** | 0 |
| **Роль** | **нормальное завершение**, не авария. Экспериментально это самое ценное действие: F20/F21 — детектор «здесь ничего делать не надо» дал основную измеренную экономию бюджета |

## 3. Общая структура исполнения действия

```
FUNCTION execute(action, graph, budget):
    # 1. Предусловия
    FOR each p в preconditions(action.type):
        IF not check(p, action.target, graph): RETURN PRECONDITION_FAILED

    # 2. Бюджет
    IF action.estimated_cost > budget.remaining: RETURN BUDGET_DENIED
    budget.reserve(action.estimated_cost)

    # 3. Контекст — строится ПОД действие, не «весь граф»
    ctx ← build_context(action, graph)          # CONTEXT_MODEL.md

    # 4. Исполнение
    run ← execute_operator(action, ctx)         # сырьё сохраняется ВСЕГДА
    persist(run)                                # даже при провале парсинга

    # 5. Разбор результата
    IF нарушен output_contract:
        evidence(FORMAT_VIOLATION); action.status ← FAILED
        # сырьё уже сохранено — можно перепроверить позже (F45)
        RETURN

    # 6. Материализация: НОВАЯ ВЕРСИЯ, старое не трогаем
    new_version ← create_version(action.target, run.parsed)
    old.superseded_by ← new_version

    # 7. Стоимость по факту
    action.actual_cost ← measure(run)
    budget.commit(action.actual_cost)

    # 8. Обновление профиля оператора
    model_profile.observe(action, run, outcome)

    # 9. Состояние — только через evidence
    state_engine.apply(new_version, evidence_from(run))
```

**Шаг 4 сохраняет сырьё безусловно.** Основание — F45: все шесть найденных за проект дефектов проверяющих правил были обнаружены пересчётом по сохранённому сырью; без него дефект инфраструктуры неотличим от свойства модели.

## 4. Ожидаемый эффект действия

Требование §15 задания. Формальная структура (не численная модель — для неё нет данных):

```
EXPECTED_EFFECT(action, target_state) := {
    target_transition   : какое изменение состояния ожидается
    evidence_gain       : какой тип/силу evidence даст (для VERIFY — главное)
    localization_gain   : улучшится ли локализация (для DECOMPOSE)
    independence_gain   : ось независимости (для CHANGE_*)
    basis               : REFERENCED_FACT | MODEL_PROFILE | UNKNOWN
}
```

**`basis = UNKNOWN` — легитимное значение** и встречается часто. Архитектура не имеет права придумывать численные ожидания там, где их нет: F18 показал, что метрика, сильно коррелирующая с общей величиной выигрыша, может **не коррелировать** с предельным выигрышем от следующего вычисления (r ≈ 0.002) — то есть «правдоподобная» оценка эффекта легко оказывается пустой.

Когда `basis = UNKNOWN` для всех кандидатов, действует STOP-условие `NO_EXPECTED_GAIN` в консервативной форме (REPAIR_MODEL.md §7.1).

## 5. Чего в пространстве действий нет

| Отсутствует | Почему |
|---|---|
| `CRITIQUE` (модель критикует артефакт как отдельное действие) | F9–F13: систематически ошибается в обе стороны; допустимо только как `VERIFY` через SOFT-шов, с соответствующей (слабой) силой evidence |
| `VOTE` / `SYNTHESIZE` | F14, F16, F17 |
| `SELF_REFLECT` | частный случай `SELF_JUDGEMENT`, сила `WEAK` по определению; отдельным действием не выделяется |
| `SCORE` (оценить качество числом) | нет экспериментального основания ни для одной такой величины |
| `EXPLORE` (сгенерировать N вариантов и выбрать) | это `GENERATE` × N + `SEAM_CONFLICT`; отдельная сущность не нужна и провоцирует голосование |
