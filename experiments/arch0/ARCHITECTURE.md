# ARCHITECTURE.md — Мицелий, ARCH-0

**Статус:** архитектурная спецификация. Не код, не MVP, не production-дизайн.
**Основание:** EXPERIMENTAL_BASIS.md (факты F1–F48, открытые вопросы OQ-1…OQ-7).
**Что это:** формальная вычислительная среда, в которой объект управления — **состояние графа артефактов и claims**, а не ответ LLM.

---

## 0. Что мы строим и чего мы НЕ строим

### Отвергнутая модель

```
TASK → несколько LLM → несколько ответов → vote/synthesis → final answer
```

Она отвергнута не по вкусу, а по данным:
- голосование/согласие не является доказательством правильности (F14);
- «критик» на базе LLM систематически ошибается и в этих данных чаще отвергал *правильное*, чем ловил неправильное (F9, F10, F11);
- pipeline из LLM-ролей не превзошёл плоский best-of-N при равном токенном бюджете (F46);
- добавление генераций не даёт нового качества там, где ошибка систематична (F1), а именно там оно и нужно.

### Принятая модель

```
TASK
 → ARTIFACT GRAPH        (что вообще произведено)
 → CLAIM GRAPH           (какие проверяемые утверждения внутри)
 → DEPENDENCY GRAPH      (что от чего зависит структурно)
 → SEAM GRAPH            (где проходят проверяемые границы)
 → EVIDENCE              (что мы реально знаем и откуда)
 → STATE                 (валидность каждого узла + версия)
 → COLLISION             (наблюдаемая несовместимость)
 → AFFECTED REGION       (безопасная верхняя граница влияния)
 → REPAIR PLAN           (фактически необходимое подмножество + действия)
 → ACTION                (атомарное вычисление со стоимостью)
 → UPDATED STATE         (новая версия, старая не уничтожена)
```

**LLM в этой схеме — вычислительный оператор.** Он производит артефакты. Он не выносит вердикт об истинности собственного результата и не является источником жёсткого доказательства (F9–F14).

## 1. Три отношения, которые нельзя смешивать

Это центральное архитектурное требование. Три разных отношения между claims часто путают в одно «зависит/сломано/чинить»; эксперименты показали, что это разные вещи с разной семантикой.

### A. STRUCTURAL DEPENDENCY — «C2 построен на C1»

Статическое свойство графа. Задаётся при декомпозиции, типизировано (LOGICAL / COMPUTATIONAL / DATA / CONTRACT / CAUSAL / DERIVATION / FORMAT / OTHER), имеет evidence и confidence.

**Что подтверждено:** обход этого графа даёт точную и безопасную оценку области потенциального влияния (F34, recall = 1.0 на 120 контролируемых случаях), независимые ветви при этом не задеваются (F35).

**Чего это НЕ значит:** dependency **не означает**, что при поломке источника цель обязана быть перегенерирована (F37: precision ≈ 0.47).

### B. VALIDITY STATE — «что мы сейчас знаем о C2»

Динамическое состояние: `UNVERIFIED / CORRECT / INCORRECT / UNKNOWN / STALE / CONFLICTED`.

**Ключевое разделение (F37 + F38):**
- `INCORRECT` — есть evidence, что утверждение неверно.
- `UNKNOWN` — нет достаточных evidence ни за, ни против.
- `STALE` — **раньше было доказано корректным, но относительно предпосылки, которая изменилась.** Прежнее доказательство больше не применимо. Это не утверждение об ошибочности.

`STALE` — главный механизм экономии. Именно он превращает «83% избыточного ремонта» (F37) в «дешёвая проверка вместо дорогой регенерации», не жертвуя теми 30% случаев, где ошибка действительно каскадирует (F38).

### C. REPAIR NECESSITY — «что с C2 делать»

Решение, принимаемое **после** коллизии и **после** уточняющей проверки: `MUST_REGENERATE / MUST_VERIFY / MAY_REUSE / DO_NOT_TOUCH / UNKNOWN`.

**Неравенства, зафиксированные экспериментом:**

```
DEPENDENCY ⊉ REPAIR_NECESSITY
AFFECTED_REGION ⊋ MINIMAL_REPAIR_SET       (F37: precision≈0.47, recall=1.0)
AFFECTED_REGION ⊉ ∅ по умолчанию            (F38: 30% реально каскадируют)
```

Архитектура обязана иметь **все три** уровня и обязана иметь **явный шаг сужения** между вторым и третьим.

## 2. Главный цикл

```
                 ┌──────────────────────────────────────────┐
                 │ 1. DECOMPOSE (если выгода > стоимости)    │
                 │    TASK → ARTIFACT PLAN → CLAIMS → DEPS   │
                 └────────────────────┬─────────────────────┘
                                      ▼
                 ┌──────────────────────────────────────────┐
                 │ 2. EXECUTE ACTIONS                       │
                 │    GENERATE / VERIFY / ...               │
                 │    → ARTIFACT vN, EVIDENCE, стоимость    │
                 └────────────────────┬─────────────────────┘
                                      ▼
                 ┌──────────────────────────────────────────┐
                 │ 3. EVALUATE SEAMS → EVIDENCE             │
                 │    HARD / SOFT / UNKNOWN                 │
                 └────────────────────┬─────────────────────┘
                                      ▼
                 ┌──────────────────────────────────────────┐
                 │ 4. UPDATE STATE (новая версия узлов)     │
                 │    + распространить STALE вниз по DAG    │
                 └────────────────────┬─────────────────────┘
                                      ▼
                 ┌──────────────────────────────────────────┐
                 │ 5. DETECT COLLISIONS                     │
                 │    (несовместимость ≠ ошибка)            │
                 └────────────────────┬─────────────────────┘
                            нет коллизий │ есть коллизии
                    ┌─────────────────┘ └──────────────┐
                    ▼                                   ▼
        ┌───────────────────────┐      ┌────────────────────────────────┐
        │ 6a. STOP-условия      │      │ 6b. LOCALIZE                   │
        │  (см. §29 / STOP)     │      │  origin → candidate_affected   │
        └───────────────────────┘      │  → verify downstream           │
                                       │  → actual_repair_set           │
                                       └───────────────┬────────────────┘
                                                       ▼
                                       ┌────────────────────────────────┐
                                       │ 7. PLAN REPAIR                 │
                                       │  per claim: VERIFY/REUSE/      │
                                       │  REGENERATE/REPAIR/BRANCH/     │
                                       │  ABORT/REQUEST_EVIDENCE        │
                                       │  сравнить со стоимостью        │
                                       │  FULL_RETRY (не догматически)  │
                                       └───────────────┬────────────────┘
                                                       │
                                                       └──► назад в шаг 2
```

**Защита от бесконечного цикла** (обязательна, см. STOP-условия в REPAIR_MODEL.md §7): счётчик итераций на коллизию, детектор повторяющегося состояния графа (хеш состояния + плана), детектор осцилляции, бюджет.

## 3. Слои и кто какое решение принимает

Требование §38 задания: никакого «AI решит, что делать». Каждое решение отнесено ровно к одному уровню.

| Уровень | Что решает | Детерминизм | Примеры |
|---|---|---|---|
| **STRUCTURAL** | форма графа: какие артефакты, какие claims, какие рёбра | детерминированный, из зафиксированной схемы декомпозиции | «C6 зависит от C4 и C5» |
| **EVIDENCE** | что мы знаем и насколько сильно | детерминированный по заданной иерархии доверия | «тесты прошли → MECHANICAL/strong» |
| **STATE** | валидность и версия узла | детерминированный (таблица переходов) | «upstream изменился → downstream STALE» |
| **POLICY** | какое действие выбрать из допустимых | **заменяемый компонент**; в ARCH-0 — фиксированные правила, позже router | «STALE + дешёвая проверка → VERIFY» |
| **MODEL** | содержание артефакта | **вероятностный, model-dependent** | текст спецификации, код, вычисление |

**Правило маркировки:** всё, что производит уровень MODEL, помечается как `probabilistic`, несёт `model_id / prompt_profile / sampling_config` и **не может** сам по себе перевести claim в `CORRECT`. Перевод в `CORRECT` — прерогатива уровня EVIDENCE на основании evidence достаточной силы (EVIDENCE_MODEL.md §3).

## 4. Модули

Полные границы — в API_BOUNDARIES.md. Кратко, зависимости строго однонаправленны:

```
        ┌────────────────────────────────────────────┐
        │  API / ORCHESTRATOR                        │
        └───┬───────────────┬──────────────┬─────────┘
            ▼               ▼              ▼
   ┌─────────────┐  ┌──────────────┐  ┌──────────────┐
   │REPAIR       │  │ACTION        │  │BUDGET        │
   │PLANNER      │  │EXECUTOR      │  │MANAGER       │
   └──┬──────┬───┘  └───┬──────────┘  └──────────────┘
      │      │          │
      │      │          ▼
      │      │   ┌──────────────┐      ┌──────────────┐
      │      │   │MODEL ADAPTER │◄─────┤MODEL PROFILE │
      │      │   └──────────────┘      └──────────────┘
      ▼      ▼
┌──────────┐ ┌──────────┐ ┌──────────┐
│STATE     │ │SEAM      │ │EVIDENCE  │
│ENGINE    │ │ENGINE    │ │ENGINE    │
└────┬─────┘ └────┬─────┘ └────┬─────┘
     └────────────┼────────────┘
                  ▼
          ┌───────────────┐
          │  GRAPH CORE   │  ← ничего не знает об LLM
          └───────┬───────┘
                  ▼
          ┌───────────────┐
          │   STORAGE     │  append-only
          └───────────────┘
```

**Инвариант модульности:** `GRAPH CORE` и `STATE ENGINE` не импортируют ничего, связанного с конкретной LLM. Замена модели не затрагивает ядро (проверка L в ARCHITECTURE_AUDIT.md).

**POLICY отделена от хранилища.** Планировщик ремонта предлагает *допустимые* действия; выбор между ними — сменный компонент с чистым интерфейсом (`MODEL_INTERFACE.md §6`), чтобы в будущем туда встал router без переписывания графа.

## 5. Что архитектура сознательно НЕ делает

| Не делает | Почему (факт) |
|---|---|
| Не голосует и не «синтезирует лучший ответ» | F14: согласие не доказывает правильность; F16: конфликт не указывает на близость истины |
| Не использует LLM-критика как оракула | F9, F10, F11, F12 |
| Не считает несколько вызовов одной модели независимыми | F1 (0.75 повтор ошибки), F5, F7 |
| Не распределяет бюджет по скалярной энтропии | F18 (r≈0.002 с предельным выигрышем), F19 |
| Не декомпозирует всё подряд | F28 (декомпозиция дороже и не повышает качество), F46 |
| Не сужает область ремонта по умолчанию | F38 (30% реально каскадируют) |
| Не расширяет ремонт на всю задачу по умолчанию | F37, F42 (реально нужна примерно половина, редко всё) |
| Не содержит глобального «score качества» | нет экспериментального основания ни для одной такой скалярной величины |
| Не включает bandit/RL на этом этапе | сначала должна работать механика; см. §33 задания |

## 6. Минимальная траектория «hello»

Проверка, что архитектура не разваливается на тривиальном (аудит A):

```
TASK("привет")
  → DECOMPOSITION_GATE: benefit(декомпозиция) < cost → NO_DECOMPOSE
  → один ARTIFACT типа EXPLANATION, один CLAIM (атомарный)
  → DEPENDENCY GRAPH: пустой (0 рёбер)
  → SEAM: нет применимого HARD seam → SEAM_UNKNOWN
  → EVIDENCE: нет → claim.state = UNVERIFIED
  → COLLISION: нет
  → STOP(reason = NO_COLLISION_AND_NO_APPLICABLE_VERIFICATION)
  → результат отдаётся с честным маркером «не верифицировано»
```

Ключевое: система **не притворяется**, что проверила. `UNVERIFIED` доезжает до пользователя как явный статус (F43 + инвариант `UNKNOWN_IS_NOT_ERROR`).

## 7. Траектория с коллизией (иллюстрация всей механики)

Задача с двумя независимыми ветвями и общим финалом (форма, на которой всё измерено в эксп. 9):

```
C1 (общая рамка)
├─► C2 (метод ветви A) ──► C4 (вычисление A) ─┐
└─► C3 (метод ветви B) ──► C5 (вычисление B) ─┴─► C6 (итог)
```

1. Все claims сгенерированы; HARD seam (арифметическая проверка) на C4, C5, C6.
2. Seam на C4 даёт `FAIL` → **COLLISION** (не «ошибка C4» — пока только несовместимость наблюдений).
3. `origin = C4` (единственный участник с локальным противоречием, не унаследованным).
4. `candidate_affected = {C4} ∪ downstream(C4) = {C4, C6}` — **ветвь B не затронута** (F35, гарантируется структурно).
5. `C6` переводится в `STALE`, **не** в `INCORRECT` (F37/F38): его прежняя валидность больше не доказана.
6. **Шаг сужения:** на `C6` запускается VERIFY (дешёвая механическая проверка), а не REGENERATE.
   - Если C6 самостоятельно корректен относительно нового C4 → `MAY_REUSE`, регенерация не нужна (это те ~70% из F38).
   - Если C6 воспроизводит старое неверное значение → `MUST_REGENERATE` (те ~30%).
7. `repair_set` = `{C4}` или `{C4, C6}` — **определяется проверкой, а не графом**.
8. Выбор действия для C4: тип коллизии + профиль модели + бюджет (ACTION_MODEL.md). Сравниваются стоимости `LOCAL_REPAIR` и `FULL_RETRY` — без догмы, что локальное дешевле (F47).
9. Новая версия C4 → новая версия C6 (если нужна) → старые версии сохранены (INVARIANTS: `NO_SILENT_OVERWRITE`).
10. Коллизия перепроверяется. Если не исчезла — новая итерация с инкрементом счётчика и проверкой на осцилляцию.

## 8. Отношение к PTG и памяти

PTG (прошлый опыт) **не входит** в core execution graph. Интерфейс односторонний:

```
PTG ──(optional contextual evidence)──► CONTEXT BUILDER ──► ACTION
```

- Core обязан работать при полностью отключённом PTG.
- PTG может поставлять: прошлые решения, прошлые провалы, известные паттерны, профили моделей.
- **Прошлый опыт не является доказательством истинности текущего claim.** Evidence из PTG получает тип `EXTERNAL_DATA` или `MODEL_JUDGEMENT` (в зависимости от происхождения) и **никогда** — `MECHANICAL`.

Обоснование: F17 (слепые зоны концентрированы и воспроизводимы) означает, что «раньше так работало» может быть ровно тем механизмом, который воспроизводит систематическую ошибку.
