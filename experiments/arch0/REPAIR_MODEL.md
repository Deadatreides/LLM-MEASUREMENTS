# REPAIR_MODEL.md — область влияния, план ремонта, остановка

Это документ о центральном механизме архитектуры: как от наблюдённой коллизии перейти к **минимально достаточному** вычислению, не потеряв корректность.

---

## 1. Три множества, а не одно

```
COLLISION
   │
   ▼
ORIGIN                       ← локализация (COLLISION_MODEL.md §3)
   │
   ▼
CANDIDATE_AFFECTED_SET       ← транзитивное замыкание по DAG
   │                            БЕЗОПАСНАЯ ВЕРХНЯЯ ГРАНИЦА
   │                            F34: recall = 1.0, ноль пропусков
   ▼
[ШАГ СУЖЕНИЯ: DOWNSTREAM VERIFICATION]
   │
   ▼
VERIFIED_AFFECTED_SET + UNAFFECTED_CONFIRMED_SET + UNKNOWN_SET
   │
   ▼
REPAIR_SET                   ← фактически необходимое
                                F37: граф шире истины (precision ≈ 0.47)
                                F38: но сужать по умолчанию нельзя (~30% каскадируют)
```

### 1.1 Почему нельзя обойтись одним множеством

| Наивный подход | Что говорят данные |
|---|---|
| «Ремонтировать всё affected» | F37: в большинстве случаев это избыточно; F42: реально нужна примерно половина claims, и почти никогда не вся задача |
| «Ремонтировать только origin» | F38: примерно в трети реальных случаев downstream действительно вобрал неверную предпосылку и остаётся неверным |
| «Ремонтировать только то, что не прошло свою проверку» | F31: невозможно отличить свой дефект от унаследованного поклеймной проверкой |

Единственный корректный путь — **три множества и явный шаг проверки между вторым и третьим**.

## 2. Шаг 1: candidate affected set

```
FUNCTION candidate_affected(collision, graph):
    IF collision.origin == null:
        RETURN участники коллизии ∪ их downstream_closure   # консервативно
    result ← ∅
    FOR each o в collision.origin (может быть несколько, F39 MULTIPLE_LOCAL):
        result ← result ∪ {o} ∪ downstream_closure(o, graph)
    RETURN result
```

**Свойства, подтверждённые экспериментально:**
- полнота: истинно затронутое никогда не остаётся снаружи (F34: 120/120, under-repair = 0);
- независимые ветви не попадают внутрь (F35: 0 загрязнений из 80);
- merge-узел попадает только со стороны реально повреждённой ветви (F36).

Это множество **никогда не используется напрямую как план ремонта.**

## 3. Шаг 2: сужение через проверку

Это тот шаг, которого не хватало в предыдущих итерациях и который отделяет «безопасно» от «дорого».

> **ПОПРАВКА AMD-1 (2026-08-16, по результатам измерения ARCH-1).**
> Порядок шагов 1 и 2 изменён: структурная эвристика больше не
> перехватывает узел до проверки. Исходная редакция и обоснование
> правки — в §3.2 ниже; она сохранена целиком, не удалена.

```
FUNCTION narrow(candidate_set, origin_set, graph, budget):
    verified   ← origin_set          # корни всегда затронуты
    unaffected ← ∅
    unknown    ← ∅

    FOR each c в candidate_set \ origin_set   в топологическом порядке:
        # 1. СНАЧАЛА проверка: evidence имеет приоритет над структурой
        #    (ARCHITECTURE.md §1 — STRUCTURAL DEPENDENCY ≠ VALIDITY STATE)
        seam ← найти применимый HARD seam для c
        checkable ← seam ≠ null AND cost(seam) ≤ cost(REGENERATE(c))

        IF checkable:
            result ← evaluate(seam, c)
            IF result == PASS:  unaffected ← unaffected ∪ {c};  CONTINUE
                                            # ~тот случай из F38, где downstream уцелел
            IF result == FAIL:  verified ← verified ∪ {c};  CONTINUE
            # ERROR/INAPPLICABLE — падаем в шаг 2, как непроверенный

        # 2. Проверки не было (нет шва / дороже ремонта / шов не дал
        #    результата) — только тогда структурная эвристика, и только
        #    как КОНСЕРВАТИВНОЕ отнесение, а не как знание
        IF ∃ ребро типа DATA/COMPUTATIONAL от подтверждённо-затронутого предка
           AND значение предка буквально присутствует в c:
            verified ← verified ∪ {c};  CONTINUE

        unknown ← unknown ∪ {c}

    RETURN verified, unaffected, unknown
```

### 3.1 Ключевые правила

1. **Проверка идёт в топологическом порядке.** Нельзя проверять downstream раньше, чем определён статус его предков — иначе проверяется соответствие устаревшему состоянию.

2. **`unknown` не сваливается ни в «затронуто», ни в «не затронуто».** Это отдельное множество, и решение по нему принимается политикой (§4.3), а не умолчанием. Основание: F43 + инвариант `UNKNOWN_IS_NOT_ERROR`.

3. **Проверка не бесплатна** (§3, строка `cost(seam) > cost(REGENERATE)`). Если проверить дороже, чем перегенерировать, шаг сужения теряет смысл для этого узла. Основание — F41 (анализ имеет стоимость) и F47 (локальное не всегда дешевле). Для задач без механического oracle это условие может выполняться повсеместно — тогда сужение не даёт экономии (OQ-4, OQ-STALE).

4. **Структурная эвристика — не знание, а умолчание для непроверенного** (поправка AMD-1). Она применяется только там, где evidence получить не удалось, и относит узел в `verified` консервативно. Там, где доступна проверка, решает проверка.

---

### 3.2 Поправка AMD-1: приоритет проверки над структурной эвристикой

**Статус:** принята 2026-08-16 по результатам измерения ARCH-1 (`arch1/REPORT_ARCH1.md`). Первая правка `arch0/` после `READY_FOR_IMPLEMENTATION`.

**Исходная редакция шага (сохранена дословно):**

```
        # 1. Если предок уже подтверждён как реально затронутый И
        #    c структурно обязан быть перегенерирован (например, содержит
        #    буквальное значение предка) — сразу verified
        IF ∃ ребро типа DATA/COMPUTATIONAL от подтверждённо-затронутого предка
           AND значение предка буквально присутствует в c:
            verified ← verified ∪ {c};  CONTINUE

        # 2. Иначе — попытаться проверить c относительно НОВОГО состояния предков
        ...
```

**Что показало измерение.** На 240 полных прогонах (`arch1`, кампания 2) шаг 1 в исходной редакции перехватывал **87.2%** не-origin узлов области ремонта, не давая проверке отработать. Контрфактический прогон на тех же данных:

| | `unaffected` | `verified` | `unknown` | `stale_resolved_by_verify_ratio` |
|---|---|---|---|---|
| шаг 1 перехватывает (исходная редакция) | 1 | 83 | 2 | **0.0119** |
| шаг 1 не перехватывает | 10 | 64 | 12 | **0.1351** |

**В чём именно дефект.** Эвристика срабатывает **и корректно, и ложно**, и различить их не может:

- *Корректно:* origin `C4 = "$145"` (неверно, ожидалось 40), потомок `C6 = "$145 + 105 = $250"` — потомок действительно унаследовал ошибочное значение.
- *Ложно:* origin `C4 = "$145"` (неверно), потомок `C6 = "40 + 105 = 145"` — **верен**. Ошибочное значение предка случайно совпало с верным значением потомка (145 — правильный итог задачи).

Проверяется только присутствие числа. Отличить «унаследовал ошибку» от «совпадение значений» присутствие не позволяет **в принципе** — для этого нужно знать, верен ли сам потомок, то есть нужна именно проверка.

**Почему это нарушение ARCHITECTURE.md §1.** Исходная редакция выводит **валидность** («затронут, регенерировать») из **структурного факта** («значение предка присутствует»), то есть ровно то, что §1 запрещает: `STRUCTURAL DEPENDENCY ≠ VALIDITY STATE`. Противоречие внутри одной спецификации: §1 формулирует запрет, §3 его нарушает.

**Почему поправка именно такая (а не удаление шага).** Рассмотренные варианты:

| Вариант | Отклонён, потому что |
|---|---|
| Удалить шаг целиком | теряется консервативное отнесение там, где проверки нет; узлы без шва уходили бы в `unknown`, а не в `verified` — это ослабляет безопасность (F38) |
| Сверять с **прежним, опровергнутым** значением предка (diff версий) | на момент `narrow()` ремонта ещё не было, новой версии предка не существует — сверять не с чем |
| Требовать HARD-evidence(REFUTES) именно на присутствующее значение | в примере выше `$145` и есть опровергнутое значение предка — не различает ложный случай |
| **Понизить приоритет (принято)** | evidence решает там, где доступно; структура остаётся умолчанием для непроверяемого. Не теряет безопасности, восстанавливает §1 |

**Цена и ограничение.** Поправка увеличивает число прогонов шва (раньше 87.2% узлов проверку пропускали). Для HARD-швов это дёшево (0 токенов), но для дорогих проверок начинает работать строка `cost(seam) > cost(REGENERATE)` — и тогда поведение возвращается к структурной эвристике. На задачах без механического oracle (OQ-4) поправка эффекта не даст.

**Что поправка НЕ доказывает.** Она устраняет известный источник занижения, но полученные после неё значения `stale_resolved_by_verify_ratio` (порядка 0.13 в контрфактическом прогоне) **существенно ниже** ожидаемых из F37 (precision ≈ 0.47 → до ~53% узлов могли бы оправдываться). Допущение A-1 остаётся неподтверждённым; поправка лишь снимает искажение измерения.

## 4. Шаг 3: план ремонта

### 4.1 Repair necessity по узлам

```
FUNCTION assign_necessity(c, verified, unaffected, unknown, origin_set, task):
    IF c ∈ origin_set:                RETURN MUST_REGENERATE
    IF c ∈ verified:                  RETURN MUST_REGENERATE
    IF c ∈ unaffected:                RETURN MAY_REUSE
    IF c ∉ candidate_set:             RETURN DO_NOT_TOUCH     # F35: независимые ветви
    IF c ∈ unknown:
        IF task.risk_level == HIGH:   RETURN MUST_REGENERATE  # консервативно
        ELSE:                         RETURN MUST_VERIFY      # отложенная проверка
    RETURN UNKNOWN
```

`DO_NOT_TOUCH` для всего вне `candidate_set` — прямое следствие F35: независимость ветвей структурно гарантирована и подтверждена без единого нарушения.

### 4.2 Выбор действия для узлов, требующих ремонта

Выбор **не** делается по скалярной метрике неуверенности (F18, F19 — прямо опровергнуто). Он делается по **типу коллизии и наблюдаемому состоянию**, потому что именно тип оказался предсказательным (F24, F32).

| Наблюдаемая ситуация | Предпочтительное действие | Основание |
|---|---|---|
| Устойчивая воспроизводимая ошибка (та же ошибка при повторе той же конфигурации) | `CHANGE_MODEL` | F22: смена модели никогда не была хуже, иногда строго лучше; F1: повтор той же конфигурации воспроизведёт ту же ошибку; F6: смена модели — сильнейший источник независимости |
| Механически подтверждённый конфликт двух валидных вариантов | **не** локальный retry | F24: локальный retry систематически ухудшал результат в этом случае (4/4) |
| Внутреннее самопротиворечие артефакта | локальный `REGENERATE` узкой области | F24: работал и был дешевле |
| Ошибка формата | `REGENERATE` с тем же оператором + ужесточённый output_contract | F27: формат стабилен, сбои редки и локальны |
| Слепая зона, общая для нескольких моделей | `CHANGE_PROMPT` / `REQUEST_EXTERNAL_EVIDENCE` | F23: смена модели не помогла, когда слепая зона общая |
| `STALE` без собственного дефекта | `VERIFY` (не regenerate) | F37 + F38: основной механизм экономии |

**Оговорка о силе.** Строки этой таблицы имеют силу MODERATE/WEAK (n от 1 до 4 чистых случаев). Они задают **начальные правила политики**, а не законы. Политика — заменяемый слой (§4.4), и она обязана логировать исход каждого выбора, чтобы правила можно было пересматривать по накопленным данным, а не по убеждению.

### 4.3 Обязательное сравнение стратегий

```
FUNCTION build_plan(region, collision, task, budget):
    entries ← [assign_necessity(c, ...) для всех c в region.candidate]

    strategies ← {
      FULL_RETRY:    стоимость перегенерации всей задачи с нуля,
      LOCAL_REPAIR:  Σ стоимость по entries,
      VERIFY_FIRST:  Σ стоимость проверок + ожидаемая доля регенераций,
      MODEL_SWITCH:  LOCAL_REPAIR с другим оператором,
      PROMPT_SWITCH: LOCAL_REPAIR с другим prompt_profile
    }

    отбросить те, что не влезают в budget
    RETURN выбор политики среди оставшихся + записать ВСЕ рассмотренные
           альтернативы в plan.alternatives_considered
```

**`FULL_RETRY` обязателен как рассматриваемая альтернатива.** Основание:
- F46: артефактный pipeline не превзошёл плоский best-of-N при равном токенном бюджете;
- F47: локальный ремонт не всегда дешевле; наблюдались случаи, где он был существенно дороже полной плоской генерации;
- F25: экономика локального ремонта модель-специфична и меняет знак.

План, не сравнивший стоимости, архитектурно некорректен (проверяемый инвариант `EVERY_PLAN_COMPARES_ALTERNATIVES`).

### 4.4 Граница политики

```
interface RepairPolicy:
    select(state_snapshot, task, candidate_actions, model_profiles, budget)
        → selected_action
```

В ARCH-0 это **фиксированные правила** из §4.2. Позже сюда встанет router. Требование: политика не имеет доступа к записи в граф и не может менять состояния — только выбирать из предложенного планировщиком множества допустимых действий.

## 5. Minimal Repair Set

### 5.1 Определение

```
MRS := минимальное по включению подмножество claims, изменение которых
       переводит финальный claim задачи в CORRECT
```

### 5.2 Что известно

- MRS **строго меньше** `candidate_affected_set` в большинстве контролируемых случаев (F37: over-repair в 83.3% случаев при recall = 1.0 и under-repair = 0).
- Точный MRS определим полным перебором подмножеств, но это **2^n** и не масштабируется (F41).
- На реальных данных оценённая граница ремонта — около половины claims задачи и почти никогда не вся задача (F42).

### 5.3 Что архитектура делает

**Не** вычисляет точный MRS перебором в общем случае. Вместо этого:

```
REPAIR_SET := origin_set ∪ verified_affected_set ∪ (unknown_set по политике риска)
```

Это **приближение сверху** к MRS, полученное шагом сужения (§3). Гарантии:
- полнота сохраняется (не хуже, чем `candidate_affected_set`, у которого recall = 1.0);
- избыточность уменьшается ровно на те узлы, которые проверка подтвердила как незатронутые.

Полный перебор допускается **только** как диагностический режим на малых графах (для калибровки правил сужения), с явным лимитом на размер.

### 5.4 Открытый вопрос

**OQ-MRS:** насколько близко приближение §5.3 к истинному MRS на реальных (не инъецированных) ошибках — **не измерено**. В эксп. 9 точный MRS считался только для контролируемых одноточечных инъекций, где по построению истинный MRS = {инъецированный claim}. Для реальных каскадных ошибок (F38, ~30% случаев) истинный MRS не совпадает с одним узлом, и качество приближения неизвестно.

## 6. Проверка после ремонта (hidden dependency)

Требование §22 задания: после применения ремонта проверить, что **неизменённые** claims остались корректными.

```
FUNCTION post_repair_check(repair_set, graph):
    untouched ← все claims, бывшие CORRECT и не входившие в repair_set
    FOR each c в untouched, достижимых из repair_set по любому ребру:
        seam ← применимый HARD seam
        IF seam ≠ null AND evaluate(seam, c) == FAIL:
            зафиксировать HIDDEN_DEPENDENCY:
                создать ребро UNKNOWN_DEPENDENCY (repair_set-элемент → c)
                со status = HYPOTHESIS и evidence = этот факт
            расширить affected region, создать новую итерацию
```

Обнаруженная скрытая зависимость **материализуется как ребро графа** — то есть система учится структуре по ходу, но только на основании наблюдаемого факта (проверка провалилась после изменения), а не по сходству.

Ограничение честности: в эксп. 9 скрытых зависимостей post-hoc **не обнаружено** — но и граф там был задан заранее и корректно. На графах, выведенных автоматически, частота этого события неизвестна (OQ-3).

## 7. STOP-условия

`STOP` — **нормальное состояние системы**, а не авария (требование §29).

| Условие | Проверка | Исход |
|---|---|---|
| `COLLISION_RESOLVED` | коллизий со статусом OPEN/LOCALIZED/PLANNED нет | `RESOLVED` |
| `NO_COLLISION_AND_NO_VERIFICATION` | коллизий нет, но и HARD-проверок не было | `STOPPED`, результат помечен `UNVERIFIED` |
| `BUDGET_EXHAUSTED` | любой из бюджетов исчерпан | `STOPPED` + `policy_on_exhaustion` |
| `REPEATED_STATE` | хеш (граф-состояние + план) уже встречался | `STOPPED`, коллизия → `UNRESOLVABLE` |
| `REPAIR_OSCILLATION` | план итерации N совпадает с планом N−2 | `STOPPED`, коллизия → `UNRESOLVABLE` |
| `MAX_ITERATIONS` | `collision.iteration_count` превысил лимит | `STOPPED` |
| `MAX_DEPTH` | глубина вложенности ремонта превысила лимит | `STOPPED` |
| `NO_EXPECTED_GAIN` | все допустимые действия имеют ожидаемый эффект ≈ 0 при ненулевой стоимости | `STOPPED` |
| `EXTERNAL_EVIDENCE_REQUIRED` | разрешение требует источника, которого нет | `STOPPED`, коллизия → `UNRESOLVABLE` |
| `UNCERTAINTY_TOO_HIGH` | доля `unknown_set` выше порога **и** `task.risk_level = HIGH` | `STOPPED_AND_REPORT` |

### 7.1 О `NO_EXPECTED_GAIN`

Это единственное STOP-условие, требующее оценки ожидаемого эффекта. Оно опирается на самый надёжный из подтверждённых сигналов — F15 («нет коллизии → тратить не нужно») и F20/F21 (детектор «уже решено» надёжен и даёт основную экономию), и **не** опирается на F16 (конфликт как индикатор пользы — опровергнут).

Формулировка нарочно консервативна: останавливаемся, когда **нет ожидаемого выигрыша**, а не когда «неуверенность высока». Второе было бы применением опровергнутого сигнала.

### 7.2 Все STOP фиксируются

```
task.stop_reason ← <условие>
```
Молчаливая остановка запрещена. Результат всегда сопровождается: какие claims `CORRECT`, какие `UNKNOWN`, какие коллизии остались `ACCEPTED`/`UNRESOLVABLE`.

## 8. Псевдокод полного цикла

```
FUNCTION handle_collision(collision, graph, task, budget):
    IF collision.iteration_count > MAX_ITERATIONS:
        collision.status ← UNRESOLVABLE;  RETURN STOP(MAX_ITERATIONS)

    localize(collision, graph)                                  # §3 COLLISION_MODEL

    IF collision.origin == null:
        IF есть доступное более сильное evidence AND budget позволяет:
            RETURN action(REQUEST_EVIDENCE, collision.participants)
        collision.status ← ACCEPTED;  RETURN STOP(EXTERNAL_EVIDENCE_REQUIRED)

    region ← new AFFECTED_REGION
    region.candidate ← candidate_affected(collision, graph)     # §2
    region.verified, region.unaffected, region.unknown
        ← narrow(region.candidate, collision.origin, graph, budget)   # §3

    propagate_stale(collision.origin, graph)                    # STATE_MACHINE §4

    plan ← build_plan(region, collision, task, budget)          # §4
    IF plan.plan_hash ∈ seen_plan_hashes:
        collision.status ← UNRESOLVABLE;  RETURN STOP(REPAIR_OSCILLATION)
    seen_plan_hashes ← seen_plan_hashes ∪ {plan.plan_hash}

    IF plan.estimated_cost > budget.remaining:
        RETURN STOP(BUDGET_EXHAUSTED)

    FOR each entry в plan.entries где necessity ≠ DO_NOT_TOUCH:
        execute(entry.action)        # создаёт новые версии, evidence, стоимость

    post_repair_check(plan.repair_set, graph)                   # §6

    IF collision всё ещё наблюдается:
        collision.iteration_count += 1
        RETURN handle_collision(collision, graph, task, budget)  # новая итерация

    collision.status ← RESOLVED
    RETURN CONTINUE
```
