# STATE_MACHINE.md — состояния и переходы

Состояния определены **не по общему представлению о жизненном цикле**, а выведены из того, что в экспериментах реально требовалось различать. Ниже для каждого состояния указано, какой факт делает его необходимым.

---

## 1. Множество состояний CLAIM

| Состояние | Смысл | Почему нужно отдельным состоянием |
|---|---|---|
| `PROPOSED` | claim выделен декомпозицией, содержимое ещё не произведено | нужно различать «запланировано» и «пусто» при частичном исполнении графа |
| `GENERATED` | содержимое есть, проверка не запускалась | F44: смешение «не проверяли» и «проверили, неизвестно» искажает статистику UNKNOWN |
| `UNVERIFIED` | проверка неприменима (нет seam) — и это известно | F43 + аудит A: «привет» никогда не станет `CORRECT`, и система не должна притворяться |
| `CORRECT` | есть evidence достаточной силы, подтверждающее верность | базовое |
| `INCORRECT` | есть evidence достаточной силы, опровергающее | базовое |
| `UNKNOWN` | evidence есть, но недостаточны/противоречивы для вывода | F43: обязательное первоклассное состояние |
| `STALE` | **раньше было `CORRECT`, но предпосылка изменилась; прежнее доказательство больше не применимо** | F37 + F38: ключевой механизм экономии, см. §4 |
| `CONFLICTED` | по claim есть одновременно поддерживающие и опровергающие evidence сопоставимой силы | F14, F16: конфликт — самостоятельное состояние, а не автоматическая ошибка |
| `REPAIRING` | по claim идёт активное действие ремонта | нужно для предотвращения параллельного двойного ремонта |
| `SUPERSEDED` | версия заменена новой | версионирование, откат (аудит J) |

**Состояния, которых сознательно НЕТ:**
- Нет `REJECTED` как автоматического исхода `CONFLICTED` — это запрещено требованием §10 задания и обосновано F16 (конфликт ≠ неверность).
- Нет `VERIFIED` без указания силы — вместо этого `CORRECT` + `verification_status` в claim (F44).
- Нет глобального «score» — нет экспериментального основания.

## 1.1 Множество состояний ARTIFACT

Артефакт агрегирует свои claims, но **не наследует их состояние механически**:

| Состояние | Правило вывода |
|---|---|
| `DRAFT` | создан, claims ещё не извлечены |
| `DECOMPOSED` | claims извлечены |
| `ACTIVE` | текущая версия артефакта в графе |
| `STALE` | хотя бы один его claim `STALE`, и ни один не `INCORRECT` |
| `DEFECTIVE` | хотя бы один его claim `INCORRECT` |
| `SUPERSEDED` | заменён новой версией |

**Важно:** артефакт с `DEFECTIVE` **не удаляется и не блокируется целиком** — его корректные claims остаются пригодными для повторного использования (это прямое следствие F29/F42: реальная область ремонта — обычно часть артефакта, а не весь).

## 2. Таблица переходов CLAIM

`E+` = добавлено поддерживающее evidence, `E−` = опровергающее, `S(x)` = сила evidence.
Порог `HARD_ENOUGH` определён в EVIDENCE_MODEL.md §3 (не число, а класс силы).

| Из | В | Триггер | Условие |
|---|---|---|---|
| `PROPOSED` | `GENERATED` | ACTION_COMPLETED(GENERATE) | содержимое получено |
| `PROPOSED` | `PROPOSED` | ACTION_FAILED | (остаётся; фиксируется failure_mode) |
| `GENERATED` | `UNVERIFIED` | SEAM_EVALUATION | нет применимого seam |
| `GENERATED` | `CORRECT` | EVIDENCE_ADDED(E+) | S(E+) ≥ HARD_ENOUGH ∧ нет E− |
| `GENERATED` | `INCORRECT` | EVIDENCE_ADDED(E−) | S(E−) ≥ HARD_ENOUGH ∧ нет E+ |
| `GENERATED` | `UNKNOWN` | EVIDENCE_ADDED | S < HARD_ENOUGH для всех |
| `GENERATED` | `CONFLICTED` | EVIDENCE_ADDED | ∃E+ ∧ ∃E− сопоставимой силы |
| `UNVERIFIED` | `CORRECT`/`INCORRECT` | EVIDENCE_ADDED | появился внешний источник проверки |
| `UNKNOWN` | `CORRECT`/`INCORRECT` | EVIDENCE_ADDED | сила выросла до HARD_ENOUGH |
| `UNKNOWN` | **не** `INCORRECT` | — | **запрещено без E−** (инвариант `UNKNOWN_IS_NOT_ERROR`) |
| `CORRECT` | `STALE` | UPSTREAM_CHANGED | ∃upstream, версия которого изменилась |
| `CORRECT` | `CONFLICTED` | EVIDENCE_ADDED(E−) | появилось опровергающее evidence |
| `STALE` | `CORRECT` | EVIDENCE_ADDED(E+) | **повторная** проверка относительно нового upstream прошла |
| `STALE` | `INCORRECT` | EVIDENCE_ADDED(E−) | повторная проверка провалилась |
| `STALE` | `UNKNOWN` | SEAM_INAPPLICABLE | повторная проверка невозможна |
| `STALE` | **не** `INCORRECT` | — | **запрещено без новой проверки** (инвариант `STALE_IS_NOT_INCORRECT`) |
| `CONFLICTED` | `CORRECT`/`INCORRECT` | EVIDENCE_ADDED | появилось evidence, разрешающее конфликт по иерархии силы |
| `CONFLICTED` | `UNKNOWN` | COLLISION_ACCEPTED | конфликт признан неразрешимым имеющимися средствами |
| `CONFLICTED` | **не** `INCORRECT` | — | **запрещено автоматически** (инвариант `COLLISION_IS_NOT_AUTOMATIC_ERROR`) |
| любое | `REPAIRING` | ACTION_STARTED(REGENERATE/PATCH) | |
| `REPAIRING` | `GENERATED` | ACTION_COMPLETED | новая версия создана |
| `REPAIRING` | предыдущее | ACTION_FAILED/ABORTED | откат к состоянию до ремонта |
| любое | `SUPERSEDED` | новая версия claim создана | |

### 2.1 Запрещённые переходы (проверяются как assert)

```
UNKNOWN    → INCORRECT   без evidence с assertion=REFUTES
STALE      → INCORRECT   без новой проверки относительно нового upstream
CONFLICTED → INCORRECT   автоматически (без разрешающего evidence)
CONFLICTED → REJECTED    (состояния REJECTED нет вовсе)
любое      → CORRECT     на основании evidence с типом SELF_JUDGEMENT или MODEL_JUDGEMENT как единственного
```

Последняя строка — прямое следствие F9–F12: в эксп. 2 именно допущение «внутренняя проверка сказала PASS» приводило к тому, что задача молча закрывалась как решённая при реальной ошибке.

```
        PROPOSED
           │ GENERATE
           ▼
        GENERATED ──────── нет seam ──────► UNVERIFIED
           │                                    │
     evidence добавлено                   появился внешний
           │                                 источник
     ┌─────┼─────┬──────────┐                  │
     ▼     ▼     ▼          ▼                  │
  CORRECT INCORRECT UNKNOWN CONFLICTED ◄───────┘
     │                 ▲        │
     │ upstream        │        │ разрешающее evidence
     │ изменился       │        └────────────► CORRECT / INCORRECT
     ▼                 │
   STALE ──────────────┘
     │  повторная проверка
     ├──► CORRECT   (проверка прошла — регенерация НЕ нужна)
     ├──► INCORRECT (проверка провалилась — регенерация нужна)
     └──► UNKNOWN   (проверка невозможна)

  любое ──REGENERATE/PATCH──► REPAIRING ──► GENERATED ──► ...
  любое ──новая версия──────► SUPERSEDED
```

## 4. STALE: правила распространения

Это главный механизм экономии в архитектуре. Экспериментальное основание:
- F37: графовая область влияния — безопасная верхняя граница (recall = 1.0), но существенно шире фактически необходимого ремонта (precision ≈ 0.47);
- F38: при этом на реальных ошибках примерно треть случаев **действительно** каскадирует — сужать по умолчанию нельзя.

`STALE` — это ровно то состояние, которое позволяет не выбирать между «перегенерировать всё» и «понадеяться, что не задело».

### 4.1 Алгоритм распространения

```
ON claim C переходит в {INCORRECT, SUPERSEDED, новая версия}:
    frontier ← прямые потомки C по CONFIRMED и HYPOTHESIS рёбрам
    для каждого D из транзитивного замыкания frontier:
        если D.state == CORRECT:
            D.state ← STALE
            D.staleness_source ← C
        если D.state == STALE:
            добавить C в множество источников (не перезаписывать)
        если D.state ∈ {INCORRECT, CONFLICTED, UNKNOWN, UNVERIFIED, GENERATED}:
            не менять   # STALE слабее этих состояний, не затирает информацию
        если D.state == PROPOSED:
            не менять
```

**Ключевые свойства:**
1. `STALE` **не затирает** более информативные состояния. Если downstream уже `INCORRECT`, он не становится `STALE`.
2. Распространение идёт по рёбрам `CONFIRMED` **и** `HYPOTHESIS` (безопасность важнее точности на этом шаге — это тот самый безопасный верхний предел из F34).
3. Рёбра со статусом `REFUTED` в распространении **не участвуют**.
4. Рёбра типа `UNKNOWN_DEPENDENCY` участвуют, но помечают потомка дополнительно как «STALE по неподтверждённой связи» — при планировании ремонта такие узлы имеют более низкий приоритет проверки (см. REPAIR_MODEL.md §4).

### 4.2 Что делать со STALE — не решается автоматически

`STALE` **не означает** «перегенерировать». Он означает «доказательство протухло». Дальше REPAIR_PLANNER выбирает между:
- `MUST_VERIFY` — дешёвая повторная проверка (предпочтительный путь, если seam дешёвый);
- `MAY_REUSE` — если проверка подтвердила корректность относительно нового upstream;
- `MUST_REGENERATE` — если проверка провалилась или невозможна, а риск задачи высок.

Именно этот выбор превращает избыточность графа (F37) в экономию, не жертвуя каскадными случаями (F38).

### 4.3 Открытый вопрос

**OQ-STALE:** правило «VERIFY дешевле REGENERATE, поэтому сначала VERIFY» верно только когда seam дёшев. Для задач без механического oracle (OQ-4) стоимость «проверки» может равняться стоимости повторной генерации, и тогда STALE-механизм не даёт экономии. Экспериментальных данных по этому режиму нет. Архитектура обязана сравнивать стоимости (BUDGET_MODEL.md §4), а не предполагать.

## 5. Состояния COLLISION

```
OPEN ──локализация──► LOCALIZED ──план──► PLANNED ──выполнение──► REPAIRING
                                                                     │
                          ┌──────────────────────────────────────────┤
                          ▼                                          ▼
                     RESOLVED                              (не устранена)
                                                                     │
                                        ┌────────────────────────────┼─────────────┐
                                        ▼                            ▼             ▼
                                  (новая итерация)            UNRESOLVABLE     ACCEPTED
                                   iteration_count++         (нет средств)   (осознанно
                                                                              оставлена)
```

`UNRESOLVABLE` и `ACCEPTED` — **нормальные терминальные состояния**, а не аварии (требование §29 задания). Разница: `UNRESOLVABLE` — «мы не можем проверить/починить имеющимися средствами», `ACCEPTED` — «можем, но решили не тратить бюджет».

## 6. Инварианты состояния (проверяемые)

```
INV-S1  ∀claim: state == CORRECT      ⇒ ∃evidence(SUPPORTS) со strength ≥ HARD_ENOUGH
INV-S2  ∀claim: state == INCORRECT    ⇒ ∃evidence(REFUTES)  со strength ≥ HARD_ENOUGH
INV-S3  ∀claim: state == STALE        ⇒ staleness_source ≠ null ∧ ранее было CORRECT
INV-S4  ∀claim: state == CONFLICTED   ⇒ ∃evidence(SUPPORTS) ∧ ∃evidence(REFUTES)
INV-S5  переход в CORRECT невозможен, если единственное evidence имеет тип
        SELF_JUDGEMENT или MODEL_JUDGEMENT
INV-S6  ∀изменение state: существует STATE_RECORD с from/to/trigger/graph_version
INV-S7  ∀claim в STALE: все его upstream либо имеют новую версию, либо сами STALE/INCORRECT
INV-S8  никакое состояние не удаляет и не перезаписывает evidence
```
