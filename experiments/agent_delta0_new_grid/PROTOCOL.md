# PROTOCOL.md — agent_delta0_new_grid (DELTA-0)

Написан на шаге C0, ДО generator/C1 и ДО любого числа прогона. Пороги
§6 не двигаются после первого посчитанного Δ (C10). Интерпретация —
только в BLOCKERS.md/REPORT_DELTA0.md, рядом с механическим вердиктом,
никогда вместо него.

## 0. Рамка и мотивация

LIFE-9 (2026-08-23, `agent_life9_decomp_alpha/`) нашла на СТАРОМ полигоне
(HETEROSTEP): недекомпозированный запрос к одной модели целиком (whole)
бьёт весь степ-декомпозированный аппарат этого проекта (B1/B2/B3/UNION,
организм LIFE-8) — а СКОНСТРУИРОВАННАЯ декомпозиция (маленький planner
сам придумывает план) резко проигрывает whole, а не помогает. Открытый
вопрос: декомпозиция как таковая бесполезна, или дело в конкретном
плохом planner'е на конкретном лёгком T? DELTA-0 — чистый замер на НОВОМ
T с ЗОЛОТЫМ (не LLM-изобретённым) планом: убирает LIFE-9's конкретный
провал (плохой planner), измеряет именно способность реальных
executor-моделей пройти ИЗВЕСТНО-ПРАВИЛЬНУЮ цепочку атомов.

Закон пакета (§0 задания) соблюдается буквально: пишем только в
`agent_delta0_new_grid/`; 0 Evolution/HGT/mutate/Pareto/stall/block
registry/ASSEMBLE где-либо в этом пакете; никакого чтения/импорта
`arch2/`, `experiment14/`, `agent_life*/`, `agent_a5*/` — полностью
самостоятельный полигон.

## 1. Класс задач T = F2 (multi-hop record), выбран и описан (C1)

Выбрано F2, не F1/F3:
- **F1 (mini-repair)** отклонён: атом, которому нужен весь файл/спека,
  структурно не может стоить в 4 раза дешевле whole — конфликт с
  `B_atom ≤ B/4` с самого начала, не по ослаблению правила, а по
  конструкции задачи.
- **F3 (schema pipeline)** отклонён: надёжный, толерантный чекер
  "schema-valid" без LLM-judge сложнее сделать герметичным, чем плоские
  set/numeric/token проверки F2.
- **F2** оставляет ровно ОДИН атом (FILTER) с размером входа как у
  whole, остальные два — дёшевы по конструкции: единственный из трёх,
  честно соблюдающий бюджетное правило без его ослабления.

**Домен**: транзакции (НЕ shipping/parcels/tariff — исключает любое
сходство с запрещённым HETEROSTEP-шаблоном).

**T1** (не одношаговая): задача требует JOIN-фильтрации по ДВУМ
критериям одновременно, затем агрегации, затем производного вывода —
минимум 3 логических хода, не "прочитай поле × посчитай".

**T2** (final oracle автоматический, детерминированный, без LLM-judge):
финальный ответ — ДА/НЕТ (сравнение агрегата с порогом), вычисляется
кодом генератора из тех же случайных чисел, что построили базу.

**T3** (≥2 intermediate checkpoint, локальный v, без LLM-judge) — здесь
их 3, НИ ОДИН не совпадает с HETEROSTEP'овскими READ/FORMAT/LOOKUP/
COMPUTE (другая семантика: фильтрация/агрегация/вывод, не
чтение/формат/поиск/вычисление):
  1. **matched_ids** — множество id транзакций, удовлетворяющих ОБОИМ
     критериям фильтра. v=1 ⟺ извлечённое множество ТОЧНО равно
     золотому (не надмножество/подмножество).
  2. **aggregate_value** — числовое значение агрегата (SUM/COUNT/MAX
     поля `amount` по matched_ids). v=1 ⟺ |extracted-oracle|≤0.01.
  3. **final** (= T2's final_oracle) — ДА/НЕТ, сравнение
     aggregate_value с порогом threshold через comparator (`>=`/`<`).
     v=1 ⟺ извлечённый токен ДА/НЕТ совпадает с золотым (регистро-
     независимо, однозначный токен; неоднозначный/отсутствующий ответ
     -> v=0, никогда не угадывается).

**T4** (контекст ≥ MIN_CONTEXT_CHARS): `MIN_CONTEXT_CHARS=2000`.
K=16 строк базы, каждая — `id | account: <company> | category: <cat> |
amount: <float> | region: <region> | date: <date>` — весь текст
СОДЕРЖАТЕЛЬНЫЙ (не padding), фактическая длина измеряется в C2 (не
гадается заранее).

**T5**: если после C7 `r_m* ≥ 0.70` на TEST — полигон всё равно ВАЛИДЕН,
корзина будет `DELTA_NONPOS`/`HIGH_SINGLE` — допустимый, не отменяющий
пакет исход (см. §7). T усложнять постфактум ЗАПРЕЩЕНО.

**T6**: `N_TRAIN=80`, `N_TEST=40` (дешёвый вариант задания), детерминизм
от `SEED_T=20260823` (буквальная константа задания).

**Запрос** (фиксированная форма на каждую задачу): два JOINT-критерия
фильтра (`category=X AND region=Y`), операция агрегации (одна из
SUM/COUNT/MAX поля `amount`), порог+компаратор (`>=`/`<`). Генератор
намеренно сажает записи, совпадающие только по ОДНОМУ критерию
(отвлекающие), и гарантирует небольшое (2-5) истинное множество
совпадений — никогда не "всё" и не "ничего" тривиально.

## 2. Атомы A (C8) — ровно 3 типа

- **FILTER**(db_text, category, region) -> список id. Единственный атом
  с размером входа порядка whole (вся база). Шов: извлечь все токены
  вида `TXN-\d{4,}`, множество, сравнить с золотым множеством.
- **AGGREGATE**(matched_ids, op, компактный `id -> amount`-срез ТОЛЬКО
  для переданных id, НЕ вся база) -> число. Шов: числовое извлечение
  (тир-1: весь ответ — число; тир-2: ровно одна строка-число; иначе
  INAPPLICABLE) — регэксп страхуется от съедания десятичной точки
  (`^\s*\d+[.)](?!\d)\s*` перед снятием маркера списка, тот же урок,
  что LIFE-9 выучила на "13.1"→"1").
- **DERIVE**(aggregate_value, threshold, comparator) -> ДА/НЕТ.
  Крошечный вход. Шов: тот же ДА/НЕТ-токен-парсер, что у whole.

## 3. Бюджет B (формула — C0; конкретное число — C5, после C2)

```
B = потолок (input_tokens + output_tokens) на ОДИН whole-вызов,
    одинаковый для всех моделей при замере r_m*.
B_atom <= B / 4                          (жёстко, не ослабляется)
cost(задача, single) <= B
B_total_union <= 2*B
```

Число `B` фиксируется на шаге C5 из РЕАЛЬНО измеренного (C2) размера
DB-текста/промпта — не угадывается здесь. Определяющее ограничение —
DB-размерный вход FILTER (`B_atom` должен его покрывать), поэтому `B`
у этого T естественно больше, чем было бы у одно-записевой задачи — это
свойство самого T, не ослабление правила (whole тоже читает всю базу).

## 4. r_m*(B), m* (C6–C7)

Whole-промпт: полная база + запрос; **просит ТОЛЬКО финальный ДА/НЕТ**
(intermediate-значения НЕ запрашиваются и НИКАК не влияют на
`v_final` — короче и надёжнее, чем HETEROSTEP-стиль "N именованных
значений в одном ответе", где LIFE-9 нашла реальный баг разбора именно
на этом узоре). 1 sample, temperature=0 (если не поддержан — 0.1,
зафиксировать факт). `cost = input+output`; `cost>B` -> FAIL (не
"почти").

```
r_m = mean(v_final) на TEST
m* = argmax r_m; ties -> меньший mean cost; ties -> меньший model_id (лекс.)
```

## 5. r_∪_lower (C9) — метод M1 (oracle-route), не M2

M2 не нужен: генератор уже знает золотые критерии/операцию/порог.
Золотой ПЛАН фиксирует, КАКИЕ атомы вызывать и их СТАТИЧЕСКИЕ параметры
(критерии/op/threshold — никогда не изобретаются моделью, в отличие от
LIFE-9's planner'а). ДИНАМИЧЕСКИЙ вход каждого атома — РЕАЛЬНЫЙ выход
предыдущего атома (не подстановка золотых значений) — честная цепочка,
которая может оборваться на любом звене.

## 6. Три зафиксированные строки (дословно, из ревью плана)

```
1. Union chain: при v=0 на любом атоме задача FAIL (без golden подстановки).
2. r_∪ = final ДА/НЕТ only after full real chain.
3. B фиксируется в C5 из C2 token measure; B_total_union ≤ 2B проверяется post-hoc.
```

Раскрыто операционально: если FILTER's извлечённое множество ≠ золотое
-> `union_pass=False` для задачи, AGGREGATE/DERIVE для неё вообще НЕ
вызываются (экономия бюджета, честность цепочки). Если FILTER прошёл, но
AGGREGATE не уложился в толеранс -> `union_pass=False`, DERIVE не
вызывается. `union_pass=True` ⟺ ВСЕ ТРИ шва прошли последовательно —
не "хотя бы один", не "только финальный" (это жёстче, чем просто
переиспользовать финальный ДА/НЕТ: блокирует случай, где неверные
промежуточные значения случайно дают верный финальный булев ответ).

```
r_∪_lower = mean(union_pass) на TEST
Δ = r_∪_lower - r_m*   на ОДНОМ И ТОМ ЖЕ TEST
```

**Стоимость** (не только Δ): REPORT_DELTA0.md несёт mean cost(whole,
m*) vs mean cost(union-chain) на тех же TEST-задачах (union-chain cost —
сумма ТОЛЬКО фактически сделанных вызовов на задачу, с учётом раннего
обрыва). Если измеренный mean union-chain cost > `2B` -> явный флаг
`BUDGET_VIOLATION` в отчёте, не молчание.

## 9. HARD_STOP (единственные стоп-краны)

- registry `generate()` не вызывается / floor < 80%
- OOM на большинстве моделей при B
- final oracle или intermediate v недетерминированы (ловится C4)
- N_TEST < 30 (не должно случиться — T6 фиксирует 40)

При срабатывании: BLOCKERS.md, корзина `DELTA_BLOCKED`, CHECKLIST с
`[ ]` на сорванном шаге, REPORT всё равно пишется, с причиной.

## 9.1 Executor-модель для цепочки атомов (не зафиксировано заданием/ревью явно)

Ни исходное задание, ни ревью плана не называют, какая модель исполняет
FILTER/AGGREGATE/DERIVE (в отличие от LIFE-9, где это был B3-greedy
per-kind победитель). Здесь нет аналогичного per-kind рейтинга, и вводить
его — новое, незапрошенное измерение. Выбор: **executor = m\*** (тот же
победитель whole-task, C7) для ВСЕХ трёх атомов. Это самая чистая
формулировка вопроса пакета — "если ТА ЖЕ модель, которая лучшая целиком,
пройдёт золотую цепочку по частям — станет ли ей лучше?" — и не вводит
скрытый confound "может, дело не в декомпозиции, а в том, что для
атомов выбрали другую модель".

## 10. Самоопределённые выборы (документированы явно, не молчаливые допущения)

- Числовой экстрактор AGGREGATE написан заново для этого пакета
  (копирование утилиты внутри пакета разрешено §0.3), с уроком LIFE-9
  сразу учтённым (negative lookahead), не переоткрывается как баг.
- 5 фикстур C4: (1) золотые входы -> v=1 на всех 3 шва; (2) пустое
  совпадение (0 записей) -> COUNT=0/SUM=0 без падения; (3) граница
  компаратора (агрегат точно равен порогу) -> `>=`/`<` ведёт себя как
  задумано; (4) корректно оформленный синтетический ответ парсится
  верно на каждом атоме; (5) испорченный ответ корректно даёт v=0 (не
  падение, не угадывание).
